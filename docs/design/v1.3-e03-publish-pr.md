## 1. 人怎麼到達

發布區塊放在看板 Work 檢視的成果區裡，也就是 `[data-work-section="attempt-result"]` 內的 `[data-work-result]`（`desktop/src/pm-kanban.js:332-346`、`desktop/src/pm-work-result.js:66`）。看板把這段排在 Start work 之下（`pm-kanban.js:336-338`）。窄螢幕用同一個檢視抽屜，同一份 DOM，沒有另一套行動版邏輯（計畫 §6.3 最後一句）。

已實作的檢視斷點在 `desktop/src/ui/components.js:245-303`：

| 寬度 | 檢視 |
|---|---|
| `min-width: 1200px` | `role="complementary"`，與看板並排 |
| 小於 1200px | `role="dialog"`、遮罩、焦點圈住、Escape 關閉 |
| `max-width: 799px` | 打開時焦點在返回鈕 |

側欄在 1000px 收進抽屜是另一個元件（`desktop/DESIGN.md` 開頭）。本區塊跟著成果檢視，不跟著側欄斷點。打開檢視時維持既有焦點（窄螢幕在返回鈕）；本表單不搶第一次焦點。

桌面與窄螢幕的路徑相同：看板打開一張 Work 卡，在成果區往下經過檢查與變更，就看到發布區塊。區塊自己的鉤子是 `data-work-publish`。

成果區今天的順序是檢查（`pm-work-result.js:359`）、變更（`:452`，推進 `:583`）、完整度（`:585-610`）、已記錄回合（`:612`）、Details（`:647`）。完整度只在 `completeness.status` 不是 `complete` 時出現。發布表單插在完整度之後、已記錄回合之前。完整度沒有畫出來時，表單緊接在變更後面。人會先看到這次讀取是否部分或不完整，再看到發布。鍵盤順序跟這段 DOM 一致。計畫 F8：先看差異、測試與接受條件，再發布。

成果區裡這個區塊只有一個主要按鈕。頁首的「開始工作」是另一段，而且只在該卡可以開始時出現。

## 2. 何時出現

UI 只消費 Result 回傳的條目，不自己組 target，也不在 Result 沒有列出時提供這個動作。E04 散文在 `docs/design/v1.3-e04-result.md:276`。

`main` 上今天的條目在 `pm_attempt_result_reads.py:1072-1106`：有 `prefilled_params.candidate_sha`（40 hex 才放，`:1075-1077`），沒有 `preconditions`，也沒有預填 `base_ref`。父啟動是 `stage == "start_unknown"` 或 `operation_status == "uncertain"` 時，`:979-982` 直接返回，只把 `work.start` 放進 `blocked_actions`。後端任務把條目補成下面這一筆，並用阻擋原因取代「動作缺席」。UI 不替缺席的動作發明一列。正式畫面統一依條目判斷：動作在允許與阻擋清單都缺席時不畫發布區；已有條目但前提不完整時，依 §4.1 顯示缺口並保留原命名空間的標題與說明草稿，不顯示送出鈕。後端補齊且授權仍有效之後才可送出。

後端任務完成後，提供時的條目是：

- `kind: "action"`
- `action: "github.pr.publish"`
- `target`: `{workspace_id, repository, host, source_operation_id}`，四個鍵與 `ActionDef` 一致（`pr_publication.py:77-78`）
- `required_scopes`: `["integrate", "manage", "observe"]`（`_action_scopes` 在 `:890-891` 會排序，再加上 `REQUIRED`，`pr_publication.py:38`）
- `required_params`: `candidate_sha`、`base_ref`、`public_title`、`public_body`、`draft`
- `optional_params`: `["quality_ref"]`
- `prefilled_params.candidate_sha`：僅在候選 SHA 是 40 hex 時出現（今天 `:1075-1077`；後端任務保留這個條件）
- `prefilled_params.base_ref`：`repository_sync.check_ref(code_source.source_ref)`。`check_ref`（`repository_sync.py:100-104`）若字串以 `refs/heads/` 開頭就去掉該前綴，再以 `HEAD_REF` 檢查，回傳的是不含前綴的分支名稱。UI 照顯示，不再剝前綴
- `preconditions`: `{repository_id, expected_base_sha}`。`repository_id` 與 `expected_base_sha` 來自同一次開始的 `code_source`（`repository_id` 與 `source_sha`；開始當下在 `pm_work_start.py:1854-1855`，`_attempt_view` 把 `code_source` 放進視圖 `:2020`，`get_attempt` 回傳該視圖 `:2052-2056`）。`base_ref` 與 `expected_base_sha` 成對出現，都來自那一次開始

`expected_base_sha` 是伺服器在發布時即時核對的期望值：`_preflight` 讀 `git/ref/heads/{base_ref}`，SHA 必須等於它（`pr_publication.py:356-360`）。它不是人可以改的欄位。

程式只在同時滿足這些條件時考慮這筆條目（`:1002`、`:1072-1073`）：有 session、`execution.state` 是 `turn-ended` 或 `process-ended`、`delivery_goal == "pull_request"`、有 `execution_op_id`、動作已註冊。`consider`（`:922-955`）再要求同一個 controller、寫入成員，以及條目上的 scopes。`delivery_goal` 未記錄時是 `"unknown"`，此時不提供這個動作（E04 `:63`）。

標題與內文永不預填。

### 2.1 完全不畫

下列情況條目不在 `next_allowed_actions`，也不在 `blocked_actions`。畫面不畫發布區塊，也不放一顆停用的「發布 PR」：

- `delivery_goal` 是 `unknown` 或 `reviewable_changes`
- 執行狀態不是 `turn-ended` 或 `process-ended`
- 沒有 session，或沒有執行操作
- 動作未註冊

成果區既有的交付目標列已經顯示目標。開始之後，這個畫面沒有改 `delivery_goal` 的控制。

今天 `:979-982` 還會在父啟動 `start_unknown` 或 `uncertain` 時整段返回，發布連 `blocked_actions` 都沒有。後端任務改為 §2.2 的 `WAIT_ORIGINAL_OPERATION_RECONCILE`，與 E04 `:276` 一致。UI 只畫條目裡真的有的那一列。

### 2.2 阻擋原因與下一步

`blocked_actions` 裡 `action == "github.pr.publish"` 時，顯示原因與下一步，藏起表單。`data-work-publish-blocked` 標出這段。已存的草稿留在原本的 storage key，直到新的 Result 再次把動作放進 `next_allowed_actions` 才顯示。

後端任務在這些情況放阻擋原因、不放可送出的條目：同一執行來源已有一筆尚未結束的發布（`WAIT_ORIGINAL_OPERATION_RECONCILE`）；同一 `candidate_sha` 已有驗證過的建立回執（`pull_request_exists`）；工作區已停止新工作（`lifecycle_stopped`）；GitHub 未設定（`github_not_configured`）；發布來源事實不完整（`publication_source_incomplete`）；以及 E04 `:276` 已寫的 uncertain 父操作（同樣是 `WAIT_ORIGINAL_OPERATION_RECONCILE`）。另外保留今天 `consider` 已有的 `not_controller`、`not_writer_member`、`missing_scope`。

### 3.1 固定 commit，以及 integration 不是「已交付」

`prefilled_params.candidate_sha` 以唯讀顯示前 12 個 hex，與成果區現有寫法相同（`pm-work-result.js:550`、`:565`）。完整 SHA 放在無障礙名稱、`title`，以及 Details。不用會把全文藏起來的 CSS 省略。人不能改這個欄位，也不能另打一個 SHA。

來源句子：

1. SHA 等於 `changes.fixed_result_commit.commit_sha` 時，沿用該物件的 `source_kind` 標籤：`turn_end_observation`、`execution_verification` 或 `session_verification`、`integration`（`pm-work-result.js:559-561`）。
2. SHA 等於最新回執的 fixed commit、且與信封上的 fixed commit 不同時，用 `wpub_commit_from_receipt`。候選 SHA 的選法在 `cand_sha_for_pr`（`pm_attempt_result_reads.py:1578-1582`）：最新回執的 `fixed_result_commit` 是 dict 時用它的 `commit_sha`，否則用信封的 fixed commit。信封優先順序是 integration、verification、再回執（`:1568-1576`）。兩者可以不同。E04 `:276` 只寫最新回執；畫面以這段程式比較。
3. 兩邊都不相等時，只用 `wpub_commit_from_result`。
4. 沒有 40 hex 的 `prefilled_params.candidate_sha` 時，顯示 `wpub_commit_missing`，不送出。回執 SHA 不是 40 hex 時，今天的程式仍會列出動作且 `prefilled_params` 是空的（`:1075-1077`）。

`source_kind == "integration"` 今天標成 `wres_source_delivered_commit`（「the delivered commit」／「已交付的 commit」，`pm-work-result-strings.js:245`、`:100`）。這個 `source_kind` 有三個生產者，信封不區分它們（`:1571-1572` 把最新一筆 `integration_commit` 放進 `fixed_result_commit`；挑選在 `:813-822`）：

1. 建立回執的 `candidate_sha`（`:659-669`）。這是已發布的候選 commit，尚未合併，也尚未部署。
2. 歸到這次執行的 integration 項目上的 `delivered_sha`（`:718-728`）。
3. 歸到這次執行的 merge 項目上的 `merged_sha`（`:780-790`）。

同一句必須三邊都成立，所以不用「已交付」「已合併」或「已發布」。Part D 的實作把 `pm-work-result.js:561` 改為 `wres_source_integration_commit`：「recorded by integration」／「整合紀錄記下的 commit」。`wres_source_delivered_commit` 不再用於這個 `source_kind`。

### 3.2 目標分支、基底 commit 與草稿

人不能輸入目標分支或基底 commit。兩者都來自條目，短顯示，並用 `wpub_base_from_start` 說明出處。

- `base_ref` 顯示 `prefilled_params.base_ref` 全文。它已是 `check_ref` 回傳的分支名稱（`repository_sync.py:100-104`）。主機腳本再把它接成 `refs/heads/` + 這個名稱（`pr_publication_host.py:32-34`、`:64-67`）。UI 不剝前綴，也不把 `code_source.source_ref` 另做一次轉換。
- `expected_base_sha` 顯示前 12 個 hex，完整值放在無障礙名稱、`title` 與 Details。發布時伺服器對 live 的 `git/ref/heads/{base_ref}` 核對這個 SHA（`pr_publication.py:356-360`）。對不上就是 `PR_PROVIDER_TARGET_CHANGED`。這個畫面不能改指到新的基底。見 §6.3 與 §10 第 20 項。
- 兩個值缺一個，或 `base_ref` 不是非空字串，或 `expected_base_sha` 不是 40 hex：顯示 `wpub_gap_preconditions`，標題與說明仍可打字存草稿，送出鈕不出現。不讓人改打一個分支或 SHA 來補。

`draft` 必須是真正的 bool（`pr_publication.py:195`）。條目不給預設。UI 不靜默送 `false`，那會建立一筆可審閱的 PR。控制項是 radiogroup，兩項都先不選。不用 segmented control，因為那個控制項總是有一個值。不用核取方塊，因為未勾選無法區分「還沒選」與「開放審閱」。

`durableForm` 只保存字串（`pm-workspace.js:80`）。草稿選擇鏡射到一個名為 `draft` 的欄位，值是 `""`、`"true"` 或 `"false"`。送出時在 `params()` 轉成 bool。兩個 radio 放在表單的 `extra` 裡；鏡射欄位不進 Tab 順序。欄位鎖定時，兩個 radio 一起停用。還原草稿時，依字串勾回對應的 radio；`""` 則兩項都不勾。

成功時 `durableForm` 只把 `fields` 裡的控制項設回 `dataset.pmDefault || ""`（`pm-workspace.js:253`）。radio 不在 `fields` 裡。鏡射欄位回到 `""` 的同時，實作要明確把兩個 radio 的 `checked` 設為 false。否則畫面上會留下上一次的選擇。`dataset.pmDefault` 全部是空字串，成功後不冒出預設。

### 3.3 草稿怎麼留

表單走看板已經傳給 Start work 的那個 `form` 包裝，不直接呼叫未匯出的 `durableForm`，也不把它 export 出來。

包裝在 `pm-workspace.js:475-488`：它呼叫 `durableForm`（`:69-310`），並加上送出閘（`canSend`）、`initialReadComplete`、生命週期閘（`newActionAllowed`）與 forms 登錄。看板建立時就收到這個 `form` 與 `namespace`（`pm-kanban.js:14`）。Start work 用的是它們（`pm-kanban.js:69-70`）。成果面板今天沒有收到（`:58-67`，`workResultPanel` 的參數在 `pm-work-result.js:53`）。實作把同一對 `form` 與 `namespace` 傳進 `workResultPanel`，發布區塊呼叫這個 `form({...})`。

`requiredScope` 傳 `'integrate'`（`durableForm` 預設是 `manage`，`:102-103`）。storage key 仍是 ``batc.pm.${namespace}.${action}.${JSON.stringify(target)}``（`:70`）。傳進表單的 namespace 是看板的值加上 `.work-publish`（Start work 的寫法在 `pm-work-start.js:784-788`）。換連線主體就換 key，不會顯示另一個主體的草稿。

送出仍由 Result 條目把關，不因為 catalog 有這個動作就送。包裝上的生命週期閘若已關閉，沿用包裝自己的不可用狀態；條目上的 `lifecycle_stopped` 則連表單都不畫。

重新整理、離開成果檢視、連線中斷之後，同一把 key 的標題、說明與草稿選擇都還在。目標分支與基底 commit 不進草稿：它們每次都從最新條目讀。有 intent 時欄位鎖定，直到該操作進入終態並且人按下「新請求」，或受理前的拒絕被按掉。見 §7。

### 3.4 不送 quality_ref

`quality_ref` 是選填。若要送，必須同時有 `review_id`、`operation_id`、`version`、`document_digest`（`pr_publication.py:201-208`）。`verification.quality_reviews.current` 只有 `review_id`、`version`、`qualified`、`kind`、`acceptance`、`dod`（`pm_attempt_result_reads.py:567-580`），沒有 `operation_id` 與 `document_digest`。這個表單省略 `quality_ref`，不提供選擇器。省略是合法的（`:118-120` 在沒有這欄時直接返回）。

## 4. 送出

UI 不增加後端行為。送出就是既有的 `POST /api/v1/operations?wait=3`，由 `durableForm` 在建立 intent 之後發出（`pm-workspace.js:215-242`）。`github.pr.publish` 不是 `pm.*` 也不是 `work.start`，所以用一般 idempotency key，不是 PM 前綴 key（`operations.py:126-127`）。UI 不自己組第二種 key。

### 4.1 什麼時候才可以按

以下條件同時成立才顯示可按的「發布 PR」：

1. 目前這份 Result 的 `next_allowed_actions` 有這筆動作，而且 target 四個值都是字串。
2. 同一筆條目的 `prefilled_params.base_ref` 是非空字串，且 `preconditions` 恰好是 `{repository_id, expected_base_sha}`：`repository_id` 是大於 0 的整數，`expected_base_sha` 是 40 hex。缺了就顯示 `wpub_gap_preconditions`，標題與說明仍可打字存草稿，送出鈕不出現。說明本身就是下一步，不用按下後的 `pm_action_unavailable` 蓋掉它。
3. `prefilled_params.candidate_sha` 是 40 hex。缺了就顯示 `wpub_commit_missing`，送出鈕不出現。
4. catalog：`caps().scopes` 含 `integrate`，且 `caps().actions` 有 `{action: "github.pr.publish", allowed: true}`。另外，`caps().scopes` 要含條目上的 `observe`、`manage`、`integrate`。catalog 不允許時顯示既有 `pm_action_unavailable`，草稿保留，不另送。

Result 條目是產品閘門。catalog 只反映包裝已有的檢查。不因為 catalog 允許就在 Result 沒列出時送出。

本地檢查（空白標題、未選草稿、標題或說明超過位元組上限）發生在 `params()` 丟錯之前，也就是 `pm-workspace.js:215-218` 寫入 intent 之前。這種檢查不建立 operation key。焦點移到該欄位。伺服器的 `INVALID_PARAMS` 仍是最終依據。目標分支沒有本地必填檢查，因為人不能輸入它。

### 4.2 請求本體

條目把受理事實都帶齊時，本體是：

- `action`: `"github.pr.publish"`
- `target`: 條目的 `target`，原樣複製。不補 null、不改 repository、不改 host
- `params`: `candidate_sha` 與 `base_ref` 來自 `prefilled_params`；`public_title` 與 `public_body` 來自欄位；`draft` 是 bool。不含 `quality_ref`
- `preconditions`: 條目的 `preconditions`，原樣複製。UI 不從 `changes.base_commit` 另抄一個 SHA。`changes.base_commit`（`pm_attempt_result_reads.py:220-224`、`:1734`）與條目上的 `expected_base_sha` 都源自開始時的 `source_sha`；以條目那一對為準，避免畫面自己配對
- `Idempotency-Key`: 這一次送出的那把 uuid，先寫進 intent 再 POST

一次送出一把新的 operation key。受理前被拒絕、而且回應帶 `admission_refused: true`、沒有 operation id 時，伺服器沒有留下操作；「新請求」清掉那把被拒絕的 intent、留下打過的字，下一次送出才是另一把新 key。這與結果不明不同。

### 4.3 契約對畫面的意義

`PR_RECEIPT_EXISTS` 表示已有建立回執，即使操作為終態失敗，也不得提供新 key 再發布同一候選。保留既有回執與原操作的檢視／對帳入口；沒有可驗證的 `html_url` 時不自組 PR 網址。

`capabilities()`（`pr_publication.py:81-84`）是 `creation_only: true`、`unknown_post_resend: false`。遺失的 GitHub POST 201 不會重送。搜尋到的候選不會升格成回執（`:516-531`）。

因此：

- 每一筆送出是自己的操作與自己的 key
- 操作已經存在而結果是 `uncertain` 或 `needs_attention` 時，不再 POST。按鈕文字是「查回原請求」，按下只 `GET /operations/{id}`（`pm-workspace.js:241-242`）
- 回覆遺失、key 已存而還沒有 `operation_id` 時，下一次按下仍用同一把 key POST。伺服器以那把 key 找回原操作。這不是第二筆發布
- 不清除鎖、不重送開始、不為了「修好」不明結果而換一把 key

`GitHubAmbiguous` 是 `AmbiguousOutcome`（`github.py:30`，`operations.py:57-61`）。執行器把操作標成 `uncertain`（錯誤代碼 `UNCERTAIN`），讀回次數用盡後變成 `needs_attention`／`UNCERTAIN_UNRESOLVED`（`operations.py:863-873`）。畫面用操作自己的狀態字，加上 `wpub_uncertain` 或 `wpub_needs_attention`。

### 4.4 人在等待時看到什麼

`durableForm` 已有的狀態區是表單裡的 `role="status"`（`pm-workspace.js:86`）。不另加第二個 live region。

自動回查的間隔是 `[250, 500, 1000, 1500, 2000, 3000]` 毫秒（`pm-workspace.js:72`），合計約 8.25 秒。這段時間內按鈕保持「發布 PR」並且 `aria-disabled="true"`（`DESIGN.md:252-255`，按鈕文字在 `pm-workspace.js:187`）。間隔用盡、又還沒有終態時，自動回查停止，按鈕改成「查回原請求」。按下只 GET。事件造成的重新讀取會再叫一次 `recheck()`，見下方與 §7。

`recheck`（`pm-workspace.js:297-302`）只在已有 operation id、且上次看到的狀態仍是 `accepted`、`running`、`waiting_external` 或 `waiting_checks` 時 GET。`uncertain` 與 `needs_attention` 不在這份名單裡，事件不會替它們自動重試；人按「查回原請求」才 GET。Start work 在重新整理嘗試清單、且表單已鎖定時呼叫 `editor.recheck()`（`pm-work-start.js:895-898`）。發布表單在成果重新讀取、且表單已鎖定時做同樣的呼叫，包含信封正規化後沒有重畫的那一條（`pm-work-result.js:153-161`）。這次 GET 不是新的 POST。

| `accepted`、`running`、`waiting_external`、`waiting_checks`，自動回查尚未結束 | 同上。重複按下被忽略（`:136-138`、`:142`） | 「查看操作」連結、該狀態的詞、`wpub_pending`。`accepted` 時加 `wpub_admitted_note` |

| `needs_attention` | 「查回原請求」 | `op_needs_attention` 與 `wpub_needs_attention`。代碼是 `PR_CREATED_TARGET_CHANGED` 時改用 `wpub_created_target_changed`。沒有「新請求」 |

| `cancelled` | 隱藏，出現「新請求」 | `op_cancelled`。原操作已結束，下一筆才是新 key。這與 `uncertain` 不同。若新的 Result 已是 `pull_request_exists`，表單不畫，不能靠「新請求」再發布同一顆 commit |

主文永遠是上表的句子或 §6 的下一句。原始代碼與伺服器英文訊息進既有 `errorBox` 的 Details（`app.js:300-310`，`error-presentation.js:8-15`）。客戶端把 `error.admissionRefused` 設成 `data.error.admission_refused === true`（`app.js:293`）。`onError` 回傳 true，並自己把 `errorBox` 放進狀態區，這樣主文可以用這份規格的句子，代碼仍在 Details。沒有專用句子的代碼用 `error_generic`。

`admission_refused` 今天只加在 `pm.*` 以及 `setup.host`、`setup.repository`、`setup.verification`、`work.start`（`api_v1.py:1487-1495`）。`github.pr.publish` 的 `OperationError` 會被重新拋出，客戶端不會看到這個旗標，也就不會走進「新請求」。後端任務把這個動作納入同一段，使每一次被拒絕的受理在沒有既有 idempotency 紀錄時帶 `admission_refused: true`，而且不留下操作。UI 測試可以在 mock 上設這個旗標來走客戶端（`work-start-fixture.ts:258`）；那個 mock 不是證明。證明是後端任務加上的測試。撰寫本節時，`ux/e04-publish-entry` 的樹與 `b71a8927` 相同，該測試還沒有名字。本文件不替它取名。它要鎖住的契約是：被拒絕的 `github.pr.publish`、且這個 actor／key 沒有既有紀錄時，回應的 `error.admission_refused` 為 true，並且沒有建立操作。

## 5. 建立之後

成功的操作結果是 `{published: true, creation_receipt, merged: false, deployed: false}`（`pr_publication.py:536-540`）。`merged: false` 與 `deployed: false` 照實理解。畫面不把 `published: true` 說成已合併、已部署、已驗收或已交付。

PR 出現在 Result 的 `delivery.pull_requests`，資料來自建立回執（`pm_attempt_result_reads.py:610-654`）。同一筆回執也把 `candidate_sha` 放進 integration 候選（`:659-669`），所以成果 commit 的來源句子改用 §3.1 的新標籤。刷新走既有事件：`app.js:786` 的 `streamEvents` 把事件交給監聽者；`pm-workspace.js:1769-1793` 對 `pm_` 資源（含 `pm_work_attempt`）以及 `operation`、`deployment`、`integration` 重新讀取可見的看板。看板 `refresh`（`pm-kanban.js:392`）再選取目前的卡，成果面板重新讀取（`pm-work-result.js:92-112`）。UI 不從操作結果捏一列 PR，也不發明 GitHub 網址。回執投影沒有 `html_url`、`state`、`draft`。有 `publication_operation_id` 時，沿用現有連結 `#/op/{publication_operation_id}`（`pm-work-result.js:416-424`）。

`requirement_acceptance` 是 `not_evaluated_by_publication`（`pr_publication.py:415`）時，顯示 `wpub_pr_not_accepted`，並可併用既有「尚未驗收／Not assessed」。`target_verified` 不是 true 時，顯示 `wpub_pr_unverified`，不說發布目標相符。`completeness.coverage.delivery` 是 `"partial"`（`:1859-1864`）時，清單旁顯示 `wpub_pr_partial`。這份清單是這次讀到的紀錄，不是總數。不把未知顯示成 0。

合併與部署留在既有 Delivery 畫面。連結不是 `#/delivery` 本身，而是：

`#/delivery/{host}/execution/{source_operation_id}/{repository}`

四段各自 `encodeURIComponent` 再以 `/` 接起，與 `observed-resource.js:108-110` 相同。`repository` 含有 `/`，不編碼會被路由拆開。`host`、`source_operation_id`、`repository` 來自條目的 `target`。種類固定是 `execution`。

`viewDelivery`（`app.js:2285`）只在種類是 `execution` 或 `task_command` 時承認這個來源（`:2288-2290`）。有來源時，儲存庫欄預填第四段（`:2291`），PR 編號留空（`:2292`），畫面上顯示來源 id（`:2308`）。編號是空的，所以它列出該儲存庫的 PR（`:2325`），不會打開某一筆 PR。路由表的 `delivery` 是 `viewDelivery`（`:4632`）；hash 其餘段作為參數傳入（`:4608`、`:4636`）。這不是 GitHub 的 `html_url`。連結文字是 `nav_delivery`，旁邊一句 `wpub_delivery_link`。成果區不加 `github.pr.merge`、`delivery.merge_and_deploy` 或 `deployment.*`。Work 檢視裡另一份交付讀取的允許清單本來就沒有 `github.pr.publish`（`pm-work-deliveries.js:74`），這份規格不把發布塞進那份清單。

成功並寫入驗證過的回執之後，下一筆 Result 對同一顆 `candidate_sha` 給 `pull_request_exists`，表單不重新出現。人不能用「新請求」再為這顆 commit 建立第二筆 PR。`cancelled` 或 `failed` 且沒有那份回執時，「新請求」仍是另一筆建立，不是更新既有 PR。`uncertain` 與 `needs_attention` 沒有「新請求」。

## 6. 拒絕代碼與下一步

每一列都說明缺什麼、在這裡能做什麼、哪個設定能處理、草稿留不留。主文用該列的句子；代碼只在 Details。草稿規則：

- 受理前拒絕、回應有 `admission_refused: true`、還沒有 operation id：欄位裡的字留下。「新請求」丟掉被拒絕的 intent，留下文字。下一次是新 key。伺服器沒有建立操作，所以這把新 key 不是重送不明結果。沒有這個旗標時，客戶端分不出拒絕與遺失回覆，按鈕留在「查回原請求」並用同一把 key。見 §4.4。
- 已有 operation id，狀態 `failed`：字鎖定，直到「新請求」。新 key 只因為原操作已以失敗結束。若此時 Result 已是 `pull_request_exists`，表單不畫。
- `uncertain`、`needs_attention`：字鎖定，「新請求」隱藏。只查回原 id。
- `succeeded`：storage 清空，欄位回到空的 `pmDefault`，兩個草稿 radio 明確取消勾選。
- Result 讀取 401／403／404：表單、PR 列與計數一起拿掉。storage 不顯示。遲到回應不能把它畫回來（`pm-work-result.js:130`、`:170-173`）。
- 信封無效時 `renderInvalid`（`pm-work-result.js:183-185`）用標題與一段說明取代整個面板，表單一起消失。實作在 `replaceChildren` 之前 `dispose()` 這張表單，與 `withdraw`（`:74-85`）相同。見 §7。

設定建議看 `caps.managed_installation`。受管安裝的連線設定（`#/settings?section=connection`，連結文字 `paths_setup`，`app.js:1922`、`shell.js:95`）可以改：儲存庫綁定、GitHub token、`allow_integrate`／`allow_merge`／`allow_pr_update`（`managed-setup.js:169-176`）；主機的寫入、orchestrate、共用 clone、managed roots 與 SSH alias（`:160-167`）。後端在 `allow_integrate` 為 true 時把主機寫進 `integrate.hosts`（`managed_setup.py:345-350`）。引導綁定不能移除既有整合（`EXISTING_INTEGRATION`，`:357-358`）。不是受管安裝時，不要為了儲存庫綁定、integrate 主機、主機層級、managed roots 或 SSH alias 把人送到那一頁；那些項目在該畫面沒有控制。憑證失效（`PR_AUTHORITY_UNAVAILABLE`）仍連到同一頁，兩種安裝都適用，因為那是憑證而不是綁定。

下面三項這個畫面始終沒有控制：GitHub provider URL（`github_config.api_url`）、開始之後的 `delivery_goal`、成員資格。

`_guard`（`pr_publication.py:294-325`）會再跑 `_source` 與 `_config`（`:300-301`）。因此 §6.1 裡由這兩個函式及其呼叫丟出的每一個代碼，都可能在操作已經存在之後，以 `failed` 再出現一次。那時欄位鎖定，不另 POST。`failed` 或 `cancelled` 才有「新請求」。

## 何時才有送出鈕

1. 目前這份 Result 的 `next_allowed_actions` 恰好有一筆 `github.pr.publish`，而且是可原樣送出的形狀：`kind` 為 `action`；`target` 恰好是 `workspace_id`、`repository`、`host`、`source_operation_id` 四個非空字串；`prefilled_params.candidate_sha` 是 40 hex；`prefilled_params.base_ref` 是非空字串；`preconditions` 恰好是大於 0 的整數 `repository_id` 與 40 hex 的 `expected_base_sha`；`required_params` 含 `candidate_sha`、`base_ref`、`public_title`、`public_body`、`draft`。
2. 目錄允許這個動作，而且 scopes 含條目上的要求與 `integrate`。
3. 成果面板收到既有的 `form` 與 `namespace`。沒有這組介面時，只顯示事實與「不會送出」，不放一顆會動作的按鈕。

`blocked_actions` 只要列了這個動作，就優先於可送出列。畫面給原因與下一步，不送出。

條目完全不在兩份清單時，不畫發布區，也不清掉既有草稿。

## 不完整的條目

今天主線會把動作列出來，但只有 `prefilled_params.candidate_sha`，沒有 `base_ref` 與 `preconditions`。這種條目顯示缺口，標題與說明仍可留在原本的 storage key，送出鈕隱藏，Enter 也不會 POST。不把缺的 target 改寫成可送出的形狀。

## 請求身分

storage namespace 是看板 namespace 加上 `.work-publish.` 與候選 SHA。POST 的 target 仍是條目上的那四個鍵，不含候選 SHA。草稿與 intent 因此跟固定的候選綁在一起。

結果不明或回覆遺失時，沿用 durable form 的原 key，不另外換 key。受理前的明確拒絕與終態失敗仍用既有 form 的規則。`PR_RECEIPT_EXISTS` 不提供「新請求」。`PR_PROVIDER_TARGET_CHANGED` 的句子說明儲存庫或記下的基底已不符，需要再核對，不只是分支移動了。

請求進行中若來了另一份候選，舊表單留在畫面上，通知這筆請求仍對準原來的 commit。不會把舊 intent 改指到新候選。
