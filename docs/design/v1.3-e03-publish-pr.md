## 2. 何時出現

UI 只消費 E04 Result 回傳的條目，不自己組 target，也不在 Result 沒有列出時提供這個動作。條目形狀以 `pm_attempt_result_reads.py:1078-1102` 為準。E04 散文在 `docs/design/v1.3-e04-result.md:276`。兩邊不一致時，以這段程式為準，並記在 §10。

提供時，條目是：

- `kind: "action"`
- `action: "github.pr.publish"`
- `target`: `{workspace_id, repository, host, source_operation_id}`，四個鍵與 `ActionDef` 一致（`pr_publication.py:77-78`）
- `required_scopes`: `["integrate", "manage", "observe"]`（`_action_scopes` 在 `:890-891`，再加上 `REQUIRED`，`pr_publication.py:38`）
- `required_params`: `candidate_sha`、`base_ref`、`public_title`、`public_body`、`draft`
- `optional_params`: `["quality_ref"]`
- `prefilled_params`: 僅在候選 SHA 是 40 hex 時含 `candidate_sha`（`:1075-1077`）。標題與內文永不預填

程式只在同時滿足這些條件時考慮這筆條目（`:1002`、`:1072-1073`）：有 session、`execution.state` 是 `turn-ended` 或 `process-ended`、`delivery_goal == "pull_request"`、有 `execution_op_id`、動作已註冊。`consider`（`:922-955`）再要求同一個 controller、寫入成員，以及條目上的 scopes。`delivery_goal` 未記錄時是 `"unknown"`，此時不提供這個動作（E04 `:63`）。

### 2.1 完全不畫

下列情況條目不在 `next_allowed_actions`，也不在 `blocked_actions`。畫面不畫發布區塊，也不放一顆停用的「發布 PR」：

- `delivery_goal` 是 `unknown` 或 `reviewable_changes`
- 執行狀態不是 `turn-ended` 或 `process-ended`
- 沒有 session，或沒有執行操作
- 動作未註冊
- 父啟動是 `stage == "start_unknown"` 或 `operation_status == "uncertain"`

最後一項程式在 `:979-982` 直接返回，只把 `work.start` 放進 `blocked_actions`。E04 `:276` 寫其餘動作會以 `WAIT_ORIGINAL_OPERATION_RECONCILE` 回報；目前實作沒有把 `github.pr.publish` 放進去。UI 不補一列阻擋。成果區既有的交付目標列已經顯示目標。開始之後，這個畫面沒有改 `delivery_goal` 的控制。

### 3.1 固定 commit

`prefilled_params.candidate_sha` 以唯讀顯示前 12 個 hex，與成果區現有寫法相同（`pm-work-result.js:550`、`:565`）。完整 SHA 放在無障礙名稱、`title`，以及 Details。不用會把全文藏起來的 CSS 省略。人不能改這個欄位，也不能另打一個 SHA。

來源句子：

1. SHA 等於 `changes.fixed_result_commit.commit_sha` 時，沿用該物件的 `source_kind` 標籤：`turn_end_observation`、`execution_verification` 或 `session_verification`、`integration`（`pm-work-result.js:559-561`）。
2. SHA 等於最新回執的 fixed commit、且與信封上的 fixed commit 不同時，用 `wpub_commit_from_receipt`。候選 SHA 的選法在 `cand_sha_for_pr`（`pm_attempt_result_reads.py:1578-1582`）：最新回執的 `fixed_result_commit` 是 dict 時用它的 `commit_sha`，否則用信封的 fixed commit。信封優先順序是 integration、verification、再回執（`:1568-1576`）。兩者可以不同。E04 `:276` 只寫最新回執；畫面以這段程式比較。
3. 兩邊都不相等時，只用 `wpub_commit_from_result`。
4. 沒有 40 hex 的 `prefilled_params.candidate_sha` 時，顯示 `wpub_commit_missing`，不送出。回執 SHA 不是 40 hex 時，程式仍會列出動作且 `prefilled_params` 是空的（`:1075-1077`）。

### 3.2 目標分支與草稿沒有預設

`base_ref` 沒有任何條目欄位可當預設。開始時的 `code_source.source_ref` 是 `refs/heads/{default_branch}` 或人指定的 ref（`pm_work_start.py:1834-1850`），套件交付物件把它抄成 `base_ref`（`:436-439`）。發布把 `base_ref` 接在 `git/ref/heads/` 後面（`pr_publication.py:356`），並當成 GitHub PR 的 `base`（`:506`）。`refs/heads/main` 會去查 `heads/refs/heads/main`。UI 不剝前綴，也不把 `source_ref` 填進欄位。人輸入分支名稱，例如 `main`。格式是 `resource_policy.HEAD_REF`（`resource_policy.py:659`）。欄位維持空白，直到人輸入。

`draft` 必須是真正的 bool（`pr_publication.py:195`）。程式不給預設。UI 不靜默送 `false`，那會建立一筆可審閱的 PR。控制項是 radiogroup，兩項都先不選。不用 segmented control，因為那個控制項總是有一個值。不用核取方塊，因為未勾選無法區分「還沒選」與「開放審閱」。

`durableForm` 只保存字串（`pm-workspace.js:80`）。草稿選擇鏡射到一個名為 `draft` 的欄位，值是 `""`、`"true"` 或 `"false"`。送出時在 `params()` 轉成 bool。兩個 radio 放在表單的 `extra` 裡；鏡射欄位不進 Tab 順序。`durableForm` 停用欄位時，兩個 radio 一起停用。還原草稿時，依字串勾回對應的 radio。`dataset.pmDefault` 全部是空字串，成功後欄位回到空白，不冒出預設。

### 3.3 草稿怎麼留

表單使用 `durableForm`（`pm-workspace.js:69-310`）。storage key 是 ``batc.pm.${namespace}.${action}.${JSON.stringify(target)}``（`:70`）。`namespace` 用看板已有的值加上 `.work-publish`（看板參數在 `pm-kanban.js:14`；Start work 的寫法在 `pm-work-start.js:784-788`）。換連線主體就換 key，不會顯示另一個主體的草稿。

`durableForm` 目前沒有 export。`workResultPanel`（`pm-work-result.js:53`）也沒有收到 `namespace`。實作時匯出既有函式或加一層薄包裝，由看板把 `namespace` 傳進成果面板。不另寫一套 key、焦點或回復。

重新整理、離開成果檢視、連線中斷之後，同一把 key 的標題、說明、目標分支與草稿選擇都還在。有 intent 時欄位鎖定，直到該操作進入終態並且人按下「新請求」，或受理前的拒絕被按掉。見 §7。

### 3.4 不送 quality_ref

`quality_ref` 是選填。若要送，必須同時有 `review_id`、`operation_id`、`version`、`document_digest`（`pr_publication.py:201-208`）。`verification.quality_reviews.current` 只有 `review_id`、`version`、`qualified`、`kind`、`acceptance`、`dod`（`pm_attempt_result_reads.py:567-580`），沒有 `operation_id` 與 `document_digest`。這個表單省略 `quality_ref`，不提供選擇器。省略是合法的（`:118-120` 在沒有這欄時直接返回）。

## 4. 送出

UI 不增加後端行為。送出就是既有的 `POST /api/v1/operations?wait=3`，由 `durableForm` 在建立 intent 之後發出（`pm-workspace.js:215-242`）。`github.pr.publish` 不是 `pm.*` 也不是 `work.start`，所以用一般 idempotency key，不是 PM 前綴 key（`operations.py:126-127`）。UI 不自己組第二種 key。

### 4.1 什麼時候才可以按

以下條件同時成立才顯示可按的「發布 PR」：

1. 目前這份 Result 的 `next_allowed_actions` 有這筆動作，而且 target 四個值都是字串。
2. 同一筆條目帶有 `preconditions`，且恰好是 `{repository_id, expected_base_sha}`：`repository_id` 是大於 0 的整數，`expected_base_sha` 是 40 hex。今天的條目沒有這個物件，見 §10.1。缺了就顯示 `wpub_gap_preconditions`，欄位仍可打字存草稿，送出鈕不出現。說明本身就是下一步，不用按下後的 `pm_action_unavailable` 蓋掉它。
3. `prefilled_params.candidate_sha` 是 40 hex。缺了就顯示 `wpub_commit_missing`，送出鈕不出現。
4. catalog：`caps().scopes` 含 `integrate`，且 `caps().actions` 有 `{action: "github.pr.publish", allowed: true}`。`durableForm` 的 `requiredScope` 傳 `'integrate'`（預設是 `manage`，`:102-103`）。另外，`caps().scopes` 要含條目上的 `observe`、`manage`、`integrate`。catalog 不允許時顯示既有 `pm_action_unavailable`，草稿保留，不另送。

Result 條目是產品閘門。catalog 只反映 `durableForm` 已有的檢查。不因為 catalog 允許就在 Result 沒列出時送出。

本地檢查（空白標題、未選草稿、空的目標分支、標題或說明超過位元組上限）發生在 `params()` 丟錯之前，也就是 `pm-workspace.js:215-218` 寫入 intent 之前。這種檢查不建立 operation key。焦點移到該欄位。伺服器的 `INVALID_PARAMS` 仍是最終依據。

### 4.2 請求本體

條目把受理事實都帶齊時，本體是：

- `action`: `"github.pr.publish"`
- `target`: 條目的 `target`，原樣複製。不補 null、不改 repository、不改 host
- `params`: `candidate_sha` 來自 `prefilled_params`；`base_ref`、`public_title`、`public_body` 來自欄位；`draft` 是 bool。不含 `quality_ref`
- `preconditions`: 條目的 `preconditions`，原樣複製。不把 `changes.base_commit` 抄進 `expected_base_sha`。`changes.base_commit` 是開始時凍結的 `code_source.source_sha`（`pm_attempt_result_reads.py:220-224`、`:1734`），不是即時的 base 分支 SHA，也不是分支名稱
- `Idempotency-Key`: 這一次送出的那把 uuid，先寫進 intent 再 POST

一次送出一把新的 operation key。受理前被拒絕時，伺服器沒有建立操作；「新請求」清掉那把被拒絕的 intent、留下打過的字，下一次送出才是另一把新 key。這與結果不明不同。

### 4.3 契約對畫面的意義

`capabilities()`（`pr_publication.py:81-84`）是 `creation_only: true`、`unknown_post_resend: false`。遺失的 GitHub POST 201 不會重送。搜尋到的候選不會升格成回執（`:516-531`）。

因此：

- 每一筆送出是自己的操作與自己的 key
- 操作已經存在而結果是 `uncertain` 或 `needs_attention` 時，不再 POST。按鈕文字是「查回原請求」，按下只 `GET /operations/{id}`（`pm-workspace.js:241-242`）
- 回覆遺失、key 已存而還沒有 `operation_id` 時，下一次按下仍用同一把 key POST。伺服器以那把 key 找回原操作。這不是第二筆發布
- 不清除鎖、不重送開始、不為了「修好」不明結果而換一把 key

`GitHubAmbiguous` 是 `AmbiguousOutcome`（`github.py:30`，`operations.py:57-61`）。執行器把操作標成 `uncertain`（錯誤代碼 `UNCERTAIN`），讀回次數用盡後變成 `needs_attention`／`UNCERTAIN_UNRESOLVED`（`operations.py:863-873`）。畫面用操作自己的狀態字，加上 `wpub_uncertain` 或 `wpub_needs_attention`。

### 4.4 人在等待時看到什麼

`durableForm` 已有的狀態區是表單裡的 `role="status"`（`pm-workspace.js:86`）。不另加第二個 live region。

## 5. 建立之後

成功的操作結果是 `{published: true, creation_receipt, merged: false, deployed: false}`（`pr_publication.py:536-540`）。`merged: false` 與 `deployed: false` 照實理解。畫面不把 `published: true` 說成已合併、已部署或已驗收。

PR 出現在 Result 的 `delivery.pull_requests`，資料來自建立回執（`pm_attempt_result_reads.py:610-654`）。刷新走既有事件：`app.js:740-773` 把事件交給監聽者；`pm-workspace.js:1769-1793` 對 `pm_` 資源（含 `pm_work_attempt`）以及 `operation`、`deployment`、`integration` 重新讀取可見的看板。看板 `refresh`（`pm-kanban.js:392`）再選取目前的卡，Start work 面板回報最新 attempt（`pm-work-start.js:899`），成果面板重新讀取（`pm-work-result.js:92-112`）。UI 不從操作結果捏一列 PR，也不發明 GitHub 網址。回執投影沒有 `html_url`、`state`、`draft`。有 `publication_operation_id` 時，沿用現有連結 `#/op/{publication_operation_id}`（`pm-work-result.js:416-424`）。

`requirement_acceptance` 是 `not_evaluated_by_publication`（`pr_publication.py:415`）時，顯示 `wpub_pr_not_accepted`，並可併用既有「尚未驗收／Not assessed」。`target_verified` 不是 true 時，顯示 `wpub_pr_unverified`，不說發布目標相符。`completeness.coverage.delivery` 是 `"partial"`（`:1859-1864`）時，清單旁顯示 `wpub_pr_partial`。這份清單是這次讀到的紀錄，不是總數。不把未知顯示成 0。

合併與部署留在既有 Delivery 畫面：`app.js:4499` 的 `delivery`，實作是 `viewDelivery`（`:2185`）。它不讀 query 來預填這筆 PR。連結是 `#/delivery`，文字是 `nav_delivery`，旁邊一句 `wpub_delivery_link`。成果區不加 `github.pr.merge`、`delivery.merge_and_deploy` 或 `deployment.*`。Work 檢視裡另一份交付讀取（`pm-engineering-delivery/v1`）的允許清單本來就沒有 `github.pr.publish`（`pm-work-deliveries.js:74`），這份規格不把發布塞進那份清單。

動作在 PR 已經存在時仍可能再次出現（`_compute_actions` 不看 `pull_requests`）。上一筆已 `succeeded`、`failed` 或 `cancelled`，而且人按了「新請求」之後，下一次送出是另一筆新的建立，不是更新。`cancelled` 可以新請求，因為原操作已結束。`uncertain` 與 `needs_attention` 不行。

## 6. 拒絕代碼與下一步

每一列都說明缺什麼、在這裡能做什麼、哪個設定能處理、草稿留不留。主文用該列的句子；代碼只在 Details。草稿規則：

- 受理前拒絕、還沒有 operation id：欄位裡的字留下。「新請求」丟掉被拒絕的 intent，留下文字。下一次是新 key。伺服器沒有建立操作，所以這把新 key 不是重送不明結果。
- 已有 operation id，狀態 `failed`：字鎖定，直到「新請求」。新 key 只因為原操作已以失敗結束。
- `uncertain`、`needs_attention`：字鎖定，「新請求」隱藏。只查回原 id。
- `succeeded`：storage 清空，欄位回到空的 `pmDefault`。
- Result 讀取 401／403／404：表單、PR 列與計數一起拿掉。storage 不顯示。遲到回應不能把它畫回來（`pm-work-result.js:130`、`:170-173`）。

「哪個設定」只有憑證或連線中斷才連到 `#/settings?section=connection`，連結文字用 `paths_setup`。儲存庫綁定、integrate 主機、主機層級、managed roots、git runner 是 Connector 的設定，這個畫面沒有編輯它們的控制，也不另開路由。

## 8. 無障礙

區塊在檢查與變更之後。Tab 順序是：公開說明（文字）、固定 commit（文字）、標題、說明、目標分支、草稿的兩個 radio、缺口或阻擋說明、送出鈕、「新請求」（出現時）、操作連結（出現時）。鏡射用的 `draft` 欄位不在 Tab 順序裡。radiogroup 的無障礙名稱是 `wpub_draft_group`。

## 10. 缺口

UI 需要、而 E04 或 `pr_publication.py` 今天沒有給的事實。不為這些缺口發明端點。

1. **沒有 preconditions。** 動作條目（`pm_attempt_result_reads.py:1078-1102`）沒有 `preconditions`。`_admit` 要求 `repository_id` 與 `expected_base_sha`（`pr_publication.py:188`）。開始當下的 `repository_id` 在 `pm_work_start.py:1855`，`_attempt_view` 把 `code_source` 放進 attempt 視圖（`:2020`），`get_attempt` 回傳該視圖（`:2052-2056`）。Result 條目與信封都沒有這兩個受理值。`changes.base_commit`（`pm_attempt_result_reads.py:1734`）是凍結的起始 SHA，不能當成 `expected_base_sha`。條目帶上這兩個值之前，表單不送出，並顯示 `wpub_gap_preconditions`。測試可以用 fixture 把 `preconditions` 放在既有動作物件上；那不是一條新路由。之後若要讓正式環境送出，是同一筆 Result 條目補上欄位，不是這份 UI 規格的依賴。
2. **沒有 `base_ref` 預設。** 見 §3.2。`pm_work_start.py:1839-1850` 與 `:439` 的 `refs/heads/…` 形狀不對。

## 11. 設計取捨

1. **草稿用 radiogroup，兩項都不預選。** 沒有預設。靜默的 `false` 會建立可審閱的 PR。`durableForm` 只能存字串，所以鏡射成 `""`／`"true"`／`"false"`。
2. **目標分支由人輸入，不填 `source_ref`，也不剝 `refs/heads/`。** 該值不在動作條目上，而且形狀會被接進 `git/ref/heads/`（`pr_publication.py:356`、`:506`）。
3. **條目沒有 `repository_id` 與 `expected_base_sha` 就不送出。** 簡報要求照條目使用、不發明端點。不另讀其他 API，也不抄 `changes.base_commit`。
4. **不送 `quality_ref`。** 現有審閱物件組不起必要欄位。省略是合法的。
5. **表單放在變更區塊之後、回合與 Details 之前。** 對應計畫 F8。鍵盤順序跟 DOM。這個區塊一個主要按鈕。
6. **窄螢幕不另做版面。** 既有檢視抽屜就是窄螢幕 UI（`components.js:245-277`）。
7. **target 不變時保留表單節點。** 焦點與進行中的回查才過得了刷新。信封沒變時本來就不會重畫（`pm-work-result.js:153-161`）。
8. **成功句用 `wpub_success`，焦點盡量留在送出鈕。** `pm_saved` 與「done／完成」會把發布說成已儲存或泛稱的完成。鈕被重畫拿掉時，焦點改到新的 PR 操作連結。
9. **錯誤主文走 `errorBox` 的 summary，代碼留在 Details。** 既有 `errorPresentation` 會用 `error_code_${code}`；這份規格的句子由 `onError` 以 summary 傳入，避免主文變成伺服器英文或原始代碼。
10. **`#/settings?section=connection` 只用在憑證或連線。** 儲存庫綁定問題連到那一頁會指錯地方。
11. **uncertain 的測試放在新檔的 dispatch 包裝，不改 work-start fixture 的預設成功。** Part A 與 Start work 測試繼續看到 `succeeded`。
12. **第二把 key 只出現在：尚無 intent 的第一次送出，或原操作已 `failed`／`cancelled`／受理前拒絕且人按了「新請求」。** `uncertain` 與 `needs_attention` 只查回原操作。回覆遺失用同一把 key。
