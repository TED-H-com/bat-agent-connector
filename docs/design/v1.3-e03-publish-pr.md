# v1.3 E03 Part D：從固定成果發布 pull request

這份文件記錄已經做在成果區裡的發布行為。送出仍是已註冊的 `github.pr.publish`，經由看板既有的 operation form。客戶端不呼叫 GitHub，不自組私人 id，也不在條目之外另選 provider、帳號或基底。

## 何時才有送出鈕

1. 目前這份 Result 的 `next_allowed_actions` 恰好有一筆 `github.pr.publish`，而且是可原樣送出的形狀：`kind` 為 `action`；`target` 恰好是 `workspace_id`、`repository`、`host`、`source_operation_id` 四個非空字串；`prefilled_params.candidate_sha` 是 40 hex；`prefilled_params.base_ref` 是非空字串；`preconditions` 恰好是大於 0 的整數 `repository_id` 與 40 hex 的 `expected_base_sha`；`required_params` 含 `candidate_sha`、`base_ref`、`public_title`、`public_body`、`draft`。
2. 目錄允許這個動作，而且 scopes 含條目上的要求與 `integrate`。
3. 成果面板收到既有的 `form` 與 `namespace`。沒有這組介面時，只顯示事實與「不會送出」，不放一顆會動作的按鈕。

`blocked_actions` 只要列了這個動作，就優先於可送出列。畫面給原因與下一步，不送出。

條目完全不在兩份清單時，不畫發布區，也不清掉既有草稿。

## 不完整的條目

今天主線會把動作列出來，但只有 `prefilled_params.candidate_sha`，沒有 `base_ref` 與 `preconditions`。這種條目顯示缺口，標題與說明仍可留在原本的 storage key，送出鈕隱藏，Enter 也不會 POST。不把缺的 target 改寫成可送出的形狀。

## 請求身分

storage namespace 是看板 namespace 加上 `.work-publish.` 與候選 SHA。POST 的 target 仍是條目上的那四個鍵，不含候選 SHA。草稿與 intent 因此跟固定的候選綁在一起。

結果不明或回覆遺失時，沿用 durable form 的原 key，不另外換 key。受理前的明確拒絕與終態失敗仍用既有 form 的規則。`PR_RECEIPT_EXISTS` 不提供「新請求」。`PR_PROVIDER_TARGET_CHANGED` 的句子說明儲存庫或記下的基底已不符，需要再核對，不只是分支移動了。

請求進行中若來了另一份候選，舊表單留在畫面上，通知這筆請求仍對準原來的 commit。不會把舊 intent 改指到新候選。

## 發布之後

成功句是已發布，不是已合併、已部署或已驗收。PR 列只在 `publication_operation_id` 是 `op_` 加 32 hex 時連到 `#/op/{id}`。回執沒有提供的 GitHub 網址不會被補上。`target_verified` 不是 true 時，在該操作連結旁說明回執沒有顯示 head 與 base 相符。交付讀取是 `partial` 時，旁邊說明這次沒有包含全部紀錄。
