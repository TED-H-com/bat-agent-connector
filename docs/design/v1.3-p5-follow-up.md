## 1. 範圍與核心原則

當使用者已透過 `work.start`（PR #194）啟動一個 Work Item，且 BAT 正在該受管工作階段（managed session）中執行時，使用者接著發出第二輪指令（例如：「再補一個失敗後重新送出的案例」）。本規格定義 v1.3 P5 的中央權威契約與資料模型，滿足 F5 的核心不變量：

1. **同一 Work、同一 Controller**：追加指令以 `{workspace_id, work_item_id}` 為目標，由 Admission 解析至該 Work 最新且處於 `stage == "started"` 的 Attempt 與其受管 `(host, session_id)`，並重用 `pm_work_start.require_work_controller`（`src/bat_agent_connector/pm_work_start.py:192-200`）強制驗證呼叫端與該 Work 的 Controller 錨點一致。
2. **Connector 自有排隊（After-Current），絕不插入（Steer）執行中回合**：若目前 Turn 仍在執行，Connector 將指令保留於自身的持久化佇列（`work_inputs`）中等待，直到該 Turn 在 `session_results` 寫入結束邊界（`boundary IN ('turn_done', 'agent_error')`）且工作階段確認閒置後才送出；`schedule="now"` 僅在工作階段確認閒置時才送出，否則立即以 `409 PM_WORK_SESSION_BUSY` / `409 PM_WORK_SESSION_WAITING_INPUT` 拒絕，絕不干預執行中的 Turn。
3. **獨立 ID 與獨立收據（Receipt）**：每一筆追加輸入皆為獨立的持久化 Operation，擁有固定 `message_id = "batc-" + operation_id`、在 `INSERT` 交易內分配的不可變序列位置 `position` 與獨立收據。
4. **遺失回覆以原 ID 調和（Reconcile），絕不重送**：傳輸中斷或遺失回覆時，沿用既有 `send` 步驟與原 `message_id` 進行調和；Claude 由 live transcript 的 `clientMessageId` 回音確認送達，未收到回音時維持 `needs_attention`（收據狀態 `unknown`）並阻擋同工作階段後續排隊輸入，絕不以新 ID 重送、絕不刪除步驟列、亦絕不以相似文字猜測成功。
5. **誠實對待上游能力（Codex 決策）**：由於 BAT Codex 不回音 `clientMessageId`（`api_actions.py:137-142`）且不登錄關聯 Turn（`service.py:1212-1214`），無法產生 `turn_attribution == "correlated"` 的 E04 `turn_done` 邊界（`service.py:545-548, 579-582`、`pm_attempt_results.py:1538-1541`）。依 F5「不假裝上游支援佇列」原則，本規格建議於 Admission 明確以 `409 PM_WORK_CODEX_FOLLOW_UP_UNSUPPORTED` 拒絕針對 Codex 受管工作階段的 Work 追加指令（詳見 §5.4 與 §14 Owner 決策問題）。

## 2. Target 結構、Admission 解析與拒絕碼（決策 1）

### 2.1 擴充既有 `session.send`，不新增動作別名

依據 `docs/design/v1.3-e00-baseline.md` §3.2（`:150`）與 §3.3（`:181`），P5 直接擴充既有的 `session.send`（`api_actions.py:377-378`），**不註冊** `work.follow_up` 動作別名。`_admit_send`（`api_actions.py:79-86`）依 `target` 區分三種目標型態：

1. **Work Target（P5 新增）**：`{"workspace_id": "<ws_id>", "work_item_id": "<wi_id>"}`
2. **Task Target（既有）**：`{"task_id": "<task_id>"}`
3. **Session Target（既有）**：`{"host": "<host>", "session_id": "<session_id>"}`

### 2.2 既有 `_admit_send` 與混合目標（Mixed Target）規則

在 `src/bat_agent_connector/api_actions.py:79-86`，現有程式碼為：

```python
def _admit_send(ops: OperationService, principal: Principal, target: dict, params: dict, pre: dict) -> dict | None:
    if target.get("task_id"):
        from .task_actions import admit_send
        return admit_send(ops, principal, target, params, pre)
    if not all(isinstance(target.get(k), str) and target[k] for k in SESSION_TARGET):
        raise OperationError("INVALID_TARGET", "host and session_id are required", 422)
    _validate_send(params)
    return _admit_session(ops, principal, target, params, pre)
```

P5 **僅在最前方加上 Work 分支**，其餘程式碼一字不改：

```python
def _admit_send(ops: OperationService, principal: Principal, target: dict, params: dict, pre: dict) -> dict | None:
    if "workspace_id" in target or "work_item_id" in target:
        from . import pm_work_follow_up
        return pm_work_follow_up.admit_send(ops, principal, target, params, pre)
    if target.get("task_id"):
        from .task_actions import admit_send
        return admit_send(ops, principal, target, params, pre)
    if not all(isinstance(target.get(k), str) and target[k] for k in SESSION_TARGET):
        raise OperationError("INVALID_TARGET", "host and session_id are required", 422)
    _validate_send(params)
    return _admit_session(ops, principal, target, params, pre)
```

- **混合目標（Mixed Target）的處置**：若呼叫端同時傳入 Work 鍵（`workspace_id` 或 `work_item_id`）與 `host`、`session_id`、`task_id`、`attempt_id` 或任何其他鍵，會先進入 `pm_work_follow_up.admit_send`，並因 `set(target) != {"workspace_id", "work_item_id"}` 立即以 HTTP `422`、`error.code = "INVALID_TARGET"`（`admission_refused: true`）被拒絕。客戶端**絕不可**在 Work Target 中自行指定底層 `host` 或 `session_id`。
- **既有呼叫端盤點（已以 `grep -rn "session.send"` 驗證全儲存庫）**：
  - `src/bat_agent_connector/orchestration_operations.py:368-370`：傳入 `target={"host": plan["host"], "session_id": plan["session_id"]}`；
  - `src/bat_agent_connector/api_actions.py:310`（`legacy_session_control`）：傳入 `target={k: request[k] for k in SESSION_TARGET}`；
  - `src/bat_agent_connector/task_actions.py:13, 135-148`：傳入 `target={"task_id": ...}`；
  - 前端 `desktop/src`（`src/bat_agent_connector/dashboard/app.js:56694`）：傳入 `target={host, session_id}`。
  - **没有任何既有呼叫端**會在 `session.send` 的 `target` 中混傳 `workspace_id` 或 `work_item_id`。因此當 `target` 不含 `workspace_id` 與 `work_item_id` 時，舊有 `{host, session_id}` 與 `{task_id}` 的檢查、`_validate_send(params)`、`_admit_session(ops, principal, target, params, pre)`、冪等鍵命名空間與執行路徑維持 byte-for-byte 不變。

## 3. `schedule` 參數契約與禁止 Steer（決策 2）

當 `session.send` 的 `target` 為 Work Target（`{workspace_id, work_item_id}`）時，`params` 的驗證規則如下：

1. **允許的參數鍵**：`{"text", "schedule"}`。
   - `text`：必填非空字串，`1 <= len(text.strip()) <= service.MAX_PROMPT_CHARS`（重用 `_validate_send`，`api_actions.py:91-92`）。
   - `schedule`：選填字串，僅允許 `"after_current"` 或 `"now"`；**省略時預設為 `"after_current"`**。傳入其他值以 `422 INVALID_PARAMS` 拒絕。
2. **拒絕 `queue` 與自訂 `message_id`**：
   - 若 `params` 含有 `"queue"`，立即以 `422 INVALID_PARAMS`（`"Work-targeted session.send uses schedule ('after_current' or 'now'), not queue"`）拒絕。
   - 若 `params` 含有 `"message_id"`，立即以 `422 INVALID_PARAMS`（`"Work-targeted session.send assigns message_id deterministically as batc-<operation_id>"`）拒絕。
3. **`schedule="after_current"`（預設）行為**：
   - 無論目標工作階段目前是否正在串流執行（`streaming` / `isStreaming`）或前方是否已有排隊中的輸入，Admission 皆核准並於 `INSERT` 交易內排入 `work_inputs` 序列。
   - 若執行時前置條件（§5.1）尚未成立，或在最後一幀檢查（`_before_frame`）發現工作階段忙碌 / 存在待處理閘門，操作進入 `Wait("waiting_external", ...)` 等待目前回合結束，**絕不**向執行中的 Turn 發送封包。
4. **`schedule="now"` 行為（僅限閒置，絕不 Steer）**：
   - Admission（及 `INSERT` 交易內的 `pm_work_follow_up.admit_operation`）要求當下同時滿足三項本地閒置條件：
     1. 該 `(host, session_id)` 在 `work_inputs` 中沒有任何尚未終結（non-terminal）的前置輸入；
     2. 該工作階段在 `session_results` 中已存在當前有效前置 `turn_marker` 的結束邊界收據（`document.boundary IN ("turn_done", "agent_error")`），且 `sessions_observed.streaming == 0`、`runtime_status` 不在執行中；
     3. 無待處理的權限或問題閘門（`sessions_observed.pending_json` 解析後為空）。
   - 若上述條件 1 或 2 不成立，Admission 立即以 `409 PM_WORK_SESSION_BUSY` 拒絕；若條件 3 不成立，立即以 `409 PM_WORK_SESSION_WAITING_INPUT` 拒絕。此外，在發送步驟的 `_before_frame` 最後一幀即時檢查中若發現工作階段變為忙碌或等待輸入，亦以相同 `PM_WORK_SESSION_BUSY` / `PM_WORK_SESSION_WAITING_INPUT` 拒絕（未送出任何封包）。

## 4. 最小且不可變的 `work_inputs` 資料表與 `INSERT` 交易分配（決策 3）

### 4.1 設計原則：最小、不可變（Immutable）、衍生狀態於讀取與執行時計算

對齊 E02 `work_attempts`（`src/bat_agent_connector/pm_work_start.py:99-123`）的設計：
- `work_inputs` 僅保存不可變的身分與排序錨點（`sequence`、`operation_id`、`workspace_id`、`work_item_id`、`attempt_id`、`host`、`session_id`、`position`、`schedule`、`message_id`、`created_at`）。
- **移除所有可變欄位與重複資料**：不儲存 `updated_at`、`sent_at`、`text_excerpt`、`text_truncated`、`text_sha256`、`controller_json`、`predecessor_operation_id`、`predecessor_turn_marker`，且**不使用** `ON DELETE CASCADE` 外鍵，並加上 `BEFORE UPDATE` 與 `BEFORE DELETE` triggers 強制不可變。

  - **有效前置 Turn 標記（`effective_predecessor_turn_marker`）與阻擋中之 `predecessor_operation_id` 一律在執行時與讀取時動態計算**（見 §5.1），避免前置輸入取消時產生靜態欄位矛盾。

## 5. 前置條件規則、Turn 邊界喚醒與輪詢退避（決策 4）

### 5.1 執行時動態前置條件規則（Predecessor Rule）

對於 `work_inputs` 中位於 `(host, session_id, position)` 的操作，每次執行 handler 時僅讀取**本地 SQLite 狀態**（零 BAT 呼叫）計算其前置狀態：

1. **檢查所有更早的輸入（`pos < position`）**：
   查詢同一 `(host, session_id)` 下所有 `pos < position` 的 `work_inputs` JOIN `operations`（依 `pos ASC`）：
   - **隊首判定（Queue Head）**：若存在任何 `pos < position` 的列其 `operations.status` 屬於非終態：
     - 若存在 `status IN ('uncertain', 'needs_attention')`（或 `operation_steps(name='send').status == 'uncertain'`），當前輸入**絕不可越過或覆蓋它**，拋出 `Wait(status="waiting_external", reason="predecessor_outcome_uncertain", delay_s=60.0)`（詳見 §5.3 與 §7.3）。
     - 若存在 `status IN ('accepted', 'queued', 'waiting_checks', 'waiting_external', 'running')`，當前輸入並非隊首，拋出 `Wait(status="waiting_external", reason="waiting_predecessor_input", delay_s=60.0)`，等待前置操作終結時主動喚醒。
   - 當所有 `pos < position` 的列皆處於終態（`succeeded`、`failed`、`cancelled`）時，當前輸入即為該工作階段佇列的**隊首（Head of Queue）**。
2. **動態決定 `effective_predecessor_turn_marker`**：
   - 取同一 `attempt_id` 下 `pos < position` 且 `operations.status == 'succeeded'` 中 `pos` 最大一列的 `work_inputs.message_id`；
   - 若前方無 `succeeded` 的追加輸入（例如 `position == 1`，或前方輸入皆在送出前 `cancelled` / `failed`），則取該 Attempt 初始 `handoff` child operation（`execution_operation_id`）之 `result.message_id`（對齊 `pm_attempt_results.py:1410-1420` 與 `pm_attempt_result_reads.py:207-217`）。
3. **隊首的本地回合邊界與閒置檢查**：
   - 檢查 `sessions_observed`：若工作階段已結束（`gone == 1` 或 `runtime_status IN ('exited', 'stopped', 'ended', 'dead')`），拋出 `OperationError("PM_WORK_SESSION_ENDED", "session ended before queued follow-up could be sent", 409)`（此時尚未過 transport fence，證明未送出，操作轉為 `failed` 並喚醒下一筆輸入）。
   - 檢查 `session_results`（`src/bat_agent_connector/pm_attempt_results.py:74-105`）：查詢該 `(workspace_id, attempt_id)` 是否已存在 `source_position LIKE f"{effective_predecessor_turn_marker}:%"`（由 `format_source_position(turn_marker, last_message_id)` 產生，`:124-130`）且 `json_extract(document, '$.boundary') IN ('turn_done', 'agent_error')` 的結果收據。
   - 檢查 `sessions_observed` 的 `streaming == 0` 且 `pending_json` 為空。
   - 若上述任一本地條件尚未滿足：
     - 當 `schedule == "after_current"` 時，隊首拋出 `Wait(status="waiting_external", reason="waiting_turn_boundary", delay_s=5.0)`；
     - 當 `schedule == "now"` 時，拋出 `409 PM_WORK_SESSION_BUSY`（或 `409 PM_WORK_SESSION_WAITING_INPUT`）。

### 5.2 與 E04 `AttemptResultCollector.after_refresh` 的整合與多輪（Multi-Turn）支援

**不新增任何 BAT 訂閱通道**，完全重用註冊於 `src/bat_agent_connector/task_daemon.py:264`（在 `src/bat_agent_connector/inventory.py:102, 344-348` 的 `after_refresh_budget_s` 下執行）的 `AttemptResultCollector.after_refresh`（`src/bat_agent_connector/pm_attempt_results.py:1360-1363`，內部呼叫 `collect_host` `:1690-1715`）：

   - **主體投影顯示最新一輪（Latest Turn）**：信封頂層的 `conversation`、`execution`、`changes`、`sources` 與 `completeness` 投影該 Attempt **最新已送出回合**（其 `turn_marker` 取自該 `attempt_id` 下已跨過 transport fence 或 `operations.status IN ('succeeded', 'uncertain', 'needs_attention')` 且 `position` 最大的 `work_inputs.message_id`；若尚無已送出的追加輸入，則為初始 `handoff` child 的 `message_id`）。

### 5.3 輪詢退避（Polling）：僅隊首計時、本地零 BAT 呼叫

2. **重評估僅讀本地 SQLite，零 BAT 呼叫**：

### 5.4 Codex 工作階段與前置條件規則的衝突與決策

1. **為何 Codex 無法滿足關聯回合邊界**：

2. **設計決策（建議方案與替代方案）**：
   - **建議方案（本規格採用）**：在 `pm_work_follow_up.admit_send` 中，當受管工作階段的 `kind == "codex"` 時，立即於 Admission 以 HTTP `409`、`error.code = "PM_WORK_CODEX_FOLLOW_UP_UNSUPPORTED"`（訊息：`"BAT Codex sessions do not echo clientMessageId or correlated turn boundaries; Work-targeted follow-up requires correlated turn completion"`）拒絕，且在 E04 `_compute_actions` 對 Codex Attempt 將 Work Target `session.send` 列入 `blocked_actions`（原因碼 `"codex_uncorrelated_turn_boundary"`）。這完全符合 F5「不假裝上游支援佇列」與誠實呈現能力的原則。
   - **替代方案（供 Owner 裁示，見 §14）**：若未來允許在無 `clientMessageId` 回音下對 Codex 判定回合結束，只能退而使用「`handoff` 送出時間戳後觀測到 assistant 訊息且 `isStreaming` 由 `True` 轉 `False`」之時間序啟發式規則；但該規則在網路重試或遺失 ACK 時無法證明訊息歸屬，違反嚴格 ID 關聯，故本規格不預設啟用。

#### 6.2.1 基準分支 `664715b9` 上 `OpContext.step` 的真實程式碼

### 7.1 以 Transport Fence 定義「開始送出（Send Began）」與取消規則

1. **「開始送出（Send Began）」的精確定義**：
   - 從 SQLite 即時讀取 `operations` 與 `operation_steps(name='send')`：當 `operations.external_refs.get("send_sent") is True`，或 `operation_steps(name='send')` 處於 `succeeded` / `uncertain`（含崩潰後 `send_sent` 非 `False` 之未決狀態）時，即視為**已開始送出**。
   - 反之，當操作處於 `accepted`、`queued`、`waiting_checks`、`waiting_external`，或處於 `running` 但尚無 `send` 步驟列、或 `send` 步驟雖為 `started` 但 SQLite 中 `send_sent is False`（尚未跨過 `on_transport` 圍欄）時，皆屬於**尚未開始送出**。
2. **開始送出前的取消路徑（重用既有 `OperationService.cancel`、`check_cancel` 與 `_invoke` 包裝器）**：
   - 當操作不在 `_running(operation_id)` 且 `status in {"accepted", "waiting_checks", "waiting_external"}` 時，`OperationService.cancel`（`src/bat_agent_connector/operations.py:714-716`）直接在同一筆交易內將操作轉為 `cancelled`（`error_code = "CANCELLED"`），並喚醒同一 `(host, session_id)` 的下一筆等待輸入。

### 7.2 當前置輸入結果未確認（`unknown`）時，後續排隊輸入的表現與使用者處置

當第 $k$ 筆輸入（`position = k`）在跨過 `on_transport` 後遺失回覆，且在 Claude live state 中尚未看到 `batc-<op_k>` 回音時：

1. **第 $k$ 筆輸入（`position = k`）**：處於 `operation_status = "needs_attention"`、收據 `state = "unknown"`。
   - **使用者看到的狀態**：顯示「送出後未收到回覆。請勿重送，請以原 ID 重新確認結果。」
   - **使用者可執行的動作**：呼叫 **以原 ID 重新確認（Reconcile with original ID）**（`POST /api/v1/operations/{op_k}/resume`）。若 BAT 實際已收到該訊息，調和後轉為 `sent` 並解除佇列阻擋；若封包確實在抵達 BAT 前遺失而永遠無回音，該筆輸入誠實保持 `unknown`（絕不重送、絕不清除鎖定、亦不可取消偽裝成未送出）。
2. **排在第 $k$ 筆之後的輸入（`position > k`）**：保持在 `operation_status = "waiting_external"`、收據 `state = "queued"`，且收據附上：
   - `"status_reason": "predecessor_outcome_uncertain"`
   - `"blocked_by_operation_id": "<op_k>"`
   - **使用者在後續輸入上看到的狀態**：明確顯示「排隊中（等待前一筆未確認結果的指令處理完畢）」及阻擋它的前置操作連結 `#/op/<op_k>`。
   - **使用者在後續輸入上可執行的兩項動作**：
     1. **取消此筆尚未送出的後續指令**（`POST /api/v1/operations/{op_later}/cancel`，因 `op_later` 的 `send_sent` 仍為 `False`，可安全取消並取回草稿）；
     2. **開啟該筆結果未確認的前置指令**（導向 `#/op/<op_k>` 或呼叫 `POST /api/v1/operations/{op_k}/resume` 進行原 ID 調和）。

### 8.2 收據狀態（`state`）判定優先序、`NOT_ACCEPTED` 與 Proven-Unsent `CANCELLED` 規則

`operation_steps.status` 的真實值集合為 `{"started", "succeeded", "failed", "uncertain"}`（`src/bat_agent_connector/operations.py:250-315`）。由於 `operations.status`、`operation_steps(name='send').status` 與 `external_refs.send_sent` 的條件可能同時成立（例如當 `service.session_send` 回傳 `{"accepted": False}` 時，`ctx.step` 先將步驟標為 `succeeded`，接著 `api_actions._send` `:154-155` 拋出 `NeedsAttention("NOT_ACCEPTED", ...)` 使操作進入 `needs_attention`；又或者在 `send()` 內跨過圍欄前取消會使操作成為 `status == "failed", error_code == "CANCELLED"`），收據 `state` **必須嚴格依下列由上而下（1 $\rightarrow$ 6）的 `if / elif` 優先序求值**：

| 求值順序 | 收據 `state` | 嚴格判定條件（由 SQLite 即時讀取之 `op`、`step` 與 `send_sent` 依序匹配） | `cancellable` |
| --- | --- | --- | --- |
| **1** | `cancelled` | `op.status == "cancelled"`，**或**（`op.status == "failed"` 且 `op.error_code == "CANCELLED"` 且 `send_sent is not True`——即在 `send()` 步驟內、`on_transport` 前由 `before_send` 觸發 `Cancelled` 並經 proven-unsent 包裝器轉為 `StepFailed("CANCELLED", ...)` 之情形，見 §6.2.2） | `false` |
| **2** | `failed` | `op.status == "failed"`（且不滿足順序 1），**或** `op.error_code == "NOT_ACCEPTED"`（含 `op.status == "needs_attention"` 且 `op.error_code == "NOT_ACCEPTED"`，見下方說明） | `false` |
| **3** | `sent` | `op.status == "succeeded"`（此時 `step.status == "succeeded"` 且 `res.get("accepted") is not False`） | `false` |
| **4** | `unknown` | `op.status in {"uncertain", "needs_attention"}`（且 `op.error_code != "NOT_ACCEPTED"`），**或**（`op.status == "running"` 且 `step.status == "uncertain"`） | `false` |
| **5** | `sending` | `op.status == "running"` 且 `step.status == "started"` 且 `send_sent is True` | `false` |
| **6** | `queued` | 其餘所有情況（包含 `op.status in {"accepted", "queued", "waiting_checks", "waiting_external"}`，以及 `op.status == "running"` 且 `send_sent is not True`） | `true` |

#### 關於 `NOT_ACCEPTED`（`api_actions.py:154-155`）的明確規則

- 在現有 `api_actions._send`（`src/bat_agent_connector/api_actions.py:154-155`）中，當 BAT 明確回覆 `res.get("accepted") is False` 時，程式碼在 `ctx.step("send", ...)` 返回後執行：
  ```python
  if res.get("accepted") is False:
      raise NeedsAttention("NOT_ACCEPTED", "BAT did not accept the message")
  ```
- **為何 `NOT_ACCEPTED` 的結果不是 `unknown`，而是 `failed`**：
  - `NOT_ACCEPTED` 代表封包雖已送達 BAT（`send_sent is True`），但 **BAT 已經明確回應拒絕接收該訊息（`accepted: false`）**，並未啟動新的 Turn，因此結果是已知的失敗，而非遺失回覆的未明狀態（`unknown`）。
  - 對於 Work Target 的 `session.send`（或在 `_send` 的 `send()` 內部），當 `res.get("accepted") is False` 時，直接在 `send()` 內拋出 `StepFailed("NOT_ACCEPTED", "BAT did not accept the message")`（使 `step.status = "failed"`、`op.status = "failed"`、`op.error_code = "NOT_ACCEPTED"`）；同時收據合成器依上表順序 **2** 將任何 `op.error_code == "NOT_ACCEPTED"` 映射為 `state = "failed"`（絕不因 `step.status == "succeeded"` 或 `op.status == "needs_attention"` 誤判為 `sent` 或 `unknown`）。
- **`NOT_ACCEPTED` 是否阻擋後續排隊輸入？**
  - **不阻擋**。因為 BAT 已明確拒絕該訊息（未產生任何新 Turn），該筆操作屬於已結算之終態失敗（`state = "failed"`）。
  - 在 §5.1 的前置條件規則中：
    1. 該筆輸入已結束（不屬於 `uncertain` / 未確認狀態），**不會**阻擋後方 `pos > k` 的排隊輸入；
    2. `effective_predecessor_turn_marker` 只取前方 `operations.status == "succeeded"` 的輸入（或初始 `handoff`），因此被拒絕的 `NOT_ACCEPTED` 輸入不會成為 `turn_marker`；
    3. 當該筆輸入以 `NOT_ACCEPTED` 失敗結束時，立即呼叫 `ops.wake` 喚醒同一 `(host, session_id)` 的下一筆隊首輸入。

#### 證明「尚未向 BAT 送出有效訊息」的失敗碼清單（`PROVEN_UNSENT_FAILURE_CODES`）

唯有當 `state == "failed"` 且同時滿足 **`(send_sent is not True and op.error_code in PROVEN_UNSENT_PRE_TRANSPORT_CODES) or op.error_code == "NOT_ACCEPTED"`** 時，收據與前端（§10）才提供 **「以新指令重試（Retry as new instruction）」**。具體錯誤碼完整列舉如下：

1. **送出前（`send_sent is not True`）之生命週期與來源閘門拒絕碼**：
   - `"PM_LIFECYCLE_STOPPED"`、`"PM_LIFECYCLE_EPOCH_CHANGED"`（`pm_lifecycle_gates.py:81-85, 115-125, 154-169`）
   - `"SOURCE_WITHDRAWN"`（`pm_source_lineage.py:118-127, 369-388`）
   - `"GIT_EXECUTION_DRIFT"`（`host_git.py:362-395`）
2. **送出前（`send_sent is not True`）之 Work / Session 狀態與權限拒絕碼**：
   - `"PM_WORK_SESSION_ENDED"`、`"PM_WORK_SESSION_BUSY"`、`"PM_WORK_SESSION_WAITING_INPUT"`、`"PM_WORK_NOT_STARTED"`、`"PM_WORK_ATTEMPT_CHANGED"`、`"PM_WORK_CONTROLLER_CONFLICT"`、`"PM_WORK_SESSION_NOT_MANAGED"`、`"PM_WORK_CODEX_FOLLOW_UP_UNSUPPORTED"`（§2.4、§5.1、§6.1）
   - `"WRITES_DISABLED"`、`"OFFLINE"`、`"SESSION_NOT_FOUND"`、`"READ_ONLY_SESSION"`、`"WORKTREE_CONFLICT"`、`"UNATTRIBUTED_SESSION"`、`"RECOVERY_REQUIRED"`、`"CONTROLLER_CONFLICT"`、`"SESSION_EXITED"`、`"WRITE_REFUSED"`（`service.py:1054-1153`、`api_actions.py:66-76`）

### 8.5 直接對同一受管工作階段發送 `{host, session_id}` 與 `/instructions` 端點的互動

舊有 Session Target（`target = {"host": host, "session_id": sid}`）對某個 Work 的受管工作階段直接呼叫 `session.send`（或透過舊 `session_send` MCP 工具）對同一 Controller 仍保持允許且繞過 `work_inputs` 佇列。兩者的互動規則明確定義如下：

1. **最後一幀閒置檢查（Final-Frame Idle Check）**：若使用者或代理透過舊 `{host, session_id}` 直接對該工作階段送出一筆指令並啟動了 BAT 回合，`sessions_observed.streaming` 與即時 `fresh_meta.get("isStreaming")` 會變為 `True`。此時任何排在 `work_inputs` 中的 Work 追加指令在本地檢查（§5.1）或 `_before_frame` 最後一幀檢查（§6.1）都會看到工作階段忙碌而保持在 `waiting_external`，絕不會對該直接回合進行 steer。
2. **E04 `turn_marker` 來源**：`AttemptResultCollector._eligible_candidates` 與 `pm_attempt_result_reads._attempt_context` 的 `turn_marker` 僅取自 `work_inputs` 中最新已送出的 Work 追加指令（或初始 `handoff`），不會被繞過 `work_inputs` 的直接 `{host, session_id}` 發送改寫。
3. **FIFO 範圍**：`work_inputs` 的嚴格 FIFO 順序（`position = 1, 2, ...`）保證成立於所有以 Work Target 送出的追加指令之間。
4. **E04 `next_allowed_actions`（`pm_attempt_result_reads._compute_actions`，`:1001-1040`）**：對於已啟動的 Work Attempt（`stage == "started"`），E04 結果信封中的 `next_allowed_actions` **只提供 Work Target 的 `session.send`**（`target: {"workspace_id": workspace_id, "work_item_id": work_item_id}`，在 `execution_state in {"active", "waiting"}` 時提供 `allowed_schedules: ["after_current"]`，在 `execution_state == "turn-ended"` 時提供 `allowed_schedules: ["after_current", "now"]`，皆標註 `default_schedule: "after_current"`, `requires_controller: True`, `requires_writer: True`），**不再**於 Work Result 頁面並排提供裸 `{host, session_id}` 的 `session.send`，確保 Workbench 與 Agent 一致走受佇列保護的 Work 路徑。
5. **與 `GET /api/v1/sessions/{host}/{sid}/instructions`（`api_v1.py:346`、`session_instructions.py:79-105`）的關係**：
   - `session_instructions.BINDING`（`src/bat_agent_connector/session_instructions.py:14-19`）查詢 `action = 'session.send'` 且 `$.resolved_target.host` / `$.resolved_target.session_id` 符合 `(host, sid)` 的操作。由於 Work Target 的 `session.send` 在 `external_refs["resolved_target"]` 記錄了 `{"host": host, "session_id": sid}`，只要呼叫端通過 `pm_source_lineage.require_session`（`session_instructions.py:86-87`）與 `pm_access.operation_visible`，Work 追加指令也會誠實出現在 `/api/v1/sessions/{host}/{sid}/instructions` 的歷史指令帳本中。
   - `api_v1.py:1256` 的 `"session_instructions": {"version": 1, "live_queue": False, "per_message_cancel": False}` 能力旗標**維持不變**（因該旗標描述的是 BAT 底層 session 層級不具備原生即時佇列與單筆撤回，而 Work 層級的 Connector 佇列與取消能力則宣告於 `features.pm_workspaces["work_follow_up"]`）。

## 12. 範圍外項目（決策 11：Out of Scope）

下列項目明確排除於本 P5 規格與實作切片之外：

1. **Steering（執行中插入）與 Interrupt**：`session.send` 絕不對執行中的 Turn 進行插入；中斷執行中回合仍由既有的 `session.interrupt` 獨立負責。
2. **平行輸入（Parallel Inputs / 另開獨立 Worktree）**：當使用者明確要求在平行分支或新 Worktree 同時嘗試另一方向時，屬於建立新的 Attempt（`work.start`），不在 `session.send` 追加指令範圍內。
3. **前端 Composer 與佇列介面元件**：本規格定義後端契約、收據讀取與雙語狀態詞（§10），前端 Workbench 的輸入框與佇列卡片屬於後續 UI 切片。
4. **原生 CLI Adapter（E06）**：直接連接原生 CLI 之 adapter 屬於 E06 範圍。

## 14. 待 Owner 裁示問題（Open Questions for the Owner）

1. **Codex 受管工作階段的 Work 追加指令策略（§5.4）**：

2. **已啟動 Work 在 E04 Result 信封中的 `session.send` 建議動作（§8.5）**：
   - **本規格建議**：在 `pm_attempt_result_reads._compute_actions`（`:1001-1040`）中，對已啟動的 Work Attempt 僅提供 Work Target 的 `session.send`（`target: {workspace_id, work_item_id}`），不再於同一信封並排提供裸 `{host, session_id}` 的 `session.send`（但直接呼叫舊 `{host, session_id}` API 仍保持相容）。請確認此行為是否符合預期。
3. **當一筆未確認（`unknown` / `needs_attention`）的追加指令因封包在抵達 BAT 前遺失而永遠無回音時，該佇列的處置策略（§7.2）**：
   - **背景**：對 Claude 工作階段而言，若封包在跨過 `on_transport`（`send_sent = True`）後、抵達 BAT 之前於網路中遺失，BAT 的 live transcript 永遠不會出現 `batc-<op_k>` 回音，因此 `POST /api/v1/operations/{op_k}/resume` 會持續維持 `needs_attention`（收據 `state = "unknown"`），而排在後方的輸入（`pos > k`）預設會一直等待（使用者可取消後續尚未送出的排隊輸入，或對未確認的那一筆執行原 ID 調和）。
   - **兩個可選方案**：
     - **方案 (a)：維持同工作階段佇列阻擋（本規格預設）**。只要 `op_k` 仍為 `unknown`，同一 `(host, session_id)` 上排在後方的 `work_inputs` 就絕不自動越過它送出（使用者可安全取消後方尚未送出的輸入）。同時，經核對 `pm_work_start.require_latest_attempt_settled`（`src/bat_agent_connector/pm_work_start.py:215-268`），該檢查僅驗證最新 `work_attempts` 列的 `start_operation_id`（Parent）與 `execution_operation_id`（`handoff` Child）是否已進入終態且無未證明步驟（`:226-267`）；由於已處於 `stage == "started"` 的 Attempt 其 `work.start` 與 `handoff` 皆早已 `succeeded`（`:243-244`），`require_latest_attempt_settled` **允許**使用者從固定檢查點啟動一個全新的 `work.start` Attempt（在新的受管工作階段與 Worktree 中繼續工作），而無須對舊工作階段強行重送或清除鎖定。（若 Owner 希望連新 `work.start` Attempt 在舊 Attempt 有 `unknown` 追加指令時也一併阻擋，亦可於 `require_latest_attempt_settled` 加入檢查。）
     - **方案 (b)：允許對已進入 `needs_attention` 的追加指令執行既有的「結果未明結案（`needs_attention` cancel）」（`src/bat_agent_connector/operations.py:717-733`）**。在 `OperationService.cancel`（`operations.py:717-733`）中，現有程式碼對 `status == "needs_attention"` 的操作會寫入 `"outcome_proven": False`、`"unproven_steps": ["send"]` 與 `"warning": "cancelled after needs_attention; the outcome of send was never proven"`。若採用方案 (b)：
       1. 在 `sending`（`op.status in {"running", "uncertain"}` 且 `send_sent is True`）與 `sent`（`op.status == "succeeded"`）時仍嚴格拒絕取消；但當經過自動重試與原 ID 調和仍無回音而停在 `needs_attention` 時，允許使用者呼叫既有的 `operations.py:717-733` 將其結案；
       2. 該筆操作的收據明確顯示為 **「已結案，送出結果未明（`closed, outcome unknown`）」**——**絕不**顯示為一般的 `cancelled`（未送出取消），且**絕不**重送該筆指令或提供重送按鈕；
       3. 後續排隊輸入（`pos > k`）解除前置阻擋，但在送出前仍必須等待一次完整的最新回合邊界與本地/最後一幀閒置檢查（確認工作階段 `isStreaming == False` 且無待處理閘門）。
   - **本規格建議**：建議採用 **方案 (a)** 作為預設安全策略（完全符合 `AGENTS.md`「絕不透過清除鎖定或重送來修復未確認結果」的原則；使用者可取消後方未送出的排隊輸入，或透過新 `work.start` Attempt 在全新受管資源從檢查點繼續），並請 Owner 裁示是否維持方案 (a)，或是否希望開放方案 (b) 的 `closed, outcome unknown` 結案路徑？
