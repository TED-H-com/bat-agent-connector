## 1. 範圍與核心原則

當使用者已透過 `work.start`（PR #194）啟動一個 Work Item，且 BAT 正在該受管工作階段（managed session）中執行時，使用者接著發出第二輪指令（例如：「再補一個失敗案例」）。本規格定義 v1.3 P5 的中央權威契約與資料模型，滿足 F5 的四項核心不變量：

1. **同一 Work、同一 Controller**：追加指令以 `{workspace_id, work_item_id}` 為目標，由 Admission 解析至該 Work 最新且處於 `stage == "started"` 的 Attempt 與其受管 `(host, session_id)`，並強制驗證 `controller_authority.same_controller` 與 Work 的 Controller 錨點一致。
2. **Connector 自有排隊（After-Current），絕不插入（Steer）執行中回合**：若目前 Turn 仍在執行，Connector 將指令保留於自身的持久化序列（`work_inputs`）中等待，直到該 Turn 達到 E04 §2.2 定義的結束邊界後才送出；`schedule="now"` 僅在工作階段確認閒置（idle）時才送出，否則立即拒絕，絕不干預執行中的 Turn。
3. **獨立 ID 與獨立收據（Receipt）**：每一筆追加輸入皆為獨立的持久化 Operation，擁有固定 `message_id = "batc-" + operation_id`、確定性的序列位置 `position` 與獨立收據。
4. **遺失回覆以原 ID 調和（Reconcile），絕不重送**：傳輸中斷或遺失回覆時，沿用既有 `send` 步驟與原 `message_id` 進行調和；Claude 可由 live transcript 的 `clientMessageId` 回音確認送達，Codex 無回音則維持 `needs_attention`（收據狀態 `unknown`），絕不以新 ID 重送或以相似文字猜測成功。

## 2. Target 結構、Admission 解析與拒絕碼（決策 1）

### 2.1 擴充既有 `session.send`，不新增動作別名

依據 `docs/design/v1.3-e00-baseline.md` §3.2（`:150`）與 §3.3（`:181`），P5 直接擴充既有的 `session.send`（`api_actions.py:377-378`），**不註冊** `work.follow_up` 動作別名。`_admit_send`（`api_actions.py:79-86`）依 `target` 的鍵集合區分三種互斥目標型態：

1. **Work Target（P5 新增）**：`{"workspace_id": "<ws_id>", "work_item_id": "<wi_id>"}`
2. **Session Target（既有）**：`{"host": "<host>", "session_id": "<session_id>"}`
3. **Task Target（既有）**：`{"task_id": "<task_id>"}`

### 2.2 嚴格禁止客戶端混傳 `host` / `session_id`

- 當 `target` 含有 `workspace_id` 或 `work_item_id` 時，`set(target.keys())` **必須精確等於** `{"workspace_id", "work_item_id"}`，且兩者皆須為非空字串（符合既有 ID 格式）。
- 若客戶端在 Work Target 中同時提供 `host`、`session_id`、`task_id`、`attempt_id` 或任何額外欄位，Admission 立即以 HTTP `422`、`error.code = "INVALID_TARGET"`（附帶 `admission_refused: true`）拒絕。客戶端**絕不可**在指定 Work Target 時自行指定底層 `host` 或 `session_id`。

### 2.3 舊有 `{host, session_id}` 與 `{task_id}` 目標維持 Byte-for-Byte 不變

- 在 `_admit_send`（`api_actions.py:79-86`）中：
  ```python
  def _admit_send(ops, principal, target, params, preconditions):
      if isinstance(target, dict) and ("workspace_id" in target or "work_item_id" in target):
          return pm_work_follow_up.admit_send(ops, principal, target, params, preconditions)
      if target.get("task_id"):
          return task_actions.admit_send(ops, principal, target, params, preconditions)
      if set(target) != set(SESSION_TARGET):
          raise OperationError("INVALID_TARGET", "target requires {'host', 'session_id'}", 422)
      _validate_send(params)
      return _admit_session(ops, principal, target, preconditions)
  ```
- 當 `target` 不含 `workspace_id` 與 `work_item_id` 時：
  - 控制流完全走原有的 `task_actions.admit_send` 或 `_validate_send` + `_admit_session`。
  - Idempotency key 命名空間維持全系統 Actor 層級（`operations._workspace_key` 對不含 `workspace_id` 的 `session.send` 回傳 `False`）。
  - `_send` 在 `"work_follow_up" not in (ctx.op.get("external_refs") or {})` 時執行與修改前完全相同的程式碼路徑、收據結構與錯誤碼，確保舊有呼叫端與測試 byte-for-byte 不變。

### 2.4 Work Target 的 Admission 解析與固定 `resolved_target`

當收到 `target = {"workspace_id": workspace_id, "work_item_id": work_item_id}` 時，`pm_work_follow_up.admit_send` 在單一資料庫交易內依序執行下列檢查，並將解析出的目標固定寫入 `operations.external_refs`：

1. **解析最新 Attempt**：查詢 `work_attempts WHERE workspace_id=? AND work_item_id=? ORDER BY attempt_number DESC LIMIT 1`，並透過 `pm_work_start.attempt_view(ops, row)`（`pm_work_start.py:1022-1122`）取得即時合成視圖（含 `stage`、`host`、`session_id`、`execution_operation_id`、`controller`）。
2. **可選 Preconditions 檢查**：`preconditions` 僅允許選填 `{"expected_attempt_id": "<att_id>"}`（未知鍵拋出 `422 INVALID_PRECONDITIONS`）。若提供 `expected_attempt_id`，且該 ID 屬於同一個 `(workspace_id, work_item_id)` 但 `attempt_id != latest_attempt["attempt_id"]`，以 `409 ATTEMPT_NOT_LATEST` 拒絕；若該 ID 不屬於此 Work，以 `409 PRECONDITION_FAILED` 拒絕。
3. **固定 `resolved_target` 於 `external_refs`**：
   - `external_refs["resolved_target"] = {"host": host, "session_id": session_id}`
   - `external_refs["work_follow_up"]` 記錄不可變綁定：`{"workspace_id": workspace_id, "work_item_id": work_item_id, "attempt_id": attempt_id, "attempt_number": attempt_number, "execution_operation_id": execution_operation_id, "schedule": schedule, "position": position, "message_id": "batc-" + operation_id, "predecessor_operation_id": predecessor_op_id, "predecessor_turn_marker": predecessor_turn_marker}`。
   - 後續執行階段透過既有的 `_bound_inputs(ctx)`（`api_actions.py:99-101`）讀取 `external_refs.resolved_target`，即使 Work 事後產生更新的狀態，此筆已核准 Operation 的目標工作階段亦永不漂移。

## 3. `schedule` 參數契約與禁止 Steer（決策 2）

當 `session.send` 的 `target` 為 Work Target（`{workspace_id, work_item_id}`）時，`params` 的驗證規則如下：

1. **允許的參數鍵**：`{"text", "schedule"}`。
   - `text`：必填非空字串，`1 <= len(text.strip()) <= service.MAX_PROMPT_CHARS`（重用 `_validate_send`，`api_actions.py:91-92`）。
   - `schedule`：選填字串，僅允許 `"after_current"` 或 `"now"`；**省略時預設為 `"after_current"`**。傳入其他值以 `422 INVALID_PARAMS` 拒絕。
2. **拒絕 `queue` 與自訂 `message_id`**：
   - 若 `params` 含有 `"queue"`，立即以 `422 INVALID_PARAMS`（`"Work-targeted session.send uses schedule ('after_current' or 'now'), not queue"`）拒絕。
   - 若 `params` 含有 `"message_id"`，立即以 `422 INVALID_PARAMS`（`"Work-targeted session.send assigns message_id deterministically as batc-<operation_id>"`）拒絕。
3. **`schedule="after_current"`（預設）行為**：
   - 無論目標工作階段目前是否正在串流執行（`isStreaming`）或前方是否已有排隊中的輸入，Admission 皆核准並依序排入 Connector 的 `work_inputs` 序列。
   - 若執行時前置條件與 E04 §2.2 Turn 邊界已成立，直接進入 `send` 步驟；否則進入 `Wait("waiting_external", ...)` 等待目前回合結束，**絕不**向執行中的 Turn 發送封包。
4. **`schedule="now"` 行為（僅限閒置，絕不 Steer）**：
   - 僅當 Admission 當下同時滿足下列三項閒置條件時才核准：
     1. 該 `(host, session_id)` 在 `work_inputs` 中沒有任何尚未終結（non-terminal）的前置輸入；
     2. 該工作階段目前已觀測到最新 Turn 滿足 E04 §2.2 的結束邊界（`pm_attempt_result_receipts` 已記錄該 `turn_marker` 之 `turn_done` / `agent_error` 收據），且 `observed_resources` 中 `streaming == False`、`runtime_status` 不在 `{"starting", "running", "streaming", "active"}`、無陳舊或失聯狀態；
     3. 無待處理的權限或問題閘門（`pending is None`）。
   - 若工作階段正在執行回合或前方仍有排隊輸入，Admission 在建立 Operation 與發送任何封包之前，立即以 `409 SESSION_BUSY` 拒絕；若有待處理的權限或問題閘門（`pending is not None`），以 `409 SESSION_WAITING_INPUT` 拒絕。**絕不對執行中的 Turn 進行插入（steer）**。

## 4. Connector 序列與 `work_inputs` 資料表（決策 3）

### 4.1 為何採用最小持久化資料表 `work_inputs`

雖然單純掃描 `operations` 表的 JSON 欄位可取得歷史操作，但為同時滿足：
- 兩個併發 Admission 競爭時（`test_racing_admissions_get_distinct_positions`），在 SQLite 交易內以 `UNIQUE(host, session_id, position)` 強制保證嚴格遞增、不跳號且不重複的確定性順序；
- 快速定位同一 `(host, session_id)` 的前置輸入（`position - 1`）與最新已發送之 `turn_marker`（供 E04 `AttemptResultCollector` 與 `pm_attempt_result_reads` 判定最新回合）；
- 支援依 `(workspace_id, work_item_id)` 的高效分頁查詢；

本規格決定新增一個最小關聯表 `work_inputs`，作為 `operations` 列的索引與排序投影（每一列 1:1 對應一筆 `action='session.send'` 的 Operation）。

### 4.2 Idempotent DDL（遵循 `AGENTS.md`：不分配 `user_version`、不新增 Data Step）

於 `src/bat_agent_connector/pm_work_follow_up.py` 定義 `ensure_schema(db)`，並由 `Journal._init_db`（`operations.py:182`）呼叫。所有 DDL 皆為冪等（`IF NOT EXISTS`），**不修改** `PRAGMA user_version`，亦**不新增** `schema_migrations.py` 的資料遷移步驟：

```sql

  operation_id TEXT PRIMARY KEY REFERENCES operations(operation_id) ON DELETE CASCADE,
  workspace_id TEXT NOT NULL,
  work_item_id TEXT NOT NULL,
  attempt_id TEXT NOT NULL,
  attempt_number INTEGER NOT NULL,
  execution_operation_id TEXT NOT NULL,
  host TEXT NOT NULL,
  session_id TEXT NOT NULL,
  position INTEGER NOT NULL,
  schedule TEXT NOT NULL CHECK (schedule IN ('after_current', 'now')),
  message_id TEXT NOT NULL,
  predecessor_operation_id TEXT,
  predecessor_turn_marker TEXT NOT NULL,
  text_excerpt TEXT NOT NULL,
  text_truncated INTEGER NOT NULL DEFAULT 0,
  text_sha256 TEXT NOT NULL,
  actor TEXT NOT NULL,
  controller_json TEXT NOT NULL,
  created_at REAL NOT NULL,
  updated_at REAL NOT NULL,
  sent_at REAL,
```

### 4.3 序列位置（`position`）分配規則

在 `OperationService.create` 的 `with self.journal.tx():`（`operations.py:619-633`）同一筆寫入交易中：

1. 計算 `position = COALESCE((SELECT MAX(position) FROM work_inputs WHERE host=? AND session_id=?), 0) + 1`。
2. 決定初始 `predecessor_operation_id` 與 `predecessor_turn_marker`：
   - 當 `position == 1` 時：`predecessor_operation_id = NULL`，`predecessor_turn_marker` 取自該 Attempt 之 `execution_operation_id`（`handoff` child operation）成功收據中的初始 `message_id`（重用 `pm_attempt_results._resolve_turn_marker` 邏輯，`pm_attempt_results.py:1352-1365`）。
   - 當 `position > 1` 時：`predecessor_operation_id` 為該 `(host, session_id)` 中 `position - 1` 的 `operation_id`；執行時的有效前置 Turn 標記（`effective_predecessor_turn_marker`）取自 `position < current.position` 中最後一筆實際送達（`operations.status == 'succeeded'`）之 `work_inputs.message_id`，若前方輸入皆在送出前已 `cancelled` 或未送出即 `failed`，則回退至初始 `handoff` 的 `message_id`。

## 5. 前置條件規則、Turn 邊界喚醒與輪詢退避（決策 4）

### 5.1 前置條件規則（Predecessor Rule）

一筆排入 `work_inputs` 的指令（位於 `(host, session_id, position)`）僅在下列三項條件**全部成立**時，才允許進入 `ctx.step("send", ...)`：

1. **所有更早的輸入皆已終結且其回合已結束**：
   - 對同一個 `(host, session_id)` 下所有 `pos < position` 的 `work_inputs` 列，其對應的 `operations.status` 必須處於終態（`succeeded`、`failed` 或 `cancelled`）。
   - 若有任何 `pos < position` 的輸入仍處於 `accepted`、`queued`、`waiting_checks`、`waiting_external` 或 `running`，當前輸入必須等待（`Wait("waiting_external", reason="waiting_predecessor_input", ...)`）。
   - 若有任何 `pos < position` 的輸入處於 `uncertain` 或 `needs_attention`（例如前一筆指令在 Codex 上遺失回覆、結果未確認），當前輸入**絕不可越過或覆蓋它**，必須等待（`Wait("waiting_external", reason="predecessor_outcome_uncertain", ...)`），直到前置操作完成調和或處置。
2. **工作階段最新回合滿足 E04 §2.2 的結束邊界**：
   - 令 `effective_predecessor_turn_marker` 為最後一筆已成功送出之前置輸入的 `message_id`（若無則為 Attempt 初始 `handoff` 的 `message_id`）。
   - 必須滿足 [`docs/design/v1.3-e04-result.md`](v1.3-e04-result.md) §2.2 的 Turn 邊界條件（重用 `pm_attempt_results.py:639-785`）：
     - `pm_attempt_result_receipts` 中已存在 `(attempt_id, effective_predecessor_turn_marker)` 的收據，且其 `boundary IN ('turn_done', 'agent_error')`；
     - 且 `observed_resources` 與即時 `_meta` 顯示工作階段目前未在串流（`isStreaming == False`、`streaming == False`、`runtime_status` 不在 `{"starting", "running", "streaming", "active"}`）。
3. **無待處理的權限或問題閘門（Permission / Question Gate）**：
   - `observed_resources` 的 `pending` 與即時 `meta.get("pending")`（含 `pendingPermission`、`pendingQuestion`）皆必須為 `None`。若存在待處理閘門，操作進入 `Wait("waiting_external", reason="waiting_permission_or_question_gate", ...)`，等待使用者透過 `session.answer` 處理完畢且回合結束。

> [!IMPORTANT]
> **工作階段若在等待期間結束（`SESSION_ENDED`）**：若在 `waiting_external` 重評估時發現工作階段已結束（`gone_at IS NOT NULL` 或 `runtime_status IN ('exited', 'stopped')`），且尚未建立 `operation_steps(name='send')`，則直接拋出 `OperationError("SESSION_ENDED", "session ended before queued follow-up could be sent", 409)`，使該輸入轉為 `failed`（證明未送出），並喚醒後續等待中的輸入一併標記未送出失敗。

### 5.2 與 E04 `AttemptResultCollector` 及 `Inventory.after_refresh` 的整合喚醒

**不新增任何 BAT 訂閱通道**，完全重用 E04 掛載於 `Inventory.after_refresh`（`inventory.py:296-297, 360-366`、`task_daemon.py:251`）的 `AttemptResultCollector.on_inventory_refresh`（`pm_attempt_results.py:1411-1556`）：

1. **動態更新 Attempt 的當前 `turn_marker`**：
   - 擴充 `pm_attempt_results._resolve_turn_marker(db, attempt_row)`（`pm_attempt_results.py:1352-1365`）與 `pm_attempt_result_reads._attempt_context`（`pm_attempt_result_reads.py:208-217`）：
     - 查詢該 `attempt_id` 在 `work_inputs` 中**已開始或完成 `send` 步驟**（即 `operations.status IN ('succeeded', 'uncertain', 'needs_attention')` 或存在 `operation_steps(name='send')`）且 `position` 最大的一列。
     - 若存在，該列的 `message_id`（`batc-<operation_id>`）即為該 Attempt 的當前 `turn_marker`；若尚無已送出的追加輸入，則維持讀取初始 `handoff` child operation 的 `message_id`。
   - 如此一來，每當一筆追加輸入送出後，`pm_attempt_result_receipts`（其表結構已具備 `UNIQUE(attempt_id, turn_marker)`，`pm_attempt_results.py:85`）就會為該筆追加輸入的 Turn 收集對應的 E04 結果收據，且 `GET /api/v1/pm/workspaces/{ws}/attempts/{att}/result` 會自動反映最新一輪 Turn 的進度與結果。
2. **邊界達成時主動 `wake` 下一筆等待中的輸入**：
   - 當 `AttemptResultCollector.on_inventory_refresh`（`pm_attempt_results.py:1411-1556`）觀測並寫入（或確認已存在）該工作階段當前 `turn_marker` 的結束邊界收據（`boundary IN ('turn_done', 'agent_error')`），且 `streaming == False`、`pending is None` 時，立即查詢該 `(host, session_id)` 下 `position` 最小且 `operations.status == 'waiting_external'` 的 `work_inputs.operation_id`，呼叫 `ops.wake(next_operation_id)`（`operations.py:768-772`）。
   - 同理，當一筆排隊中的 `work_inputs` 操作被使用者取消（`cancelled`）或未送出即失敗（`failed`）時，亦立即對同一個 `(host, session_id)` 的下一筆 `waiting_external` 操作呼叫 `ops.wake(next_operation_id)`。

### 5.3 輪詢退避（Polling Fallback）與邊界限制

若 `Inventory.after_refresh` 尚未觸發（例如無背景觀測事件期間），操作透過 `Wait(status="waiting_external", reason=..., delay_s=...)`（`operations.py:81-89`）由 `OperationService._loop`（`operations.py:775-785`）定期重評估：

- **退避延遲（`delay_s`）**：固定為 **`5.0` 秒**（常數 `WORK_FOLLOW_UP_WAIT_DELAY_S = 5.0`，允許範圍 `1.0 <= delay_s <= 15.0`）。
- **單次重評估上限**：每次到期重跑時，先檢查本地 SQLite（前置輸入狀態、`pm_attempt_result_receipts`、`observed_resources`）；僅當本地顯示工作階段已非串流但尚未寫入該 `turn_marker` 收據時，才呼叫一次 `AttemptResultCollector.collect_for_attempt`（受 E04 既有 `30.0` 秒退避節流保護，`pm_attempt_results.py:55`）。
- **不因長回合而自動丟棄**：只要工作階段仍存活（未 `exited`/`stopped`/gone）且使用者未取消，排隊中的指令保持在 `waiting_external`，不會因固定超時而被自動取消或重送。Daemon 重啟後，`OperationService._loop`（`operations.py:778-785`）直接從 SQLite 讀取 `status='waiting_external'` 且到期的操作繼續等待與喚醒。

## 6. 發送步驟、Pre-frame `WriteRefused` 與遺失回覆調和（決策 5）

### 6.1 沿用既有 `send` 步驟與固定 `message_id`

當前置條件（§5.1）成立時，`_send`（`api_actions.py:104-156`）執行原有的 `ctx.step("send", send, request={"message_id": mid, "text_sha256": sha256(text)}, reconcile=reconcile)`：

- `mid = "batc-" + ctx.operation_id`（固定由 `operation_id` 推導，寫入 `work_inputs.message_id` 與 `operation_steps.request`）。
- 呼叫 `service.send_message(fleet, host, sid, text, queue=False, message_id=mid, journal=..., registry=..., operation_id=ctx.operation_id)`（強制 `queue=False`，絕不使用 BAT 端無排程保證的 `queue=True`）。
- 當 `send` 步驟完成時，更新 `work_inputs.sent_at = time.time()`，並於完成後觸發下一個排隊輸入的檢查（若該回合極快完成）。

### 6.2 發送封包前的 `WriteRefused` 退回等待（Proven Unsent $\rightarrow$ Waiting）

在 `service.send_message`（`service.py:1134-1137`）中，若即時 `_meta(c, sid)` 發現 `isStreaming` 在競態下又變為 `True`，且 `queue=False`，會在記錄 `audit.record(..., channel="claude:send-message", phase="attempt")`（`service.py:1145`）與呼叫 `c.invoke("claude:send-message", ...)`（`service.py:1178`）**之前**拋出 `WriteRefused("session is currently streaming a turn; ...")`。

- **證明未送出（Proven Unsent）的條件**：捕獲 `WriteRefused` 時，檢查 `audit_events` 表中是否存在 `operation_id = ctx.operation_id AND channel = 'claude:send-message' AND phase = 'attempt'`。若不存在，證明**沒有任何封包離開 Connector**。
- **處置方式**：
  - 當 `schedule == "after_current"` 時：清除本次尚未送出封包的 `operation_steps(operation_id, name='send')` 暫態列，並拋出 `Wait(status="waiting_external", reason="session_busy_pre_frame", delay_s=5.0)`，使操作退回 `waiting_external`（收據狀態維持 `queued`），等待下一次邊界喚醒。
  - 當 `schedule == "now"` 時：因尚未送出任何封包，轉換為 `OperationError("SESSION_BUSY", "session is currently streaming a turn", 409)`，使操作以未送出狀態 `failed` 結束。

### 6.3 傳輸中斷與遺失回覆調和（Reconcile）

一旦進入 `audit.record(..., phase="attempt")`（`service.py:1145`）並發出 `c.invoke("claude:send-message", ...)`，若發生網路中斷、`TimeoutError`、`BatError`（`AMBIGUOUS`）或 Daemon 崩潰重啟：

1. `StepContext.step`（`operations.py:272-286, 303-308`）將步驟標記為 `uncertain` 並呼叫既有的 `reconcile()`（`api_actions.py:132-149`）。
2. **Claude 工作階段**：`reconcile()` 先查 `session_registry.get_turn(host, sid, mid)`；若無，呼叫 `service._live_state(c, sid)`（`api_actions.py:143`），檢查 `state.get("messages", [])` 中是否存在 `m.get("id") == mid and m.get("role") == "user"`（`api_actions.py:144`）。若找到精確的 `mid` 回音，補登 `registry.record_turn` 並回傳成功收據（`reconciled: True, turn_attribution: "client_message_id_echo"`），操作轉為 `succeeded`（收據狀態 `sent`）。
3. **Codex 工作階段**：Codex transcript 不回傳 `clientMessageId`，因此 `reconcile()` 在 `kind == "codex"` 時回傳 `None`（`api_actions.py:141-142`）。`StepContext.step` 拋出 `Uncertain`，使操作進入 `needs_attention`（`error_code = "UNCERTAIN_UNRESOLVED"`，收據狀態 `unknown`）。
4. **嚴格禁止重送與相似文字猜測**：
   - `reconcile` **只比對** `m.get("id") == "batc-" + operation_id`，絕不比對 `m.get("content") == text` 或相似文字。
   - 操作處於 `needs_attention`（`unknown`）時，呼叫 `POST /api/v1/operations/{op}/resume`（`operations.py:738-766`）只會以原 `operation_id` 與原 `message_id` 重新執行 `reconcile`（`operations.py:272-286`），**絕不**再次執行 `send()`，亦**絕不**以新 ID 重送或清除任何鎖定。

## 7. 取消語意與介面文案（決策 6）

### 7.1 取消規則（僅限 `send` 步驟開始前）

- **允許取消的時機**：僅當該筆追加輸入仍處於等待狀態（`operations.status IN ('accepted', 'queued', 'waiting_checks', 'waiting_external')`，或處於 `running` 但尚未執行至 `ctx.step("send", ...)`），且 `operation_steps` 中**不存在** `(operation_id, name='send')` 列（`work_inputs.sent_at IS NULL`）時，才允許取消。
  - 在 `OperationService.cancel`（`operations.py:683-736`）的 `with self.journal.tx():` 交易內，驗證上述條件成立後，立即將 `operations.status` 轉為 `"cancelled"`（不執行 handler 與 `send` 步驟），並呼叫 `ops.wake` 喚醒同工作階段的下一筆等待輸入。
- **開始發送後拒絕取消**：一旦 `operation_steps(operation_id, name='send')` 已建立（包含發送中 `running`、已送出 `succeeded`、或結果未確認 `uncertain` / `needs_attention`），呼叫 `POST /api/v1/operations/{op}/cancel` 將以 HTTP `409`、`error.code = "CANCEL_NOT_ALLOWED_AFTER_SEND"` 明確拒絕，且**不設定** `cancel_requested = 1`，避免誤導使用者以為指令已撤回。
- **取消與恢復的授權**：對 Work Target 的 `session.send` 呼叫 `cancel` 或 `resume` 時，除檢查 `pm_access.require_operation`（Workspace 成員可見性）與 `principal.actor == op["actor"]` 外，亦強制檢查 Workspace 寫入成員資格（`pm_workspace.require_member(..., write=True)`）與 `controller_authority.same_controller`（對齊 `pm_work_start._authorize_existing`，`pm_work_start.py:988-996`）。

## 12. 範圍外項目（決策 11：Out of Scope）
