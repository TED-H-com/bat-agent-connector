## 1. 範圍與核心原則

當使用者已透過 `work.start`（PR #194）啟動一個 Work Item，且 BAT 正在該受管工作階段（managed session）中執行時，使用者接著發出第二輪指令（例如：「再補一個失敗後重新送出的案例」）。本規格定義 v1.3 P5 的中央權威契約與資料模型，滿足 F5 的核心不變量：

1. **同一 Work、同一 Controller**：追加指令以 `{workspace_id, work_item_id}` 為目標，由 Admission 解析至該 Work 最新且處於 `stage == "started"` 的 Attempt 與其受管 `(host, session_id)`，並重用 `pm_work_start.require_work_controller`（`src/bat_agent_connector/pm_work_start.py:192-200`）強制驗證呼叫端與該 Work 的 Controller 錨點一致。
2. **Connector 自有排隊（After-Current），絕不插入（Steer）執行中回合**：若目前 Turn 仍在執行，Connector 將指令保留於自身的持久化佇列（`work_inputs`）中等待，直到該 Turn 在 `session_results` 寫入結束邊界（`boundary IN ('turn_done', 'agent_error')`）且工作階段確認閒置後才送出；`schedule="now"` 僅在工作階段確認閒置時才送出，否則立即以 `409 PM_WORK_SESSION_BUSY` / `409 PM_WORK_SESSION_WAITING_INPUT` 拒絕，絕不干預執行中的 Turn。
3. **獨立 ID 與獨立收據（Receipt）**：每一筆追加輸入皆為獨立的持久化 Operation，擁有固定 `message_id = "batc-" + operation_id`、在 `INSERT` 交易內分配的不可變序列位置 `position` 與獨立收據。
4. **遺失回覆以原 ID 調和（Reconcile），絕不重送**：傳輸中斷或遺失回覆時，沿用既有 `send` 步驟與原 `message_id` 進行調和；Claude 由 live transcript 的 `clientMessageId` 回音確認送達，未收到回音時維持 `needs_attention`（收據狀態 `unknown`）並阻擋同工作階段後續排隊輸入，絕不以新 ID 重送、絕不刪除步驟列、亦絕不以相似文字猜測成功。
5. **誠實對待上游能力（Codex 決策）**：由於 BAT Codex 不回音 `clientMessageId`（`api_actions.py:137-142`）且不登錄關聯 Turn（`service.py:1212-1214`），無法產生 `turn_attribution == "correlated"` 的 E04 `turn_done` 邊界（`service.py:545-548, 579-582`、`pm_attempt_results.py:1538-1541`）。依 F5「不假裝上游支援佇列」原則，本規格建議於 Admission 明確以 `409 PM_WORK_CODEX_FOLLOW_UP_UNSUPPORTED` 拒絕針對 Codex 受管工作階段的 Work 追加指令（詳見 §5.4 與 §14 Owner 決策問題）。

## 2. Target 結構、Admission 解析與拒絕碼（決策 1）

### 2.1 擴充既有 `session.send`，不新增動作別名

依據 `docs/design/v1.3-e00-baseline.md` §3.2（`:150`）與 §3.3（`:181`），P5 直接擴充既有的 `session.send`（`api_actions.py:377-378`），**不註冊** `work.follow_up` 動作別名。`_admit_send`（`api_actions.py:79-86`）依 `target` 區分三種目標型態：

1. **Work Target（P5 新增）**：`{"workspace_id": "<ws_id>", "work_item_id": "<wi_id>"}`
2. **Task Target（既有）**：`{"task_id": "<task_id>"}`
3. **Session Target（既有）**：`{"host": "<host>", "session_id": "<session_id>"}`

### 2.2 既有 `_admit_send` 與混合目標（Mixed Target）規則

在 `src/bat_agent_connector/api_actions.py:79-86`，現有程式碼為：

```python
def _admit_send(ops: OperationService, principal: Principal, target: dict, params: dict, pre: dict) -> dict | None:
    if target.get("task_id"):
        from .task_actions import admit_send
        return admit_send(ops, principal, target, params, pre)
    if not all(isinstance(target.get(k), str) and target[k] for k in SESSION_TARGET):
        raise OperationError("INVALID_TARGET", "host and session_id are required", 422)
    _validate_send(params)
    return _admit_session(ops, principal, target, params, pre)
```

**P5 提議實作（Proposed in P5）**：僅在最前方加上 Work 分支，其餘程式碼一字不改：

```python
def _admit_send(ops: OperationService, principal: Principal, target: dict, params: dict, pre: dict) -> dict | None:
    if "workspace_id" in target or "work_item_id" in target:
        from . import pm_work_follow_up
        return pm_work_follow_up.admit_send(ops, principal, target, params, pre)
    if target.get("task_id"):
        from .task_actions import admit_send
        return admit_send(ops, principal, target, params, pre)
    if not all(isinstance(target.get(k), str) and target[k] for k in SESSION_TARGET):
        raise OperationError("INVALID_TARGET", "host and session_id are required", 422)
    _validate_send(params)
    return _admit_session(ops, principal, target, params, pre)
```

- **混合目標（Mixed Target）的處置**：若呼叫端同時傳入 Work 鍵（`workspace_id` 或 `work_item_id`）與 `host`、`session_id`、`task_id`、`attempt_id` 或任何其他鍵，會先進入 `pm_work_follow_up.admit_send`，並因 `set(target) != {"workspace_id", "work_item_id"}` 立即以 HTTP `422`、`error.code = "INVALID_TARGET"`（`admission_refused: true`）被拒絕。客戶端**絕不可**在 Work Target 中自行指定底層 `host` 或 `session_id`。
- **既有呼叫端盤點（已以 `grep -rn "session.send"` 驗證全儲存庫）**：
  - `src/bat_agent_connector/orchestration_operations.py:368-370`：傳入 `target={"host": plan["host"], "session_id": plan["session_id"]}`；
  - `src/bat_agent_connector/api_actions.py:310`（`legacy_session_control`）：傳入 `target={k: request[k] for k in SESSION_TARGET}`；
  - `src/bat_agent_connector/task_actions.py:13, 135-148`：傳入 `target={"task_id": ...}`；
  - 前端 `desktop/src`（`src/bat_agent_connector/dashboard/app.js:56694`）：傳入 `target={host, session_id}`。
  - **没有任何既有呼叫端**會在 `session.send` 的 `target` 中混傳 `workspace_id` 或 `work_item_id`。因此當 `target` 不含 `workspace_id` 與 `work_item_id` 時，舊有 `{host, session_id}` 與 `{task_id}` 的檢查、`_validate_send(params)`、`_admit_session(ops, principal, target, params, pre)`、冪等鍵命名空間與執行路徑維持 byte-for-byte 不變。

## 3. `schedule` 參數契約與禁止 Steer（決策 2）

當 `session.send` 的 `target` 為 Work Target（`{workspace_id, work_item_id}`）時，`params` 的驗證規則如下：

1. **允許的參數鍵**：`{"text", "schedule"}`。
   - `text`：必填非空字串，`1 <= len(text.strip()) <= service.MAX_PROMPT_CHARS`（重用 `_validate_send`，`api_actions.py:91-92`）。
   - `schedule`：選填字串，僅允許 `"after_current"` 或 `"now"`；**省略時預設為 `"after_current"`**。傳入其他值以 `422 INVALID_PARAMS` 拒絕。
2. **拒絕 `queue` 與自訂 `message_id`**：
   - 若 `params` 含有 `"queue"`，立即以 `422 INVALID_PARAMS`（`"Work-targeted session.send uses schedule ('after_current' or 'now'), not queue"`）拒絕。
   - 若 `params` 含有 `"message_id"`，立即以 `422 INVALID_PARAMS`（`"Work-targeted session.send assigns message_id deterministically as batc-<operation_id>"`）拒絕。
3. **`schedule="after_current"`（預設）行為**：
   - 無論目標工作階段目前是否正在串流執行（`streaming` / `isStreaming`）或前方是否已有排隊中的輸入，Admission 皆核准並於 `INSERT` 交易內排入 `work_inputs` 序列。
   - 若執行時前置條件（§5.1）尚未成立，或在最後一幀檢查（`_before_frame`）發現工作階段忙碌 / 存在待處理閘門，操作進入 `Wait("waiting_external", ...)` 等待目前回合結束，**絕不**向執行中的 Turn 發送封包。
4. **`schedule="now"` 行為（僅限閒置，絕不 Steer）**：
   - Admission（及 `INSERT` 交易內的 `pm_work_follow_up.admit_operation`）要求當下同時滿足三項本地閒置條件：
     1. 該 `(host, session_id)` 在 `work_inputs` 中沒有任何尚未終結（non-terminal）的前置輸入；
     2. 該工作階段在 `session_results` 中已存在當前有效前置 `turn_marker` 的結束邊界收據（`document.boundary IN ("turn_done", "agent_error")`），且 `sessions_observed.streaming == 0`、`runtime_status` 不在執行中；
     3. 無待處理的權限或問題閘門（`sessions_observed.pending_json` 解析後為空）。
   - 若上述條件 1 或 2 不成立，Admission 立即以 `409 PM_WORK_SESSION_BUSY` 拒絕；若條件 3 不成立，立即以 `409 PM_WORK_SESSION_WAITING_INPUT` 拒絕。此外，在發送步驟的 `_before_frame` 最後一幀即時檢查中若發現工作階段變為忙碌或等待輸入，亦以相同 `PM_WORK_SESSION_BUSY` / `PM_WORK_SESSION_WAITING_INPUT` 拒絕（未送出任何封包）。

## 4. 最小且不可變的 `work_inputs` 資料表與 `INSERT` 交易分配（決策 3）

### 4.1 設計原則：最小、不可變（Immutable）、衍生狀態於讀取與執行時計算

對齊 E02 `work_attempts`（`src/bat_agent_connector/pm_work_start.py:99-123`）的設計：
- `work_inputs` 僅保存不可變的身分與排序錨點（`sequence`、`operation_id`、`workspace_id`、`work_item_id`、`attempt_id`、`host`、`session_id`、`position`、`schedule`、`message_id`、`created_at`）。
- **移除所有可變欄位與重複資料**：不儲存 `updated_at`、`sent_at`、`text_excerpt`、`text_truncated`、`text_sha256`、`controller_json`、`predecessor_operation_id`、`predecessor_turn_marker`，且**不使用** `ON DELETE CASCADE` 外鍵，並加上 `BEFORE UPDATE` 與 `BEFORE DELETE` triggers 強制不可變。
- **執行期與讀取期衍生來源**：
  - 操作狀態、錯誤碼、時間戳記與是否已過發送圍欄（`send_sent`）由 `operations`、`operation_steps(name='send')` 與 `operations.external_refs` 即時推導；
  - 指令文字摘要（`text_excerpt`、`text_truncated`）由 `operations.params`（`$.text`）在讀取時計算；
  - Controller 綁定由 `operations.external_refs.admission_binding.controller_authority` 讀取；
  - **有效前置 Turn 標記（`effective_predecessor_turn_marker`）與阻擋中之 `predecessor_operation_id` 一律在執行時與讀取時動態計算**（見 §5.1），避免前置輸入取消時產生靜態欄位矛盾。

## 5. 前置條件規則、Turn 邊界喚醒與輪詢退避（決策 4）

### 5.1 執行時動態前置條件規則（Predecessor Rule）

對於 `work_inputs` 中位於 `(host, session_id, position)` 的操作，每次執行 handler 時僅讀取**本地 SQLite 狀態**（零 BAT 呼叫）計算其前置狀態：

1. **檢查所有更早的輸入（`pos < position`）**：
   查詢同一 `(host, session_id)` 下所有 `pos < position` 的 `work_inputs` JOIN `operations`（依 `pos ASC`）：
   - **隊首判定（Queue Head）**：若存在任何 `pos < position` 的列其 `operations.status` 屬於非終態：
     - 若存在 `status IN ('uncertain', 'needs_attention')`（或 `operation_steps(name='send').status == 'uncertain'`），當前輸入**絕不可越過或覆蓋它**，拋出 `Wait(status="waiting_external", reason="predecessor_outcome_uncertain", delay_s=60.0)`（詳見 §5.3 與 §7.3）。
     - 若存在 `status IN ('accepted', 'waiting_checks', 'waiting_external', 'running')`，當前輸入並非隊首，拋出 `Wait(status="waiting_external", reason="waiting_predecessor_input", delay_s=60.0)`，等待前置操作終結時主動喚醒。
   - 當所有 `pos < position` 的列皆處於終態（`succeeded`、`failed`、`cancelled`）時，當前輸入即為該工作階段佇列的**隊首（Head of Queue）**。
2. **動態決定 `effective_predecessor_turn_marker`**：
   - 取同一 `attempt_id` 下 `pos < position` 且 `operations.status == 'succeeded'` 中 `pos` 最大一列的 `work_inputs.message_id`；
   - 若前方無 `succeeded` 的追加輸入（例如 `position == 1`，或前方輸入皆在送出前 `cancelled` / `failed`），則取該 Attempt 初始 `handoff` child operation（`execution_operation_id`）之 `result.message_id`（對齊 `pm_attempt_results.py:1410-1420` 與 `pm_attempt_result_reads.py:207-217`）。

```python
            raise Uncertain(name, f"step {name!r} may or may not have happened ({type(exc).__name__})") from None
        except Exception as exc:  # noqa: BLE001 - recorded, then re-raised as a definitive failure
            code = _error_code(exc)
            message = redact(str(exc)) if isinstance(exc, BatError | OperationError | StepFailed) else type(exc).__name__
            self.service._step_status(self.operation_id, name, "failed", error={"code": code, "message": message})
            raise StepFailed(code, message) from exc
        self.service._step_done(self.operation_id, name, response or {})
        return response or {}
```

現況行為分析：
1. `NeedsAttention`（`src/bat_agent_connector/operations.py:302-304`）將步驟標為 `uncertain` 並原樣重拋（由 `_execute_bound` `:871-873` 轉為 `needs_attention`）；
2. `(*AMBIGUOUS, OSError)`（`src/bat_agent_connector/operations.py:305-308`）將步驟標為 `uncertain`（`error={"code": "UNCERTAIN", ...}`）並拋出雙參數 `Uncertain(name, message)`（定義於 `operations.py:91-94`）；
3. 其他任何異常（包含 `Wait` 與 `Cancelled`）皆進入 `src/bat_agent_connector/operations.py:309-313` 的 `except Exception as exc:`，將步驟標為 `failed` 並拋出 `StepFailed(code, message)`。

#### 6.2.2 `Cancelled`：不修改 `OpContext.step`，重用既有 `_invoke` 包裝器模式

    ```python

        raise StepFailed('CANCELLED', 'cancelled before the next transport frame') from None
    ```
  - `failover_operations._invoke`（`src/bat_agent_connector/failover_operations.py:455-460`）：

### 6.3 跨過圍欄後的傳輸中斷、BAT 忙碌回覆與遺失回覆調和（Reconcile）

由於 §6.1 第 5 點的單一圍欄規則將所有即時 `_fence_sent(ctx) is not True` 下的 `(*AMBIGUOUS, OSError)`（於 `schedule == "after_current"` 時）轉為 `Wait(delay=...)`（`step.status` 維持 `"started"`、`uncertain_tries == 0`），**只有當 SQLite 中 `send_sent is True`**（即 `client.py:357` 的 `on_transport()` 已執行、封包已交予 `await self._ws.send(encoded)` `:358`）後發生任何異常（包含網路中斷 `ConnectionClosed` $\rightarrow$ `ConnectionLost` `:364-365`、逾時 `InvokeTimeout` `:360-363`、BAT 回傳含 `BUSY_TEXT` 的 `InvokeError` `:50, 453-458` 或任何其他異常）或 Daemon 崩潰重啟時，步驟與操作才會進入 `uncertain` / `needs_attention`：

1. `OpContext.step`（`operations.py:272-278, 305-308`）將步驟標記為 `uncertain`（`send_sent` 保持 `True`）並呼叫既有的 `reconcile(_request)`（`src/bat_agent_connector/api_actions.py:132-149`）。
2. `reconcile(_request: dict)` 於 P5 新增之 `_unsent(ctx)` 檢查確認 `not _unsent(ctx)`（即 `_fence_sent(ctx) is True`，若尚未送出則回傳 `RERUN`）後，先查 `registry.get_turn(host, sid, mid)`（`api_actions.py:133-136`）；若無，呼叫 `service._live_state(c, sid, kind, await service._meta(c, sid))`（`:143`），檢查 `(state or {}).get("messages") or []` 中是否存在 `m.get("id") == mid and m.get("role") == "user"`（`:144-146`）。
3. **若找到精確的 `mid` 回音**：
   - 若命中 `registry.get_turn(host, sid, mid)`（`:133-136`），回傳 `{"host": host, "session_id": sid, "message_id": mid, "accepted": True, "queued": turn.get("queued"), "turn_marker": mid, "settled_by": "accepted_turn_record"}`；
   - 若命中 Claude live transcript（`api_actions.py:144-148`），回傳 `{"host": host, "session_id": sid, "message_id": mid, "accepted": True, "turn_marker": mid, "settled_by": "bat_transcript"}`；
   - 操作轉為 `succeeded`（收據狀態 `sent`）。
4. **若未找到 `mid` 回音**（例如封包在抵達 BAT 前遺失，或 BAT 因忙碌未寫入）：`reconcile` 回傳 `None`（`recovered is None`），`OpContext.step`（`src/bat_agent_connector/operations.py:275-276`）將步驟標記為 `uncertain` 並在 `:277` 拋出 `raise Uncertain(name, f"outcome of step {name!r} is not proven; reading it back again later")`，經 `_execute_bound`（`:861-870`）重試 `UNCERTAIN_RETRY_S`（`:49`）後進入 `needs_attention`（`error_code = "UNCERTAIN_UNRESOLVED"`，收據狀態 `unknown`）。
5. **嚴格禁止重送與相似文字猜測**：
   - 既有 `reconcile` 在 `api_actions.py:144-146` 中檢查 `m.get("id") == mid and m.get("role") == "user" and ("message_id" not in params or m.get("content") == text)`，當呼叫端於 `params` 傳入自訂 `message_id` 時會一併比對 `content`。而 Work 追加指令在 Admission 時即明確拒絕客戶端自訂 `message_id`（見 §3，`params` 嚴禁包含 `message_id`），因此對 Work 追加指令而言 `"message_id" not in params` 恆為真，`reconcile` **只比對** `m.get("id") == "batc-" + operation_id`（絕不對 Work 指令比對 `m.get("content") == text` 或相似文字）。
   - 操作處於 `needs_attention`（`unknown`）時，呼叫 POST /api/v1/operations/{op}/resume（經由 `OperationService.resume`，`src/bat_agent_connector/operations.py:738-766`）只會以原 `operation_id` 與原 `message_id` 重新執行 `reconcile`（`operations.py:272-278`），**絕不**再次執行 `send()`，亦**絕不**以新 ID 重送或清除鎖定。

## 7. 取消語意、未確認前置輸入之佇列阻擋與介面文案（決策 6）

### 7.1 以 Transport Fence 定義「開始送出（Send Began）」與取消規則

1. **「開始送出（Send Began）」與「尚未開始送出（Before Send Began）」的精確定義（僅使用 `operations.py:35-36` 的真實 `STATES` 與 `:250-315` 的步驟狀態）**：
   - 從 SQLite 即時讀取 `operations` 與 `operation_steps(name='send')`：當 **`operations.external_refs.get("send_sent") is True`**，或 `operations.status in {"succeeded", "uncertain", "needs_attention"}`，或 `operation_steps(name='send')` 處於 `succeeded` / `uncertain` 時，即視為**已開始送出**（在 §8.2 收據狀態表中對應 `sending`、`sent`、`unknown`，或 `send_sent is True` 下因 `NOT_ACCEPTED` 終結的 `failed`；其 `cancellable` 恆為 `false`）。
   - 反之，當 **`send_sent is not True`** 且 `operations.status in {"accepted", "running", "waiting_checks", "waiting_external"}` 且（尚無 `send` 步驟列，或 `send` 步驟處於 `started` / `failed`）時，屬於**尚未開始送出**（完全對應 §8.2 順序 6 的 `state == "queued"`，也是唯一 `cancellable == true` 的狀態）。
2. **開始送出前的取消路徑（重用既有 `OperationService.cancel`、`check_cancel` 與 `_invoke` 包裝器）**：
   - 當操作不在 `_running(operation_id)` 且 `status in {"accepted", "waiting_checks", "waiting_external"}` 時，`OperationService.cancel`（`src/bat_agent_connector/operations.py:714-716`）直接在同一筆交易內將操作轉為 `cancelled`（`error_code = "CANCELLED"`），並喚醒同一 `(host, session_id)` 的下一筆等待輸入。
   - 當操作正在 `_running(operation_id)`（handler 正在執行，但 SQLite 中 `send_sent` 仍為 `False`）時，`OperationService.cancel` 設定 `cancel_requested = 1`（`operations.py:711`）。接著 `ctx.check_cancel()`（`operations.py:188-192`）會在三個在封包送出前的檢查點攔截並拋出 `Cancelled`：
     1. 首次進入 `ctx.step("send", ...)` 時、呼叫 `fn()` 之前的 `self.check_cancel()`（`operations.py:298`）——拋出 `Cancelled` 至 `_execute_bound`（`:854-855`），操作轉為 `status = "cancelled", error_code = "CANCELLED"`；
     2. 重啟步驟（`outcome is RERUN`）時、呼叫 `fn()` 之前的 `self.check_cancel()`（`operations.py:284`）——同樣拋出 `Cancelled` 至 `_execute_bound`（`:854-855`），操作轉為 `status = "cancelled", error_code = "CANCELLED"`；
     3. 已進入 `send()`（已提交 `send_sent = False`），在 `service.session_send` 持有 `_write_lock(host)` 後，於 `c.invoke` 前的 P5 `before_invoke()`（`service.py:1176-1177`）或 `c._sem`（`client.py:438`）內、`on_transport` 圍欄正前方的同步 `final_gate` / `before_send()`（`client.py:410-411, 447-448`）閘門內——`ctx.check_cancel()` 拋出 `Cancelled`，由 `send()` 的單一圍欄包裝器（見 §6.1 第 5 點與 §6.2.2，對齊 `session_start_operations.py:230-231` 與 `failover_operations.py:455-460`）在確認即時讀取之 `_fence_sent(ctx)` 不為 `True` 後轉為 `StepFailed("CANCELLED", "operation cancelled before session send")`，經 `_execute_bound`（`operations.py:874-880`）結束為 `status = "failed", error_code = "CANCELLED"`（收據狀態依 §8.2 順序 1 映射為 `cancelled`），並喚醒同一 `(host, session_id)` 的下一筆等待輸入。
3. **開始送出後的拒絕取消（透過動作專屬取消函式，與 §8.2 圍欄規則完全一致）**：
   - `OperationService.cancel`（`operations.py:686-710`）原本就會針對特定動作委派專屬邏輯（例如 `:690-710` 委派 `worktree_merge_operations.cancel`、`failover_operations.cancel`、`pm_work_start.cancel_children` 等）。
   - P5 在 `operations.py:687-690`（於 `self._may_steer(principal, op, "cancel")` 之後、`if op["status"] in TERMINAL:` 之前）新增 `if pm_work_follow_up.is_work_follow_up(op): pm_work_follow_up.cancel(self, principal, op)`：
     - 驗證呼叫端具備該 Workspace 寫入成員資格（`pm_workspace.require_member(..., write=True)`）與 `pm_work_start.require_work_controller`（在 `OperationService._may_steer` `:636-650` 與 `resume` `:738-766` 同樣呼叫此授權檢查）；
     - 從 SQLite 即時讀取最新 `op` 與 `send` 步驟列：若該操作已跨過發送圍欄（`send_sent is True`——由於圍欄具單調性，一旦為 `True` 永不重設回 `False`，涵蓋 §8.2 的 `sending`、`sent`、`unknown` 與 `NOT_ACCEPTED`——或 `op["status"] in {"succeeded", "uncertain", "needs_attention"}`，或 `send` 步驟為 `succeeded` / `uncertain`），立即拋出 HTTP `409`、`error.code = "PM_WORK_CANCEL_NOT_ALLOWED_AFTER_SEND"`，**不設定** `cancel_requested = 1`，亦**不進入** `operations.py:717-733` 的 `needs_attention` 取消分支。
     - 若 `send_sent is not True`（尚未開始送出），當 `op["status"] in TERMINAL`（如已在圍欄前 `cancelled` 或 `failed`）時接著由 `operations.py:688-689` 回傳 `op`，當 `op["status"] in {"accepted", "running", "waiting_checks", "waiting_external"}`（即 §8.2 順序 6 的 `queued`，`cancellable == true`）時則繼續執行 `:711-716` 的圍欄前取消。
     - 因此，跨過圍欄（`send_sent is True`）的操作絕不會顯示為 `queued`（`cancellable: true`），亦絕不會被轉為 `cancelled`；且萬一收據合成器在防禦性路徑上看到 `send_sent is True` 但狀態為 `cancelled`（或非 `NOT_ACCEPTED` 的狀態），§8.2 的優先序表也會因為圍欄優先分流而將其歸入順序 4（`unknown`），絕不會把已送出或可能已送達 BAT 的指令顯示為 `queued`、`cancelled` 或 `failed`。

### 7.2 當前置輸入結果未確認（`unknown`）時，後續排隊輸入的表現與使用者處置

當第 $k$ 筆輸入（`position = k`）在跨過 `on_transport` 後遺失回覆，且在 Claude live state 中尚未看到 `batc-<op_k>` 回音時：

1. **第 $k$ 筆輸入（`position = k`）**：處於 `operation_status = "needs_attention"`、收據 `state = "unknown"`。
   - **使用者看到的狀態**：顯示「送出後未收到回覆。請勿重送，請以原 ID 重新確認結果。」
   - **使用者可執行的動作**：呼叫 **以原 ID 重新確認（Reconcile with original ID）**（`POST /api/v1/operations/{op_k}/resume`）。若 BAT 實際已收到該訊息，調和後轉為 `sent` 並解除佇列阻擋；若封包確實在抵達 BAT 前遺失而永遠無回音，該筆輸入誠實保持 `unknown`（絕不重送、絕不清除鎖定、亦不可取消偽裝成未送出）。
2. **排在第 $k$ 筆之後的輸入（`position > k`）**：保持在 `operation_status = "waiting_external"`、收據 `state = "queued"`，且收據附上：
   - `"status_reason": "predecessor_outcome_uncertain"`
   - `"blocked_by_operation_id": "<op_k>"`
   - **使用者在後續輸入上看到的狀態**：明確顯示「排隊中（等待前一筆未確認結果的指令處理完畢）」及阻擋它的前置操作連結 `#/op/<op_k>`。
   - **使用者在後續輸入上可執行的兩項動作**：
     1. **取消此筆尚未送出的後續指令**（`POST /api/v1/operations/{op_later}/cancel`，因 `op_later` 的 `send_sent` 仍為 `False`，可安全取消並取回草稿）；
     2. **開啟該筆結果未確認的前置指令**（導向 `#/op/<op_k>` 或呼叫 `POST /api/v1/operations/{op_k}/resume` 進行原 ID 調和）。

### 8.2 由發送圍欄（`send_sent`）優先決定收據狀態（`state`）與「證明未送出」規則

在 `src/bat_agent_connector/operations.py:137-149` 中，`_error_code(exc)` 的真實程式碼為：

```python
def _error_code(exc: BaseException) -> str:
    from .confinement import ConfinementRefused
    from .session_permissions import PermissionsRefused

    if isinstance(exc, ConfinementRefused | ResourceReadOnly | TaskControlRefused | PermissionsRefused):
        return exc.code
    if isinstance(exc, StepFailed | NeedsAttention | OperationError):
        return exc.code
    if isinstance(exc, WriteRefused):
        return "REFUSED"
    if isinstance(exc, BatError):
        return "BAT_ERROR"
    return "INTERNAL"
```

因此，「一筆指令是否已開始送出、是否證明未向 BAT 送出（或未啟動 Turn）」**不能也不應依賴錯誤碼字串清單**，而是直接由 SQLite 即時讀取之發送圍欄 `send_sent = (op.get("external_refs") or {}).get("send_sent")`（配合 `operations.py:35-36` 的真實 `STATES` 與 `:250-315` 的 `send` 步驟狀態）**由圍欄優先分流（Fence Decides First）**：

1. **當 `send_sent is True`（已跨過 `on_transport` 圍欄）**：
   - 收據 `state` **必為 `sending`、`sent`、`unknown` 或 `failed`（僅限 `NOT_ACCEPTED`）其中之一**，**絕不可能**為 `queued` 或 `cancelled`，且 `cancellable` 恆為 `false`：
     - **`op.status == "failed"` 且 `op.error_code == "NOT_ACCEPTED"`**：當 `service.session_send` 正常返回且 BAT 對該單一幀明確回覆 `r.get("accepted") is False` 時，`send()` 在 `try / except` 區塊**之後**拋出 `StepFailed("NOT_ACCEPTED", "BAT did not accept the message")`（對齊 `session_start_operations.py:508-509`，重用既有 `"NOT_ACCEPTED"` 代碼，見 `api_actions.py:155`、`checkpoints.py:642`、`task_actions.py:294`；傳統非 Work 發送則保留 `api_actions.py:154-155` 的 `NeedsAttention("NOT_ACCEPTED", ...)` 不變）。操作結算為終態 `op.status == "failed", op.error_code == "NOT_ACCEPTED"`，收據為 **`state = "failed"`**，提供「以新指令重試（Retry as new instruction）」，並立即喚醒下一筆排隊輸入（順序 2）。
     - **`op.status == "succeeded"`**：收據為 **`state = "sent"`**（順序 3）。
     - **`op.status == "running"`**：
       - 當 `send` 步驟處於 `uncertain` 時，收據為 **`state = "unknown"`**（順序 4）；
       - 當 `send` 步驟處於 `succeeded`（即 `operations.py:314` `_step_done` 與 `:882` 操作本身轉為 `succeeded` 之間的視窗）時，收據為 **`state = "sent"`**（順序 3）；
       - 其餘情況（如 `send` 步驟為 `started`），收據為 **`state = "sending"`**（順序 5）。
     - **任何其他順序 2 未匹配的狀態**（包含 `op.status in {"accepted", "waiting_checks", "waiting_external", "needs_attention", "uncertain", "cancelled"}`，或 `op.status == "failed"` 且 `op.error_code != "NOT_ACCEPTED"`）：一律為 **`state = "unknown"`**（順序 4），僅提供「以原 ID 重新確認（Reconcile with original ID）」，**絕不**顯示 `queued`、`cancelled` 或 `failed`。
2. **當 `send_sent is not True`（`False` 或尚未設定，未跨過 `on_transport` 圍欄）**：
   - 正常可達之收據 `state` 為 **`queued`、`cancelled` 或 `failed`**（保守防禦回退為 `unknown`），且**唯有 `queued` 可設定 `cancellable: true`**：
     - **`op.status == "cancelled"` 或（`op.status == "failed"` 且 `op.error_code == "CANCELLED"`）**：圍欄前取消，收據為 **`state = "cancelled"`**（`cancellable: false`，提供「編輯並以新指令送出」，順序 1）。
     - **`op.status == "failed"` 且 `op.error_code != "CANCELLED"`**：由於 `on_transport()` 在 `await self._ws.send(encoded)`（`client.py:356-358`）正前方同步寫入 `send_sent = True`，`send_sent is not True` 即由圍欄本身證明該指令從未寫入 WebSocket；無論 `_error_code(exc)` 產生的 `op.error_code` 為何，收據皆為 **`state = "failed"`**（`cancellable: false`，提供「以新指令重試」，順序 2）。
     - **`op.status in {"uncertain", "needs_attention", "succeeded"}` 或 `send` 步驟處於 `{"uncertain", "succeeded"}`（保守防禦回退）**：在 §6.1 第 5 點 / §6.2.3 規則下，圍欄前的 `AMBIGUOUS` 或 `OSError` 在 `schedule == "after_current"` 轉為 `Wait`（`uncertain_tries = 0`）或在 `schedule == "now"` 轉為 `StepFailed("BAT_ERROR", ...)`，因此正常流程中 `uncertain` / `needs_attention` / `succeeded` 蘊含 `send_sent is True`；若防禦性讀取遇到 `send_sent is not True` 卻處於上述狀態，一律保守映射為 **`state = "unknown"`**（`cancellable: false`，順序 4）。
     - **`op.status in {"accepted", "running", "waiting_checks", "waiting_external"}` 且（`step is None` 或 `step.status in {"started", "failed"}`）**：收據為 **`state = "queued"`**（**唯一 `cancellable: true` 的狀態**，提供「取消排隊中的指令」，順序 6）。

#### 收據 `state` 的 1 $\rightarrow$ 6 嚴格優先序表（由圍欄優先分流規則直接導出，僅使用 `STATES` 真實狀態）

令 `op` 為從 SQLite 即時讀取之 `operations` 列（`op.status` 屬於 `operations.py:35-36` 的 `STATES = ("accepted", "running", "waiting_checks", "waiting_external", "needs_attention", "uncertain", "succeeded", "failed", "cancelled")`）、`step` 為 `operation_steps(name='send')` 列（`None` 或 `step.status in {"started", "succeeded", "failed", "uncertain"}`）、`send_sent = (op.get("external_refs") or {}).get("send_sent")`。收據 `state` 與 `cancellable` 依下列由上而下（1 $\rightarrow$ 6）的互斥條件求值：

| 求值順序 | 收據 `state` | 嚴格判定條件（由 SQLite 即時讀取之 `send_sent`、`op.status in STATES` 與 `step` 求值） | `cancellable` | 是否提供「以新指令重試」 |
| --- | --- | --- | --- | --- |
| **1** | `cancelled` | `send_sent is not True` **且**（`op.status == "cancelled"` **或** (`op.status == "failed"` 且 `op.error_code == "CANCELLED"`)） | `false` | 提供「編輯並以新指令送出」 |
| **2** | `failed` | （`send_sent is not True` 且 `op.status == "failed"` 且 `op.error_code != "CANCELLED"`）**或**（`send_sent is True` 且 `op.status == "failed"` 且 `op.error_code == "NOT_ACCEPTED"`） | `false` | **是**（所有進入順序 2 的收據皆已由圍欄或 BAT `accepted: false` 證明未啟動 Turn） |
| **3** | `sent` | `send_sent is True` **且**（`op.status == "succeeded"` **或** (`op.status == "running"` 且 `step is not None` 且 `step.status == "succeeded"`)） | `false` | 否 |

## 12. 範圍外項目（決策 11：Out of Scope）

下列項目明確排除於本 P5 規格與實作切片之外：

1. **Steering（執行中插入）與 Interrupt**：`session.send` 絕不對執行中的 Turn 進行插入；中斷執行中回合仍由既有的 `session.interrupt` 獨立負責。
2. **平行輸入（Parallel Inputs / 另開獨立 Worktree）**：當使用者明確要求在平行分支或新 Worktree 同時嘗試另一方向時，屬於建立新的 Attempt（`work.start`），不在 `session.send` 追加指令範圍內。
3. **前端 Composer 與佇列介面元件**：本規格定義後端契約、收據讀取與雙語狀態詞（§10），前端 Workbench 的輸入框與佇列卡片屬於後續 UI 切片。
4. **原生 CLI Adapter（E06）**：直接連接原生 CLI 之 adapter 屬於 E06 範圍。

3. **當一筆未確認（`unknown` / `needs_attention`）的追加指令因封包在抵達 BAT 前遺失而永遠無回音時，該佇列的處置策略（§7.2）**：
   - **背景**：對 Claude 工作階段而言，若封包在跨過 `on_transport`（`send_sent = True`）後、抵達 BAT 之前於網路中遺失，BAT 的 live transcript 永遠不會出現 `batc-<op_k>` 回音，因此 `POST /api/v1/operations/{op_k}/resume` 會持續維持 `needs_attention`（收據 `state = "unknown"`），而排在後方的輸入（`pos > k`）預設會一直等待（使用者可取消後續尚未送出的排隊輸入，或對未確認的那一筆執行原 ID 調和）。
   - **兩個可選方案**：
      - **方案 (a)：維持同工作階段佇列阻擋（本規格預設）**。只要 `op_k` 仍為 `unknown`，同一 `(host, session_id)` 上排在後方的 `work_inputs` 就絕不自動越過它送出（使用者可安全取消後方尚未送出的輸入）。同時，經核對 `pm_work_start.require_latest_attempt_settled`（`src/bat_agent_connector/pm_work_start.py:215-265`），該函式係查詢最新 `work_attempts` 列的 `start_operation_id`（或 `origin_id`，`:220-226`）以及該父操作在 `pm_work_start_children` 表中的子操作列（`:228-235`），檢查其是否皆已進入終態且無未證明步驟（`:236-267`）；它**不會**讀取 `work_attempts.execution_operation_id`，且 P5 的追加指令（`work_inputs`）並非 `pm_work_start_children` 的子操作列。因此，對於已啟動（`stage == "started"`）的 Attempt，`require_latest_attempt_settled` **允許**使用者從固定檢查點啟動一個全新的 `work.start` Attempt（在新的受管工作階段與 Worktree 中繼續工作），即使舊 Attempt 仍有一筆 `unknown` 的追加指令，也無須對舊工作階段強行重送或清除鎖定。（若 Owner 希望連新 `work.start` Attempt 在舊 Attempt 有 `unknown` 追加指令時也一併阻擋，亦可於 `require_latest_attempt_settled` 加入對 `work_inputs` 的檢查。）
     - **方案 (b)：允許對已進入 `needs_attention` 的追加指令執行既有的「結果未明結案（`needs_attention` cancel）」（`src/bat_agent_connector/operations.py:717-733`）**。在 `OperationService.cancel`（`operations.py:717-733`）中，現有程式碼對 `status == "needs_attention"` 的操作會寫入 `"outcome_proven": False`、`"unproven_steps": ["send"]` 與 `"warning": "cancelled after needs_attention; the outcome of send was never proven"`。若採用方案 (b)：
       1. 在 `sending`（`send_sent is True` 且 `op.status == "running"` 且 `send` 步驟非 `succeeded` / `uncertain`）、`sent`（`send_sent is True` 且 `op.status == "succeeded"` 或 `send` 步驟為 `succeeded`），以及仍在自動重試 `UNCERTAIN_RETRY_S` 期間的 `unknown`（`op.status == "uncertain"`，或 `op.status == "running"` 且 `send` 步驟為 `uncertain`）時，仍嚴格拒絕取消；但當經過自動重試與原 ID 調和仍無回音而停在 `op.status == "needs_attention"`（收據 `state == "unknown"`）時，允許使用者呼叫既有的 `operations.py:717-733` 將其結案；
       2. 該筆操作的收據明確顯示為 **「已結案，送出結果未明（`closed, outcome unknown`）」**——**絕不**顯示為一般的 `cancelled`（未送出取消），且**絕不**重送該筆指令或提供重送按鈕；
       3. 後續排隊輸入（`pos > k`）解除前置阻擋，但在送出前仍必須等待一次完整的最新回合邊界與本地/最後一幀閒置檢查（確認工作階段 `isStreaming == False` 且無待處理閘門）。
   - **本規格建議**：建議採用 **方案 (a)** 作為預設安全策略（完全符合 `AGENTS.md`「絕不透過清除鎖定或重送來修復未確認結果」的原則；使用者可取消後方未送出的排隊輸入，或透過新 `work.start` Attempt 在全新受管資源從檢查點繼續），並請 Owner 裁示是否維持方案 (a)，或是否希望開放方案 (b) 的 `closed, outcome unknown` 結案路徑？

## 15. 實作紀錄（p5-impl，對齊合併後的 `origin/main`）

§14 的三題在實作時採用本規格的建議答案，沒有另開結案路徑：

1. Codex 受管工作階段的 Work Target `session.send` 在 Admission 以 `409 PM_WORK_CODEX_FOLLOW_UP_UNSUPPORTED` 拒絕。
2. 已啟動 Work 的 Result 下一步只提供 Work Target `session.send`。直接 `{host, session_id}` 的 `session.send` 仍走既有 API。
3. 結果未確認的輸入擋住同一工作階段後方的排隊輸入。尚未送出的後方輸入可以取消；未確認的那一筆只用原 ID 調和。`needs_attention` 取消不會把一筆已跨過圍欄的送出標成已取消。

下列行為與規格正文不同。程式以此節為準。

1. **缺列事件可見性（§8.4）。** 事件不會只因為 `body.workspace_id` 存在就被隱藏。只有 Work 輸入事件會改走缺列規則：`body.work_follow_up is True`、Work Target，或 `work_inputs` 已有該 `resource_id`。沒有 `work_inputs` 列時不顯示。有列時，呼叫端仍須具備 `observe`、Workspace 成員資格，以及該 Work Item 與工作階段的來源可見性。規格所寫的 `pm_source_lineage.session_visible` 與 `pm_source_lineage.operation_visible` 不存在；實作使用 `pm_source_lineage.visible(...)`。列表裡最新 Attempt 的可見性使用 `pm_work_start.operation_visible`。
2. **忙碌判定。** 觀察列若明確帶有 `streaming` / `isStreaming == false`，該旗標優先於 `runtime_status`。單獨的 `runtime_status` 為 `running` 或 `active` 不算忙碌。忙碌的 runtime 值只有 `streaming`、`busy`、`starting`。
3. **雙語文案。** 人可讀的中英文字放在收據的 `labels`（以及下一步動作的 `label` / `label_zh_TW`）。`OperationError.message` 維持與鄰近動作相同的英文句子，不把兩種語言接在同一個 `error.message`。
4. **外來工作階段。** `session_registry` 沒有 `created_by_operation_id`。外來與手動的判定是：registry 的 `start_operation_id` 與本次 Attempt 的 handoff 不一致、provenance 為 `manual_bat` 或 `discovered_existing`、或不在 registry。拒絕碼為 `409 PM_WORK_SESSION_NOT_MANAGED`。`resource_policy` 判為唯讀時沿用該列的 `read_only_code`（預設 `READ_ONLY`），HTTP 403。
5. **未知 Host。** Host 不在 fleet 設定時沿用 `_admit_session` 的 `404 UNKNOWN_HOST`。此碼不在 §2.4 對照表，但是既有碼。寫入層級關閉仍是 `403 TIER_DISABLED`。
6. **輸入列表形狀。** `list_inputs` 與 `list_attempts` 一樣回傳 `workspace_id`、`work_item_id`、篩選用的 `attempt_id`、`latest_attempt_id`、`items`、`next_cursor`、`has_more`、`visibility_filtered`。不另複製一份 `inputs` 陣列。
7. **收據連結。** 除了 operation 與 attempt result，還包含 inputs 路徑，以及 `#/op/{operation_id}`（被擋住時另有 blocked-by 的同樣兩種連結）。
8. **讀者的 `session.send` 阻擋原因。** `consider()` 先檢查 controller、再檢查 writer。讀者因此看到 `not_controller`，而不是 `not_writer_member`。
9. **桌面 bridge。** `desktop/src-tauri/src/bridge.rs` 的 GET 允許清單沒有 E04 的 `/work-attempts/{attempt_id}/result`，也沒有 `/inputs`。本切片不修改 bridge。
10. **交易內的 started 代理。** `admit_operation` 在同一筆 INSERT 交易裡以 execution operation 的 `status == "succeeded"` 代表該 Attempt 仍是 started。不在交易內重算完整 stage 視圖。
11. **Controller authority。** `require_work_controller` 使用帶 `pm_workspace_id` 的 binding。寫進 `admission_binding.controller_authority`、以及 `require_entry` 所用的 authority，是 `controller_authority.binding(db, principal)`，不帶 workspace。受管工作階段是 `repository.continue` 以未帶 workspace 的 binding 蓋章的；帶 workspace 的 actual authority 會被 `require_binding` 拒為 `CONTROLLER_WORKSPACE_CHANGED`。
12. **`Wait` 盤點。** §6.2.4 正文寫基準 `664715b9` 有 47 處。該節表格列出的每一行在合併後的 HEAD 仍在原行。以同一大小寫敏感的 `raise .*Wait` 在合併後的樹搜尋，得到 52 行：51 行是 `raise Wait(`，另 1 行是 `managed_setup.py` 錯誤訊息裡的英文 "Wait"（不是 `Wait` 例外）。`deployment.py:408` 與 `:446` 仍是 `raise dispatch_wait(...)`，不匹配該大小寫敏感模式，且仍在 `ctx.step` 的 `fn()` 之外。P5 新增的 6 處都在 `pm_work_follow_up.py`（排隊等待、回合邊界等待、串流中、待處理閘門、最後一幀忙碌、圍欄前傳輸不可用）。既有 proven-unsent 包裝器在步驟函式內消化傳輸錯誤，不會把 `Wait` 送出步驟；唯一會進入 `fn()` 且未設定 `<name>_sent` 的舊路徑仍走缺鍵分支，與今日的 `StepFailed` 相同。
13. **每一幀前重查寫入成員（§6.1、§9.1）。** 存進 operation 的 controller authority 不帶 workspace，所以 `controller_authority.require_binding` 不會呼叫 `require_member(write=True)`。來源可見性也只檢查讀取。`_before_send_gate` 因此在取消、controller incarnation 與 `require_local` 之後，以 `pm_workspace.admitted_principal` 重建的 principal 呼叫 `pm_workspace.require_member(db, principal, workspace_id, write=True)`。同一檢查也放在 `prepare_send` 即將派送、進入 `ctx.step` 之前：否則已被移出的成員會先被 `require_new_effect` 拒成 `404 PM_HANDOFF_SOURCE_UNAVAILABLE`。讀者是 `403 FORBIDDEN`（「Workspace membership does not permit this action」），非成員是 `404 NOT_FOUND`（「Workspace not found」）。兩者都在 `send_sent` 變成 `True` 之前，收據為 `failed`，該 `clientMessageId` 的送出幀數為 0。已送出或 `uncertain` 的調和不再重查。同一工作階段裡稍後仍具寫入資格的輸入照常各送一次。
14. **被 BAT 明確拒絕的回合不是已送出回合（§5.2、§8.2）。** `latest_sent_turn` 略過 `error_code == "NOT_ACCEPTED"` 的列，即使該列已跨過 `send_sent`。明確 `accepted: false` 證明沒有回合開始，Result 的 `conversation.turn_marker` 留在前一個標記（或初始 handoff），收集器不會為了該標記等待一則不會出現的回音。`FOLLOW_UP_PROMPT_UNPROVEN`（`needs_attention` / `unknown`）仍算已送出，後方輸入繼續等待。下一筆輸入照常送出。
