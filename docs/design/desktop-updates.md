# Explicit desktop updates

The native Settings panel checks one fixed GitHub release feed, reviews one candidate,
downloads and verifies its bytes, then requires a separate Install action. The browser
has no update command. The WebView cannot choose URLs, keys, file paths or installer
arguments. Default CI packages contain no updater public key and visibly disable updates.

The official Tauri updater 2.13.2 verifies Minisign signatures and requires the signed
version to equal the announced version. Only a newer Windows x64 NSIS version is eligible.
The native adapter overrides endpoints, target and headers, disables proxy inheritance,
limits redirects to GitHub asset origins and caps downloads at 128 MiB and 185 seconds.
The feed also identifies API 1, contract `2026-10-08`, source SHA and canonical workflow.
The feed generator and updater share the `workflow_version` validator: ASCII
`YYYY-MM-DD.revision` (one or more revision digits), at most 64 characters, independent of the contract date.
These feed metadata fields are descriptive; the signature binds artifact bytes and version,
not the feed's source/workflow assertions. Release tooling derives those from the reviewed
checkout. A corrupted or relabelled download never becomes installable.

Check failures preserve the original candidate. A cached verified download can restore
the Install state without another network request. Rechecking successfully replaces that
candidate. All mutation commands serialize; candidate IDs prevent stale buttons from
installing a replacement. Only local Status is allowed during an in-flight command.

Install validates verified bytes before stopping local connections. Quit and updates share
one lifecycle guard. The original Fleet ticket is invalidated before shutdown, and the
native Launcher/Monitor guards remain held through the installer call. Only positively
owned local processes may be stopped. Unknown ownership or an active launcher refuses.
Missing Fleet configuration uses an independent absence check with both mutexes held:
the fixed native launch journal, both BAT data directories and legacy monitor candidates
must prove no remaining owner. Existing ownership residue requires restoring configuration
and ordinary reviewed recovery; removing the config cannot bypass shutdown.
Central tasks and remote BAT processes continue independently.

Before invoking the installer, Rust durably creates a receipt under `update-intents`,
keyed by the source binary version. It records candidate, target version, source SHA and
artifact digest. An unreadable, partial or existing receipt blocks another installation
attempt. A lost reply or process restart reads the original receipt; it cannot resend.
The old binary keeps local launches fenced and opens Settings for recovery. A newly
installed binary has a different version epoch; the old receipt remains historical.
Installer launch/exit is not proof that installation succeeded. A refusal before intent
creation can be reviewed again after Fleet ownership is resolved.

## Release preparation

The ordinary `desktop` workflow builds **unsigned validation packages**. The manually
invoked `desktop-signed-candidate` workflow only builds and uploads an updater-signed
candidate and runs the disposable hosted-runner NSIS/WebView install fixture; it never
creates a release, publishes a feed, installs on an operator machine or restarts a live host.
Its exact 40-character source SHA must already belong to main. Version comes from the
committed Tauri config; canonical workflow comes from the same checkout's skill and is checked against that shared format.

The repository owner supplies a `desktop-release` environment with an independently
backed-up signing identity: public `DESKTOP_UPDATER_PUBLIC_KEY` variable and
`TAURI_SIGNING_PRIVATE_KEY` / optional `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` secrets.
Private signing keys are not generated by this implementation or stored in the repository.
Keep the public key stable across releases; changing it requires a separately planned
transition for installed clients. Increment the committed app version for each release.
If the bundled core changes, also increment the Python package/runtime version and
validate two distinct actual core bundles with the retained-data upgrade fixture
in [the managed installation contract](managed-installation.md). The application
version alone does not trigger a same-version core replacement.

The `update_manifest` Rust example verifies the actual installer bytes and signature
against that public key and requires exactly the committed signed version before writing
`dashboard-update.json`. A temporary key, wrong key, changed bytes or relabelled version
cannot silently produce a valid feed for another installation identity. Upload the
reviewed `.exe`, `.exe.sig` and JSON together to the matching `v<version>` release only
after installed acceptance; the application reads the latest release's JSON. The workflow
has only read repository permission, so publication remains an explicit operator action.

Updater signing and Windows Authenticode are separate. This workflow does not claim a
trusted Windows publisher certificate or SmartScreen reputation. Authenticode must be
configured in the release environment before it is claimed as part of a distributed build.
See [Tauri updater signing](https://v2.tauri.app/plugin/updater/) and
[Windows signing](https://v2.tauri.app/distribute/sign/windows/).

## Evidence and remaining acceptance

Tests use ephemeral in-memory keys and loopback HTTP peers with the real Tauri verifier:
valid download, changed bytes, missing/mismatched signed version, cached recovery, original
receipt after reopen, and partial receipt refusal. The release verifier rejects altered
bytes, wrong keys and ambiguous signed versions. No fixture invokes an installer.
Shared UI tests cover both languages at 390/768/1440, disabled unsigned builds, explicit
actions and lost-reply recovery. Keyboard focus stays on the pressed update action
while it runs, moves to Install after a verified download, and returns to Read
status when the pressed action ends unavailable. Native final-effect tickets have separate queue/quit tests.

The NSIS/WebView fixture installs the exact built package on a disposable Windows runner,
checks digest/version readback, close/single-instance/relaunch and uninstall, and uploads
receipts/screenshots. The signed workflow runs it after signature/feed verification and
before uploading the distributable candidate. It does not exercise the in-app signed
upgrade path, real credentials, physical tray interaction or an existing user's data.

Installed Windows updater stop/install/reopen, signing-environment execution, real release feed
publication and installed version readback remain acceptance gates. Linux packages do not
offer this Windows installer flow. Fixture/CI results are not installed/live evidence.

## macOS signed candidates

`desktop-macos-signed-candidate` accepts an exact reviewed main commit and builds both
Apple Silicon and Intel DMGs in the `desktop-release` environment. Configure variables
`APPLE_SIGNING_IDENTITY` (Developer ID Application) and `APPLE_TEAM_ID`, plus secrets
`APPLE_CERTIFICATE` (base64 P12), `APPLE_CERTIFICATE_PASSWORD`, `APPLE_ID` and
`APPLE_PASSWORD` (an app-specific password). The maintained identity is supplied by the
owner; this workflow does not generate a replacement or request account passwords in chat.
Tauri signs and notarizes, then the gate checks the expected Team ID, Developer ID chain,
stapled ticket and Gatekeeper acceptance before exercising the exact installed DMG.
The workflow only uploads candidate artifacts; it does not publish a release or feed.
See [Tauri's macOS signing contract](https://v2.tauri.app/distribute/sign/macos/).

Ordinary Mac CI uses ad-hoc signing and cannot pass as notarized distribution evidence.
This signed-DMG workflow is separate from Minisign updater signing; the in-app updater
currently remains Windows-only. Until the maintained Apple identity is configured and
this workflow passes, Developer ID/notarization is unverified.

## Local candidate receipts

`scripts/validate_release_candidate.py` compares local producer claims and the
bytes they cover with one explicit candidate SHA. It never fetches, publishes,
signs, tags, installs or starts a product process. For example:

```sh
uv run python scripts/validate_release_candidate.py receipt wheel dist/package.whl > wheel-receipt.json
uv run python scripts/validate_release_candidate.py validate --candidate FULL_SHA --source . --receipt wheel-receipt.json
```

Each format-1 receipt contains `component`, `version`, `commit`, `artifact`,
`sha256` and `coverage`. Package receipts cover the archive; the separate
dashboard receipt covers only dashboard bytes inside its wheel and inherits
that wheel's build identity. The source comparison uses the candidate's local
Git objects, never the current checkout's modified files. Wheel/sdist package
comparison reuses the Connector installer's source-verification rules; no old
package is imported or executed. Runtime receipts cover the producer manifest
and compressed payload, including both compressed and uncompressed integrity.
The manifest's optional `build_commit` is the same build input embedded in the
runtime; legacy manifests without it remain unknown. Native readers retain
strict unknown-field rejection and accept the added optional field.

Screenshot receipts reuse the capture-manifest reader and content checks,
including listed PNG hashes, capture guarantees, the frontend Git tree and
source-file hashes. README and static-site receipts cover their source bytes;
their `version` comes from project metadata. They do not certify the readable
release captions or select a new published version. Screenshot `version` is its
capture schema. These distinct version sources are not interchangeable.
The static-site checker keeps capture/source integrity checks without a
hand-maintained release SHA comparison. Candidate agreement belongs to this
validator's explicit candidate input; a screenshot from a different candidate
is refused even when its own images and capture manifest remain intact.

Each required component has `matches`, `differs` or `unknown`, with its own
reason. Missing/malformed claims, missing files, unavailable candidate objects
or unsupported producer evidence never pass. Different commits, changed
receipt digests or source/content mismatches are refused by component name.
Receipts establish consistency of producer claims and bytes, not signatures,
independent build attestation, running-process identity or product acceptance.

The default required set includes wheel, sdist, dashboard, managed runtime,
screenshots, README, static site, native Desktop and the site demo. Current
Desktop installers and demo output do not ship a supported offline artifact
receipt; these components stay unknown, so the full set cannot pass today.
`--required COMPONENT` may be repeated for an explicit partial assembly check;
the result always lists its required scope. Passing such a subset is not a
complete release qualification. Native `app_build` remains a running-build
observation, not an installer-digest receipt. No workflow or signing changes
are made to manufacture missing evidence.

Run the complete check after candidate artifacts and capture receipts exist,
before uploading release assets or switching update channels, and before
publishing the corresponding Pages output. Those workflow integration points
remain separate work. Choosing the candidate, pin timing, tag/feed mapping,
readable version and support wording remain owner decisions.

Normalized producer goldens are regenerated with
`uv run python -m tests.test_release_identity --scratch /path/on/disk`.
The generator builds two real Hatch candidates from metadata-declared package
inputs, invokes the runtime writer, and evaluates the capture producer's actual
metadata statement with explicit fixture clock/browser inputs. Existing PNG
bytes are fixtures; no browser capture or native installation is claimed.
Golden hashes/commits/versions are placeholders, not committed hashes of all
frontend sources. The separate runtime parser golden hashes only fixed,
de-identified fixture text. Freshness tests compare both with their producers.
