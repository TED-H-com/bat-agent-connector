## 1. Profile 是什麼

### 1.1 它不是哪三個既有的 profile

這三個名字已經有別的意思，E01 不重用它們的表、動作或回應：

| 既有名字 | 位置 | 實際意思 |
|---|---|---|
| `pm_profiles` / MCP `pm_profiles_get` | `src/bat_agent_connector/mcp_server.py:582-584`、`src/bat_agent_connector/pm_reads.py:454-455` | 討論用途目錄（idea、planning），不是 coding profile。 |
| `HostConfig.profile_id` | `src/bat_agent_connector/config.py:124`，預設字串是 `"default"` | BAT 連線 profile。`managed_setup.state` 把這個欄與 `url`、`fingerprint`、`token_available` 一起回傳。 |

### 1.2 範圍與綁定

一個 work profile 同時屬於：

1. 一個 PM workspace，識別是 `ws_` 加 32 個十六進位字元，與今天的 PM workspace 相同。
2. 恰好一筆已經寫在安裝裡的 repository 綁定。三個鍵是 `repository`、`host`、BAT `workspace_id`。BAT workspace 是綁定上的字串，不是 PM 的 `ws_` 識別。`tests/test_pm_work_start.py:2215-2219` 的例子是 repository `o/r`、host `h1`、BAT workspace `ws-1`。本文例子只用這種公開占位，不用真實主機名。

### 1.3 與 `work.start` 今天的輸入

`work.start` 今天必填 `instruction`、`agent`、`delivery`、`code_target`，選填 `model` 與 `requirement_ids`。`code_target` 四鍵含 `source_ref`。profile 只固定其中的綁定三鍵、agent，以及非 null 的 model 與 delivery。`instruction` 與 `requirement_ids` 仍由每一次啟動自己帶。profile 不取代它們，也不把草稿文字存進文件。

### 1.4 為什麼 v1 不接預算政策

程式裡沒有 coding 用的 budget policy 表。維護政策的 `policy_id`（`pmmp_…`）是另一個領域。`work.start` 的交付詞彙只有 `DELIVERY_GOALS` 那兩個 goal。v1 不把維護政策識別填進 `budget_policy_ref`，非 null 就拒絕。以後若有真正的預算物件，再以新的文件版本接上，不在這份規格假造一個識別。

## 2. 儲存

### 2.1 為什麼不完全照 E00 的欄位清單

E00 §4.2 建議 `work_profiles` 的欄是 `profile_id, workspace_id, revision, document, digest, operation_id, created_at`，唯一鍵 `(profile_id, revision)`。同一節寫明：JSON 不能用來避開身份索引與 withdrawal gate；readiness 的現在值與上次真正驗證分開；不能因為設定存在就當成 ready。

本規格沿用那張表與那些不變量，並補兩個欄，理由都來自這條 gate：

- `withdrawn`：撤回必須是列上的值，列表、讀取與 readiness 才能一起拿掉，不能只藏在 JSON。
- `sequence`：沿用 `pm_work_packages` 的游標方式，給列表分頁，不把修訂編號兼做成全域序號。

預設不放在這張表。若把 `is_default` 寫進某一筆 profile 修訂，清掉舊預設就得再追加舊 profile 的一筆修訂。那會改變該 profile 的最新 `revision` 與呼叫者沒有送出的那一列，§5 釘住的 revision 與 digest 就會被一次無關的預設切換弄失敗。預設改放 `work_profile_defaults`。最新一列由該表自己的 `sequence` 決定。`profile_id` 可以是 null，表示這個 workspace 目前沒有預設。

`revision` 仍是每個 `profile_id` 自己的正整數，從 1 開始，只增不改。最新一筆是該 `profile_id` 的最大 `revision`。`sequence` 只用於分頁。

### 2.2 文件版本 1

存進 `document` 的是單一 JSON 物件，版本只能是 1。允許的鍵只有：

| 鍵 | 值 |
|---|---|
| `version` | `1` |
| `binding` | `{repository, host, workspace_id}`，三個非空白字串，各 1–256 |
| `agent` | `claude` 或 `codex` |
| `model` | 字串 1–256，或 null。空白，以及 `.strip()` 之後是空的字串，是 `INVALID_PARAMS`。規則與 `work.start` admission 相同 |
| `delivery_policy_ref` | null，或 `{goal}` 且 goal 屬於既有的兩個交付 goal |
| `budget_policy_ref` | null。鍵可以省略，省略視同 null |

其他鍵，包含 `default`、`is_default`、`withdrawn`、`source_ref`、`controller_id`、`actor`、`scopes`，都是既有的 `INVALID_PARAMS`（422）。`withdrawn` 只放 `work_profiles` 的欄，由參數 `withdrawn` 決定。預設只放 `work_profile_defaults`，由參數 `make_default` 決定。文件與這兩處各說各話時，以拒絕這份文件處理。

下面這些鍵出現在物件樹的任何一層，都是 `INVALID_PARAMS`：`secret_ref`、`token`、`token_ref`、`password`、`authorization`、`credential`、`fingerprint`、`url`、`endpoint`。不掃描字串值裡有沒有 "token" 這個詞，避免把模型名稱誤殺。寫入路徑拒絕它們；讀取路徑也只輸出允許的鍵，避免舊列或測試植入的值漏出去。

位元組上限是規範 JSON 的 UTF-8 長度 16384。規範方式與 `pm_work_start._json` 相同：`sort_keys`、`ensure_ascii` 為 false、分隔符 `(',', ':')`、不允許 NaN。超過上限是新的 413 `PM_WORK_PROFILE_TOO_LARGE`。E04 的 256 KiB 是 Result 文件的上限，這裡不沿用那個數字。`digest` 是這段 UTF-8 的 SHA-256，64 個小寫十六進位，沒有 `sha256:` 前綴，算法與 `pm_work_start._digest` 相同。

`managed_setup.stage_secret` 的回傳行是 `return {"secret_ref": ref, "kind": body["kind"]}`（`src/bat_agent_connector/managed_setup.py:232`）。profile 連這個 `secret_ref` 也不存。credential 的值不進文件、回應、事件或日誌。

```sql
    operation_id TEXT NOT NULL UNIQUE,
    created_at REAL NOT NULL,
    UNIQUE (profile_id, revision)
);
CREATE INDEX IF NOT EXISTS work_profiles_workspace
    ON work_profiles(workspace_id, profile_id, revision);
CREATE INDEX IF NOT EXISTS work_profiles_cursor
    ON work_profiles(workspace_id, sequence);
CREATE TRIGGER IF NOT EXISTS work_profiles_update_immutable
BEFORE UPDATE ON work_profiles
BEGIN SELECT RAISE(ABORT, 'work profile history is immutable'); END;
CREATE TRIGGER IF NOT EXISTS work_profiles_delete_immutable
BEFORE DELETE ON work_profiles
BEGIN SELECT RAISE(ABORT, 'work profile history is immutable'); END;
CREATE TABLE IF NOT EXISTS work_profile_defaults (
    sequence INTEGER PRIMARY KEY AUTOINCREMENT,
    workspace_id TEXT NOT NULL,
    profile_id TEXT,
    operation_id TEXT NOT NULL UNIQUE,
    created_at REAL NOT NULL
);

    ON work_profile_defaults(workspace_id, sequence);

BEFORE UPDATE ON work_profile_defaults
BEGIN SELECT RAISE(ABORT, 'work profile default history is immutable'); END;
CREATE TRIGGER IF NOT EXISTS work_profile_defaults_delete_immutable
BEFORE DELETE ON work_profile_defaults
BEGIN SELECT RAISE(ABORT, 'work profile default history is immutable'); END;
```

`work_profiles.operation_id` 唯一，因為一筆 save 只追加它點名的那一個 profile。`work_profile_defaults.operation_id` 也唯一，因為同一筆 save 最多再追加一列預設。`profile_id` 允許 null，表示清掉預設。兩張表的 trigger 都拒絕 UPDATE 與 DELETE。不對「目前預設」做部分唯一索引：歷史列要留下，最新與否只看該 workspace 最大的 `sequence`。

## 3. 寫入路徑

### 3.1 為什麼是一個新的簡單動作

決策 7 只允許兩個新的組合動作，名稱已由 E02 用掉：`work.start` 與未來的 `work.adopt_and_start`。組合的意思是一筆 operation 底下再建立子 operation 或對外送出效果。profile 寫入沒有子 operation，不呼叫 BAT，不呼叫 GitHub，不解析 token。它只在本地 journal 追加修訂。這是一個簡單動作，不是第三個組合動作。實作採用 `pm.work_profile.save`，名稱寫成模組常數。負責人的回覆仍待確認，見 §14。

不能延伸 `setup.host`、`setup.repository` 或 `setup.verification`。它們的 scope 是 `manage`，目標是 host、repository 或空目標，改的是這次安裝的設定與 `config_revision`，不是 PM 成員資格：

現行程式 `src/bat_agent_connector/managed_setup.py:659-668`。

### 3.3 預設的同一筆交易

預設的目前值是 `work_profile_defaults` 裡該 `workspace_id` 最大 `sequence` 的那一列。沒有列，就是沒有預設。該列的 `profile_id` 為 null，或指向的 profile 最新修訂已撤回，讀取時都看成沒有預設，而且不補寫一列去修它。

會追加預設列的請求只有三種。每一種都在同一個 `journal.tx()` 裡，先重讀最新 `sequence`，再寫入點名的那一個 profile 的新修訂，並恰好追加一列預設：

| 請求 | profile 修訂 | 預設列的 `profile_id` |
|---|---|---|
| `make_default: true` | 點名的 profile，`withdrawn` 為 0 | 該 `profile_id` |
| `make_default: false`，而且它就是目前預設 | 點名的 profile | null |
| `withdrawn: true`，而且它就是目前預設 | 點名的 profile，`withdrawn` 為 1 | null |

這三種都要帶 `expected_default_sequence`。它是該 workspace 目前最大的 `sequence`；一列都沒有時必須是 null。清掉之後的「沒有預設」仍是一列，所以期望值是那一列的 `sequence`，不是 null。重讀不符：新的 409 `PM_WORK_PROFILE_DEFAULT_CHANGED`。profile 修訂與預設列都不插入。

其餘請求不寫預設表，也不讀 `expected_default_sequence`：

- 省略 `make_default`。
- `make_default: false`，而且點名的 profile 不是目前預設。
- 撤回一個不是目前預設的 profile。

這些請求不建立其他 profile 的修訂。Q 成為預設時，P 的最大 `revision` 與 `digest` 保持不變，§5 釘住的 P 仍可 admission。

不允許 `withdrawn: true` 同時 `make_default: true`，那是 `INVALID_PARAMS`。競態只靠這次重讀。不事後改已寫入的列，trigger 也不允許。

### 3.4 撤回之後的讀取

最新列 `withdrawn=1` 時：

- 列表不包含它，`count` 也不算它。
- 單筆 GET 與 readiness 對成員回 404，新碼 `PM_WORK_PROFILE_WITHDRAWN`。回應沒有文件。
- 歷史列留在表裡，v1 沒有歷史列表路由。撤回那筆 operation 的結果可以寫 `withdrawn: true`，成員仍可從既有的 operation 讀到這筆回執。
- 隨後的 GET 仍是 404。讀取無伺服器快取；每次都先查成員與撤回。晚到的回應不能把已撤回的列、計數或詳情放回來。
- 成員資格消失時，沿用 `require_member` 的 404 `NOT_FOUND`。該 workspace 的 profile 一起從這位呼叫者的讀取消失，不逐筆留詳情。

未知的 `profile_id`，對已經是成員的呼叫者，是既有的 404 `NOT_FOUND`。不另造 `PM_WORK_PROFILE_NOT_FOUND`。

save、preview 與 admission 的順序是：先成員資格，再識別形狀，再未知（404 `NOT_FOUND`），再撤回，最後才是修訂與 digest。撤回一定追加一筆修訂。最新列已撤回時，持有較舊 pin 或過期 `expected_revision` 的呼叫者得到撤回碼，而不是修訂衝突或 `PM_WORK_PROFILE_CHANGED`。admission 拿舊 pin 是 409 `PM_WORK_PROFILE_WITHDRAWN`。preview 是 404 `PM_WORK_PROFILE_WITHDRAWN`。save 帶過期的 `expected_revision` 是 409 `PM_WORK_PROFILE_WITHDRAWN`。

### 3.5 錯誤碼

| 碼 | HTTP | 新或既有 | 何時 |
|---|---|---|---|
| `NOT_FOUND` | 404 | 既有 | 非成員、未知 workspace、成員查未知 profile。非成員的訊息維持 workspace 不存在。 |
| `FORBIDDEN` | 403 | 既有 | 成員角色或 scope 不夠。 |
| `INVALID_PARAMS` | 422 | 既有 | 未知鍵、禁止鍵、空字串、`withdrawn` 與 `make_default` 同時為 true、草稿文字、返回網址。profile 的 goal 不是 null，而 preview 省略 `delivery` 或送成 JSON null，也是這個既有碼；訊息點名該 goal。 |
| `INVALID_TARGET` | 422 | 既有 | target 不是恰好 `{workspace_id}`。 |
| `REPOSITORY_NOT_BOUND` | 403 | 既有 | 三鍵不在 `repository_sync.capabilities`。 |
| `IDEMPOTENCY_CONFLICT` | 409 | 既有 | 同一個 key 配不同 body。 |
| `PM_WORK_PROFILE_REVISION_CONFLICT` | 409 | 新 | 最新列未撤回，而 `expected_revision` 不是最新。先看撤回。不重用 `CONFIGURATION_CHANGED`、`PM_PACKAGE_VERSION_CONFLICT` 或 `PM_BAT_BINDING_CHANGED`。前兩個屬於安裝修訂與 package，後者屬於 PM 分析綁定。 |
| `PM_WORK_PROFILE_DEFAULT_CHANGED` | 409 | 新 | `expected_default_sequence` 不是該 workspace 預設表的最新 `sequence`。profile 修訂與預設列都不插入。 |
| `PM_WORK_PROFILE_BUDGET_UNSUPPORTED` | 422 | 新 | `budget_policy_ref` 不是 null。 |
| `PM_WORK_PROFILE_TOO_LARGE` | 413 | 新 | 文件超過 16384 位元組。既有的 413 形狀見 `PM_PACKAGE_READ_TOO_LARGE`。 |
| `PM_WORK_PROFILE_WITHDRAWN` | 404 或 409 | 新 | 讀取與 readiness 用 404。對已撤回 profile 再 save，以及 §5 的 preview 與 admission，用上面的順序：最新列已撤回就是這個碼，即使呼叫者拿的是較舊的修訂。save 與 admission 用 409，preview 用 404。 |
| `PM_WORK_PROFILE_CHANGED` | 409 | 新 | §5。最新列未撤回，而 preview 釘住的修訂已不是最新，或 digest 不符。不另造 digest 專用碼。錯誤與其他 `OperationError` 一樣只有碼與訊息。訊息用普通話寫出目前的修訂號，不帶文件，也不在信封上加 `revision` 欄。客戶端要目前的修訂，再以單筆 GET 讀一次。 |
| `PM_WORK_PROFILE_TARGET_MISMATCH` | 409 | 新 | §5。preview 查三個 `code_target` 鍵，以及有送出但與非 null goal 不同的 `delivery`。省略 `delivery` 不是這個碼。admission 才查 `agent`、`model`、`delivery` 與那三鍵。 |

reason 字串不是 `OperationError` 碼，列在 §4。它們可以出現在 200 的 readiness 裡。

## 4. Readiness 讀取

### 4.1 路由與誰可以讀

| 讀取 | HTTP | RPC 與 MCP | Scope |
|---|---|---|---|
| 列表 | `GET /api/v1/pm/workspaces/{workspace_id}/work-profiles` | `pm_work_profiles_list` | `observe`，任一成員含 reader |
| 單筆 | `GET /api/v1/pm/workspaces/{workspace_id}/work-profiles/{profile_id}` | `pm_work_profile_get` | 同上 |
| readiness | `GET /api/v1/pm/workspaces/{workspace_id}/work-profiles/{profile_id}/readiness` | `pm_work_profile_readiness_get` | 同上 |

寫入沒有自己的 URL，走既有的 `("POST", r"/api/v1/operations", self.create_operation, None)`（`src/bat_agent_connector/api_v1.py:355`）。

列表的 query 只有 `limit` 與 `cursor`。`limit` 預設 50，最大 100。`profiles` 是該 workspace 每一筆最新且未撤回的 profile，依該筆最新修訂的 `sequence` 由小到大排列，不把預設提前。預設只出現一次，就在它自己的位置，`is_default` 是 true。`default_profile_id` 是回應的新鍵，每一頁都有：目前預設那筆 profile 的最新修訂未撤回時，它是該 `profile_id`，否則 null。客戶端若要在翻到那一頁之前先看預設的欄位，用單筆 GET 讀它。`count` 仍是同一快照裡最新且未撤回的 profile 總數，不是這一頁的長度。還有後續列時，`next_cursor` 是這一頁最後一列的 `sequence`，否則 null。帶了 `cursor` 的請求只列 `sequence` 大於 cursor 的列。兩次翻頁之間，一筆 profile 若又追加了修訂，可以帶著新修訂再出現一次；不會有列被跳過。成員資格、`default_profile_id`、列、`count` 與每一列的 `actor` 來自同一個讀取點，沿用 `pm_source_reads.scope`（`src/bat_agent_connector/pm_source_reads.py:63-125`）。未知的 query 鍵，包含 `draft`、`prompt`、`from`、`return_url`，是 `INVALID_PARAMS`。

`is_default` 不是表上的欄。列表與單筆在讀取時計算：該 profile 的最新修訂未撤回，而且預設表最新列的 `profile_id` 等於它，才是 true。否則 false。

單筆與列表項目只投影允許的顯示欄：`profile_id`、`revision`、`digest`、`is_default`、`agent`、`model`、`delivery_goal`、`repository`、`host`、BAT `workspace_id`、`created_at`、`operation_id`，以及該筆 operation 的 `actor`。不含 actor 的 scopes，不含 `url`、`fingerprint`、token 或 `secret_ref`。

A01 要讓人從清單挑一筆綁定，不必先背 `profile_id`。顯示欄因此包含 agent、repository、邏輯 host 名與 BAT workspace。

### 4.4 六個狀態

現在值按下表第一個符合的條件決定。reason 使用既有碼，或標成 reason 字串。reason 字串不是新的 `OperationError`。

2026-10-22 來源範圍修正：Work 透過
`Inventory.current_source_evidence(self, host: str) -> CurrentSourceEvidence`
取得 `observation`、`discovery_bodies` 及 `reason`。下表的主機觀測與 discovery

Inventory 對 URL、fingerprint、profile 計算，不另建來源識別。主機名稱或連接埠相同
不能證明來源相同。來源不符時，即使尚未 refresh，`discovered`／`can_observe`
也回 `unknown`／`DISCOVERY_SCOPE_CHANGED`（其他既有能力阻擋仍優先），不帶目前
觀測的 evidence 或期限；未有 discovery 時沿用原未驗證路徑。先前來源的列仍留在
Inventory 歷史，但不供目前的 Work 狀態使用。

Setup 的 `_connection_state` 與 Work 共用此 accessor，Setup 只取其 `observation`。
這是行為不變的重構：原 join 從 observation 出發；accessor 從 discovery 左連
observation，任一列缺少時，Setup 都取不到 observation 證據。Setup 仍先比較兩份
設定物件的 `same_source`，並保留 live-client shortcut、`stale_after_s` 時效規則
與 `connected`／`unreachable`／`checking` 映射。

若切換 profile 後又恢復完全相同的 binding，未過期的原證據可再次適用；讀取不更新
原觀測時間或期限。已過期的證據只能作為 `verified` 歷史。這項修正不改 refresh 的
`DISCOVERY_SCOPE_CHANGED` 拒絕流程、不執行 probe 或寫入，也不改 picker 的
workspace／profile／revision／digest fences、action admission 或 60 秒顯示規則。

### 4.5 最小缺口

只給一個 `smallest_gap`。依序取第一個符合的：

1. 綁定三鍵不在 `capabilities`：`fix.action` 是 `setup.repository`。
2. host 名稱不在 fleet 設定：`fix.action` 是 `setup.host`。這是主機還沒設定，不是把一台本機 Git 的 host 改寫成 SSH。
3. `status.reason` 是 `local_git_not_enabled`、`local_git_platform_unsupported` 或 `local_git_tools_missing`：`fix` 是 null，`fallback` 是 null，reason 就是該字串。說明文字要求改用 Linux BAT 上已經設定好的 SSH host。不提供「改走本機 SSH」或代為改寫 `git` 的動作。
4. `ssh_alias_missing`、token 不存在、`orchestrate_enabled` 為 false，或沒有 `managed_roots`：`fix.action` 是 `setup.host`。
5. `git_execution_location_changed`：`fix` 是 null。不建議換執行位置。
6. `host_unreachable` 或 `host_not_refreshed`：`fix` 是 null。顯示 `last_success_at`，沒有則是 null。不主動 ping。
7. `repository.continue` 或後續的 `session.send` 未註冊：`fix` 是 null，reason `action_unavailable`。
8. 以上都沒有，只剩 `unknown`：`smallest_gap` 是 null，`unverified` 列出那些狀態的名字。

`fix` 存在時的形狀是 `{action, route: "POST /api/v1/operations", ui_hash: "#/settings?section=connection"}`。`fallback` 永遠是 null。這個 hash 是既有的連線設定頁，見 `desktop/src/app.js:1858`。伺服器不在 hash 上加 `from`，也不儲存返回位置。

主機不可達時，最小缺口停在第 6 步，不把缺口說成「請登入」。若同時沒有 token，第 4 步會先指向 `setup.host`，因為憑證也是主機設定的一部分；狀態 `signed_in_or_available` 仍寫 `CREDENTIAL_REQUIRED`，文案不說成代理已登出。本機 Git 在第 3 步就停住，即使 token 也缺，也不把人送去把該 host 的 `git` 改成 `ssh`。

沒有 Claude 或 Codex 的登入動作可建議。v1 不提供模型試跑。若以後要試模型，必須是另一個標明費用的動作，不能是這個 GET。

## 7. Scope、可見性與 controller

讀取：`observe`，加上 `require_member` 的任一角色，包含 reader。

## 9. 平台誠實

## EC-1.1：開始前顯示下一輪限制

readiness 增量欄位 `work_follow_up` 只描述 `bat_work_start` 路線：固定該
profile 的 `agent`，`admission_checked` 永遠為 false。沿用既有 Work follow-up
capability：未註冊 `session.send` 是 `unavailable/action_unavailable`；目前 BAT
Codex 路線是 `unavailable/codex_uncorrelated_turn_boundary`；其餘已實作路線
是 `requires_attempt/owned_attempt_required`，並非已允許送出。

這與歷史 `repository.continue` 的 `can_continue_own.verified` 分開。歷史上
成功建立自己的 session，不證明 Work 目標的回合關聯可用。無新增寫入、模型
呼叫、BAT 探測或 schema；HTTP、RPC、MCP 仍讀取同一份 readiness。舊中央
沒有此欄位、格式不符或 agent 不匹配時，客戶端顯示尚未回報，不猜測可用性。

選取設定檔便顯示此說明；切換或撤回來源沿原規則清除。開始按鈕與送出
仍由原 admission、controller、attempt、權限與 final-frame 檢查決定。
本增量不代表 Codex 的其他路線無法接續，也不改變 `codex_supported` 的值。
