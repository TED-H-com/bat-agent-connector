## 1. Profile 是什麼

### 1.1 它不是哪三個既有的 profile

這三個名字已經有別的意思，E01 不重用它們的表、動作或回應：

| 既有名字 | 位置 | 實際意思 |
|---|---|---|
| `pm_profiles` / MCP `pm_profiles_get` | `src/bat_agent_connector/mcp_server.py:582-584`、`src/bat_agent_connector/pm_reads.py:454-455` | 討論用途目錄（idea、planning），不是 coding profile。 |
| `HostConfig.profile_id` | `src/bat_agent_connector/config.py:124`，預設字串是 `"default"` | BAT 連線 profile。`managed_setup.state` 把這個欄與 `url`、`fingerprint`、`token_available` 一起回傳。 |
| PM runtime profile | `src/bat_agent_connector/pm_bat_operations.py:132-151`、`src/bat_agent_connector/pm_native_capabilities.py:8-19` | Connector 上的 PM 分析是否裝得起來。`auth_validity` 固定是未驗證。 |

`tests/test_pm_work_start.py` 的 fixture 使用 `profile_id="prof-1"` 時，指的是 host 設定，不是本文件的 work profile。

新的識別是伺服器指定的 `wpf_` 加 32 個小寫十六進位字元。客戶端不能自選，也不能把 host 的 `profile_id` 填進來。

### 1.2 範圍與綁定

一個 work profile 同時屬於：

1. 一個 PM workspace，識別是 `ws_` 加 32 個十六進位字元，與今天的 PM workspace 相同。
2. 恰好一筆已經寫在安裝裡的 repository 綁定。三個鍵是 `repository`、`host`、BAT `workspace_id`。BAT workspace 是綁定上的字串，不是 PM 的 `ws_` 識別。`tests/test_pm_work_start.py:2215-2219` 的例子是 repository `o/r`、host `h1`、BAT workspace `ws-1`。本文例子只用這種公開占位，不用真實主機名。

三個鍵與 `repository_sync.configured` 要求的目標相同，但是儲存與 readiness **不呼叫** `configured`。`configured` 在綁定不存在時就拒絕，而且還要求 orchestrate、managed root 與 Git runner 可用：

現行程式 `src/bat_agent_connector/repository_sync.py:73-88`。
```python
def configured(ops, target):
    if (set(target) != {"repository", "host", "workspace_id"} or any(not isinstance(v, str) or
            not 1 <= len(v) <= 256 for v in target.values())):
        raise OperationError("INVALID_TARGET", "exact repository, host and workspace_id are required", 422)
    fleet = ops.context["fleet"]
    repo = fleet.config.github.repos.get(target["repository"].lower())
    pair = target["host"], target["workspace_id"]
    if not repo or not repo.sync or pair not in repo.sync.bindings:
        raise OperationError("REPOSITORY_NOT_BOUND", "no explicit repository/host/workspace binding", 403)
    hc = fleet.config.hosts.get(pair[0])
    runner = ops.context.get("git_runner")
    if not hc or not fleet.orchestrate_enabled(pair[0]) or not hc.managed_roots:
        raise OperationError("REPOSITORY_HOST_UNAVAILABLE", "target needs write/orchestrate and a managed root", 403)
    if not runner or not runner.available(pair[0]) or ops.context.get("github") is None:
        raise OperationError("REPOSITORY_HOST_UNAVAILABLE", "GitHub read client and SSH Git runner are required", 409)
    return repo, hc
```

profile 要能先被記下來，再由 readiness 說明缺什麼。儲存時只檢查這三鍵出現在 `repository_sync.capabilities` 的本地清單，以及 repository 以不區分大小寫的方式出現在該 PM workspace 的 `repositories`。`capabilities` 本身只讀設定，不連線：

現行程式 `src/bat_agent_connector/repository_sync.py:196-198`。
```python
def capabilities(ops):
    return [{"repository": r.repository, "host": h, "workspace_id": w, "exact_ref_head_only": True}
            for r in ops.context["fleet"].config.github.repos.values() if r.sync for h, w in r.sync.bindings]
```

PM workspace 的 `repositories` 只在 `pm.workspace.create` 寫入（`src/bat_agent_connector/pm_workspace.py:302-306`）。`pm.workspace.member.set` 不改這份清單（`src/bat_agent_connector/pm_workspace.py:344-346`）。因此：

- 三鍵不在 `capabilities`：沿用既有 `REPOSITORY_NOT_BOUND`（403）。最小缺口指向既有 `setup.repository`。
- repository 不在這個 PM workspace 的清單：這是新的 422 `PM_WORK_PROFILE_REPOSITORY_UNLISTED`。沒有既有動作可以事後把 repository 加進 workspace，所以 `fix` 是 null。不把這件事說成 `setup.repository` 可以修好。

`source_ref` 不放進 profile。E02 的 preview 仍依每一次啟動解析分支與發布頭。

profile 還固定：

| 欄位 | 規則 | 沿用 |
|---|---|---|
| `agent` | 必填，`claude` 或 `codex` | `AGENTS`，見下面 §5 的現行常數 |
| `model` | 字串 1–256，或 null。null 表示沒有指定，也不是已就緒 | `work.start` 今天的 model 就是選填 |
| `delivery_policy_ref` | null，或 `{goal}`，goal 是 `pull_request` 或 `reviewable_changes` | `DELIVERY_GOALS` |
| `budget_policy_ref` | v1 只能是 null。非 null 以新的 422 `PM_WORK_PROFILE_BUDGET_UNSUPPORTED` 拒絕 | 見 §1.4 |

一個 PM workspace 可以有多個 profile。最多一個目前的預設，由欄位 `is_default` 表示，不靠文件裡的旗標。`work.start` 不因為有預設就自動選它。呼叫者要嘛不帶 profile，走今天的 `work.start`；要嘛明確帶 `profile_id` 與修訂。

### 1.3 與 `work.start` 今天的輸入

`work.start` 今天必填 `instruction`、`agent`、`delivery`、`code_target`，選填 `model` 與 `requirement_ids`。`code_target` 四鍵含 `source_ref`。profile 只固定其中的綁定三鍵、agent，以及非 null 的 model 與 delivery。`instruction` 與 `requirement_ids` 仍由每一次啟動自己帶。profile 不取代它們，也不把草稿文字存進文件。

### 1.4 為什麼 v1 不接預算政策

程式裡沒有 coding 用的 budget policy 表。維護政策的 `policy_id`（`pmmp_…`）是另一個領域。`work.start` 的交付詞彙只有 `DELIVERY_GOALS` 那兩個 goal。v1 不把維護政策識別填進 `budget_policy_ref`，非 null 就拒絕。以後若有真正的預算物件，再以新的文件版本接上，不在這份規格假造一個識別。

## 2. 儲存

### 2.1 為什麼不完全照 E00 的欄位清單

E00 §4.2 建議 `work_profiles` 的欄是 `profile_id, workspace_id, revision, document, digest, operation_id, created_at`，唯一鍵 `(profile_id, revision)`。同一節寫明：JSON 不能用來避開身份索引與 withdrawal gate；readiness 的現在值與上次真正驗證分開；不能因為設定存在就當成 ready。

本規格沿用那張表與那些不變量，並補三個欄，理由都來自這條 gate：

- `withdrawn`：撤回必須是列上的值，列表、讀取與 readiness 才能一起拿掉，不能只藏在 JSON。
- `is_default`：一個 workspace 只能有一個目前預設，必須在交易裡重讀欄位，不能只比較 JSON。
- `sequence`：沿用 `pm_work_packages` 的游標方式，給列表分頁，不把修訂編號兼做成全域序號。

`revision` 仍是每個 `profile_id` 自己的正整數，從 1 開始，只增不改。最新一筆是該 `profile_id` 的最大 `revision`。`sequence` 只用於分頁。

### 2.2 文件版本 1

存進 `document` 的是單一 JSON 物件，版本只能是 1。允許的鍵只有：

| 鍵 | 值 |
|---|---|
| `version` | `1` |
| `binding` | `{repository, host, workspace_id}`，三個非空白字串，各 1–256 |
| `agent` | `claude` 或 `codex` |
| `model` | 字串 1–256，或 null |
| `delivery_policy_ref` | null，或 `{goal}` 且 goal 屬於既有的兩個交付 goal |
| `budget_policy_ref` | null。鍵可以省略，省略視同 null |

其他鍵，包含 `default`、`withdrawn`、`source_ref`、`controller_id`、`actor`、`scopes`，都是既有的 `INVALID_PARAMS`（422）。`is_default` 與 `withdrawn` 只放欄位，由參數 `make_default` 與 `withdrawn` 決定，避免文件與欄位各說各話。

下面這些鍵出現在物件樹的任何一層，都是 `INVALID_PARAMS`：`secret_ref`、`token`、`token_ref`、`password`、`authorization`、`credential`、`fingerprint`、`url`、`endpoint`。不掃描字串值裡有沒有 "token" 這個詞，避免把模型名稱誤殺。寫入路徑拒絕它們；讀取路徑也只輸出允許的鍵，避免舊列或測試植入的值漏出去。

位元組上限是規範 JSON 的 UTF-8 長度 16384。規範方式與 `pm_work_start._json` 相同：`sort_keys`、`ensure_ascii` 為 false、分隔符 `(',', ':')`、不允許 NaN。超過上限是新的 413 `PM_WORK_PROFILE_TOO_LARGE`。E04 的 256 KiB 是 Result 文件的上限，這裡不沿用那個數字。`digest` 是這段 UTF-8 的 SHA-256，64 個小寫十六進位，沒有 `sha256:` 前綴，算法與 `pm_work_start._digest` 相同。

`managed_setup.stage_secret` 的回傳行是 `return {"secret_ref": ref, "kind": body["kind"]}`（`src/bat_agent_connector/managed_setup.py:236`）。profile 連這個 `secret_ref` 也不存。credential 的值不進文件、回應、事件或日誌。

下面這段是本規格的提議，`5840f41d` 沒有這張表。實作時放進新模組的 `schema(journal)`，由該模組的 `install` 呼叫，不放進 `task_journal` 的開庫路徑。

```sql
CREATE TABLE IF NOT EXISTS work_profiles (
    sequence INTEGER PRIMARY KEY AUTOINCREMENT,
    profile_id TEXT NOT NULL,
    workspace_id TEXT NOT NULL,
    revision INTEGER NOT NULL,
    withdrawn INTEGER NOT NULL CHECK (withdrawn IN (0, 1)),
    is_default INTEGER NOT NULL CHECK (is_default IN (0, 1)),
    document TEXT NOT NULL,
    digest TEXT NOT NULL,
    operation_id TEXT NOT NULL,
    created_at REAL NOT NULL,
    UNIQUE (profile_id, revision),
    UNIQUE (operation_id, profile_id)
);
CREATE INDEX IF NOT EXISTS work_profiles_workspace
    ON work_profiles(workspace_id, profile_id, revision);
CREATE INDEX IF NOT EXISTS work_profiles_cursor
    ON work_profiles(workspace_id, sequence);
CREATE TRIGGER IF NOT EXISTS work_profiles_update_immutable
BEFORE UPDATE ON work_profiles
BEGIN SELECT RAISE(ABORT, 'work profile history is immutable'); END;
CREATE TRIGGER IF NOT EXISTS work_profiles_delete_immutable
BEFORE DELETE ON work_profiles
BEGIN SELECT RAISE(ABORT, 'work profile history is immutable'); END;
```

不對 `is_default` 做唯一索引。舊修訂會留下當時的 `is_default`，唯一索引會把歷史列也算進去。一個 workspace 同時只有一個預設，改由 §3 的同一筆交易重讀最新列來保證。

`operation_id` 與 `profile_id` 合成唯一，是因為設成預設時，同一筆 operation 可能再追加「前一個預設」的清除修訂。同一 profile 在同一筆 operation 仍只有一列。

## 3. 寫入路徑

### 3.1 為什麼是一個新的簡單動作

決策 7 只允許兩個新的複合動作，名稱已由 E02 用掉：`work.start` 與未來的 `work.adopt_and_start`。複合的意思是一筆 operation 底下再建立子 operation 或對外送出效果。profile 寫入沒有子 operation，不呼叫 BAT，不呼叫 GitHub，不解析 token。它只在本地 journal 追加修訂。這是一個簡單動作，不是第三個複合動作。

不能延伸 `setup.host`、`setup.repository` 或 `setup.verification`。它們的 scope 是 `manage`，目標是 host、repository 或空目標，改的是這次安裝的設定與 `config_revision`，不是 PM 成員資格：

現行程式 `src/bat_agent_connector/managed_setup.py:598-603`。
```python
ACTIONS = [ActionDef("setup.host", "manage", "Configure a verified BAT connection for this installation", _run,
                    _admit("setup.host"), target_keys=("host",), authorize_existing=_authorize_existing),
           ActionDef("setup.repository", "manage", "Bind a verified GitHub repository and BAT workspace", _run,
                    _admit("setup.repository"), target_keys=("repository",), authorize_existing=_authorize_existing),
           ActionDef("setup.verification", "manage", "Configure explicit verification commands for task projects", _run,
                    _admit("setup.verification"), target_keys=(), authorize_existing=_authorize_existing)]
```

`setup.host` 接受的欄位包含 `secret_ref`、`url`、`fingerprint`、`profile_id`、`ssh_alias` 與 `git`（`src/bat_agent_connector/managed_setup.py:262`）。那個 `profile_id` 是 host 連線 profile。把 work profile 塞進這條路徑，會把 PM 成員閘門、追加修訂與安裝 TOML 混成一次寫入。

也不能把寫入放進 `work.start`。沒有 profile 的啟動必須維持今天的參數與 precondition；多一個必填欄位就會改變既有測試。見 §5。

`preferences.models.update` 是個人顯示偏好，scope 是 `observe`，不是 workspace 的 coding 綁定。`pm.workspace.member.set` 只改成員。

建議的動作名稱是 `pm.work_profile.save`。放在 `pm.` 底下，既有的 idempotency 命名空間才會帶上 PM workspace：

```python
    if isinstance(exc, StepFailed | NeedsAttention | OperationError):
        return exc.code
    if isinstance(exc, WriteRefused):
        return "REFUSED"
    if isinstance(exc, BatError):
        return "BAT_ERROR"
    return "INTERNAL"
```

### 3.2 入場

| 項目 | 規則 |
|---|---|
| 註冊 | `ActionDef`，主 scope `manage`，`target_keys=("workspace_id",)`。建立與更新都用這個目標，`profile_id` 放在 params。 |
| Scope | admission 另要 `observe`。不要 `start`。儲存 profile 不是啟動。 |
| 成員 | `require_member(..., write=True)`。reader 得到既有的 403 `FORBIDDEN`。非成員與未知 workspace 得到既有的 404 `NOT_FOUND`，訊息與今天一樣是 workspace 不存在，而且在查 profile 之前就回。 |
| 管理員 | 沿用 `require_member` 既有的 admin 覆寫，不新增 scope。 |
| 建立 | 省略 `profile_id`，`expected_revision` 必須是 null。伺服器產生 `wpf_` 識別，`revision` 為 1。 |
| 更新 | params 帶 `profile_id` 與 `expected_revision`。`expected_revision` 必須等於目前最新修訂，否則新的 409 `PM_WORK_PROFILE_REVISION_CONFLICT`，不插入。 |
| 撤回 | 同一個動作，`withdrawn: true`。再追加一筆，不刪歷史。已撤回的最新列不能再被這個動作更新，回新的 409 `PM_WORK_PROFILE_WITHDRAWN`，避免把撤回的 profile 救回來。 |
| 預設 | 參數 `make_default` 是布林。省略時，建立為 false，更新則沿用該 profile 目前的 `is_default`。 |
| 外部呼叫 | 不呼叫 BAT、GitHub、`resolve_token`。不把 token 放進文件。 |

`require_member` 的現行拒絕：

### 3.3 預設的同一筆交易

`make_default: true` 時，admission 在同一個 `journal.tx()` 裡重讀該 workspace 目前最新且 `is_default=1`、`withdrawn=0` 的 profile。

- 呼叫者另帶 `expected_default_revision`。沒有目前預設時，這個值必須是 null。
- 重讀結果與 `expected_default_revision` 不符：新的 409 `PM_WORK_PROFILE_DEFAULT_CHANGED`，兩筆都不插入。
- 目前預設是另一個 profile：同一筆 operation 再追加那個 profile 的清除修訂，文件與 digest 原樣複製，`is_default` 改為 0，`revision` 加 1。然後才寫入本次 profile 的新修訂且 `is_default` 為 1。
- `make_default: false` 作用在目前預設上：這筆新修訂的 `is_default` 為 0，workspace 暫時沒有預設。同樣要帶對的 `expected_default_revision`。
- `make_default: false` 作用在不是預設的 profile 上：不動其他 profile。
- 撤回目前預設：新修訂 `withdrawn=1` 且 `is_default=0`。不允許 `withdrawn: true` 同時 `make_default: true`，那是 `INVALID_PARAMS`。

不使用第二張表。競態靠這次重讀與 `expected_default_revision`，不靠事後修補。

### 3.4 撤回之後的讀取

最新列 `withdrawn=1` 時：

- 列表不包含它，`count` 也不算它。
- 單筆 GET 與 readiness 對成員回 404，新碼 `PM_WORK_PROFILE_WITHDRAWN`。回應沒有文件。
- 歷史列留在表裡，v1 沒有歷史列表路由。撤回那筆 operation 的結果可以寫 `withdrawn: true`，成員仍可從既有的 operation 讀到這筆回執。
- 隨後的 GET 仍是 404。讀取無伺服器快取；每次都先查成員與撤回。晚到的回應不能把已撤回的列、計數或詳情放回來。
- 成員資格消失時，沿用 `require_member` 的 404 `NOT_FOUND`。該 workspace 的 profile 一起從這位呼叫者的讀取消失，不逐筆留詳情。

未知的 `profile_id`，對已經是成員的呼叫者，是既有的 404 `NOT_FOUND`。不另造 `PM_WORK_PROFILE_NOT_FOUND`。

### 3.5 錯誤碼

| 碼 | HTTP | 新或既有 | 何時 |
|---|---|---|---|
| `NOT_FOUND` | 404 | 既有 | 非成員、未知 workspace、成員查未知 profile。非成員的訊息維持 workspace 不存在。 |
| `FORBIDDEN` | 403 | 既有 | 成員角色或 scope 不夠。 |
| `INVALID_PARAMS` | 422 | 既有 | 未知鍵、禁止鍵、空字串、`withdrawn` 與 `make_default` 同時為 true、草稿文字、返回網址。 |
| `INVALID_TARGET` | 422 | 既有 | target 不是恰好 `{workspace_id}`。 |
| `REPOSITORY_NOT_BOUND` | 403 | 既有 | 三鍵不在 `repository_sync.capabilities`。 |
| `IDEMPOTENCY_CONFLICT` | 409 | 既有 | 同一個 key 配不同 body。 |
| `PM_WORK_PROFILE_REVISION_CONFLICT` | 409 | 新 | `expected_revision` 不是最新。不重用 `CONFIGURATION_CHANGED`、`PM_PACKAGE_VERSION_CONFLICT` 或 `PM_BAT_BINDING_CHANGED`。前兩個屬於安裝修訂與 package，後者屬於 PM 分析綁定。 |
| `PM_WORK_PROFILE_DEFAULT_CHANGED` | 409 | 新 | 預設在重讀時已經換人。 |
| `PM_WORK_PROFILE_BUDGET_UNSUPPORTED` | 422 | 新 | `budget_policy_ref` 不是 null。 |
| `PM_WORK_PROFILE_TOO_LARGE` | 413 | 新 | 文件超過 16384 位元組。既有的 413 形狀見 `PM_PACKAGE_READ_TOO_LARGE`。 |
| `PM_WORK_PROFILE_REPOSITORY_UNLISTED` | 422 | 新 | repository 不在該 PM workspace 的清單。 |
| `PM_WORK_PROFILE_WITHDRAWN` | 404 或 409 | 新 | 讀取與 readiness 用 404。對已撤回 profile 再 save，以及 §5 的 admission，用 409，因為那是拒絕一次已審查的寫入或啟動。 |
| `PM_WORK_PROFILE_CHANGED` | 409 | 新 | §5。preview 釘住的修訂已不是最新，或 digest 不符。不另造 digest 專用碼。回應帶目前的 `revision`，不帶文件。 |
| `PM_WORK_PROFILE_TARGET_MISMATCH` | 409 | 新 | §5。呼叫者的綁定三鍵、agent，或非 null 的 model、delivery 與該修訂不一致。 |

reason 字串不是 `OperationError` 碼，列在 §4。它們可以出現在 200 的 readiness 裡。

### 4.5 最小缺口

只給一個 `smallest_gap`。依序取第一個符合的：

1. 綁定三鍵不在 `capabilities`：`fix.action` 是 `setup.repository`。
2. host 名稱不在 fleet 設定：`fix.action` 是 `setup.host`。這是主機還沒設定，不是把一台本機 Git 的 host 改寫成 SSH。
3. `status.reason` 是 `local_git_not_enabled`、`local_git_platform_unsupported` 或 `local_git_tools_missing`：`fix` 是 null，`fallback` 是 null，reason 就是該字串。說明文字要求改用 Linux BAT 上已經設定好的 SSH host。不提供「改走本機 SSH」或代為改寫 `git` 的動作。
4. `ssh_alias_missing`、token 不存在、`orchestrate_enabled` 為 false，或沒有 `managed_roots`：`fix.action` 是 `setup.host`。
5. `git_execution_location_changed`：`fix` 是 null。不建議換執行位置。
6. `host_unreachable` 或 `host_not_refreshed`：`fix` 是 null。顯示 `last_success_at`，沒有則是 null。不主動 ping。
7. `repository.continue` 或後續的 `session.send` 未註冊：`fix` 是 null，reason `action_unavailable`。
8. 以上都沒有，只剩 `unknown`：`smallest_gap` 是 null，`unverified` 列出那些狀態的名字。

`fix` 存在時的形狀是 `{action, route: "POST /api/v1/operations", ui_hash: "#/settings?section=connection"}`。`fallback` 永遠是 null。這個 hash 是既有的連線設定頁，見 `desktop/src/app.js:1858`。伺服器不在 hash 上加 `from`，也不儲存返回位置。

主機不可達時，最小缺口停在第 6 步，不把缺口說成「請登入」。若同時沒有 token，第 4 步會先指向 `setup.host`，因為憑證也是主機設定的一部分；狀態 `signed_in_or_available` 仍寫 `CREDENTIAL_REQUIRED`，文案不說成代理已登出。本機 Git 在第 3 步就停住，即使 token 也缺，也不把人送去把該 host 的 `git` 改成 `ssh`。

沒有 Claude 或 Codex 的登入動作可建議。v1 不提供模型試跑。若以後要試模型，必須是另一個標明費用的動作，不能是這個 GET。

## 7. Scope、可見性與 controller

讀取：`observe`，加上 `require_member` 的任一角色，包含 reader。

寫入：`observe` 與 `manage`，加上 `require_member(..., write=True)`，所以是 owner 或 contributor。reader 是 403 `FORBIDDEN`。非成員是 404 `NOT_FOUND`，沒有 profile 文件。

不另設名為 admin 的 scope。既有的 `principal.admin` 覆寫停留在 `require_member` 裡。

controller 在 Work 第一次啟動時固定。`require_work_controller` 拒絕另一個 controller 接手已經有 attempt 的 Work，碼是既有的 `PM_WORK_CONTROLLER_CONFLICT`（`src/bat_agent_connector/pm_work_start.py:192-200`）。比對的是 `server_id` 與 `controller_id`。

現行程式 `src/bat_agent_connector/controller_authority.py:108-113`。

```python
def same_controller(left, right) -> bool:
    try:
        left, right = _validated(left), _validated(right)
    except ResourceReadOnly:
        return False
    return (left["server_id"], left["controller_id"]) == (right["server_id"], right["controller_id"])
```

profile 文件沒有 `controller_id`、`actor` 或 `scopes`。儲存 profile 不寫 `work_attempts`，也不呼叫 `require_work_controller`。任何符合寫入資格的成員都可以儲存 workspace 的 profile；這不把 Work 的 controller 轉給他。帶著 profile 的 `work.start` 仍執行今天的 `controller_authority.binding(..., pm_workspace_id=wid)` 與 `require_work_controller`。profile 也不授權對 manual、foreign 或 unknown session 送出、恢復或停止。

## 9. 平台誠實

R1 的客戶端是 Web、Windows Tauri 與 Mac Tauri，連到一台已就緒的 Linux BAT。profile 不記錄瀏覽器或桌面 OS 當作執行位置。執行位置是 BAT host，不是客戶端 OS。

本機 Git 維持不可用。§4 引用的 `_readiness` 不會因為呼叫者在 Linux 就把 `local` 改成可用。不提供 local 到 SSH 的 fallback，也不在文案裡建議把這台 host 的 transport 改掉。Windows 的 reason 維持 `local_git_platform_unsupported`，其他平台維持 `local_git_not_enabled`，工具不齊時維持 `local_git_tools_missing`。這三個字串已在 `LOCAL_GIT_REASONS`（`src/bat_agent_connector/host_git.py:20`）。

UI 不得在只有 coding route 的某個狀態看起來可用時，顯示 PM 已就緒。也不得在 `pm_analysis.pm_ready` 為 true 時，顯示寫程式路線已就緒。兩塊的標題分開：

| 語言 | coding 區塊 | PM 區塊 |
|---|---|---|
| en | Coding route | PM analysis |
| zh-TW | 寫程式路線 | PM 分析 |

`coding_route_ready` 為 true 且 `pm_ready` 為 false 時，句子是：

- zh-TW：寫程式路線已就緒。PM 分析尚未就緒。
- en：The coding route is ready. PM analysis is not ready.

只有 PM 是 `pm_ready` 時：

- zh-TW：PM 分析已就緒。這不是寫程式路線已就緒。
- en：PM analysis is ready. This is not a ready coding route.

以 §4 的規則，`can_start_own` 的現在值不會是 `ready`，所以第一句在這次 GET 不會出現。把它寫進契約，是為了以後若有明確的執行檢查，UI 仍不能把兩塊合成一個「已就緒」。
