## 1. 看板 Work 檢視「成果」（Part A）

### 1.1 畫面位置與取代規則（Placement & Replacement）
- **位置**：位於看板 Work Inspector（`pm-kanban.js` + `pm-work-inspector.js`），排列於 `[data-work-section="start"]` 正下方、`[data-work-section="blocker"]`／`delivery`／`details` 正上方。
- **能力閘門與替換**：當 workspace capability 宣告 `features.pm_workspaces.work_attempt_results`（`version: 1`）且已啟用 Work Start 時，原本靜態的「成果」區塊（v1.2 僅顯示歷史 evidence snapshot 或無成果提示）由動態 Attempt Result 面板（`workResultPanel`）取代；若無此 capability 或最新 Attempt 尚未建立 session，則維持乾淨折疊或原靜態結構，絕不顯示假資料或偽造 0 值。

### 1.2 純讀取與資料庫邊界（Read-Only DB Access）
- **0 次 BAT IPC**：Part A 嚴格只呼叫 `GET /pm/workspaces/{ws}/work-attempts/{att}/result`，此為 Connector 本地資料庫之有界投影（0 次 BAT IPC、0 次 DB 寫入、不發出 `api_events`）。
- **禁止提前呼叫 `/changes` 與 `/diff`**：兩者皆會發起 Fleet/BAT IPC 呼叫；Part A 絕不自動觸發，完整檔案清單與 diff 檢視保留至 Part B 在使用者明確點擊時按需載入。

### 1.3 刷新與事件通知規則（Refresh Rules）
- **事件驅動更新**：當收到 `work.attempt.result_recorded` 或該 Attempt 相關之 `api_events` 時，自動發起背景讀取；若正在讀取中則保留最新事件序號待完成後補讀一次（single-flight coalescing）。
- **保留展開狀態**：各區塊（如歷史回合 `results` 清單、變更檔案清單、Details 原始資料）之 `<details>` 展開／收合狀態在資料重整與事件輪詢時完整保留，不因重新渲染而意外關閉。

### 1.4 狀態分離與誠實揭露（State Separation & Honest Data）
- **狀態分離**：模型自述（`self_reported`，如 `claimed_done`）、驗證（`verification`）、審閱（`review_decision`）、需求驗收（`acceptance`）、PR 與部署各自獨立呈現；代理自述「表示已完成」永遠標記為「未經驗證」，絕不視為驗證通過或需求已驗收。
- **未知誠實揭露**：BAT 未提供退出碼（`exit_code: "unknown"`）與耗時皆如實顯示「未知」；BAT `git:status` 空陣列標記為「BAT 無法證明工作樹沒有未提交的修改」，絕不宣稱工作區為乾淨（clean）或未修改為 0。
- **退出碼與原因**：程序退出碼維持「未知（未由 BAT 提供）」；已知原因（如 `bat_unreachable`、`bat_empty_status_not_clean_proof`）在地化顯示，未識別之字串保留於 Details。

### 1.5 Part B 擴充接縫（Part B Seams）
- **按需變更讀取**：Part B 將於成果面版新增「載入即時變更（Load live changes）」按鈕，連線 `/changes` 取得即時 worktree 差異與完整檔案清單。
- **逐檔 Diff 檢視**：針對單一檔案與指定 commit 提供「查看差異（View diff）」互動彈窗或抽屜，連線 `/diff`（帶有界 256 KiB 限制）。
- **操作導引與後續動作**：依 `next_allowed_actions` 接上 `session.send` 追加輸入、`github.pr.publish` 發布 PR 與品質審閱等動作入口。
