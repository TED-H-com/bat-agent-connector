# v1.3 E02（Slice P3）：`work.start` 複合動作規格

本文件定義 `work.start`（`docs/product/v1.3-closed-loop-plan.md` §7.1–§7.4、§9.1–§9.2、§11.3；`docs/design/v1.3-e00-baseline.md` §2 F4/F5、§3.1–§3.3、§4.1–§4.3、§10.2 P3/P6），滿足驗收案例 `UX-A12`–`UX-A14`、`UX-A19` 與 `A05`–`A08`。

## 1. 最終契約（Target、Params、Preconditions、Scopes）

- **Action 註冊**：`ActionDef("work.start", "start", "Start one bound Work item in its own managed BAT worktree and session", _run, _admit, ("workspace_id", "work_item_id"), authorize_existing=_authorize_existing)`。
- **權限與角色（Scopes & Membership）**：
  - 主 scope 為 `start`；admission、既有操作查詢（`_authorize_existing`）與復原執行（`_current_principal`）皆須同時具備 `observe`、`manage`、`start` 三項 scopes，且呼叫者須為該 PM workspace 之寫入成員（`pm_workspace.require_member(ops.db, principal, workspace_id, write=True)`）。不新增獨立「work admin」權限。
  - `_current_principal` 於每個子步驟前重新驗證原始 `actor` 仍持有未撤銷之有效憑證、寫入成員資格，以及 `controller_authority.same_controller(current, saved_controller)`。
- **Target**：`{"workspace_id": "ws_<32hex>", "work_item_id": "wi_<20hex>"}`。Work 須已存在於該 workspace（`pm_evidence.work_row`）並歸屬有效 PM project；從採納提案建立 Work 屬下一切片 `work.adopt_and_start`。
- **Params（僅含使用者意圖，不含內部 ID）**：
  - `instruction`：必填，非空白字串（上限 4,000 字元）。
  - `agent`：必填，`"claude"` 或 `"codex"`；`model`：選填，非空白模型識別字串（於 E01 Execution Profiles 落地前顯式指定）。
  - `delivery`：必填，`"pull_request"` 或 `"reviewable_changes"`。
  - `requirement_ids`：選填，1–50 個已採納計畫（`pm_plan_accepted`）中之 requirement IDs。當 Work 尚未綁定至目前 `accepted_revision_id` 時必填；若已綁定則可省略，若提供須與既有綁定一致。
  - `code_target`：選填，`{repository, host, workspace_id, source_ref}`。省略時，伺服器盤點該 workspace 已設定且可用之程式碼目標：僅當**恰好唯一**候選存在時自動選取；若為 0 或多個候選，立即以 `PM_WORK_START_CODE_TARGET_MISSING` 或 `PM_WORK_START_CODE_TARGET_AMBIGUOUS`（附 `details.candidates`）拒絕，絕不猜測（計畫 §7.2、`UX-A12`、`A05`）。
- **Preconditions（固定已審閱基準）**：
  - `expected_work_item_fingerprint`：Work 目前之 SHA-256 指紋（`work_items._fingerprint`）。
  - `expected_scope_revision_id`：目前 `pm_plan_accepted.accepted_revision_id`。
  - `expected_binding_id`：Work 目前之 `pm_work_bindings.binding_id`（未綁定時為 `null`）。
  - `expected_previous_package_id`：Work 目前最新 `pm_work_packages.package_id`（無套件時為 `null`）。
  - `expected_repository_id`、`expected_binding_digest`（及選填 `expected_source_sha`）：由 `repository_sync.source_preview` 驗證之程式碼基準。
  - 完整 admission 快照（含 `composition_profile: "work_start_thin_v1"`、`controller_authority`、解析後 `code_source`、`predecessor_attempt_id` 與子操作預期摘要）僅寫入不可變之 `operations.admission_binding["work_start"]`，不放入 `params`。

## 2. 子操作槽位（Child Slots）、固定鍵與 Authority Anchor

每個子操作於執行前先在不可變表 `pm_work_start_children` 寫入固定槽位與 `operation_id`，並附 `external_refs={"work_start_parent": {"operation_id": parent_id, "slot": slot}}`：

| Ordinal | Slot | 子動作（Action） | 固定 Idempotency Key | 觸發條件與責任 |
|---:|---|---|---|---|
| 0 | `bind` | `pm.work.bind` | `work-start:{parent_id}:bind` | 僅當 Work 尚未綁定至 `expected_scope_revision_id` 時建立並執行。 |
| 1 | `package` | `pm.work_package.create` | `work-start:{parent_id}:package` | 若最新套件已符合目前採納範圍、`binding_id`、`code_source` 與 `delivery` 則直接重用（`package_reused=true`）；否則由伺服器組合決定性薄套件。 |
| 2 | `handoff` | `repository.continue` | `work-start:{parent_id}:handoff` | 帶入 `pm_package_ref`、`pm_code_basis`、`prompt=instruction`、`work_item_id`，建立 Work 專屬受管 worktree 與 BAT session（同 `desktop/src/pm-package-handoff.js` 之 `handoffParams`）。 |

**Attempt 映射與 Authority Anchor 寫入時機（E00 §4.2）**：
- E00 §4.2 規定 `work_attempts.origin_id` 為 `handoff` 子操作 ID（僅於建立 `handoff` 子操作時產生），同時要求首次 admission 交易即固定 Work 的原 controller authority，避免啟動失敗或外部證據變更後換手 controller。
- 因此採用雙層不可變錨定：
  1. **首次 admission 交易（`operations.create` 內）**：同步寫入 `pm_work_controllers(workspace_id, work_item_id, controller_id, server_id, first_operation_id, created_at)`（若該 Work 尚無紀錄）並檢核 `controller_authority` 一致性。即使 `work.start` 在建立 `handoff` 前失敗，Work 的 controller 歸屬亦已於首次 admission 交易永久鎖定。
  2. **`handoff` 子操作建立之本地交易（`ctx.effect("work.start.handoff")`）**：在任何外部 Git/BAT 副作用發生前，於同一 SQLite 交易內同時建立 `repository.continue` 子操作、`pm_work_start_children(slot='handoff')` 與不可變之 `work_attempts` 列（`attempt_id="att_"+parent_id[3:]`、`origin_kind='operation'`、`origin_id=handoff_op_id`、`start_operation_id=parent_id`）。
- **Work 讀取串接已啟動 Session**：`repository.continue` 首步本地效果已寫入 `work_item_links(kind='operation', ref=handoff_op_id)`。於 `work_items.STARTS_SESSION` 加入 `"repository.continue"`，使 `work_item_get` 與 `work_item_results` 直接透過既有 `operation` 連結解析 `{host, session_id}` 與對話紀錄，不新增重複 link kind。

## 3. 決定性薄套件組合規則（`work_start_thin_v1`）

不呼叫任何模型（計畫 §7.3、`A06`），由伺服器根據已採納計畫（`pm_plan_accepted`）與 `code_source` 決定性產生 `pm.work_package.create` 文件：
- `requirements`：綁定之 `requirement_ids`；`source_refs`：`[]`（無獨立規格檔引用）。
- `code_source`：`{repository, host, workspace_id, source_ref, source_sha, repository_id, binding_digest}`。
- `design`：`{"status": "not_applicable", "text": "Thin package composed by work.start (work_start_thin_v1); standalone design document not applicable.", "source_ids": []}`。
- `tasks`：依 `requirement_ids` 順序每項 requirement 產生一筆 task：`key` 為 `req_{idx}_{id}`、`description` 取自已採納計畫 `selected_inputs` 對應需求文字、`requirement_ids=[req_id]`、`depends_on` 映射同套件內依賴需求之 task key、`source_ids=[]`。
- `verification`：依各需求之 `acceptance` 輸入順序每項產生一筆：`key` 為 `ver_{req_idx}_{acc_idx}`、`requirement_id=req_id`、`acceptance_input_ids=[source_input_id]`、`method` 與 `expected_evidence` 取自驗收文字、`source_ids=[]`。
- `delivery`：`{repository, repository_id, base_ref: source_ref, goal: params.delivery}`，且 `migration`、`rollout`、`rollback`、`observation` 皆設為 `{"status": "not_applicable", "text": "Managed by standard work.start delivery policy (work_start_thin_v1)."}`。
- `rationale`：`params["instruction"]`。父操作 `admission_binding` 與 `result` 皆標記 `composition_profile: "work_start_thin_v1"`。

## 4. 階段與復原對照表（Stage & Recovery Table）

父操作 `result` 結構包含 `work_item_id`、`stage`、`composition_profile`、`binding_id`、`package_id`、`package_reused`、`handoff_operation_id`、`attempt_id`、`session`（`{host, session_id}` 或 `null`）與 `child_operation_ids`（`UX-A13`、`UX-A14`、`UX-A19`、`A07`、`A08`）：

| 步驟 / 階段（Stage Facet） | 副作用前保存之身分（Identity Saved Before Effect） | 成功行為（Success） | 可見失敗表現（Visible Failure） | 僅續接未完成部分（Resume Only Unfinished Part） |
|---|---|---|---|---|
| **Admission** (`accepted`) | `operations` 列、`admission_binding`、`pm_work_controllers` 錨點、`(workspace_id, idempotency_key)` | 回傳固定 `operation_id` 與 `attempt_id` 預告 | 條件不符以 `409/422` 拒絕，0 子操作、0 副作用 | 相同 `idempotency_key` 直接重播原 `operation_id` 與結果 |
| **1. Bind** (`preparing`) | `pm_work_start_children(slot='bind', operation_id)` 與 `request_digest` | 取得或確認 `binding_id`，前進至套件步驟 | 子操作終態非成功時父轉 `needs_attention` (`PM_WORK_START_CHILD_STOPPED`) | 重啟或 `resume` 由 `pm_work_start_children` 找回原 `bind` 子操作；已成功則跳過 |
| **2. Package** (`package_prepared`) | 重用既有 `package_id`；或寫入 `pm_work_start_children(slot='package', operation_id)` | 固定 `package_id`、`package_reused`，持久化 `stage='package_prepared'` | 子操作失敗時父轉 `needs_attention`；未建立 handoff 或 worktree | 已成功之 `package` 子操作直接讀取其 `package_id`，絕不建立第二份 package |
| **3. Handoff & Attempt** (`starting` / `start_unknown` / `started` / `start_failed`) | 同一本地交易寫入 `pm_work_start_children(slot='handoff')` 與 `work_attempts(attempt_id, origin_id=handoff_op_id)` | 子操作執行中為 `starting`；成功後解析 `{host, session_id}`，父完成並標記 `stage='started'` | 子操作 `uncertain` 時父維持等待並呈報 `stage='start_unknown'`；子操作確定失敗時父轉 `needs_attention` (`PM_WORK_START_HANDOFF_FAILED`)，保留 `package_id` 且 `stage='start_failed'` | `uncertain` 時僅等待原 `handoff` 子操作自身對帳，絕不重送 start/send；確定失敗後若以新 `work.start` 重試，自動重用已備妥之 `package_id` 並建立新 `predecessor_attempt_id` 鏈 |

## 5. 資料表結構（Schema DDL）

遵循 `AGENTS.md`，所有 DDL 皆為冪等（`CREATE ... IF NOT EXISTS`），不配置 `user_version`，不新增 data step：

```sql
CREATE TABLE IF NOT EXISTS pm_work_controllers (
    workspace_id TEXT NOT NULL,
    work_item_id TEXT NOT NULL,
    controller_id TEXT NOT NULL,
    server_id TEXT NOT NULL,
    first_operation_id TEXT NOT NULL,
    created_at REAL NOT NULL,
    PRIMARY KEY(workspace_id, work_item_id)
);
CREATE TABLE IF NOT EXISTS pm_work_start_children (
    parent_id TEXT NOT NULL,
    slot TEXT NOT NULL,
    ordinal INTEGER NOT NULL,
    operation_id TEXT NOT NULL UNIQUE,
    request TEXT NOT NULL,
    request_digest TEXT NOT NULL,
    created_at REAL NOT NULL,
    PRIMARY KEY(parent_id, slot),
    UNIQUE(parent_id, ordinal)
);
CREATE TABLE IF NOT EXISTS work_attempts (
    sequence INTEGER PRIMARY KEY AUTOINCREMENT,
    attempt_id TEXT NOT NULL UNIQUE,
    workspace_id TEXT NOT NULL,
    work_item_id TEXT NOT NULL,
    origin_kind TEXT NOT NULL,
    origin_id TEXT NOT NULL,
    start_operation_id TEXT UNIQUE,
    predecessor_attempt_id TEXT,
    admission_digest TEXT NOT NULL,
    created_at REAL NOT NULL,
    UNIQUE(origin_kind, origin_id)
);
CREATE INDEX IF NOT EXISTS work_attempts_by_work
    ON work_attempts(workspace_id, work_item_id, sequence DESC);
```

- `pm_work_controllers`、`pm_work_start_children` 與 `work_attempts` 皆加上 `BEFORE UPDATE` 與 `BEFORE DELETE` 不可變 trigger（`RAISE(ABORT, ...)`）。
- 加上 `pm_work_start_child_settled` trigger（同 PR #189 模式）：當 `operations.status` 更新為終態（`succeeded`、`failed`、`cancelled`、`needs_attention`）且屬於 `pm_work_start_children` 時，將 `status='waiting_external'` 之父 `work.start` 的 `next_run_at` 設為 `0`；同時保留 `Wait(..., 1)` 輪詢作為保底。

## 6. 必須顯式接線之 Hooks（E00 §3.2）

1. **Operation 可見性與事件過濾**：`pm_workspace.operation_visible` 與 `pm_access._visible` / `event_visible` 除 `pm.*` 外，將 `action == "work.start"` 及 `pm_work_attempt` 事件導向 `pm_work_start.operation_visible`（檢核 workspace 成員資格與原始來源可見性）。
2. **Source Lineage 衍生動作白名單**：`pm_source_lineage.DERIVED_ACTIONS` 加入 `"work.start"`；`inherit`、`_visible_roots`、`require_new_effect` 與 `_require_frame` 接線 `pm_work_start.require_child` 與 `source_visible`。
3. **PM Lifecycle Gates 與 `require_local`**：`pm_lifecycle_gates.kind("work.start")` 視為 `"investment"`（受 `paused`/`closed` 阻擋），並在 `pm_work_start._admit` 與 `_guard` 顯式拒絕 `stage == "idea"`（`PM_WORK_START_LIFECYCLE_IDEA`）；`pm_lifecycle_gates.require_local` 接線 `pm_work_start.require_child`。
4. **私有子操作授權**：`pm_evidence._admit_work_bind`、`pm_work_packages._admit`、`pm_package_handoff.admit`/`guard` 與 `pm_work_start.require_child` 驗證帶有 `work_start_parent` ref 之子操作僅能由原父操作在一致之 `request_digest` 與基準下建立與執行。
5. **既有操作與重啟授權（`operations.py`）**：`_pm_key_prefix`、`has_idempotency_record`、`_prepare_create`、`_decode` 與 `_authorize_controller` 納入 `"work.start"`，確保 workspace 範圍 idempotency key 與重啟復原一致。
6. **Discovery 與讀取對稱性**：
   - `GET /api/v1/capabilities` 於 `features.pm_workspaces.work_start` 公布 `{available, action: "work.start", version: 1, composition_profiles: ["work_start_thin_v1"]}`。
   - 新增唯讀查詢 `pm_work_attempts_list`（`GET /api/v1/pm/workspaces/<ws>/work/<wi>/attempts`）與 `pm_work_attempt_get`（`GET /api/v1/pm/workspaces/<ws>/work-attempts/<attempt_id>`），同步接線 HTTP、`pm_reads.py`、`task_daemon.py`（`API_RPC`）與 `mcp_server.py`（`READ_TOOLS`）。

## 9. 開放問題（Open Questions，最多 5 項）

1. **Authority Anchor 表設計**：本規格以 `pm_work_controllers` 於首次 admission 交易鎖定 controller，並於 `handoff` 子操作建立交易寫入非空 `origin_id` 之 `work_attempts`，讓兩表皆維持 100% 不可變（無 `UPDATE`）。是否同意此結構，或偏好於首次 admission 即寫入 `work_attempts` 並允許單次綁定 `origin_id`？
2. **Attempts 讀取端點範圍**：除 `pm_work_attempts_list(workspace_id, work_item_id, after, limit)` 外，是否同時暴露單筆 `pm_work_attempt_get(workspace_id, attempt_id)`（比照 `pm_work_batches_list` / `pm_work_batch_get`）？
3. **Lifecycle `maintain` 階段行為**：Idea、Paused、Closed 明確拒絕 `work.start`；當 workspace 處於 `maintain` 階段時，`work.start` 是否與一般開發動作相同預設拒絕（維護修復走既有 `pm.maintenance.repair.start`），僅允許 `planning` 與 `development`？
