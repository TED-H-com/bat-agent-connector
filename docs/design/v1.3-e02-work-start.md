# v1.3 E02（Slice P3）：`work.start` 複合動作規格（審閱修訂版）

## Adapter handoff installation / Adapter handoff 安裝

Work handoff builders share one route table, selected from the server-admitted
profile. The optional profile field is `"adapter": "ahp"`; omission means BAT
and adds no field to an existing canonical document or admission digest.
`bat_work_start` retains the original `repository.continue` builder, key,
`pm_work_start_children` row and request digest. `ahp_work_start` builds the
internal `ahp.work.create` child with its original profile and package references.
The request carries no instruction, session URI or endpoint credential.

`pm_ahp_work_start.install(ops)` is explicit and service-local; no daemon calls
it. A different existing action or builder refuses with `PM_WORK_ROUTE_CONFLICT`.
Absent installation refuses profile writes and Work admission with
`PM_WORK_ROUTE_UNAVAILABLE`. The same route and profile revision are checked
again before a child effect. Only the synchronous handoff slot can admit the
child; direct API/MCP submit or replay refuses `AHP_HANDOFF_REQUIRED`.

Creation is still unavailable in this increment. Readiness first requires an
explicit SSH Git binding for the selected host (`GIT_RUNNER_UNAVAILABLE` otherwise),
then reports `AHP_CREATE_UNAVAILABLE`. The registered child's handler also refuses;
it opens no endpoint, prepares no carrier and sends no frame. No operation yet
reports a created AHP session. The create implementation must later persist
“session created, first turn not sent” in the parent's operation, with its exact
session/chat evidence. Delivering the Work instruction remains a subsequent turn.

繁體中文：handoff 共用 route table，由伺服器釘選的 profile 決定；新增選填
`adapter` 欄位，省略仍為 BAT，既有文件、revision、digest 與 BAT handoff bytes
不變。AHP 只經明確 install 註冊，daemon 不安裝；未安裝時寫入 profile 與
Work admission 都以 `PM_WORK_ROUTE_UNAVAILABLE` 拒絕。handoff child 限原 slot
受理，直接提交或重播為 `AHP_HANDOFF_REQUIRED`，晚到的 profile／安裝變更也會攔下。
目前 readiness 仍為 unavailable：無同 host 的 SSH Git 綁定時回報
`GIT_RUNNER_UNAVAILABLE`，有綁定仍為 `AHP_CREATE_UNAVAILABLE`。尚未建立 session，
沒有 carrier／endpoint／訊息效果；後續 create 才新增「session 已建立、首個 turn
尚未送出」的持久狀態，再由 turn 增量送出 instruction。

本文件定義 `work.start` 與 `pm_work_start_preview`（`docs/product/v1.3-closed-loop-plan.md` §7.1–§7.4、§9.1–§9.2、§11.3；`docs/design/v1.3-e00-baseline.md` §2 F4/F5、§3.1–§3.3、§4.1–§4.3、§10.2 P3/P6、§11 Q3），滿足驗收案例 `UX-A12`–`UX-A14`、`UX-A19` 與 `A05`–`A08`。

## 1. 唯讀預覽 `pm_work_start_preview` 與 `work.start` 最終契約

### 1.1 唯讀預覽 `pm_work_start_preview`
Admission 為同步本地交易，不直接呼叫 GitHub 或 BAT；已發布程式碼基準由唯讀預覽先行解析：
- **入口**：`POST /api/v1/pm/workspaces/{ws}/work/{wi}/start-preview`、daemon RPC `pm_work_start_preview`、MCP read tool `pm_work_start_preview`（唯讀、0 journal 寫入）。
- **權限**：`observe` scope 與該 PM workspace 成員資格。
- **請求 Body**：選填之部分 `code_target`、`delivery`（預設 `"pull_request"`）與 `requirement_ids`。
- **行為**：
  1. **候選目標盤點**：自 `repository_sync.capabilities(ops)` 篩選 `repository` 屬於該 Work 所屬 PM project `repositories`（並符合部分 `code_target` 篩選條件）之綁定。僅當**恰好唯一**候選時自動選取；若為 0 或多個候選，回傳 `candidates` 且 `code_target=null`，絕不猜測（計畫 §7.2、`UX-A12`、`A05`）。
  2. **分支與發布頭解析**：若指定 `code_target.source_ref` 則以 `check_ref` 驗證；未指定時透過既有 GitHub client 讀取 repository 之 `default_branch` 組成 `refs/heads/<default_branch>` 並以 `check_ref` 驗證，再呼叫 `repository_sync.source_preview` 取得 `{source_ref, source_sha, repository_id, binding_digest}`。
  3. **本地狀態與套件規劃**：讀取 Work 目前 `version` 與 `fingerprint`、project 綁定（檢核 `PM_PROJECT_BINDING_REQUIRED`）、Work 綁定、已採納計畫之 `scope_revision`（`pmscope_…`）、project `version` 與最新 package。依與 `work.start` 相同規則判定 `reuse` 或 `compose`，並執行就緒檢查（§1.3）。
- **回應**：`{workspace_id, work_item_id, candidates, code_target, source, binding, package_plan, readiness, preconditions, observed_at}`。

### 1.2 `work.start` Action、Scopes、Target、Params、Preconditions
- **Action 註冊**：`ActionDef("work.start", "start", "Start one bound Work item in its own managed BAT worktree and session", _run, _admit, ("workspace_id", "work_item_id"), authorize_existing=_authorize_existing)`。
- **權限與角色**：主 scope 為 `start`；admission、`_authorize_existing` 與 `_current_principal` 皆須具備 `observe`、`manage`、`start`（透過 `principal.allows` 支援管理員）且為 workspace 寫入成員（`require_member(..., write=True)`）。`_current_principal` 於每步前重驗原 `actor` 之有效憑證、寫入成員資格與 `controller_authority.same_controller`。
- **Target**：`{"workspace_id": "ws_<32hex>", "work_item_id": "wi_<20hex>"}`。Work 與所屬 project 須已存在且該 project 已綁定至 workspace（否則拒絕 `PM_PROJECT_BINDING_REQUIRED`）。
- **Params**：
  - `instruction`：必填，1–4,000 字元非空白字串。
  - `agent`：必填，`"claude"` 或 `"codex"`；`model`：選填，1–256 字元模型識別字串。
  - `delivery`：必填，`"pull_request"` 或 `"reviewable_changes"`。
  - `requirement_ids`：選填，1–50 個已採納計畫之 requirement IDs（未綁定至目前採納計畫時必填；已綁定時可省略或須與既有綁定一致）。
  - `code_target`：必填完整四鍵 `{repository, host, workspace_id, source_ref}`（唯一候選與預設分支僅於 preview 解析；admission 僅以本地 `config_snapshot`、project `repositories` 與本地狀態驗證，絕不連線 GitHub 或 BAT）。
- **Preconditions（十項皆必填）**：
  - `expected_work_item_fingerprint`、`expected_work_version`（供 `bind` 子操作使用）、`expected_binding_id`（未綁定為 `null`）、`expected_scope_revision`（`pmscope_…`）、`expected_previous_package_id`（可為 `null`）、`expected_project_version`（供 `handoff` 子操作使用）、`repository_id`、`binding_digest`、`expected_source_sha`、`expected_latest_attempt_id`（Work 目前最新 `attempt_id`，首次啟動為 `null`）。
  - 完整 admission 快照（含 `composition_profile: "work_start_thin_v1"`、`controller`、解析後 `code_source`、`package_plan` 與 `execution_epoch`）存入 `operations.admission_binding["work_start"]`。

### 1.3 子操作建立前之就緒檢核（Readiness Gate）
- 抽取 `pm_work_packages.readiness` 之純文件與本地檢核為共用 helper（保持 `pm_work_packages.readiness` 輸出位元組完全一致）。
- 若需求宣告 `depends_on`，薄路徑於 admission 直接以 `PM_WORK_START_PREREQUISITES` 拒絕（提示改用既有 package 與 batch 流程），建立 0 個子操作。
- Admission 與每個子操作前之 `_guard` 對組合描述（或重用套件之實際 `readiness`）檢核除 `spec_code_alignment` 外之所有項目（含 `source_status:<rid>` 須為 `user_confirmed`、`acceptance:<rid>` 至少一項且全映射、`design`、`delivery_plan`、`unresolved`、`task_coverage`、`scope`、`work`、`code_configuration`、`project_repository`）。任一未通過即以 `PM_WORK_START_NOT_READY`（列出未通過之 check 名稱）拒絕，建立 0 個子操作。

## 2. 子操作槽位、單一 `work_attempts` Anchor 與取消語意

### 2.1 固定子操作槽位（不修改子領域 `_admit`）
子操作皆透過一般 `ctx.service.create(principal, ..., entry="work-start")` 建立並通過各自完整 admission，不修改 `pm_evidence._admit_work_bind`、`pm_work_packages._admit` 或 `pm_package_handoff.admit`/`guard`。若 `create` 回傳 `fresh=False` 則以 `PM_WORK_START_CHILD_CHANGED` 停止：

| Ordinal | Slot | 子動作（Action） | 固定 Idempotency Key | 觸發條件與 Envelope |
|---:|---|---|---|---|
| 0 | `bind` | `pm.work.bind` | `work-start:{parent_id}:bind` | 僅當 Work 未綁定至目前採納計畫時建立；`params={rationale, plan_revision_id, requirement_ids}`，`preconditions={expected_binding_id, expected_work_version}`。 |
| 1 | `package` | `pm.work_package.create` | `work-start:{parent_id}:package` | 若最新 package 符合目前 `scope_revision`、`binding_id`、`requirement_ids`、`code_source` 與 `delivery.goal` 且就緒則重用（`package_reused=true`）；否則以薄套件描述建立。 |
| 2 | `handoff` | `repository.continue` | `work-start:{parent_id}:handoff` | `params` 含 `source_ref`、`source_sha`、`agent`、`model?`、`prompt=instruction`、`title=work.title[:256]`、`project_id`、`work_item_id`、`pm_package_ref`、`pm_code_basis`（`rationale` 決定性載明已審閱之 `source_ref@source_sha`）；`preconditions={repository_id, binding_digest, expected_project_version, expected_work_item_fingerprint}`。 |

### 2.2 單一 `work_attempts` Anchor 與 Controller 規則（E00 §4.2）
- 不建立 `pm_work_controllers`；於 `OperationService.create` 的 `INSERT` 交易內（緊鄰 `pm_lifecycle_gates.admit_operation` 與 `pm_source_lineage.bind_operation`）為 `work.start` 寫入 `work_attempts`：
  - `attempt_id = "att_" + operation_id[3:]`、`origin_kind = "operation"`、`origin_id = start_operation_id = operation_id`、`predecessor_attempt_id` 為該 Work 前一筆最新 `attempt_id`（無則為 `null`）、`admission_digest` 為 admission 快照雜湊。
- **Controller 歸屬、Attempt 樂觀並行與 Settled 限制**：Work 的 controller 由其最早一筆 `work_attempts` 對應操作所保存之 `controller_authority` 固定。每次啟動須滿足：(1) `expected_latest_attempt_id` 符合目前最新 `attempt_id`（無則為 `null`），否則以 `PM_WORK_ATTEMPT_CHANGED`（409，訊息載明目前最新 `attempt_id` 與其啟動 `operation_id`）拒絕，防止快速重用成功後遺失 ACK 以新 idempotency key 重送而建立第二個 session；(2) 最新 attempt 須已完全 settled：父啟動操作須處於 `operations.TERMINAL`（`succeeded`、`failed`、`cancelled`；`needs_attention` 仍可透過 `resume` 續跑故非終態，以 `PM_WORK_START_IN_PROGRESS` 409 拒絕並載明原 `operation_id`），且 `pm_work_start_children` 內所有子操作皆須處於 `operations.TERMINAL`（否則同樣以 `PM_WORK_START_IN_PROGRESS` 載明父啟動操作拒絕）；若任一子操作帶有未經證實之外部步驟（`_uncertain`，含已 `cancelled` 但外部步驟 `was never proven` 之子操作），則以 `PM_WORK_START_OUTCOME_UNPROVEN`（409，載明該子操作 `operation_id`，提示前次 handoff 可能已啟動 session，須先檢查 BAT 上該 Work 的 sessions）拒絕，絕不重送。若讀回證明該 handoff 的 `session.start` frame 從未送出，步驟會重跑或成為已證實的失敗，不再屬於未經證實，後續啟動不受這條拒絕；可能已送出的 start 維持原樣。`_check_admission` 與 `INSERT` hook 皆於同一交易執行此檢核，使並行啟動序列化且後者交易回滾。無 `work_attempts` 紀錄之舊有 Work 絕不從 links 或 `created_by` 推論擁有權。
- **Session 串接與取消級聯語意**：`work_items.STARTS_SESSION` 納入 `"repository.continue"`，由既有 `operation` link 直接解析 `{host, session_id}`。取消父 `work.start` 時先透過 `pm_work_start.cancel_children` 對所有尚未進入 `operations.TERMINAL` 之子操作呼叫 `ops.cancel`（保留子操作對可能已送出步驟之回讀與對帳），再取消父操作；已啟動之 BAT session 維持原操作權限繼續運行，結果標記 `existing_sessions: "continue_under_original_authority"`。

## 4.1 子操作建立前的停止：不可續接與可修復（#216）

`_run` 在建立下一個子操作之前，用三個 `except OperationError` 收下 `_guard` 與 `_admit_child` 的拒絕，並交給 `_stop_before_child`（`pm_work_start.py:1507`）：bind `:1592-1593`（`stage='preparing'`）、package `:1639-1642`（`stage='preparing'`）、handoff `:1696-1706`（`stage='starting'`）。不可續接代碼改存 `stage='start_failed'` 後拋 `OperationError`（父操作 `failed`）；其餘代碼仍存原階段後拋 `NeedsAttention`。`NeedsAttention` 不是 `OperationError` 的子類（`operations.py:75`），不會進入這三個 `except`。子操作列已經提交之後的失敗、不確定的子操作，以及 handoff 送出之後的對帳，仍走 `_raise_child_stopped` 與原有等待路徑，不在本節的改寫範圍。`ctx.effect` 在回呼拋錯時回滾子操作 INSERT（巢狀 SAVEPOINT），所以這三個 `except` 接到的是尚未提交的子操作。

分類只看代碼，不看單次原因。無法證明「同一個已受理的 `work.start` 再 `resume` 也過不了 `_guard`」的代碼維持可修復：父操作留在 `needs_attention`，修好之後用原 operation 續跑。不可續接代碼則像已失敗的子操作一樣結束父操作：`stage='start_failed'`，`failed`，並保留該代碼與 `_failure_message` 的訊息。`failed` 屬於 `operations.TERMINAL`，所以同一 Work 的下一次啟動不再被 `PM_WORK_START_IN_PROGRESS` 卡住。可修復的 `needs_attention` 仍不是終態。人用公開動作無法把原因改回去時，才算不可續接；測試裡用 SQL 把 `version` 寫回去不算公開修復。

`_admit_child` 裡的 `create()` 若在提交前拋出與下表相同的代碼，同樣落在這三個 `except`，分類不變。

### 議題主張與程式不符（不因此把父操作改成 `failed`）

- `PM_ADOPTED_PLAN_REQUIRED` 不是這三個攔截的公開停止。Admission（`pm_work_start.py:769`）與 preview（`:1739`）在 `_run` 之前就拒絕。`_guard` 在目前計畫缺失時拋的是 `PM_PACKAGE_SCOPE_CHANGED`（`:1247-1248`），`current_plan is None` 短路，不會呼叫 `_plan_ref`。`_plan_ref`（`pm_work_packages.py:115`）與套件 `_check`（`:214`，僅 `binding.plan_revision_id is None`）以及 bind 的 `_requirements`（`pm_evidence.py:198`，該修訂沒有採納列）才拋 `PM_ADOPTED_PLAN_REQUIRED`。採納列只插入、不刪除（`pm_plans.py:476` 與 `:78-81`）。公開再採納不會清掉舊修訂的採納列，也不會把同一 `binding_id` 的 `plan_revision_id` 改回 null；新的 bind 會先變成 `PM_WORK_BINDING_CHANGED`。
- `PM_WORK_START_CONTROLLER_CHANGED`（`pm_work_start.py:996-998`）只比較 `server_id` 與 `controller_id`（`controller_authority.py:108-113`）。`controller_id` 是 `uuid5(server_id, actor)`（`pm_workspace.py:53-55`），`server_id` 是啟動時的單例（`pm_workspace.py:48-50`，註記不建立第二個身分）。角色、scope 與成員資格不在這個比較裡。沒有公開動作改這兩個身分；若身分被還原，resume 會通過。因此維持可修復，而且不是「換了一個 controller」的公開路徑。`PM_WORK_CONTROLLER_CONFLICT`（`pm_work_start.py:196-200`）是另一個代碼，同樣只比身分，維持可修復。

## 4.2 已發布開工的未送出證明（#242）

讀回能證明 start frame 從未送出時，原 handoff 可以在既有取消、權限與 lifecycle 檢查後重跑；父狀態跟隨同一 handoff 的結果。只有成功或已證實的失敗結束後，新 `work.start` 才能再受理。已送出或仍無法確認的 start/send 不重送。

證明與 reservation 規則見 [repository-sync](repository-sync.md)：沒有列也沒有 reservation ref，或仍屬於本次操作且明確未送出的相符 reservation，才可重跑。恢復若替換 reservation 後在保存新 ref 前中斷，保留未結算的 step 與原 Work 開工鎖，不能把身分不符結算成失敗而放行另一件開工。

## 7. 看板 Work 檢視「開始工作」（v1.3 P3 前端整合）

本節定義 Kanban 看板 Work inspector 內「開始工作」面板（`workStartPanel`）的互動與展示規格：
- **面板配置與標頭捷徑**：於 Work inspector 內緊接「狀態與負責人」下方建立「開始工作」區塊（`data-work-section="start"`）。當該卡片具備啟動資格（`startable`）時，於檢視器標頭「討論」按鈕旁提供「開始工作…」按鈕，點擊可聚焦至工作指示文字框。
- **指示與預先填入**：自 Work 項目讀取 `request`、`goal` 或 `title` 作為預設工作指示；使用者可編輯指令（上限 4,000 字元）、選擇代理（`claude` / `codex`）、交付成果（`pull_request` / `reviewable_changes`）與選填模型名稱。
- **計畫重綁與需求選取（Bind-needed）**：若該卡片綁定之計畫版本與目前採納計畫不一致，自動展開需求勾選清單並預選既有需求；依據後端規格要求 Workspace 擁有者權限（`permitted(true)`）方能送出，非擁有者檢視時保留草稿並顯示擁有者權限提示。
- **唯讀預覽與就緒檢核**：點擊「檢查就緒狀態」呼叫 `POST start-preview`；恰好 1 筆候選目標時展示已解析之儲存庫、分支、SHA 短碼與套件規劃事實；0 筆或多筆候選時顯示清楚說明或候選目標下拉選單。依後端回傳之各項 readiness checks 逐條列出通過或待處理狀態與說明。
- **過期預覽保護（Stale preview guard）**：以指令、交付目標、需求選取及候選目標計算指紋；任何欄位變更即時標記預覽過期，隱藏過期事實並停用「開始工作」送出按鈕，直到重新執行就緒檢查。
- **耐久表單與冪等重試**：整合 `durableForm`，於提交前先持久化請求意圖與固定 idempotency key。遭遇 LOST_REPLY 或斷線重載時，使用原 key 檢查或復原，絕不發送重複啟動。遭遇 16 種 admission refusal 拒絕碼時，顯示本地化錯誤訊息並提供「新請求」按鈕重置。面板錯誤文字區分面板專屬與全域規則：10 項跨領域共用拒絕碼使用面板專屬鍵（`wst_error_<CODE>`）說明工作與就緒狀態脈絡，9 項啟動專屬拒絕與失敗碼則保留為全域鍵（`error_code_<CODE>`），統一由 `panelErrorBox` 優先解析面板專屬鍵。
- **Attempt 狀態字與執行追蹤**：依最新紀錄更新進度狀態字（如「已受理」、「正在準備工作依據」、「工作依據已就緒」、「正在 BAT 啟動」、「已開始」、「開始結果未確認」、「開始失敗」等，完全對應字串定義）；當進度進入 `started` 時，表單與標頭按鈕隱藏，並顯示「開啟即時輸出」（導向 `sessionHref`）與「開啟工作」連結。使用者在檢視器重新整理或背景事件推播時，輸入焦點、文字選取區與游標位置皆完整保留。
