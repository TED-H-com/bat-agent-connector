# v1.3 E02（Slice P3）：`work.start` 複合動作規格（審閱修訂版）

本文件定義 `work.start` 與 `pm_work_start_preview`（`docs/product/v1.3-closed-loop-plan.md` §7.1–§7.4、§9.1–§9.2、§11.3；`docs/design/v1.3-e00-baseline.md` §2 F4/F5、§3.1–§3.3、§4.1–§4.3、§10.2 P3/P6、§11 Q3），滿足驗收案例 `UX-A12`–`UX-A14`、`UX-A19` 與 `A05`–`A08`。

## 1. 唯讀預覽 `pm_work_start_preview` 與 `work.start` 最終契約

### 1.1 唯讀預覽 `pm_work_start_preview`
Admission 為同步本地交易，不直接呼叫 GitHub 或 BAT；已發布程式碼基準由唯讀預覽先行解析：
- **入口**：`POST /api/v1/pm/workspaces/{ws}/work/{wi}/start-preview`、daemon RPC `pm_work_start_preview`、MCP read tool `pm_work_start_preview`（唯讀、0 journal 寫入）。
- **權限**：`observe` scope 與該 PM workspace 成員資格。
- **請求 Body**：選填之部分 `code_target`、`delivery`（預設 `"pull_request"`）與 `requirement_ids`。
- **行為**：
  1. **候選目標盤點**：自 `repository_sync.capabilities(ops)` 篩選 `repository` 屬於該 Work 所屬 PM project `repositories`（並符合部分 `code_target` 篩選條件）之綁定。僅當**恰好唯一**候選時自動選取；若為 0 或多個候選，回傳 `candidates` 且 `code_target=null`，絕不猜測（計畫 §7.2、`UX-A12`、`A05`）。
  2. **分支與發布頭解析**：若指定 `code_target.source_ref` 則以 `check_ref` 驗證；未指定時透過既有 GitHub client 讀取 repository 之 `default_branch` 組成 `refs/heads/<default_branch>` 並以 `check_ref` 驗證，再呼叫 `repository_sync.source_preview` 取得 `{source_ref, source_sha, repository_id, binding_digest}`。
  3. **本地狀態與套件規劃**：讀取 Work 目前 `version` 與 `fingerprint`、project 綁定（檢核 `PM_PROJECT_BINDING_REQUIRED`）、Work 綁定、已採納計畫之 `scope_revision`（`pmscope_…`）、project `version` 與最新 package。依與 `work.start` 相同規則判定 `reuse` 或 `compose`，並執行就緒檢查（§1.3）。
- **回應**：`{workspace_id, work_item_id, candidates, code_target, source, binding, package_plan, readiness, preconditions, observed_at}`。

### 1.2 `work.start` Action、Scopes、Target、Params、Preconditions
- **Action 註冊**：`ActionDef("work.start", "start", "Start one bound Work item in its own managed BAT worktree and session", _run, _admit, ("workspace_id", "work_item_id"), authorize_existing=_authorize_existing)`。
- **權限與角色**：主 scope 為 `start`；admission、`_authorize_existing` 與 `_current_principal` 皆須具備 `observe`、`manage`、`start`（透過 `principal.allows` 支援管理員）且為 workspace 寫入成員（`require_member(..., write=True)`）。`_current_principal` 於每步前重驗原 `actor` 之有效憑證、寫入成員資格與 `controller_authority.same_controller`。
- **Target**：`{"workspace_id": "ws_<32hex>", "work_item_id": "wi_<20hex>"}`。Work 與所屬 project 須已存在且該 project 已綁定至 workspace（否則拒絕 `PM_PROJECT_BINDING_REQUIRED`）。
- **Params**：
  - `instruction`：必填，1–4,000 字元非空白字串。
  - `agent`：必填，`"claude"` 或 `"codex"`；`model`：選填，1–256 字元模型識別字串。
  - `delivery`：必填，`"pull_request"` 或 `"reviewable_changes"`。
  - `requirement_ids`：選填，1–50 個已採納計畫之 requirement IDs（未綁定至目前採納計畫時必填；已綁定時可省略或須與既有綁定一致）。
  - `code_target`：必填完整四鍵 `{repository, host, workspace_id, source_ref}`（唯一候選與預設分支僅於 preview 解析；admission 僅以本地 `config_snapshot`、project `repositories` 與本地狀態驗證，絕不連線 GitHub 或 BAT）。
- **Preconditions（十項皆必填）**：
  - `expected_work_item_fingerprint`、`expected_work_version`（供 `bind` 子操作使用）、`expected_binding_id`（未綁定為 `null`）、`expected_scope_revision`（`pmscope_…`）、`expected_previous_package_id`（可為 `null`）、`expected_project_version`（供 `handoff` 子操作使用）、`repository_id`、`binding_digest`、`expected_source_sha`、`expected_latest_attempt_id`（Work 目前最新 `attempt_id`，首次啟動為 `null`）。
  - 完整 admission 快照（含 `composition_profile: "work_start_thin_v1"`、`controller`、解析後 `code_source`、`package_plan` 與 `execution_epoch`）存入 `operations.admission_binding["work_start"]`。

### 1.3 子操作建立前之就緒檢核（Readiness Gate）
- 抽取 `pm_work_packages.readiness` 之純文件與本地檢核為共用 helper（保持 `pm_work_packages.readiness` 輸出位元組完全一致）。
- 若需求宣告 `depends_on`，薄路徑於 admission 直接以 `PM_WORK_START_PREREQUISITES` 拒絕（提示改用既有 package 與 batch 流程），建立 0 個子操作。
- Admission 與每個子操作前之 `_guard` 對組合描述（或重用套件之實際 `readiness`）檢核除 `spec_code_alignment` 外之所有項目（含 `source_status:<rid>` 須為 `user_confirmed`、`acceptance:<rid>` 至少一項且全映射、`design`、`delivery_plan`、`unresolved`、`task_coverage`、`scope`、`work`、`code_configuration`、`project_repository`）。任一未通過即以 `PM_WORK_START_NOT_READY`（列出未通過之 check 名稱）拒絕，建立 0 個子操作。

## 2. 子操作槽位、單一 `work_attempts` Anchor 與取消語意

### 2.1 固定子操作槽位（不修改子領域 `_admit`）
子操作皆透過一般 `ctx.service.create(principal, ..., entry="work-start")` 建立並通過各自完整 admission，不修改 `pm_evidence._admit_work_bind`、`pm_work_packages._admit` 或 `pm_package_handoff.admit`/`guard`。若 `create` 回傳 `fresh=False` 則以 `PM_WORK_START_CHILD_CHANGED` 停止：

| Ordinal | Slot | 子動作（Action） | 固定 Idempotency Key | 觸發條件與 Envelope |
|---:|---|---|---|---|
| 0 | `bind` | `pm.work.bind` | `work-start:{parent_id}:bind` | 僅當 Work 未綁定至目前採納計畫時建立；`params={rationale, plan_revision_id, requirement_ids}`，`preconditions={expected_binding_id, expected_work_version}`。 |
| 1 | `package` | `pm.work_package.create` | `work-start:{parent_id}:package` | 若最新 package 符合目前 `scope_revision`、`binding_id`、`requirement_ids`、`code_source` 與 `delivery.goal` 且就緒則重用（`package_reused=true`）；否則以薄套件描述建立。 |
| 2 | `handoff` | `repository.continue` | `work-start:{parent_id}:handoff` | `params` 含 `source_ref`、`source_sha`、`agent`、`model?`、`prompt=instruction`、`title=work.title[:256]`、`project_id`、`work_item_id`、`pm_package_ref`、`pm_code_basis`（`rationale` 決定性載明已審閱之 `source_ref@source_sha`）；`preconditions={repository_id, binding_digest, expected_project_version, expected_work_item_fingerprint}`。 |

### 2.2 單一 `work_attempts` Anchor 與 Controller 規則（E00 §4.2）
- 不建立 `pm_work_controllers`；於 `OperationService.create` 的 `INSERT` 交易內（緊鄰 `pm_lifecycle_gates.admit_operation` 與 `pm_source_lineage.bind_operation`）為 `work.start` 寫入 `work_attempts`：
  - `attempt_id = "att_" + operation_id[3:]`、`origin_kind = "operation"`、`origin_id = start_operation_id = operation_id`、`predecessor_attempt_id` 為該 Work 前一筆最新 `attempt_id`（無則為 `null`）、`admission_digest` 為 admission 快照雜湊。
- **Controller 歸屬、Attempt 樂觀並行與 Settled 限制**：Work 的 controller 由其最早一筆 `work_attempts` 對應操作所保存之 `controller_authority` 固定。每次啟動須滿足：(1) `expected_latest_attempt_id` 符合目前最新 `attempt_id`（無則為 `null`），否則以 `PM_WORK_ATTEMPT_CHANGED`（409，訊息載明目前最新 `attempt_id` 與其啟動 `operation_id`）拒絕，防止快速重用成功後遺失 ACK 以新 idempotency key 重送而建立第二個 session；(2) 最新 attempt 須已完全 settled：父啟動操作須處於 `operations.TERMINAL`（`succeeded`、`failed`、`cancelled`；`needs_attention` 仍可透過 `resume` 續跑故非終態，以 `PM_WORK_START_IN_PROGRESS` 409 拒絕並載明原 `operation_id`），且 `pm_work_start_children` 內所有子操作皆須處於 `operations.TERMINAL`（否則同樣以 `PM_WORK_START_IN_PROGRESS` 載明父啟動操作拒絕）；若任一子操作帶有未經證實之外部步驟（`_uncertain`，含已 `cancelled` 但外部步驟 `was never proven` 之子操作），則以 `PM_WORK_START_OUTCOME_UNPROVEN`（409，載明該子操作 `operation_id`，提示前次 handoff 可能已啟動 session，須先檢查 BAT 上該 Work 的 sessions）拒絕，絕不重送。`_check_admission` 與 `INSERT` hook 皆於同一交易執行此檢核，使並行啟動序列化且後者交易回滾。無 `work_attempts` 紀錄之舊有 Work 絕不從 links 或 `created_by` 推論擁有權。
- **Session 串接與取消級聯語意**：`work_items.STARTS_SESSION` 納入 `"repository.continue"`，由既有 `operation` link 直接解析 `{host, session_id}`。取消父 `work.start` 時先透過 `pm_work_start.cancel_children` 對所有尚未進入 `operations.TERMINAL` 之子操作呼叫 `ops.cancel`（保留子操作對可能已送出步驟之回讀與對帳），再取消父操作；已啟動之 BAT session 維持原操作權限繼續運行，結果標記 `existing_sessions: "continue_under_original_authority"`。

## 3. 決定性薄套件組合規則（`work_start_thin_v1`）

不呼叫模型（計畫 §7.3、`A06`），英文固定描述供代理執行，UI 依 `composition_profile` 顯示本地化標籤：
- `title`：取 Work `title`；若超過 200 字元則取前 199 個 code points 加 `…`（Work 本身標題不變）。
- `requirements`：綁定之 `requirement_ids`；`source_refs`：`[]`。
- `code_source`：`{repository, host, workspace_id, source_ref, source_sha, repository_id, binding_digest}`。
- `design`：`{"status": "not_applicable", "text": "The change is limited to the adopted requirements; no separate design was authored for this small change.", "source_ids": []}`。
- `tasks`：依序產生 `req_1`, `req_2`, …；`description` 為已採納計畫之需求敘述，`requirement_ids=[rid]`，`depends_on=[]`，`source_ids=[]`。
- `verification`：依各需求驗收項產生 `ver_1_1`, `ver_1_2`, …；`requirement_id=rid`，`acceptance_input_ids=[source_input_id]`，`method="Verify the resulting changes against the adopted acceptance statement before delivery."`，`expected_evidence` 為驗收敘述原文，`source_ids=[]`。
- `delivery`：`{repository, repository_id, base_ref: source_ref, goal: params.delivery}`；`migration`、`rollout`、`rollback`、`observation` 皆為 `{"status": "not_applicable", "text": "Not part of this attempt: delivery stops at <goal>; merge and deployment are not authorized. Reviewers assess any migration in the resulting changes."}`。
- `rationale`：`params["instruction"]`。

## 4. 階段與復原對照表（Stage & Recovery Table）

| 步驟 / 階段（Stage Facet） | 副作用前保存之身分（Identity Saved Before Effect） | 成功行為（Success） | 可見失敗表現（Visible Failure） | 僅續接未完成部分（Resume Only Unfinished Part） |
|---|---|---|---|---|
| **Admission** (`accepted`) | `operations`、`admission_binding`、`work_attempts(attempt_id, origin_id=parent_id)` | 回傳固定 `operation_id` 與 `attempt_id` | 條件不符、未就緒（`PM_WORK_START_NOT_READY` / `PM_WORK_START_PREREQUISITES`）、attempt 變更（`PM_WORK_ATTEMPT_CHANGED`）、前次未 settled（`PM_WORK_START_IN_PROGRESS` / `PM_WORK_START_OUTCOME_UNPROVEN`）或 controller 衝突以 403/409/422 拒絕，0 子操作 | 相同 `(workspace_id, idempotency_key)` 重播原操作；同 key 不同請求以 `IDEMPOTENCY_CONFLICT` 拒絕 |
| **1. Bind** (`preparing`) | `pm_work_start_children(slot='bind', operation_id)` | 取得或確認 `binding_id` | 子操作確定失敗（`failed` 或 `cancelled`，且無未證實外部步驟）時父轉 `failed` (`stage='start_failed'`)；子操作 `needs_attention` 或建立前 `_guard` 攔截時父轉 `needs_attention`（保留 `stage='preparing'`，由 `status` 與 `error_code` 表達原因） | 重啟或 `resume` 從 `pm_work_start_children` 找回原 `bind` 子操作；已成功則跳過；取消父操作時級聯 `ops.cancel` 未終態之 `bind` 子操作 |
| **2. Package** (`package_prepared`) | 重用既有 `package_id`；或寫入 `pm_work_start_children(slot='package', operation_id)` | 固定 `package_id`、`package_reused`，持久化 `stage='package_prepared'` | 若發布頭於 admission 後移動，子操作以 `PM_PACKAGE_CODE_SOURCE_CHANGED` 確定失敗，父轉 `failed` (`stage='start_failed'`) 並提示以 `pm_work_start_preview` 重新審閱；子操作 `needs_attention` 或 `_guard` 攔截則父轉 `needs_attention`（保留 `stage='preparing'`） | 已成功之 `package` 子操作保留 `package_id`，重試絕不建立第二份同基準 package；重跑 preview 指向新 commit 後直接提送新 `work.start` 產生新 package 修訂並保留原 package；取消父操作時級聯取消未終態子操作 |
| **3. Handoff** (`starting` / `start_unknown` / `started` / `start_failed`) | `pm_work_start_children(slot='handoff', operation_id)` | 執行中為 `starting`；成功後回填 `{host, session_id}` 且 `stage='started'` | 若發布頭於 package 後移動，handoff 以 `REPOSITORY_REF_CHANGED` 確定失敗，父轉 `failed` (`stage='start_failed'`)、保留 `package_id` 並提示以 `pm_work_start_preview` 重新審閱；若子操作含未證實外部步驟（`_uncertain`）則父轉 `needs_attention` (`stage='start_unknown'`，code 為 `UNCERTAIN_UNRESOLVED` 或子操作錯誤碼)；子操作 `needs_attention` 或 `_guard` 攔截則父轉 `needs_attention`（保留 `stage='starting'`） | 未證實外部步驟（`_uncertain`）時僅等待原 `handoff` 對帳且新啟動以 `PM_WORK_START_OUTCOME_UNPROVEN` 拒絕（要求先檢查 BAT sessions），0 重送 start/send；確定失敗（`failed`）且基準未變時，新 `work.start` 自動重用已備妥之 `package_id`；取消父操作時級聯 `ops.cancel` 未終態子操作（含回讀可能已送出步驟），已建立之 session 維持 `existing_sessions: "continue_under_original_authority"` |

## 5. 資料表結構（Schema DDL）

```sql
CREATE TABLE IF NOT EXISTS pm_work_start_children (
    parent_id TEXT NOT NULL,
    slot TEXT NOT NULL,
    ordinal INTEGER NOT NULL,
    operation_id TEXT NOT NULL UNIQUE,
    request TEXT NOT NULL,
    request_digest TEXT NOT NULL,
    created_at REAL NOT NULL,
    PRIMARY KEY(parent_id, slot),
    UNIQUE(parent_id, ordinal)
);
CREATE TABLE IF NOT EXISTS work_attempts (
    sequence INTEGER PRIMARY KEY AUTOINCREMENT,
    attempt_id TEXT NOT NULL UNIQUE,
    workspace_id TEXT NOT NULL,
    work_item_id TEXT NOT NULL,
    origin_kind TEXT NOT NULL,
    origin_id TEXT NOT NULL,
    start_operation_id TEXT UNIQUE,
    predecessor_attempt_id TEXT,
    admission_digest TEXT NOT NULL,
    created_at REAL NOT NULL,
    UNIQUE(origin_kind, origin_id)
);
CREATE INDEX IF NOT EXISTS work_attempts_by_work
    ON work_attempts(workspace_id, work_item_id, sequence DESC);
```

- `pm_work_start_children` 與 `work_attempts` 皆設 `BEFORE UPDATE` / `BEFORE DELETE` 不可變 trigger；另設 `pm_work_start_child_settled` trigger 於子操作停止執行時將 `waiting_external` 之父 `work.start` 的 `next_run_at` 設為 `0`，並保留 `Wait(..., 1)` 輪詢。
