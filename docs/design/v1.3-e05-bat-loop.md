## 0. 這份規格要證明的事

計畫把 E05 定義成一條循環，不是六個新動作。本基準上，新工作、固定結果、交付發布與原操作對帳已經各自存在；採用並開始、下一輪佇列、operation loop 還在審查。本文件把這六個元素對到現有程式與審查中規格，指出缺口與最小工作項，並寫下一條只用公開 HTTP 與 MCP、mock BAT、mock GitHub 的黃金情境。

手動、外來與來源不明的工作階段維持唯讀。這條循環不發送、不恢復、不中斷、不改權限、也不清理它沒有建立的東西，並且不從路徑或名稱推斷所有權（`src/bat_agent_connector/resource_policy.py:1-18`、`:36-38`、`:332-360`）。結果未確認時，對帳用原 operation 與原 message id；不重送 start、不重送該輪、不清除鎖定。

## 3. 四個問題

### 3.1 Stream：回合進行時，人今天怎麼看到輸出

人在 Work 上看到的是狀態與一條離開本頁的連結，不是嵌在 Work 裡的逐字稿。

1. 開始面板在 stage 為 `started` 且 Attempt 帶有 session 時，顯示「開啟即時輸出」（`pm-work-start.js:262-267`）。成果區在有 host 與 session id 時顯示同一句（`pm-work-result.js:318-323`）。連結由 `sessionHref` 組成，`from` 是 `board`。
2. 工作階段頁載入該 session 的訊息，並在 journal 出現這個 session 的事件時重讀。那些事件來自 inventory：MATERIAL 欄位的摘要變了才發 `session.updated`（`inventory.py:27`、`:214-219`）。活動時間戳本身不發事件。
3. 看板訂閱 session 與 operation 事件後重選卡片，卡片再讀 Attempt 與 `/result`。`/result` 不呼叫 BAT。成果區的逐字內容是上一筆已固定回執；回合進行中收集器寫下 `mid_turn` 並返回，不新增回執（`pm_attempt_results.py:1543-1546`）。所以 Work 上的文字不會逐 token 前進。它會在 `streaming` 等 MATERIAL 欄位翻轉，或 `work.attempt.result_recorded` 到達時，改成新的狀態或新的固定回執。

受管 session 的逐字稿可以從 Work 連過去，讀的是工作階段頁，不是 `/result`。更新它的是工作階段頁自己的讀取，加上 inventory 在 MATERIAL 改變時發出的 `session.updated`。

相對 F5（計畫 `:150`）還缺的是：開始之後，Work 卡自動連上該 Attempt 的即時輸出，而不是只留 operation id 與一條連結。這份缺口的負責人與做法見元素表的 stream 列。固定成果已經連在同一張卡的成果區（E03 Part A）；缺的是回合進行中的輸出。

### 3.2 Busy：Connector 怎麼知道受管 session 在忙，和 P5 是否同一信號

不是同一信號。即時送出、inventory／Result、P5 佇列各看一組欄位。

兩套判定不一致時，人會看到：

1. Inventory 的 `streaming` 仍為 true（最久約一個刷新間隔，`inventory.py:68`；主機不可達時保留最後一列），即時 meta 已經是 `isStreaming == false`。成果區仍顯示「執行中」。這時直接 `session.send` 且不帶 queue，有可能成功。P5 仍要等本地回合邊界回執，不會因為這一刻的即時 meta 就送出排隊句。
2. Inventory `streaming` 為 false，`runtime_status` 為 `running`。Result 顯示「執行中」（`pm_attempt_result_reads.py:1364-1368`）。P5 §15 第 2 點說這不算忙。人在成果區看到執行中，而 `schedule=now` 依 P5 可能被接受。本文件不選邊修改任一邊；黃金情境用明確的 `isStreaming` 與回執邊界，不靠單獨的 `runtime_status`。
3. `pending` 有值且沒有在串流。Result 顯示「等待回答或權限」。P5 對 `schedule=now` 拒絕 `PM_WORK_SESSION_WAITING_INPUT`。直接 `session.send` 只看 `isStreaming`（`service.py:1134`），有可能在等待閘門時仍送出。
4. 工作階段頁的 queue 核取方塊走 BAT 的上游佇列（`app.js:1475-1486`）。P5 把句子留在 Connector 的 `work_inputs`，呼叫 `session.send` 時不傳 `queue`。這是兩條佇列。Work 循環只用後者。
5. 收集器可以把程序結束記成 `process_ended`（`pm_attempt_results.py:1565-1566`）。P5 不把程序結束當成放行下一句的邊界；該句在圍欄前失敗，字是 P5 §10 的「失敗」／「Failed」，並提供「以新指令重試」。
6. 工作階段頁在收到它自己的 `SESSION_BUSY` 時，會勾起 queue 再送一次（`app.js:1475-1478`）。那是裸 session 路徑。Work 循環的排隊句不走這條自動重送。

### 3.4 外面的變更：受管 session 被關掉，或同一工作樹出現手動 session

受管 session 被外面關掉或殺掉：inventory 連續兩次成功列舉都看不到該列，就寫 `gone_at` 並發 `session.gone`（`inventory.py:32`、`:222-232`，`GONE_AFTER_MISSES = 2`）。Result 接著是 `process-ended`，原因 `session_gone`（`pm_attempt_result_reads.py:1354-1358`），字是「工作階段已結束」。循環不會改連到別的分頁，也不會為了補上它而 start 一次。

同一工作樹裡，人另外開一個手動 session：那是另一個 session id，沒有 Connector 的建立紀錄。`resource_policy` 把沒有建立紀錄的 BAT 分頁標成 `manual`，永久唯讀，碼 `MANUAL_READ_ONLY`（`resource_policy.py:11-12`、`:36-37`、`:340-346`）。來源對不上或建立未被確認的是 `unknown`／`UNKNOWN_READ_ONLY`（`:12-13`、`:38`、`:353-357`）。路徑相同不構成所有權。分類在寫入幀之前拒絕變更（同檔開頭與 `authorize` 路徑）。

循環顯示的仍是這次 Attempt 的受管 session。收集器在讀之前比對 registry 的 `start_operation_id` 與交接 operation id，不符就記 `registry_mismatch`，不讀（`pm_attempt_results.py:1512-1524`）。手動、外來、未確認與 registry 不符的 session 不會被收集（`tests/test_pm_attempt_results.py:758`）。`/changes` 與 `/diff` 在任何 BAT 呼叫之前拒絕這種 Attempt（`tests/test_pm_work_attempt_result.py:510`）。`work.start` 也不改寫早已存在的手動 session 與人的 checkout（`tests/test_pm_work_start.py:1305` 那段，既有手動 session id 保持原樣，新 session id 不是它們）。

P5 對 Work target 的拒絕是 `409 PM_WORK_SESSION_NOT_MANAGED`；`resource_policy` 已判唯讀時沿用該列的 `read_only_code`，HTTP 403（P5 §15 第 4 點）。本基準的 provenance 常數是 `manual`、`connector_managed`、`unknown`（`resource_policy.py:36-38`）。P5 §15 寫的 `manual_bat` 與 `discovered_existing` 是該實作分支的字，不是本基準分類器的字。見 §7。

工作階段頁對 `manual` 顯示唯讀說明、不放撰寫框（`desktop/src/app.js:1850-1860`）。來源撤回（403／404／410）時，訊息、待處理、交付與中繼資料一起清掉（`app.js:1964-1982`）；較晚的讀取因序號票被丟棄，不能把已撤回的列畫回來。

## 7. 審查中規格與本基準不一致的地方

這裡只記錄兩邊都寫了、而且不能同時當合約的句子。不選邊改那些規格。

1. **下一句的 target。** E04 §5.2 與本基準 `_compute_actions` 在 `execution.state == turn-ended` 時提供 `session.send`，target 是 `{host, session_id}`（`docs/design/v1.3-e04-result.md` §5.2；`pm_attempt_result_reads.py:1028-1039`）。P5 §14 第 2 點與 §15 第 2 點改為已啟動 Work 只提供 Work target `{workspace_id, work_item_id}`。直接呼叫舊的 host／session API 在 P5 仍保留。黃金情境的 Work 路徑依 P5；本基準的成果區在 P5 合併前仍會建議 host／session。
