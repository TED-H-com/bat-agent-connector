## 0. 這份規格要證明的事

計畫把 E05 定義成一條循環，不是六個新動作。本基準上，新工作、固定結果、交付發布與原操作對帳已經各自存在；採用並開始、下一輪佇列、operation loop 還在審查。本文件把這六個元素對到現有程式與審查中規格，指出缺口與最小工作項，並寫下一條只用公開 HTTP 與 MCP、mock BAT、mock GitHub 的黃金情境。

E05 指定黃金情境與故障注入。E11 採用它們做驗收（計畫 `:527`）。恢復、忙碌對齊，以及那些測試怎麼跑，不歸 E05。

手動、外來與來源不明的工作階段維持唯讀。這條循環不發送、不恢復、不中斷、不改權限、也不清理它沒有建立的東西，並且不從路徑或名稱推斷所有權（`src/bat_agent_connector/resource_policy.py:1-18`、`:36-38`、`:332-360`）。結果未確認時，對帳用原 operation 與原 message id；不重送 start、不重送該輪、不清除鎖定。

## 3. 四個問題

### 3.1 Stream：回合進行時，人今天怎麼看到輸出

人在 Work 上看到的是狀態與一條離開本頁的連結。逐字稿的公開讀取已經存在。

1. 開始面板在 stage 為 `started` 且 Attempt 帶有 session 時，顯示「開啟即時輸出」（`pm-work-start.js:262-267`）。成果區在有 host 與 session id 時顯示同一句（`pm-work-result.js:318-323`）。
2. `GET /result?cursor&wait_ms` 在相關事件到達時醒來：Attempt、啟動 operation、執行 operation、以及 `session/{host}/{sid}`（`pm_attempt_result_reads.py:1190-1241`）。這次讀取不呼叫 BAT。
3. 信封的 `events_read` 指向既有事件讀取（`:1882-1888`）。`conversation.transcript_read` 在 host、session 與 `turn_marker` 都在時，指向 `GET /api/v1/sessions/{host}/{sid}/messages?after={turn_marker}`，RPC 與 MCP 都是 `session_read`（`:1464-1473`）。
4. 收集器在 `streaming` 時寫 `mid_turn` 並返回，不新增回執（`pm_attempt_results.py:1543-1546`）。inventory 只在 MATERIAL 摘要改變時發 `session.updated`（`inventory.py:214-219`）。`isStreaming` 維持 true 而 token 增加時，不發這個事件。

所以 Work 上的固定文字不會逐 token 前進。即時輸出要讀 `transcript_read`。刷新走 `/result` 的長輪詢，以及工作階段頁自己的讀取。

相對 F5（計畫 `:150`）還缺的是畫面：開始之後，Work 開啟或嵌入 `transcript_read`，並用既有的 `/result` 長輪詢刷新。不新增後端。負責人是 E03。

### 3.2 Busy：三道閘門

直接送出、Result、P5 最後一幀看的是同一組 BAT 信號，判定順序不同。

| 閘門 | 它讀什麼 | 人看到或呼叫端得到什麼 |
