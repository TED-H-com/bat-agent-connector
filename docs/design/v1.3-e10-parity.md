## 1. 範圍

### 1.1 R1 要 E10 補上的

計畫 `:542` 的 R1 是 E01–E05 加上 E10 的最小對等。`:108` 把 MCP 定成產品的 agent 入口。`:422` 要求回應帶上 Work、Attempt、Operation、目前狀態、下一個允許動作、打得開的 Dashboard 深層連結，以及資料完整度。不可以只回成功。`:631` 要求 agent 不點 UI、不共用管理員 token、不偽裝成另一個 controller。

A15（`:572`）是外部 agent 不點 UI 就開始自己的工作，Dashboard 看到同一筆 Work 與 Attempt。A16（`:573`）是同一授權意圖，兩種入口的規則、狀態與 Result 相同，操作來源仍分得出來。

今天這條路的寫入已經進同一個 `OperationService`。差的是回應沒有那組共用欄位、深層連結怎麼組成絕對 URL 沒有寫下來，以及 canonical skill 沒有把整條迴圈教完。E10 只補這三件事，再加上實作階段的對等測試。

### 3.2 最小附加

實作在 daemon 裡做一個投影，MCP 工具維持薄包裝，不在 `mcp_server.py` 各寫一份。投影是一支新函式 `attach`，放在 `src/bat_agent_connector/pm_operation_loop.py`。這個檔在 `39da0e4b` 不存在，由實作 commit 新增。0 次 BAT IPC，0 次資料庫寫入。不新增表。

`attach` 不放進 `OperationService.get`（`src/bat_agent_connector/operations.py:359`）或 `create`（回傳在 `:634`）。這兩個方法的內部呼叫者必須繼續拿到沒有 `loop` 的列。`wait_s` 大於 0 時，handler 先用今天的方式再 `get` 一次（`src/bat_agent_connector/api_v1.py:1496-1500`、`src/bat_agent_connector/task_daemon.py:422-426`），然後才把要放進回應的那份 operation 交給 `attach`。

鍵名是 `loop`，放在 operation 物件裡面。物件上沒有 contract 名。能力廣告在 §3.4。兩邊客戶端拿到的是同一份 `operation.loop`。外層該有的 `created`、`work_items`、`cleanup_receipts` 仍在原處。

HTTP `GET /api/v1/operations/{id}`、cancel、resume，以及對應的 RPC 出口，在 E10 之前就回這筆 operation。`loop` 不得把一筆本來讀得到的 operation 變成讀不到。attempt 視圖或 E04 Result 讀取若以 `OperationError` 拒絕，投影降級並在完整度說明；這筆回應仍成功。`KeyError`、`TypeError`、`RegistryInvariantError` 不是 `OperationError`，是程式錯誤，投影不接。

cancel／resume 在改寫狀態、取消或恢復子操作之前，先檢查整份已存 operation 的來源可讀性。僅檢查 operation 自己的 admission roots 不足以涵蓋後來保存的收據。若收據來源不可讀，沿用讀取的 `NOT_FOUND` 拒絕，不寫狀態、`cancel_requested` 或事件，也不喚醒 worker；HTTP 與 RPC／MCP 共用此檢查。內部對既有副作用的讀回與對帳仍使用原本的恢復路徑。

## 6. 處處成立的規則

MCP 與 HTTP 使用同一份已註冊動作、同一份 scope、同一套 controller 檢查，以及同一把 idempotency key。單筆 operation 的 `loop` 在這兩個出口是同一份：同一個 Work、同一個 Attempt、同一個 `result_read`、同一組可用與被拒的動作，以及同一套來源可見性。`operation_submit` 的 `entry` 是 `mcp`（`src/bat_agent_connector/mcp_server.py:393` 的 `principal_daemon`）。來源因此分得出來，規則不分叉。profile、Result 面板與 P5 仍是草案，不在這個建置裡標成完成。

Principal-only 的說明在 `src/bat_agent_connector/mcp_server.py:1797`。舊的 Fleet 寫入工具在 `:1513` 被拿掉。`operation_submit` 仍在。迴圈不使用共用的 admin token，也不借用另一個 controller 的 session。`principal_daemon` 要求 `confirm=true` 與呼叫端自己的 token（`src/bat_agent_connector/mcp_server.py:386-393`）。

Manual、foreign、unknown session 維持唯讀。不從 cwd、標題或路徑推測擁有權。要接別人的成果，開自己的工作，不往那條 session 送 `session.send`。

不確定的結果不重送 start，也不清 lock。恢復用原 operation id 與原 key。`operation_cancel` 與 `operation_resume` 維持既有工具（`src/bat_agent_connector/mcp_server.py:109` 的 `OPERATION_TOOLS`）。這兩個動詞出不出現在 `loop`，按 §3.2，不在工具層另做一套資格。

R0 決策 7：這條迴圈上新的複合動作只有 `work.start` 與 `work.adopt_and_start`。E10 不加第三個。`session.send` 的 Work target 是 P5 對既有動作的擴充，不是新動作。P5 擴充受其 capability、controller、成員資格與傳輸圍欄約束；本投影不另加送出權限。

撤回時，API、MCP、事件與 UI 一起拿掉該來源的列、計數與詳情。單筆 operation 不是在一份仍可讀的 body 裡拿掉一列：來源在這筆文件的具名欄位裡時，整筆是 404；id 或 hash 只在別列時，`loop` 拿掉它，operation 仍可讀。投影用同一次可見性檢查，不另做快取。

## 7. 實作階段的測試

新檔建議 `tests/test_pm_loop_parity.py`。既有 `tests/test_pm_work_start.py` 與 Result 測試保持原斷言。執行用 mock BAT、暫存 repository、`tests/operation_helpers.py:42` 的 `settle_operations`。不連真的主機，不使用真實 credential。

E10 擁有的每一項差額都要有兩類測試。

**同一份 `loop`。** 經 HTTP POST /api/v1/operations 建立一筆，再經 MCP `operation_submit` 建立另一筆。這是兩筆 operation，id 不同，兩份 `loop` 不會是同一份 JSON。比較分兩段。第一，`settle_operations`（`tests/operation_helpers.py:42`）之後，對同一筆 operation 做 HTTP GET /api/v1/operations/{id} 與 MCP `operation_get`，兩份 `operation.loop` 相等。同一筆的 cancel 與 resume 回應也納入。清單不比。第二，要比較兩次建立回應時，先把 operation id，以及 `loop` 裡的這個 id，換成同一個佔位再比。至少覆蓋一筆會建立 attempt 的 `work.start`，以及一筆沒有 attempt 的 `session.send`。不比較外層：HTTP GET 仍多 `work_items` 與 `cleanup_receipts`，建立回應仍有 `created`。同一把 key 再送一次，回到原 operation，`loop.operation_id` 不變，不產生第二筆 start。

**`work.start` 的 cancel 與 resume。** 同一位 principal，`loop` 的 cancel、resume 等於 Result 信封的 operation_endpoint 列。`blocked_actions` 裡 action 為 cancel、resume 或 `work.start` 的列，也等於信封裡的那些列。期望值來自信封，不在測試裡寫第二套資格。沒有 attempt 時兩邊清單都是空的。

**其他動作的 cancel 與 resume。** 至少覆蓋一筆討論動作（例如 `pm.message.append`）、`pm.work_package.create`、`session.send`，以及 `delivery.merge_and_deploy`（resume 要同時有 merge 與 deploy）。每個動作在它允許的 principal 上各測：原 actor、不是 actor 的 writer 成員、reader 成員、缺少所需 scope 的 principal、controller 綁定不同的 principal。期望值來自真正的 HTTP 端點，測試裡不放第二張對照表。每個案例先以該 principal 讀 `loop`，再以同一 principal 呼叫真正的 HTTP cancel；resume 用一筆狀態已是 needs_attention 的 operation。`loop.next_allowed_actions` 提供了該動詞時，真正的呼叫不被授權拒絕。動詞被省略，或出現在 `blocked_actions` 時，真正的呼叫被拒絕。blocked 列的 reason 對得上 §3.2 那張表裡、真正呼叫所回的碼。每一次真正的 cancel 用一筆新的 operation，避免前一個案例改掉下一個。

Result 信封不得多出一個巢狀的 `loop`。Preview 與 `pm_work_attempt_get` 的既有鍵不得因為這次投影而改變。

**MCP 在 HTTP 拒絕的地方也拒絕。** 至少覆蓋：缺 scope 的 `FORBIDDEN`、非成員的 `NOT_FOUND`、manual session 的 `MANUAL_READ_ONLY`、相同 key 不同內容的 `IDEMPOTENCY_CONFLICT`，以及 `work.start` 的 `PM_WORK_START_IN_PROGRESS` 或 `PM_WORK_ATTEMPT_CHANGED`。HTTP 回它今天的 status 與 `error.code`。MCP 不得回傳 operation；工具錯誤字串含同一個碼。不要求 RPC 的 HTTP status 從 400 改成 403 或 409。Admission 被拒時資料庫沒有新的 operation 列。

撤回有兩種，都走公開讀取，不直接呼叫投影。先準備好的舊回應不得在測試裡把列補回去。這條加在 operation `loop` 上，不放寬 Result 測試已有的撤回斷言。

第一種：operation 自己的文件含有被藏起來的來源。`session.send` 的 target 同時有 host 與 session_id，`work.start` 的 target 有 work_item_id。下一次 HTTP GET 是 404，`error.code` 是 `NOT_FOUND`，message 是 `Original resource sources are unavailable`。MCP `operation_get` 是帶同一個碼與同一句訊息的工具錯誤，沒有 operation。兩份回應都沒有 `loop`、那筆 operation id，或那個 work id。

第二種：已證明的 `work.start` package 子 operation，`loop` 從父 attempt 視圖抄到受管理 session。那個 host 與 session id 不在這筆子 operation 自己被 `references` 掃到的欄位裡。藏起那個 session 之後，HTTP GET 與 MCP `operation_get` 都成功，兩份 `loop` 相等，session id 與它的 hash 都不在，`completeness` 是 `unavailable`，reason 是 `source_withdrawn`。execution id 是同一種形狀，這次測試不另藏它。

Skill：`scripts/generate_agent_skills.py --check` 在 canonical 與兩份產生檔不一致時失敗。迴圈段落只存在於 canonical；產生檔的差異只有既有的 adapter 前言與 sha256。
