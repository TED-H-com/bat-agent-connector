# v1.3 E00 可點擊互動原型設計與對照說明（R0 驗收關卡）

本文件說明 `desktop/prototype/v1.3/` 可點擊互動原型的建置與開啟方式、八大情境與黃金流程所對應的流程（F1–F7）及驗收案例（A01–A40，見 `docs/product/v1.3-closed-loop-plan.md` §17）、複用的正式共用元件與新增候選共用元件、本原型刻意不預先拍板的工程細節，以及提請專案負責人（Owner）於 R0 關卡確認的五項互動設計問題與建議預設值。

---

## 1. 如何建置與開啟原型

### 1.1 建置靜態原型

於 `desktop/` 目錄執行：

```bash
cd desktop
npm run build:prototype
```

- 建置設定位於 `desktop/prototype/v1.3/vite.config.ts`。
- 產出目錄為 `desktop/dist-prototype/v1.3/`（已列入 `.gitignore`），包含 `index.html`、`app.js` 與 `app.css`。
- 所有資源皆使用相對路徑（`./app.js`、`./app.css`），可掛載於任意子路徑（例如專案網站的 `/prototype/v1.3/`），且 `index.html` 內含 `<meta name="robots" content="noindex" />`。
- 嚴格遵守產品 CSP（`default-src 'none'; script-src 'self'; style-src 'self'`）：無任何行內 `<script>`、`<style>`、`style="…"` 屬性或動態 `innerHTML`。

### 1.2 本地開啟與自動化驗證

1. **透過測試靜態伺服器開啟**：
   ```bash
   cd desktop
   node tests/static-server.mjs
   ```
   於瀏覽器開啟 `http://127.0.0.1:1421/prototype/v1.3/`（若設定 `BATC_UI_TEST_PORT` 則使用對應連接埠）。支援查詢參數快速指定語系與初始情境：
   - 繁體中文：`?lang=zh-TW`
   - 英文：`?lang=en`
   - 指定初始情境：`?scene=idea`、`?scene=planned`、`?scene=running`、`?scene=waiting_input`、`?scene=awaiting_verification`、`?scene=external_readonly`、`?scene=disconnect_recovery`、`?scene=maintenance`
2. **執行 Playwright 端到端互動驗證**：
   ```bash
   cd desktop
   npx playwright test tests/prototype-v1-3.spec.ts
   ```

## 3. 複用的正式共用元件與新增候選共用元件

### 3.1 直接複用的正式共用元件（`desktop/src/ui/` 與既有樣式）

本原型未修改 `desktop/src/` 下任何檔案，直接透過 ES Module 引入並組合下列產品正式元件與樣式：

- **DOM 與狀態基礎設施**：
  - `desktop/src/ui/dom.js`：`h()`、`place()`（所有節點皆由安全 DOM 建構器產生，零 `innerHTML`）。
  - `desktop/src/ui/view-state.js`：`viewState()`（保存跨視圖切換的檢視偏好）。
  - `desktop/src/ui/time.js` 與 `desktop/src/ui/stamps.js`：`compactTime()`、`timeStamp()`（搭配固定基準時間 `FIXED_NOW` 呈現雙語相對時間與完整時間戳記）。
- **視覺與互動元件**：
  - `desktop/src/ui/components.js`：`button()`、`segmented()`、`statusPill()`、`pageHeader()`、`sectionCard()`、`disclosure()`、`contextChip()`、`inspector()`。
  - `desktop/src/ui/icons.js`：`icon()`（Lucide SVG 圖示系統）。
  - `desktop/src/ui/ui-strings.js`：`uiStrings`、`statusVocabulary`、`phaseVocabulary`。
- **產品樣式表**：
  - `desktop/src/ui/tokens.css`、`desktop/src/ui/components.css`、`desktop/src/app.css`、`desktop/src/shell.css`、`desktop/src/pm-overview.css`、`desktop/src/pm-workbench.css`、`desktop/src/pm-session.css`。

### 3.2 新增之候選共用元件（`desktop/prototype/v1.3/candidate-components.js`）

針對 v1.3 閉環工作流所需、但目前 `desktop/src/ui/` 尚未內建的互動區塊，我們以相同設計語彙與 Token 規範於 `desktop/prototype/v1.3/candidate-components.js` 實作以下 **8 個候選共用元件**，供 R0 確認後於 E03 階段移入 `desktop/src/ui/`：

1. **`diagnosticStateCard`（§6.4 結構化診斷與復原狀態卡）**：
   - 統一呈現空白、無法使用、部分成功或斷線狀態的四項必備資訊：（1）缺少什麼、（2）在此處可以做什麼、（3）去哪裡修復、（4）草稿與操作鍵是否已保留，並附上修復／接續動作按鈕。
2. **`intentComposer`（§6.2 三意圖統一輸入框）**：
   - 整合 `segmented()` 意圖切換器（討論／規劃／執行）、多行草稿輸入框、意圖專屬主次動作按鈕（「傳送給 PM」／「只存筆記」、「整理／更新計畫」、「開始工作」／「送出下一步」），以及絕不自動執行的意圖切換建議橫幅。
3. **`shortPlanCard`（§6.2 / F3 簡短計畫摘要卡）**：
   - 以結構化欄位呈現目標、修改範圍、完成條件、工作設定檔與執行位置，並提供「採用計畫，稍後執行」與「採用並開始」雙路徑動作。
4. **`compoundStepList`（§7.3 複合操作步驟清單）**：
   - 呈現「採用並開始」的八個順序步驟與各自的即時狀態標籤（已完成、執行中、停在此步驟、待執行），內建「計畫已採用，工作尚未開始」部分成功診斷卡與「繼續未完成步驟」按鈕。
5. **`liveStreamOutput`（§6.3 公開工具活動與即時串流輸出檢視器）**：
   - 以清晰的步驟列表呈現代理人公開工具呼叫摘要，搭配等寬字體（`data-mono`）串流終端輸出區塊。
6. **`unifiedDiffView`（§6.3 結構化程式碼差異檢視器）**：
   - 不使用任何行內樣式或外部 HTML 渲染器，以語意化 CSS 類別（`.proto-diff-line--add` / `.proto-diff-line--del`）與雙欄行號呈現檔案變更差異。
7. **`deliveryProgressionBar`（§10.2 / A32 六階段交付證據狀態鏈）**：
   - 將「代理人自報完成」、「測試通過」、「PR 已開啟」、「已驗收」、「已合併」、「已部署」並列為六個獨立證據節點，確保未取得中央證據前絕不混同或超前標示。
8. **`pmAssessmentCard`（§12.1 PM 需求回填與決策關卡卡片）**：
   - 整合 PM 評估三態（通過／未通過／證據不足）、已查核證據來源清單、目前判斷、本輪建議，以及負責人的拍板決策按鈕（決策後直接返回總覽或討論串）。

## 4. 本原型刻意不預先拍板的事項

依據 `docs/product/v1.3-closed-loop-plan.md` 與 `docs/product/v1.3-agent-handoff.md` 的 E00 邊界，本原型專注於讓專案負責人在 R0 關卡驗證單頁閉環互動體驗，因此刻意不決定以下後續工程階段（E01–E11）的實作細節：

1. **真實網路協定與 SSE/WebSocket 封包格式**：原型以記憶體狀態模擬串流與事件推進；實際的即時事件負載與重連游標由 E00 工程基線（`docs/design/v1.3-e00-baseline.md`）與 E01–E04 定義。
2. **資料庫 Schema 擴充與遷移步驟**：工作收件匣（Work Inbox）、簡短計畫版本關聯與複合操作步驟的持久化資料表結構，留待後端任務在遵循「冪等 DDL、不配置新 `user_version`」規則下實作。
3. **跨 CLI 轉接器（Claude / Codex / Gemini via BAT）的底層剖析器細節**：原型僅展示標準化後的公開工具活動、提問卡片與成果摘要，不綁定特定 CLI 的原始 stdout 控制碼格式。
4. **GitHub PR 建立之認證權杖傳遞路徑**：原型驗證「從成果區建立 PR」的互動位置與狀態回填；實際呼叫 GitHub API 的範圍檢查與持久化操作由既有 Connector 權限閘門負責。

以下五項互動細節請專案負責人於點擊原型後拍板；若無異議，團隊將於 E03 直接採用建議預設值：

1. **「採用並開始」完成後的頁面跳轉時機**
   - **問題**：當使用者在討論串點擊「採用並開始」且八個步驟全數成功後，應自動跳轉至「工作頁面（F5）」，還是留在原討論串並顯示「開啟工作頁面」按鈕？
   - **建議預設值**：**在討論串原位顯示八步驟全數完成與「開啟工作頁面」主按鈕（並於側邊欄亮起新工作）**；若直接從輸入框的「執行 → 開始工作」啟動，則直接進入工作頁面。如此可讓使用者清楚看見計畫採用與工作建立的八步回執，同時支援一鍵進入工作頁。
2. **工作頁面「成果區（Results）」四個子區塊的預設展開狀態**
   - **問題**：當工作進入「成果待驗證（Result awaiting verification）」時，成果區的「變更檔案」、「程式碼差異」、「自動化測試」與「PR 與交付狀態」是否應全部自動展開？
   - **建議預設值**：**預設展開「PR 與交付狀態（含六階段狀態鏈與建立 PR 按鈕）」，而「變更檔案」、「程式碼差異」與「自動化測試」維持摘要標題、點擊按需展開**（於專屬「成果待驗證」檢閱情境下可全部展開以利審閱），避免長篇 Diff 擠壓下方 PM 回填決策區。
3. **負責人於工作頁拍板驗收後的預設返回位置**
   - **問題**：負責人在工作頁或總覽的 PM 回填卡拍板「驗收需求」後，預設應返回「專案總覽（Overview）」還是原「討論串（Discussion）」？
   - **建議預設值**：**提供兩個明確並列的決策動作按鈕：「驗收需求並返回總覽」（主按鈕）與「驗收需求並返回討論串」（次按鈕）**，讓負責人依當下檢視動線一鍵完成拍板與返回。
4. **忙碌中送出第二句指令（`after_current`）時的佇列上限與編輯能力**
   - **問題**：當第 1 輪仍在執行且使用者已排入一則下一輪指令（`msg_q_02`）時，在下一輪開始前是否允許再追加第二則佇列指令，或合併修改已排入的那一則？
   - **建議預設值**：**預設單一待執行佇列槽位（可於下一輪開始前直接附加說明或取消重寫）**，避免代理人在尚未看到前一輪結果前累積過多過期的多輪指令。
5. **外部代理人（Hermes）工作收件匣（Work Inbox）訊息的預設處理方式**
   - **問題**：當使用者對 Hermes 控制的執行中工作點擊「傳送至 Hermes 的工作收件匣」後，該訊息何時交付給 Hermes？
   - **建議預設值**：**比照 `after_current` 安全原則，將訊息寫入中央服務的該工作收件匣，待 Hermes 目前回合結束或主動查詢收件匣時讀取，絕不中途打斷或注入 Hermes 正在執行的回合**。
