# v1.3 E03 Work follow-up (second input)

This note records the Work-lane slice that queues one next instruction for a
connector-managed work item. It follows the reviewed loop spec's second-input
rules and the operation contract at `23e17e76`. It does not use the older
`0ab073fc` field names.

## Where it is mounted

The section is `[data-work-section="next-turn"]` inside the existing Work lane
of a linked session (`viewSession`). Work, Lineage, and Live hide that lane.
They do not rebuild the textarea, the legacy `#workspace-message-input`, or
`[data-workspace-result]`.

The earlier loop note placed this section in the kanban inspector. This slice
does not mount there. Kanban cards do not show it. The start panel's “Open live output” and “Open work”
links carry the explicit selection. The Result uses the existing fixed Result
panel for that same Attempt. Refresh and a newer Attempt in input history never
change this selection. Legacy links still open their session; they do not infer
Work send authority from the last workspace. With the follow-up capability,
a linked Work without validated context does not fall back to raw session.send.

When this capability is on, the Work lane has one instruction composer: the
next-step field. It sends only the work target. The old session field stays in
the page so its draft is kept, and it is hidden. The empty session panel is
hidden with it. It does not send. Question and permission answers stay in the
session panel. The mobile collapse control follows the next-step field, not
the hidden one. Enter uses the existing composer shortcut, including its
composition guard.

Without the capability, the session composer is unchanged and still sends
`{host, session_id}` with `queue: true`. The next-step section is not a
fallback to that target.

## When it is shown

All of these are required:

- `features.pm_workspaces.work_follow_up` is `{version: 1, available: true}`.
- The workspace, Work, and Attempt are explicitly selected in the route. Public Work and Attempt reads must match that workspace, Work, host, and session. A remembered workspace is only a return location and never an action target.
- The work item id is `work_item.work_item_id` on the linked item (`wi_` + 20 hex).
- The browser build is in use. The desktop shell does not offer the section.
  Typed input, exact Attempt, and Result reads are now integrated, but the
  complete native flow remains gated pending its integration acceptance.
  No broad route fallback is added.
- The attempt result is `pm-work-attempt-result/v1` for that same work item,
  and `next_allowed_actions` contains `session.send` whose target is exactly
  `{workspace_id, work_item_id}`, with `after_current` allowed.
- The session observation is `provenance: connector_managed` and
  `api_access: managed`, and the principal has `operate` plus `session.send`.

Missing capability, `available: false`, a manual or unknown session, a Codex
block (`codex_uncorrelated_turn_boundary`), or `not_controller` leaves the
section without a send, cancel, or resume control. A list or result
`403`/`404`/`410` removes the list, the receipt text, and the controls
together. A later `200` for a read that started earlier does not put them back.
A failed or malformed list or result drops send and row actions before the
replacement is known. It does not keep the previous admission. A partial page
does not prove that an omitted receipt is still authorized.

While a result read is unfinished, send is disabled. A failed read removes that field.

## What is sent

`POST /api/v1/operations` with action `session.send`.

- `target` is only `workspace_id` and `work_item_id`.
- `params` is trimmed `text` and `schedule: "after_current"`. `now` is not
  offered, even when the result also lists it.
- `preconditions` is `{expected_attempt_id}` when the list reported a real
  `att_` + 32 hex id, otherwise `{}`. That value is captured only when a new
  request is created.
- Empty text is not posted. Text longer than 20,000 characters is not posted.
- The idempotency key is the durable-form key. A lost acknowledgement retries
  that same key. `PM_WORK_ATTEMPT_CHANGED` and `INVALID_PRECONDITIONS` without
  `admission_refused` keep that same key and the same request. They do not
  start a new key. An explicit `admission_refused` response uses New request,
  and only that new request reads the current attempt.

Busy means the server queue (`after_current`), not a local queue and not
`schedule: now`.

## What counts as accepted

Only `operation.input_receipt` on the operation response, and only when its
`operation_id` is that operation. `result.input_receipt` is ignored. The list
row's `labels.state` and `labels.detail` for the active locale are shown as
the service wrote them. A missing locale string is "Unknown" / "未知", not
English copied into Traditional Chinese. "Queued for the next turn" is used
only for a correlated receipt whose state is `queued` or `waiting_external`.
A missing or mismatched receipt says accepted when the operation status is
`accepted` or `succeeded`, and unknown otherwise. The operation link stays so
it can be recovered. Queued is not called sent.

An acknowledged row stays only until a successful input page speaks about it.
If that page does not include the row, the page is not treated as permission
to keep showing it. `has_more` still means more steps exist and is not a total.

After that id, the field clears and can take another instruction. The first
receipt remains. Two identical sentences are two keys and two operation ids.
Cancel and resume post `{}` to the operation endpoint named by the receipt,
and only when that action's `operation_id` is this receipt, the actor matches,
and cancel is still `cancellable`. A blocked later row links to
`blocked_by_operation_id` and does not resume that later row. Edit and retry
copy `params.text` into the field and do not submit it. They do not read the
operation back, and they do not substitute `text_excerpt`.

The list is `GET .../work/{work_item_id}/inputs`. `has_more` says there are
more steps and does not invent a total. `visibility_filtered` says some steps
are hidden and does not show zero. There is no second event reader, poll loop,
or draft store. The existing durable form and the session's event refresh are
reused.
