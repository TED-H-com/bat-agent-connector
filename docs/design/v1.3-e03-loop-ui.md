## 0. 三個入口共用的規則

1. **手動、外來、未知工作階段只讀。** 不提供送出、恢復、中斷或清理。判定跟 P5 §15.4：registry 的 `start_operation_id` 與這次 Attempt 的 handoff 不一致、provenance 為 `manual_bat` 或 `discovered_existing`、或不在 registry。畫面不從路徑或名稱推測擁有者。表單不出現，而不是一顆不能按的送出。
2. **六個詞各說各的。** 「已保存」「已送達」「執行中」「本輪結束」「已驗收」「已部署」不能共用 Finished（計畫 §6.4）。本檔另外保持：父階段 `accepted` 是「已排入採用並開始工作」，不是藥丸「已驗收」；Work 階段 `started` 是「已開始」，不是 P5 的「已送出」，也不是交付的「已部署」。排隊獲准不等於已送出。
3. **中斷是另一個意圖。** 現有工作階段頁的 `session.interrupt`（`desktop/src/app.js:1498-1501`，工作台開啟時收在溢位選單 `:1558-1567`）保持獨立。下一輪的送出不附中斷、不附「立刻送出」。
4. **中央證據。** 沒有 operation id 之前不說已受理。未知不顯示成 0。分頁的 `next_cursor` 不是總數。來源以 403／404 撤回時，列、計數與檢視細節一起拿掉；遲到回應不得把它們補回來。
5. **持久表單。** 採用並開始，以及開始工作面板裡的設定檔選擇，沿用 `durableForm`（`desktop/src/pm-workspace.js:69-310`）：送出前先把 idempotency key 寫進 `localStorage`，遺失回覆用原 key 查，入場拒絕凍結該意圖並顯示既有的「新請求」（`pm_edit_request`）。送出中焦點留在提交鈕，用 `aria-disabled` 而不是把焦點放掉（`:179-188`）。連線元件在斷線時停收據計時、保留 key、不另送一筆（`:275-284`）；離開畫面時 `dispose` 停計時並停用欄位（`:303-307`）。工作區事件仍走 `onEvents`（`desktop/src/app.js:721`、`:740-774`）與 `desktop/src/pm-workspace.js:1771-1794`。
6. **下一輪不能把輸入框鎖到 `succeeded`。** `durableForm` 要到 `status === "succeeded"` 才清掉意圖（`desktop/src/pm-workspace.js:250-255`），而 `locked()` 在意圖還在時保持鎖定（`:286`）。排隊中的下一輪會停在 `waiting_external`。下一輪改用同一套意圖、原 key 與連線觀察，但只要回覆裡已經有 operation id，就放開輸入框、把該句掛到那張回執、下一句用新 key。詳見 §2.4。這不是新的後端動作。
7. **字串。** 新文案進既有的 `*-strings.js`，鍵名用下表的 `loop_*`。英文字與台灣慣用繁中成對。不把原始錯誤碼、`undefined`、`null` 或英文殘句顯示成主要句子。錯誤碼只進既有的 Details（討論用 `pd_details`，設定頁用 `global_details` 的寫法，見 `desktop/src/settings-agents.js:19-38`）。
8. **CSP。** 用既有的 `h()` 建節點。不加行內 `<style>`、`style=""` 或會解析標記的 `innerHTML`。不渲染代理或提供者給的 HTML。

## 1. 採用並開始

計畫 F3：一次授權、兩個分開記錄的階段，不假裝跨資料庫、Git 與 runtime 有一筆原子交易。負責人方向：「採用，稍後做」留在討論；「採用並開始」直接開啟準備中的工作。

### 1.1 位置與怎麼到達

提案審閱就是 `planProposals`（`desktop/src/pm-plan-proposals.js:28`），由工作區掛進 `.pd-transcript`。既有「審閱並採用」鈕（`data-proposal-review`，`pd_review`，`:250-266`）仍只負責打開審閱，不改成送出。

打開之後，在既有採用表單（`pm.conversation.adopt`，`:58-72`）旁邊加第二個表單，動作 `work.adopt_and_start`，目標仍是 `{workspace_id, thread_id}`。

| 寬度 | 呈現 |
|---|---|
| 桌面 | 兩個送出留在同一份審閱裡，跟在理由欄之後。選定工作是審閱內的核取清單，不是新頁。 |
| 窄螢幕 | 同一份討論卷軸。不另做抽屜資料。人送出並拿到 operation id 之後，看板檢視用既有的全寬檢視（`components.css:114-116`）顯示父階段。 |

到達方式：討論串 → 提案 → 審閱並採用。不從看板卡片直接呼叫 `work.adopt_and_start`。看板只負責落地之後的父階段與各 Work 階段。

**誰看得到第二個送出。** 能力 `features.pm_workspaces.work_adopt_and_start.version === 1` 且 `available === true`，呼叫端已是既有 `deciding()`（`pm-plan-proposals.js:34-35`：寫入、`decide`、scope `start`、`pm.conversation.adopt` 允許、計畫可採用），並且 scope 含 `manage`、該動作在能力清單裡允許。做不到的人仍只看到既有的「採用」。缺的是什麼寫在那顆鈕的位置，不顯示一顆不能按的主要鈕。

能力還沒掛上時，既有送出文案維持 `pcp_adopt`（「採用」／「Adopt」）。能力掛上之後，同一顆既有送出改成「採用，稍後做」。動作仍是 `pm.conversation.adopt`，成功後仍留在討論（`:163-175`）。

### 1.3 請求

介面只呼叫 P6 已經寫的預覽與 `POST /api/v1/operations`。子操作的 key（`work-adopt-and-start:{parent_id}:adopt` 與 `:work:{i}`）由伺服器鑄，畫面不送。

**列出可選工作。** 用看板已經在讀的 `GET /api/v1/pm/workspaces/{workspace_id}/kanban`（`desktop/src/pm-kanban.js:391`）。分頁沿用 `after`／`limit`／`next_cursor`。有 `next_cursor` 就提供「還有工作」，不把這一頁的長度當總數。P6 沒有另一份工作目錄，本檔也不新增。封存或找不到的卡從清單移除。不能在這個動作裡建立 Work（P6 Decision 2，`:317-321`）。

**預覽。** `POST /api/v1/pm/workspaces/{workspace_id}/threads/{thread_id}/adopt-and-start-preview`（P6 Decision 9.2，`:1205`）。scope `observe` 加上成員。它不建立 operation。Body 用 Decision 9.3（`:1213-1224`）：`proposal_id`、審閱裡的 `review`、選填 `rationale`、以及 1 到 10 筆 `works`。每一筆帶 `work_item_id`、`requirement_ids`（必須出現在 `review.requirements`）、選填的部分 `code_target`、`delivery`、`agent`、`model`、`instruction`。不帶 `profile_id`（Decision 2 的欄位沒有它，`:322-331`）。

預覽成功是 HTTP 200，即使某一筆 `readiness.ready === false`（Decision 9.3，`:1231`）。整筆失敗才是提案、討論、計畫基線、缺工作或目標不合法。頂層 `preconditions` 是四個基線加上每一筆九個固定鍵，**不含** `expected_scope_revision`（`:1238`，Decision 3 `:356`）。送出時原樣複製這份 `preconditions`，畫面不自組 `scope_revision`。

**送出。** 一筆 `work.adopt_and_start`。目標 `{workspace_id, thread_id}`。參數是 P6 §4.1 與 Decision 2：`proposal_id`、`review`、`rationale`（1..4000）、`works` 1..10。每一筆的 `instruction` 1..4000、`agent`、`delivery`、完整四鍵 `code_target`、`requirement_ids`。前提是預覽回傳的那份，且指紋仍與畫面上的審閱、選取、指令、交付、目標一致。選取在入場後凍結；畫面不再改這筆 operation 的清單。

冪等：同一個 key 加同一份 body 重播同一 `operation_id`。body 不同是 `IDEMPOTENCY_CONFLICT`（409）。key 在第一次送出前寫入 `durableForm`。預覽不是 operation，不消耗這個 key。預覽過期時，若 key 還沒寫入，先重跑預覽再送；若 key 已經寫入，只查原筆，不換 key。

空選取不呼叫預覽，也不顯示「採用並開始」。重複的 `work_item_id` 在畫面上就擋下。伺服器對空清單、超過 10 筆或重複 id 仍以 `INVALID_PARAMS`（422）拒絕。第 11 個核取方塊停用。

**取消與恢復。** 只在 §1.2 該列有寫的階段，對**父** operation id 呼叫既有的 `POST /api/v1/operations/{id}/cancel` 或 `/resume`。不另造取消路由。`start_unknown` 的取消文案必須說明它不會結案未知的啟動。`works[i].status === "stopped"` 時，取消的是該筆 `start_operation_id`，不是父 id。結果未知時不提供新的 `work.start`（否則會碰到 `PM_WORK_START_OUTCOME_UNPROVEN`）。

**落地。** 回應裡出現 `operation_id` 之後，離開討論，打開 `#/pm/{workspace_id}/board?select={第一筆選定工作}`。第一筆是送出清單的 index 0，不是「看起來最就緒」的那筆。其餘選定工作是檢視裡的連結，不另做多工檢視。討論裡未送出的訊息草稿保留。返回連結回到 `#/pm/{workspace_id}/discussions/{thread_id}`。

這顆瀏覽器要能在重新整理後找到父 operation：在拿到 id 的當下，把 `{version:1, operation_id, thread_id, work_item_ids}` 寫進 `localStorage` 鍵 `batc.pm.${namespace}.adopt-start-landing.${workspaceId}`。這只是本機書籤。清掉它不會取消伺服器上的操作。沒有這筆記錄時，檢視不顯示父階段，也不掃全部 operations。人仍可從討論回執的 `#/op/{id}` 打開原操作。

### 1.4 狀態與刷新

- 預覽用遞增票號。回應的票號、`proposal_id` 或連線世代不符就丟棄。斷線時丟掉進行中的預覽回應，保留表單草稿，不自動重送。
- 父階段的權威讀取是 `GET /api/v1/operations/{operation_id}`（P6 Decision 10.2）。`result` 只在父操作自己寫入進度時更新（Decision 4，`:482`）。已有 `start_operation_id` 的 Work，另外讀該筆 operation 或既有的 attempt 讀取，不把父 `result` 裡較舊的列當成即時真相。
- `result` 還沒有、operation 仍是 `accepted`：用「已排入採用並開始工作」。不把缺少的 `works[i]` 顯示成「尚未開始」。`result` 是 null 而 status 已是 `running`：只顯示既有操作狀態詞，不自造 `works[]`（§5）。
- 事件：`operation`、`pm_`、`work_item` 來到時重讀這筆 operation 與預覽所依賴的提案。重繪時保留審閱草稿、核取、指令游標，以及已展開的 Details。人正在打字的那一列不因刷新被搬走。
- 離開討論：`proposalReview.dispose`（`pm-workspace.js:1803`）停計時。草稿與已寫入的 key 留在 `localStorage`。回到同一討論時用原 key 查，不另 POST。
- 連線換成另一個 namespace：舊 key 不可在新連線上重送。表單停用，狀態說明連線已換。草稿文字留在原鍵，不搬過去。
- 討論或工作區 403／404：拿掉審閱、選定列、父階段與計數。遲到的預覽不得把列補回。
- 「採用，稍後做」成功後的確認維持現況，留在討論並連到已採用修訂。

### 1.6 無障礙

鍵盤順序：審閱開關 → 既有審閱欄位 → 理由 → 工作核取（看板卡片順序）→ 已勾選項的指令 → 檢查就緒 → 採用，稍後做 → 採用並開始。狀態區是 `role="status"`，不進 Tab 順序。

打開審閱時，焦點維持現況，落在審閱裡第一個核取方塊（`pm-plan-proposals.js:262`）。預覽回來不搶焦點，只更新狀態區：「就緒已更新」／「Readiness updated」。送出中焦點留在「採用並開始」。入場失敗把焦點移到「新請求」或狀態區，沿用 `durableForm`。拿到 operation id 後，焦點移到看板檢視的標題，狀態區朗讀父階段標題。無法換頁時，焦點留在討論裡的階段狀態。

取消與恢復之後，焦點留在該按鈕；按鈕若因階段改變而消失，移到階段狀態。Esc 關閉檢視並把焦點還給打開它的卡片，沿用既有檢視。

## 2. 下一輪

計畫 F5：人留在同一項已開始的工作。忙碌時先排進 Connector 的下一輪，不改向正在跑的回合。每一則輸入有自己的 id 與回執。中斷不是這顆送出的一部分。

P5 不新增 `work.follow_up`。動作仍是 `session.send`，目標恰好是 `{workspace_id, work_item_id}`。P5 §15 是實作紀錄，與正文衝突時以 §15 為準：Codex 在入場拒絕；成果上的下一步只有 Work 目標；結果未確認會擋住後面的排隊輸入，而且不能把已送出的那筆取消成未送出。

### 2.1 位置與怎麼到達

只放在看板 Work 檢視，不改工作階段頁底部的舊輸入框。舊輸入框仍送 `{host, session_id}` 與 `queue`（`desktop/src/app.js:1455-1486`），它不是下一輪，本檔不刪它，也不把佇列核取方塊搬過來。

新區是檢視的頁尾，`data-work-section="next-turn"`，做為 `.ui-inspector` 的頁尾，與 `.ui-inspector-body` 同層，所以正文捲動時輸入框留在底部。桌面寬 400px；799px 以下同一顆頁尾在全寬檢視裡。節點由看板插入，順序在既有成果區之後、檢視底部之前，並且像 Part A 一樣保留兄弟節點（`pm-work-inspector.js:281-307`、`pm-kanban.js:311-349`）。

人從看板卡片打開已開始、且由自己控制的受管工作。工作階段頁的「開啟即時輸出」仍通往工作階段，那個頁面不加 Work 目標的輸入框。

能力 `features.pm_workspaces.work_follow_up.version === 1`，而且成果的 `next_allowed_actions` 允許這個 Work 目標的 `session.send`，表單才出現。手動、外來、未知、Codex 被拒、或讀取尚未結束時，表單不在。讀取中不放一顆會讓人以為可以送的按鈕。

| `unknown` | Delivery unconfirmed | 結果未確認 | Reply was lost after send began. Do not resend; reconcile with the original ID.／送出後未收到回覆。請勿重送，請以原 ID 重新確認結果。 | 「Reconcile with original ID」／「以原 ID 重新確認」。沒有取消，沒有重送 |
| `cancelled` | Cancelled | 已取消 | Cancelled while waiting before any frame was sent to BAT.／於等待期間取消，未向 BAT 送出任何封包。 | 「Edit and send as new instruction」／「編輯並以新指令送出」 |

取消鈕的可見文字就是上表那句，不縮成會和「取消工作」混淆的單字「取消」。它超過三個英文詞，因為更短的字會和中斷、取消父操作相混；這是刻意的。

「已送出」只用於 `sent`。不把 `queued` 說成已送達，不把 `sent` 說成已驗收或已部署，不把回合結束說成已開始。

### 2.3 請求

**送出。** `POST /api/v1/operations`，`action` 是 `session.send`。目標只有 `{workspace_id, work_item_id}`。多帶 `host`、`session_id`、`task_id` 或 `attempt_id` 會被 `INVALID_TARGET`（422），畫面不帶。參數只有 `{text, schedule}`。`schedule` 固定 `"after_current"`。不送 `queue`，不送 `now`，不送呼叫端的 `message_id`。文字是去掉首尾空白後的 1..20000 字元。

前提只送 `expected_attempt_id`，值是這次檢視正在看的最新 attempt。還沒有 attempt id 時，省略整個前提，不送 null。未知的前提鍵是 `INVALID_PRECONDITIONS`（422）。

每一則送出有自己的 idempotency key，在該則 POST 前寫入。同一 key 與同一 body 重播同一 operation。換文字或換 attempt 就是另一則，用新 key。不把兩句併成一筆。

權限沿用 P5：送出要 `operate`、寫入成員、同一個控制者。讀取清單要 `observe` 與成員。取消與恢復的路由要 `observe`，而且必須是原動作人、寫入成員、同一個控制者。畫面不放寬。

**清單。** `GET /api/v1/pm/workspaces/{workspace_id}/work/{work_item_id}/inputs`（`pm_work_inputs_list`）。query 只有 `after`、`limit`（1..100，預設 50）與選填 `attempt_id`。順序是 `sequence` 升冪。回應使用 `items`、`next_cursor`、`has_more`、`visibility_filtered`、`latest_attempt_id`，以及 P5 §15.6 的 `workspace_id`、`work_item_id`、`attempt_id`。沒有總數欄，畫面不造一個。

**取消。** 只有回執 `cancellable === true`。P5 §7.1 與 §8.2 順序 6：那就是 `state === "queued"` 且 `send_sent is not True`。呼叫 `POST /api/v1/operations/{operation_id}/cancel`。圍欄之後沒有這顆鈕。若人仍打到取消而得到 `PM_WORK_CANCEL_NOT_ALLOWED_AFTER_SEND`，拿掉鈕，句子用 §7.3：「指令已進入送出階段；開始送出後無法透過取消撤回指令。」

**結果未確認。** `POST /api/v1/operations/{operation_id}/resume`，原 id。不重送、不取消。後面被擋住的列保持排隊，並連到 `#/op/{blocked_by_operation_id}`。

**沒有原地編輯。** `work_inputs` 不可變（P5 §4.1）。取消成功後，「編輯並以新指令送出」把文字放回輸入框並使用**新** key。完整文字來自既有的 `GET /api/v1/operations/{operation_id}` 的 `params.text`（回執連結已含這支，P5 §15.7）。回執只有 `text_excerpt` 且 `text_truncated` 時，不得把摘要填進輸入框冒充全文。那支 GET 被撤回時，輸入框留空，狀態用 `loop_next_unavailable`。

**不提供 `schedule=now`。** 即使成果的 `allowed_schedules` 含 `now`，這顆鈕仍只送 `after_current`。`now` 會在忙碌或等待輸入時被拒，而且不是改向。要等以後的規格再加第二顆意圖。

### 2.4 狀態與刷新

- 輸入草稿鍵：`batc.pm.${namespace}.work-next.${workspaceId}.${workItemId}`，只存尚未送出的文字與尚未取得 operation id 的那一筆意圖。已獲 id 的句子改掛在回執上，不留在輸入框。
- POST 回了 operation id（含 `accepted`、`waiting_external`、清單上的 `queued`）：清空輸入框、放開、下一句用新 key。狀態區說「已排入下一輪」／「Queued for the next turn」，不用「已送出」。
- POST 在拿到 id 前遺失：輸入框保持鎖定，鈕變成「查回原請求」，用原 key 再查。人按才查。查到 id 就放開並顯示回執。查到入場拒絕就凍結，顯示「新請求」，文字還在。
- 同一時間只有一筆尚未取得 id 的送出。前一筆還在排隊不阻止下一句，因為前一筆已經有 id。
- 斷線：停輪詢，保留 key，不新 POST。連上之後若已有 id 就重讀該 operation 與清單；若還沒有 id，維持「查回原請求」。
- 離開檢視：停計時，文字留在本機。檢視節點還在時保留游標。節點重建時還原文字，游標放在結尾。不把人正在打的那一列換位。
- 事件刷新重讀清單與相關 operation，票號不符的回應丟棄。展開的 Details 保持。連線世代變了就停用這個頁尾，不把舊 key 送到新連線。
- 工作或來源 403／404：頁尾、清單與檢視裡的這項細節一起拿掉。遲到清單不得補回。
- `visibility_filtered`：顯示 `loop_next_hidden`，不把被濾掉的列數顯示成 0。

### 2.6 無障礙

鍵盤順序：清單裡每一列的回執連結 → 該列唯一的下一步按鈕 → 輸入框 → 送出下一步。取消只在 `cancellable === true` 的列上，位置在該列連結之後。

狀態區 `role="status"`。清單更新時朗讀新增列的狀態詞，不把整份清單重讀。撤回時朗讀「這項工作已不在這裡」。

其他 query 拒絕。這樣看板草稿的 hash 回得去，也不會把 operation id 塞進允許清單。

### 3.4 狀態與刷新

- 設定檔選單與就緒用票號。換工作、換設定檔或連線世代前進時，舊回應丟棄。
- 清單或就緒 403／404／`PM_WORK_PROFILE_WITHDRAWN`：從選單拿掉該列、拿掉六個狀態與缺口連結，選回「不使用設定檔」。遲到回應不得把該列加回。`count` 用新的清單回應，不在本機減一個湊數。
- 草稿仍在開始面板的 `durableForm`（`pm-work-start.js:784-788`，鍵 `${namespace}.work-start`）。去設定頁不會清它。返回原 hash 時還原指令與選擇。面板既有的游標保留規則繼續有效（E02）：節點還在就不動游標；重建則還原文字並把游標放在結尾。
- 從設定頁返回時，焦點放在就緒狀態區，讓人聽到新的六個狀態，而不是直接按開始。事件刷新不搶走正在輸入的指令欄。
- 斷線：停就緒讀取，保留已選 id 與開始草稿，不另送 `work.start`。連上後重讀清單與就緒。
- 離開檢視：停讀取。草稿留下。另一個連線不讀這份草稿。

### 3.5 錯誤與下一步

| 代碼 | 缺什麼 | 在這裡可以做 | 哪個設定能補 | 草稿 |
|---|---|---|---|---|
| `PM_WORK_PROFILE_WITHDRAWN` | 設定檔已撤回。讀取與預覽是 404，入場是 409 | 選單移除該列。開始改走「不使用設定檔」，或另選一列後重新預覽 | 無。不在這裡恢復撤回 | 指令保留。已凍結的開始意圖按「新請求」後才改 |
| `PM_WORK_PROFILE_CHANGED` 409 | 修訂或 digest 已不是預覽時那一筆 | 重新檢查就緒與啟動預覽。不送舊前提 | 無 | 保留 |
| `PM_WORK_PROFILE_TARGET_MISMATCH` 409 | 儲存庫、主機、工作區、交付、代理或模型與設定檔不同 | 改面板上的選擇，或改選設定檔，然後重新預覽 | 無。不在開始鈕裡改設定檔文件 | 保留 |
| `NOT_FOUND` 404 | 沒有這份設定檔，或人不是成員 | 拿掉該列 | 無 | 保留 |
| `FORBIDDEN` 403 | 連讀取的 `observe` 都沒有 | 整個選單不出現 | 成員資格 | 開始草稿若已存在則保留，但不套設定檔 |
| `INVALID_PARAMS` 422 | 清單 query 不合法，或預覽在設定檔要求交付時省略了 `delivery` | 不送那份 query。交付沿用面板已選的值 | 無 | 保留 |
| 既有 `work.start` 的拒絕 | 與今天的開始面板相同 | 沿用 `wst_error_*` 與 E02 §7。本節不改寫那些斷言 | 綁定與主機仍走上面的缺口連結 | 保留 |
| 缺口是本機 Git、主機不可達、動作不存在 | 沒有可按的修復 | 只顯示 §3.2 的句子 | 無。不探測、不改寫 Git | 保留 |
| 設定已保存但就緒仍是尚未驗證 | 沒有這次執行的證據 | 句子用「已設定不等於就緒」 | 人可以再去連線設定，但保存不會讓開始變成已驗證 | 保留 |

開始鈕在設定檔已選、但 `can_start_own` 不是 `ready` 時，仍可依今天的啟動預覽就緒來啟用。它表示這次預覽的檢查過了，不表示寫程式路線已驗證。按鈕旁保持 `loop_profile_saved_not_ready`。

### 3.6 無障礙

鍵盤順序：設定檔選單 → 六個狀態（若缺口有連結，連結緊接在狀態後面）→ 既有的指令、代理、交付、需求與檢查 → 開始。返回連結是連線區裡、表單之前的第一個連結。

選了設定檔之後，焦點留在選單，狀態區朗讀六個狀態裡第一個非就緒的名稱與「已設定不等於就緒」。按下缺口連結再返回時，焦點在就緒狀態，不在開始鈕。開始的送出焦點規則不變（指令空白時焦點回指令，`pm-work-start.js:575-577`；面板 `focus()` 仍先到指令，`:1028-1032`）。

撤回時狀態區朗讀 `loop_profile_withdrawn`。

## 5. 後端規格缺口

介面不補這些缺口，也不自造欄位。

1. **P6 Decision 9.2（`:1208`）寫預覽會回 `can_submit`。** Decision 9.3 的 JSON（`:1240-1316`）與 Decision 10 的能力物件（`:1354-1371`）都沒有這個鍵。畫面改用已經拿得到的 scope、`deciding()` 與動作是否允許。不假設有 `can_submit`。
2. **P6 預覽的 `code_target` 可以是部分篩選（`:1220`），但回應只有一個 `code_target` 與 `source`，沒有 `candidates`。** 開始面板在 0 或多個候選時會收到 `candidates`（`pm-work-start.js:621-628`）。採用並開始的回應沒寫這種形狀。`code_target` 或 `source` 缺了，該列就是還不能開始，畫面不猜測、不加選單。
3. **沒有「這項工作目前的採用並開始」讀取。** 父階段只靠這次瀏覽器在 POST 之後記下的 operation id，再 `GET /api/v1/operations/{id}`。沒有這筆記錄就不顯示父階段。不掃 operations 清單。
4. **父 `result` 為 null 且 status 已是 `running` 時，Decision 4 沒有對應階段。** `accepted` 且尚未建立採用子操作時，用「已排入採用並開始工作」（Decision 4，`:413`）。其餘 null `result` 只顯示既有操作狀態，不自造 `works[]`。
5. **Decision 11 的 `{current_work_item_id}` 不是回應欄位。** 由第一個 `stage === "starting"` 的列推出。沒有這種列就不填名字。
6. **P5 清單的指令只有 `text_excerpt`／`text_truncated`（§8.1）。** 全文用既有 operation GET 的 `params.text`。不要求清單加一個 `text` 欄。
7. **P5 §15.9。** 桌面 bridge 的 GET 允許清單沒有 `/inputs` 與成果路由。本檔不改 bridge，也不把這件事說成新的 HTTP 路由。
8. **E01 §6.3 寫的派工 hash 是一段專案識別。** 應用程式還有兩段的 `#/dispatch/{project}/{work}`（`repair-panel.js:44`）。允許清單含這兩種既有形狀，不含第三段，也不含 E01 沒點名的 query。這是返回位置要對得上現有連結，不是新的設定 API。

## 6. 設計取捨

1. **採用並開始一拿到 operation id 就打開第一筆選定工作的看板檢視。** 另一個做法是留在討論直到全部 `started`。負責人寫的是直接開啟準備中的工作，所以採用前者。其餘工作用連結，不做多工檢視。
2. **「採用，稍後做」仍是 `pm.conversation.adopt`。** 能力未掛上時不改既有「採用」文案，避免出現一個沒有配對的「稍後」。
3. **Decision 11 與 P5 §10 的長句是狀態與無障礙名稱。** 採用並開始的可見按鈕維持三個詞以內。下一輪的取消鈕保留全句，因為「取消」會和取消工作、中斷回合相混。
4. **下一輪只送 `after_current`。** 不提供 `now`，即使允許清單裡有它。`now` 不是預設，也不是改向，失敗模式和排隊不同。
5. **排隊沒有原地編輯。** 資料列不可變。要改就先取消仍可取消的那筆，再以新 key 送出。
6. **下一輪不把輸入框鎖到操作成功。** 否則第二句無法在第一句還在等回合時送出。原 key、凍結的入場拒絕與斷線不重送仍然保留。
7. **設定檔不自動套用，也不放進採用並開始。** 與 E01 決策 1、P6 Decision 2 一致。
8. **父 operation 的書籤放在 `localStorage`，不放進 hash。** E01 的返回允許清單沒有 operation id。另一個做法是 `?op=`，那會擴大允許清單，本檔不做。
9. **錯誤碼只進 Details。** Decision 11 的原因模板含 `{error_code}`。主要句子用階段標題與 §1.5／§2.5／§3.5 的在地化說明，避免 zh-TW 畫面出現英文碼。
