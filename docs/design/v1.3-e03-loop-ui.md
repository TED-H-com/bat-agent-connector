## 0. 三個入口共用的規則

1. **手動、外來、未知工作階段只讀。** 不提供送出、恢復、中斷或清理。判定跟 P5 §15.4：registry 的 `start_operation_id` 與這次 Attempt 的 handoff 不一致、provenance 為 `manual_bat` 或 `discovered_existing`、或不在 registry。畫面不從路徑或名稱推測擁有者。表單不出現，而不是一顆不能按的送出。
2. **六個詞各說各的。** 「已保存」「已送達」「執行中」「本輪結束」「已驗收」「已部署」不能共用 Finished（計畫 §6.4）。本檔另外保持：父階段 `accepted` 是「已排入採用並開始工作」，不是藥丸「已驗收」；Work 階段 `started` 是「已開始」，不是 P5 的「已送出」，也不是交付的「已部署」。排隊獲准不等於已送出。
3. **中斷是另一個意圖。** 現有工作階段頁的 `session.interrupt`（`desktop/src/app.js:1561`）保持獨立。停止鈕在受管列上依 `session.interrupt` 是否允許來啟用（`:1812-1813`）。下一輪的送出不附中斷、不附「立刻送出」。
4. **中央證據。** 沒有 operation id 之前不說已受理。未知不顯示成 0。分頁的 `next_cursor` 不是總數。來源以 403／404 撤回時，列、計數與檢視細節一起拿掉；遲到回應不得把它們補回來。
5. **持久表單。** `durableForm`（`desktop/src/pm-workspace.js:69-310`）在送出前把 idempotency key 寫進 `localStorage`。鍵的格式是 `batc.pm.${namespace}.${action}.${JSON.stringify(target)}`（`:70`）。`allowed()` 要求 `requiredScope` 在 scopes 裡，而且該動作列 `allowed === true`（`:102-103`）。預設 `requiredScope` 是 `manage`。它在意圖還在時保持鎖定（`locked()`，`:286`），要到 `status === "succeeded"` 才清掉意圖（`:250-255`）。入場拒絕只有在錯誤帶 `admission_refused === true` 時才凍結該意圖並顯示既有的「新請求」（`pm_edit_request`，`:265-268`、`:188`）。沒有這個旗標時，表單不會自己解鎖。送出中焦點留在提交鈕，用 `aria-disabled`（`:179-188`）。連線元件在斷線時停收據計時、保留 key、不另送一筆（`:275-284`）；離開畫面時 `dispose` 停計時並停用欄位（`:303-307`）。工作區事件仍走 `onEvents`（`desktop/src/app.js:767`、`streamEvents` 自 `:786`）與 `desktop/src/pm-workspace.js:1771-1794`。
6. **下一輪的解鎖是 `durableForm` 的新選項，不是今天已有的行為。** 今天沒有在成功之前放開輸入框的路徑。下一輪傳 `releaseAfterAcknowledgement: true`（預設 false）與 `requiredScope: 'operate'`。選項為 false 時，行為與今天完全相同。選項為 true 時：還沒有 operation id 就不放開，遺失的 POST 仍是「查回原請求」與同一個 key；回覆裡一旦有 operation id，就清掉這一則的意圖與輸入值，讓下一則用新 key，該則改由輸入清單呈現。入場拒絕仍只靠 `admission_refused`，而且在沒有 operation id 時不放開。同一時間只有一則尚未取得 id 的送出。這不是新的後端動作，也不另做第二套儲存。詳見 §2.4。
7. **字串。** 新文案進既有的 `*-strings.js`，鍵名用下表的 `loop_*`。英文字與台灣慣用繁中成對。不把原始錯誤碼、`undefined`、`null` 或英文殘句顯示成主要句子。錯誤碼只進既有的 Details（討論用 `pd_details`，設定頁用 `global_details` 的寫法，見 `desktop/src/settings-agents.js:19-38`）。說明句不重複同一顆鈕上的字。
8. **CSP。** 用既有的 `h()` 建節點。不加行內 `<style>`、`style=""` 或會解析標記的 `innerHTML`。不渲染代理或提供者給的 HTML。

實作順序在 §4。E01 的後端已定案，它的畫面最先做。

## 1. 採用並開始

計畫 F3：一次授權、兩個分開記錄的階段，不假裝跨資料庫、Git 與 runtime 有一筆原子交易。負責人方向：「採用，稍後做」留在討論；「採用並開始」直接開啟準備中的工作。

### 1.1 位置與怎麼到達

提案審閱就是 `planProposals`（`desktop/src/pm-plan-proposals.js:28`），由工作區掛進 `.pd-transcript`。既有「審閱並採用」鈕（`data-proposal-review`，`pd_review`，`:250-266`）仍只負責打開審閱，不改成送出。

打開之後，在既有採用表單（`pm.conversation.adopt`，`:58-72`）旁邊加第二個表單，動作 `work.adopt_and_start`，目標仍是 `{workspace_id, thread_id}`。兩個表單共用同一份審閱與同一份理由，不各做一份輸入。審閱是採用表單既有的隱藏 `review`，理由是既有的 `rationale`（`:58`、`:66-68`）。第二個表單送出時讀這兩個值。

兩份表單互相鎖住，比照準備與採用（`:49`、`:53`、`:70`）：任一份 `locked()` 為真且還沒有 `replaceable()` 時，另一份不能送，共用的審閱與理由停用。`replaceable()` 是操作已失敗或已取消，或入場拒絕已經帶著 `admission_refused`（`pm-workspace.js:286`；`terminal()` 只含這兩個狀態，`:126`）。成功會清掉意圖，`locked()` 因而放開。待處理或已受理的那一筆因此會擋住另一份，直到它失敗、取消、成功，或人按「新請求」。

| 寬度 | 呈現 |
|---|---|
| 桌面，至少 1200px | 兩個送出留在同一份審閱裡，跟在理由欄之後。選定工作是審閱內的核取清單，不是新頁。 |
| 800–1199px | 同一份討論卷軸。看板檢視是既有覆蓋層（`components.css:111-113`）。 |
| 799px 以下，含 768px 與 390px | 同一份討論卷軸。看板檢視是既有全寬（`components.css:114-116`）。 |

到達方式：討論串 → 提案 → 審閱並採用。不從看板卡片直接呼叫 `work.adopt_and_start`。看板只負責落地之後的父階段與各 Work 階段。

**誰看得到第二個送出。** 三個條件一起成立才顯示，並且才把既有「採用」改成「採用，稍後做」：

1. 能力 `features.pm_workspaces.work_adopt_and_start.version === 1` 且 `available === true`（P6 Decision 10，`:1355-1357`）。
2. 動作列有 `work.adopt_and_start` 且 `allowed === true`。
3. 呼叫端已是既有 `deciding()`（`pm-plan-proposals.js:34-35`）。`deciding()` 已經要求 `writing()` 的 `manage`、`decide`、scope `start`、`pm.conversation.adopt` 允許，以及計畫可採用。看得到採用的人不會再單獨缺 `manage` 或 `start`。

做不到的人仍只看到既有的「採用」（`pcp_adopt`）。不顯示沒有配對的「採用，稍後做」，也不顯示一顆不能按的主要鈕。缺的是什麼寫在第二個送出的位置：

| 達不到的條件 | English | zh-TW |
|---|---|---|
| 能力不在，或 `available !== true` | Adopt and start is not available on this connection. | 這次連線沒有採用並開始。 |
| 動作列不在，或 `allowed !== true` | Adopt and start is not allowed on this connection. | 這次連線不允許採用並開始。 |
| 不是工作區擁有者（沒有 `decide`） | Only the workspace owner can adopt and start. | 只有工作區擁有者可以採用並開始。 |

前兩列用 `loop_adopt_start_unavailable` 與 `loop_adopt_start_denied`。第三列用 `loop_not_owner`。沒有「有採用、卻缺 manage 或 start」這一句，因為那條路走不到。

`depends_on` 非空時，父操作入場會以 `PM_WORK_START_PREREQUISITES`（409）整筆拒絕，而且不建立 operation（Decision 2，`:326`；Decision 9.3，`:1217-1220`）。預覽對單筆阻礙仍回 HTTP 200，該列 `readiness.ready === false`、`blocking_code` 為 `PM_WORK_START_PREREQUISITES`（`:1231`）。人在送出前看到的是停用的需求，加上該列的「還不能開始」。這種列不進送出 body。

預覽成功是 HTTP 200，即使某一筆 `readiness.ready === false`（`:1231`）。整筆失敗才是提案、討論、計畫基線、缺工作或目標不合法。`WORK_ITEM_NOT_FOUND` 在預覽是整筆失敗，回應不指出哪一列（`:1230`）。這時重新讀工作目錄，留下仍在目錄裡的勾選，用 `loop_works_removed` 說出被拿掉的標題，然後對剩下的勾選再預覽一次。一個都不剩就回到空清單，不送出。

頂層 `preconditions` 是四個基線加上每一筆九個固定鍵，**不含** `expected_scope_revision`（`:1238`，Decision 3 `:356`）。送出時原樣複製這份 `preconditions`，畫面不自組 `scope_revision`。

回應的 `adoptable` 是能不能送出的信號（Decision 9.2 的散文在 `:1208` 同時寫了 `can_submit`；Decision 9.3 的 JSON 只有 `adoptable` 與 `adoptable_reason`，`:1245-1247`）。畫面讀 `adoptable`，不假設有 `can_submit`。`adoptable === false` 時不送出，`adoptable_reason` 進 Details。每一列還看自己的 `ready`：只有 `readiness.ready === true` 的列能進送出 body。

**送出。** 一筆 `work.adopt_and_start`。目標 `{workspace_id, thread_id}`。`requiredScope` 傳 `start`，`permitted()` 另外要求 scopes 含 `manage` 與 `observe`、動作列允許，以及上面的能力旗標。參數是 P6 §4.1 與 Decision 2：`proposal_id`、`review`、`rationale`（1..4000）、`works` 的長度是 1 到 `max_selected_works`。

每一筆的 `requirement_ids`、`agent`、`delivery`、四鍵 `code_target` 與可省略的 `model` 都抄該列預覽回應（`:1271-1284`），不抄人在預覽之後另改的值。`model` 只有在回應是字串時才放進送出；`null` 就省略。`instruction` 用該列回傳的文字，而且必須與欄位裡預覽填上的文字相同。回應缺了 `requirement_ids`、`agent`、`delivery`、`instruction` 或四鍵裡的任何一鍵時，該列不能送出，也不另造選單（§5）。

前提是預覽回傳的那份。指紋是審閱、理由、勾選的工作、每一筆的需求與指令，加上預覽列回傳的代理、交付、模型與程式目標。這些和上次預覽不同，預覽就過期。

選取在入場後凍結；畫面不再改這筆 operation 的清單。

冪等：同一個 key 加同一份 body 重播同一 `operation_id`。body 不同是 `IDEMPOTENCY_CONFLICT`（409）。key 在第一次送出前寫入 `durableForm`。預覽不是 operation，不消耗這個 key。

- key 還沒寫入，而審閱、理由、選取、需求、指令或預覽前提變了：先重跑預覽，再用新的前提送出。
- key 已經寫入，而下一份 body 會和儲存的那份不同：這是新請求。人按「新請求」清掉凍結的意圖，下一筆用新 key。不在舊 key 上重跑預覽再送出。那樣送的是新 body 配舊 key，伺服器回 `IDEMPOTENCY_CONFLICT`。
- 回覆在拿到 operation id 之前遺失：只查原 key，不換 key，不另 POST。

空選取不呼叫預覽，也不顯示「採用並開始」。「採用，稍後做」只在它和「採用並開始」成對出現時才顯示；第二個送出不出現時，按鈕維持 `pcp_adopt`。重複的 `work_item_id` 在畫面上就擋下。伺服器對空清單、超過 `max_selected_works` 或重複 id 仍以 `INVALID_PARAMS`（422）拒絕。

上限不是把第 `{count}+1` 個核取方塊設成 `disabled`。停用的控制項不會觸發變更，狀態區也不會因此朗讀。所有目錄核取都保持可操作。勾到第 `{count}` 項時，狀態區朗讀 `loop_works_limit`。再勾一項時，那一項立刻回到未勾，選取數不變，狀態區再朗讀一次。

**取消與恢復。** 只在 §1.2 該列有寫的階段，對**父** operation id 呼叫既有的 `POST /api/v1/operations/{id}/cancel` 或 `/resume`。不另造取消路由。`start_unknown` 的取消文案必須說明它不會結案未知的啟動，恢復用「Resume reconciliation」。`works[i].status === "stopped"` 時，取消的是該筆 `start_operation_id`，不是父 id。結果未知時不提供新的 `work.start`（否則會碰到 `PM_WORK_START_OUTCOME_UNPROVEN`）。

**落地。** 回應裡出現 `operation_id` 之後，離開討論，打開 `#/pm/{workspace_id}/board?select={第一筆選定工作}`。第一筆是送出清單的 index 0，不是「看起來最就緒」的那筆。其餘選定工作是檢視裡的連結，不另做多工檢視。討論裡未送出的訊息草稿保留。返回連結回到 `#/pm/{workspace_id}/discussions/{thread_id}`。

本機書籤只負責讓看板檢視在重新整理後找到這一筆父操作。鍵是 `batc.pm.${namespace}.adopt-start-landing.${workspaceId}.${operationId}`，值是 `{version:1, operation_id, thread_id, work_item_ids}`。第二筆採用並開始用自己的 operation id，不會蓋掉第一筆。清掉書籤的時機：父操作已是 `succeeded`、`failed` 或 `cancelled`，而且這份階段已經顯示過；或這筆 `GET /api/v1/operations/{id}` 對這個人回 403／404；或人關掉該階段區。清掉書籤不會取消伺服器上的操作。

沒有這一筆的書籤時，看板檢視不顯示父階段，也不掃全部 operations。伺服器上找得到的入口是既有的操作紀錄，而且打開需要處理的那一篩：`#/operations/attention`（`viewOperations`，`desktop/src/app.js:2897-2916`；`attention` 的狀態是 `needs_attention,uncertain`，`:2899`；路由名 `operations` 在 `:4632`）。連結文字用既有的 `nav_operations`。

人回到這條討論時，回執在採用並開始那張表單的回執區。`durableForm` 在父操作尚未 `succeeded` 時仍留著這個 operation id，並連到既有的操作頁 `#/op/{id}`。那是伺服器上的操作，不是只存在這顆瀏覽器的連結。表單意圖與書籤都已經清掉時，人從 `#/operations/attention` 找需要處理的操作。

### 1.4 狀態與刷新

- 預覽用遞增票號。回應的票號、`proposal_id` 或連線世代不符就丟棄。斷線時丟掉進行中的預覽回應，保留表單草稿，不自動重送。
- 父階段的權威讀取是 `GET /api/v1/operations/{operation_id}`（P6 Decision 10.2）。`result` 只在父操作自己寫入進度時更新（Decision 4，`:482`）。已有 `start_operation_id` 的 Work，另外讀該筆 operation 或既有的 attempt 讀取，不把父 `result` 裡較舊的列當成即時真相。
- `result` 還沒有、operation 仍是 `accepted`：用「已排入採用並開始工作」。不把缺少的 `works[i]` 顯示成「尚未開始」。`result` 是 null 而 status 已是 `running`：只顯示既有操作狀態詞，不自造 `works[]`（§5）。
- 事件：`operation`、`pm_`、`work_item` 來到時重讀這筆 operation 與預覽所依賴的提案。重繪時保留審閱草稿、核取、指令游標，以及已展開的 Details。人正在打字的那一列不因刷新被搬走。
- 離開討論：`proposalReview.dispose`（`pm-workspace.js:1803`）停計時。草稿與已寫入的 key 留在 `localStorage`。回到同一討論時用原 key 查，不另 POST。
- 連線換成另一個 namespace：舊 key 不可在新連線上重送。表單停用，狀態說明連線已換。草稿文字留在原鍵，不搬過去。
- 討論或工作區 403／404：拿掉審閱、選定列、父階段與計數。遲到的預覽不得把列補回。
- 「採用，稍後做」成功後的確認維持現況，留在討論並連到已採用修訂（`pm-plan-proposals.js:163-175`）。那條連結的 `?revision=` 必須繼續有效，見 §3.3。

### 1.6 無障礙

鍵盤順序：審閱開關 → 既有審閱欄位 → 理由 → 工作核取（目錄順序）→ 已勾選項的需求 → 已勾選項的指令 → 檢查就緒 → 採用，稍後做（只有成對出現時）→ 採用並開始。狀態區是 `role="status"`，不進 Tab 順序。

打開審閱時，焦點維持現況，落在審閱裡第一個核取方塊（`pm-plan-proposals.js:262`）。預覽回來不搶焦點，只更新狀態區：「就緒已更新」／「Readiness updated」。送出中焦點留在「採用並開始」。入場失敗且帶著 `admission_refused` 時，焦點移到「新請求」或狀態區，沿用 `durableForm`。拿到 operation id 後，焦點移到看板檢視的標題，狀態區朗讀父階段標題。無法換頁時，焦點留在討論裡的階段狀態。

取消與恢復之後，焦點留在該按鈕；按鈕若因階段改變而消失，移到階段狀態。Esc 關閉檢視並把焦點還給打開它的卡片，沿用既有檢視。

新檔 `desktop/tests/adopt-and-start.spec.ts`。延伸 `desktop/tests/conversation-fixture.ts` 的 `mountConversation`、`desktop/tests/pm-fixture.ts` 的 `pmFixture`，落地檢視延伸 `desktop/tests/pm-kanban-runtime-fixture.ts` 的 `runtimeFixture` 與 `mountRuntime`。刷新手法對齊 `desktop/tests/pm-refresh-event.spec.ts`。`en-US` 與 `zh-TW` 都跑。埠使用環境變數 `BATC_UI_TEST_PORT`，不覆寫。

至少這些情境：

1. 能力未掛上，或 `available === false` 時，只有「採用」，沒有「採用並開始」，也沒有「採用，稍後做」。狀態句是 `loop_adopt_start_unavailable`。
2. 能力掛上但動作列 `allowed !== true` 時，同樣只有「採用」，狀態句是 `loop_adopt_start_denied`。
3. 能力與動作都允許時，「採用，稍後做」與「採用並開始」成對出現。勾選兩項、預覽一項就緒一項阻擋：阻擋項的主要句子不是錯誤碼。`depends_on` 非空的需求在預覽前就停用，並看得到相依句。拿掉阻擋項並重新預覽後才能送出。送出的每一筆 `requirement_ids`、`agent`、`delivery`、`code_target` 與 `model` 來自預覽列。body 沒有 `profile_id`，前提沒有 `expected_scope_revision`。
4. `{count}` 取自 `max_selected_works`，測試不寫死 10。勾到第 `{count}` 項時狀態區朗讀上限。再勾一項時該項回到未勾，而且狀態區再朗讀一次。不靠一顆 `disabled` 的核取方塊來觸發朗讀。空選取時「採用並開始」不出現。
5. 改了指令且 key 尚未寫入：不能送，重新預覽後才送。key 已寫入後再改指令：出現「新請求」，不把新 body 配舊 key 送出。回覆在拿到 operation id 前遺失時，只打一次原 key，沒有第二個 POST。
6. 拿到 operation id 後路由是第一筆工作的看板 `?select=`。檢視有父階段與返回討論的連結。其他工作是連結。第二筆採用並開始的書籤鍵含自己的 operation id，第一筆還在。
7. 「採用，稍後做」留在討論。兩份表單在任一份還有未終結的 operation 時，另一份不能送，審閱與理由停用。
8. 重新整理、離開討論再回來、斷線再連上：草稿還在，沒有第二筆採用並開始。父階段跟原 operation。沒有書籤時，看板上沒有父階段，討論回執或 `#/operations/attention` 仍找得到操作。
9. 討論 404 之後，遲到的預覽補不回列。整筆預覽 `WORK_ITEM_NOT_FOUND` 會重讀目錄、留下還在的工作，並說出被拿掉的標題。
10. `result.adopted === true` 時沒有「新請求」。帶 `admission_refused: true` 的拒絕才有「新請求」。`start_unknown` 的可見字含「Resume reconciliation」，而且沒有新的開始工作送出。`stopped` 先取消該 `start_operation_id`。
11. 父階段 `accepted` 的可見標題是「已排入採用並開始工作」，不是「已驗收」。Work `started` 是「已開始」，不是「已送出」。
12. 1440、1000（覆蓋層，800–1199px）、768 與 390 使用同一組核取與同一筆預覽，不另打一支 API。說明句不是按鈕文字的複述。

入場拒絕的 `admission_refused: true` 要有 P6 的後端測試。這裡的 Playwright 可以模擬旗標，但不能當成那個缺口已經補上。

Cancelling removes this instruction before it is sent to BAT.」／「正在等待目前回合結束。此時取消會在送交 BAT 前撤回此指令。」（`pm_work_follow_up.py:1388-1392`、`:1410-1411`）。測試讀回執上的這兩個欄位。

按鈕只在回執的 `next_allowed_actions` 有該動作，而且目前 `caps().actor` 等於回執的 `actor` 時才顯示。取消與重新確認都要原動作人（P5 §9.1）。其他寫入者看得到回執與 `labels`，看不到這兩顆鈕，狀態用 `loop_next_not_actor`。他們仍可在自己是控制者時另送一則新指令。

「已送出」只用於回執狀態 `sent` 的 `labels.state`。不把 `queued` 說成已送達，不把 `sent` 說成已驗收或已部署，不把回合結束說成已開始。

### 2.3 請求

**這一部分呼叫的中央路由，凡是 bridge 還沒允許的，都在這一部分的介面 PR 加進允許清單，並通過 #235 的前端與 bridge 檢查。** 本檔不改 bridge。P5 §15.9 已寫明 GET 允許清單沒有 `/inputs`，也沒有成果路由 `GET /api/v1/pm/workspaces/{workspace_id}/work-attempts/{attempt_id}/result`。`POST /api/v1/operations` 與 `POST /api/v1/operations/{id}/cancel`、`/resume` 已在允許清單。瀏覽器測試可以模擬清單；不把 Tauri 尚未放行寫成已通過。

**送出。** `POST /api/v1/operations`，`action` 是 `session.send`。`requiredScope` 是 `operate`。目標只有 `{workspace_id, work_item_id}`。多帶 `host`、`session_id`、`task_id` 或 `attempt_id` 會被 `INVALID_TARGET`（422），畫面不帶。參數只有 `{text, schedule}`。`schedule` 固定 `"after_current"`。不送 `queue`，不送 `now`，不送呼叫端的 `message_id`。

畫面送出的 `text` 是去掉首尾空白後的字串。伺服器用收到的原始字串算 `len(text)`，並且拒絕空白或長度過限（`pm_work_follow_up.py:650-651`，上限 `MAX_PROMPT_CHARS` 20000）。因為送出前已經去掉首尾空白，長度就是這份去掉空白的字串。去掉之後是空的，就不送。

前提只送 `expected_attempt_id`，值是這次檢視正在看的最新 attempt。還沒有 attempt id 時，省略整個前提，不送 null。未知的前提鍵是 `INVALID_PRECONDITIONS`（422）。

每一則送出有自己的 idempotency key，在該則 POST 前寫入。同一 key 與同一 body 重播同一 operation。換文字或換 attempt 就是另一則，用新 key。不把兩句併成一筆。

權限沿用 P5 §9.1：送出要 `operate`、寫入成員、同一個控制者。讀取清單要 `observe` 與成員，含讀者。取消與恢復的路由要 `observe`，而且必須是原動作人、寫入成員、同一個控制者。畫面不放寬。

**單筆回執。** P5 `23e17e76` 的 POST、GET、cancel、resume 回應只在 `operation.input_receipt` 放入 Work 輸入回執。`labels`、`status_reason` 與下一步的 `params.text` 都從這個物件讀取；不讀 `operation.result.labels` 或頂層 `operation.labels`。清單的 `items` 則直接是回執。回執必須與這筆 operation、Work 和工作區相符，才可用來顯示排隊或送達狀態。

**清單。** `GET /api/v1/pm/workspaces/{workspace_id}/work/{work_item_id}/inputs`（`pm_work_inputs_list`，P5 §8.3 與 §15.6）。query 有 `after`、`limit`（1..100，預設 50）與選填 `attempt_id`。這一區已經持有字串 `latest_attempt_id` 時（成果，或上一頁清單），query 帶 `attempt_id`，讓這一頁是目前這次 Attempt。值是 null 或還沒有時省略這個篩選，不送空字串。`after` 接上一頁的 `next_cursor`。順序是 `sequence` 升冪。清單含每一種狀態，不只排隊。回應使用 `items`、`next_cursor`、`has_more`、`visibility_filtered`、`latest_attempt_id`，以及 `workspace_id`、`work_item_id`、`attempt_id`。沒有總數欄，畫面不造一個。有 `has_more` 就顯示「還有步驟」。

**取消。** 只有回執 `cancellable === true`、下一步裡有 cancel，而且目前 principal 是回執 `actor`。P5 §7.1 與 §8.2：那就是 `state === "queued"` 且尚未開始送出。呼叫 `POST /api/v1/operations/{operation_id}/cancel`。圍欄之後沒有這顆鈕。若人仍打到取消而得到 `PM_WORK_CANCEL_NOT_ALLOWED_AFTER_SEND`，拿掉鈕，句子用 §7.3：「指令已進入送出階段；開始送出後無法透過取消撤回指令。」

**結果未確認。** 下一步是 `resume`，而且目前 principal 是回執 `actor` 時，才顯示重新確認。呼叫 `POST /api/v1/operations/{operation_id}/resume`，原 id。不重送、不取消。後面被擋住的列保持排隊，並連到 `#/op/{blocked_by_operation_id}`。其他寫入者看到 `loop_next_not_actor`，沒有這顆鈕。

**沒有原地編輯。** `work_inputs` 不可變（P5 §4.1）。失敗與取消的下一步已經帶著全文：`params.text`，而且 `requires_new_idempotency_key: true`（`pm_work_follow_up.py:1565-1593`）。

- 「Edit and send as new instruction」／「編輯並以新指令送出」把 `params.text` 填進輸入框，不送出。人改完後按「送出下一步」，那一則用新 key。
- 「Retry as new instruction」／「以新指令重試」同樣只把 `params.text` 填進輸入框，不送出。人確認後按「送出下一步」，用新 key。
- 不為了取文字再 `GET` 那筆 operation。下一步沒有 `params.text` 時，輸入框留空，不用 `text_excerpt` 充當全文。

**不提供 `schedule=now`。** 即使成果的 `allowed_schedules` 含 `now`，這顆鈕仍只送 `after_current`。`now` 會在忙碌或等待輸入時被拒，而且不是改向。要等以後的規格再加第二顆意圖。

### 2.6 無障礙

鍵盤順序：清單裡每一列的回執連結 → 該列唯一的下一步按鈕（只有原動作人看得到取消或重新確認）→ 輸入框 → 送出下一步。

### 3.3 請求

**這一部分呼叫的中央路由，凡是 bridge 還沒允許的，都在這一部分的介面 PR 加進允許清單，並通過 #235 的前端與 bridge 檢查。** 本檔不改 bridge。三支新的 GET 都不在 `bridge.rs:1168-1176`：`GET .../work-profiles`、`GET .../work-profiles/{profile_id}`、`GET .../work-profiles/{profile_id}/readiness`。既有的 `POST .../work/{id}/start-preview`（`pm-work-start.js:610`）也不在 POST 允許清單（`:1179`）。這一部分不另造第二支預覽。同一支介面 PR 放行那三支 GET，以及這支既有的啟動預覽 POST，因為釘選之後的預覽仍呼叫它。`POST /api/v1/operations` 已經允許。

**清單。** `GET /api/v1/pm/workspaces/{workspace_id}/work-profiles`（`pm_work_profiles_list`）。`observe` 與任一成員，含讀者。query 只有 `limit` 與 `cursor`。`count` 是未撤回的總數，不是這一頁的長度；有 `next_cursor` 就繼續翻。`default_profile_id` 每一頁都有，但預設列不提前。畫面不為了挑預設而另外假設順序。單筆 `GET .../work-profiles/{profile_id}` 只在人要看尚未翻到的預設欄位時使用。

**就緒。** `GET .../work-profiles/{profile_id}/readiness`（`pm_work_profile_readiness_get`）。合約 `work-profile-readiness/v1`。`calls_bat` 是 false，這次讀取 0 次資料庫寫入。畫面不把這次 GET 說成探測過主機。

**開始。** 仍是 `work.start` 與既有的 `POST .../work/{id}/start-preview`（`pm-work-start.js:610`）。

沒選設定檔：預覽 body 不送 `profile_id` 或 `profile_revision`。前提維持十鍵。代理、模型、交付與程式目標維持今天可編輯的控制。指紋維持今天的指令、交付、需求與目標選擇（`pm-work-start.js:369-378`）。

選了設定檔：預覽 body 同時送 `profile_id` 與 `profile_revision`。只送一個是 `INVALID_PARAMS`（E01 `pm_work_start.py:1825-1826`，對照 `6ed90614`）。`agent` 與 `model` 不是預覽 body 的允許鍵（`:1820-1824`）。把它們送進預覽會被拒。它們填在表單上，隨 `work.start` 的參數送出。

預覽 body 還要帶設定檔釘住的目標。帶了 profile 之後，不再沿用「省略 `code_target` 就採用唯一候選」（E01 §5.2）：

- `code_target` 送 `repository`、`host`、`workspace_id`，三個值抄清單列。少一鍵是 `INVALID_PARAMS`（`_profile_code_target`，`:1772-1775`；預覽在 `:1864` 呼叫它）。`source_ref` 不送，仍由預覽解析。這三鍵不能編輯。送出時的四鍵 `code_target` 用預覽回傳的那份，其中三鍵仍須符合設定檔（`:1777-1782`）。
- `delivery`：設定檔的 `delivery_goal` 是字串時，預覽 body 送出同一個值，控制項鎖住。省略或送 null 是 422 `INVALID_PARAMS`，不是不符，伺服器也不會把 goal 填進省略的欄位（E01 §5.2，`:1785-1796`）。`delivery_goal` 是 null 時，交付維持今天可編輯的兩個值；省略則預設 `pull_request`（`:1787-1791`）。入場在 goal 不是 null 時再比一次（`:1804-1805`）。
- `agent` 在 `work.start` 參數裡必須等於設定檔的 `agent`（`:1799-1801`）。控制項鎖住。
- `model` 在設定檔有模型時，參數必須相等（`:1802-1803`），控制項鎖成該字串。設定檔的模型是 null 時，伺服器不比較；面板仍清空並鎖住，送出省略 `model`，人不另填一個模型。

人要改被鎖住的值，就改選設定檔，或改回「不使用設定檔」。那是這些欄位的來源。指令與需求選擇不在釘選裡，維持可編輯。`delivery_goal` 為 null 時，交付的編輯沿用今天的過期預覽。

預覽若回 `code_target: null` 與 `candidates`（`pm-work-start.js:617-628`），選了設定檔時不打開候選選單來改寫釘選。開始維持還不能送。人改設定檔，或改回「不使用設定檔」。

指紋在今天的四個值之外加上 `agent` 與 `model`（`:369-378` 今天沒有這兩項）。換設定檔會改代理、模型與程式目標，所以預覽過期。

- key 還沒寫入：立刻用新列的 `profile_id`、`profile_revision`、三鍵 `code_target`，以及該列要求的 `delivery`，重跑啟動預覽。舊的前提不能送出。狀態區說正在檢查就緒，不搶走指令欄的游標，也不把焦點拉去開始鈕。
- key 已經寫入：不把新的設定檔配進舊 key。顯示「新請求」，焦點到那顆鈕。人按了之後才套用新的設定檔並預覽。直接重送會是 `IDEMPOTENCY_CONFLICT`。

送出的 `work.start` 參數帶 `profile_id`，並帶上被釘住的 `agent`、有字串時的 `model`、`delivery`，以及預覽回傳的四鍵 `code_target`。前提是預覽回傳的整份，必須是原來十鍵再加 `expected_profile_revision` 與 `expected_profile_digest`。畫面不自己組這兩個鍵（E01 §5.2）。預覽請求裡的 `profile_revision` 是清單列的 `revision`，不是這兩個前提鍵的複本。

寫入設定檔的 `pm.work_profile.save` 不是這個面板的工作。選單只選已保存的列。E01 §14 採用的動作名稱是 `pm.work_profile.save`；本檔若提到它，只用這個名字。

**返回允許清單。** 放寬 `internalFrom`（`desktop/src/work-paths.js:15-23`），既有拒絕保持不變：長度、必須以 `#/` 開頭、編碼失敗、空白與控制字元、`://`、`//`、第二個 `#`、`.` 與 `..`。在現有討論、sessions、單筆 session 之外，只再接受：

### 3.4 狀態與刷新

- 設定檔選單與就緒用票號。換工作、換設定檔或連線世代前進時，舊回應丟棄。
- 清單或就緒 403／404／`PM_WORK_PROFILE_WITHDRAWN`：從選單拿掉該列、拿掉六個狀態與缺口連結，選回「不使用設定檔」，解開被釘住的欄位。遲到回應不得把該列加回。`count` 用新的清單回應，不在本機減一個湊數。
- 草稿仍在開始面板的 `durableForm`（`pm-work-start.js:784-800`，namespace 參數是 `${namespace}.work-start`，動作 `work.start`）。去設定頁不會清它。返回原 hash 時還原指令與選擇。面板既有的游標保留規則繼續有效（E02）：節點還在就不動游標；重建則還原文字並把游標放在結尾。
- 從設定頁返回時，焦點放在就緒狀態區，讓人聽到新的六個狀態，而不是直接按開始。事件刷新不搶走正在輸入的指令欄。
- 斷線：停就緒讀取，保留已選 id 與開始草稿，不另送 `work.start`。連上後重讀清單與就緒。
- 離開檢視：停讀取。草稿留下。另一個連線不讀這份草稿。

### 3.6 無障礙

鍵盤順序：設定檔選單 → 六個狀態（若缺口有連結，連結緊接在狀態後面）→ 被釘住的唯讀值 → 既有的指令、需求與檢查 → 開始。返回連結是連線區裡、表單之前的第一個連結。選了設定檔時，代理、模型、交付與程式目標不在 Tab 順序裡當成可編輯欄位；它們是選單說明的一部分。

選了設定檔之後，焦點留在選單，狀態區朗讀六個狀態裡第一個非就緒的名稱與「已設定不等於就緒」。按下缺口連結再返回時，焦點在就緒狀態，不在開始鈕。開始的送出焦點規則不變（指令空白時焦點回指令，`pm-work-start.js:575-577`；面板 `focus()` 仍先到指令，`:1028-1032`）。

換設定檔且 key 尚未寫入時，不把焦點拉去開始鈕。key 已寫入時，焦點到「新請求」。撤回時狀態區朗讀 `loop_profile_withdrawn`。

## 5. 缺口

介面不補這些缺口，也不自造欄位。

1. **P6 #215，後端要求。** `main` `b71a8927` 的 `api_v1.py:1487-1495` 只在動作以 `pm.` 開頭，或是 `setup.host`、`setup.repository`、`setup.verification`、`work.start` 時，把入場拒絕標成 `admission_refused: true`。`work.adopt_and_start` 不在其中。沒有這個旗標時，`durableForm` 不會顯示「新請求」（`pm-workspace.js:265-268`），表單會一直鎖著。P6 的實作要把 `work.adopt_and_start` 加進這個判斷，比照 P5 對自己的送出。P6 的後端測試要斷言：被拒絕的 `work.adopt_and_start` 回應帶 `admission_refused: true`，而且沒有建立 operation。Playwright 模擬這個旗標不能代替那支測試。畫面只在旗標為 true 時顯示「新請求」。
2. **預覽列沒有候選清單。** P6 Decision 9.3 的 `works[i]` 回一個 `code_target` 與 `source`（`:1276-1288`），沒有開始面板那種 `candidates`（`pm-work-start.js:621-628`）。採用並開始不另做目標選單。若該列缺 `requirement_ids`、`agent`、`delivery`、`instruction` 或四鍵 `code_target` 的任一鍵，該列不能送出。`model` 為 null 時送出省略該鍵。這不是新路由。Decision 9.2 的散文寫了 `can_submit`（`:1208`），JSON 沒有這個鍵（`:1245-1247`）。畫面用 `adoptable` 當送出信號，不自造 `can_submit`。
3. **父 `result` 為 null 且 status 已是 `running` 時，Decision 4 沒有對應階段。** `accepted` 且尚未建立採用子操作時，用「已排入採用並開始工作」（Decision 4，`:413`）。其餘 null `result` 只顯示既有操作狀態，不自造 `works[]`。
4. **Decision 11 的 `{current_work_item_id}` 不是回應欄位。** 由第一個 `stage === "starting"` 的列推出。沒有這種列就不填名字。
5. **桌面 bridge 是各部分介面 PR 的工作，在 #235 的前端與 bridge 檢查之下。** 不是新的 HTTP 路由，也不是 P5 #209、P6 #215 或 E01 #220 的後端缺口。要放行的路由是 §1.3 的採用並開始預覽 POST、§2.3 的兩支 GET、§3.3 的三支設定檔 GET，以及開始面板已經在呼叫、但 POST 允許清單還沒有的 `start-preview`。`GET /api/v1/work-items` 與工作區的專案綁定 GET 已經在允許清單。
6. **E01 §6.3 寫的派工 hash 是一段專案識別。** 應用程式還有兩段的 `#/dispatch/{project}/{work}`（`repair-panel.js:44`，單段在 `app.js:3749`）。允許清單含這兩種既有形狀，不含第三段。這是返回位置要對得上現有連結，不是新的設定 API，也不是 E01 的後端缺口。

P5 #209 對這份畫面沒有尚未寫明的後端要求。回執的 `labels` 與失敗、取消下一步的 `params.text` 已經在 `0ab073fc`。E01 #220 對這份畫面沒有尚未寫明的後端要求。選了設定檔時要送的 `profile_id`、`profile_revision`，以及代理、模型、交付與程式目標的比對，已經在 `6ed90614`。

## 6. 設計取捨

1. **採用並開始一拿到 operation id 就打開第一筆選定工作的看板檢視。** 負責人寫的是直接開啟準備中的工作。其餘工作用連結。每一筆父操作的書籤含自己的 operation id。沒有書籤時，人用 `#/operations/attention` 或回到討論後的表單回執。
2. **「採用，稍後做」仍是 `pm.conversation.adopt`，而且只和「採用並開始」成對出現。** 能力未掛上、`available` 不是 true，或動作列不允許時，按鈕維持「採用」。
3. **兩個送出共用同一份審閱與理由。** 任一份還有未終結的 operation 時，另一份不能送。
4. **採用並開始的每一筆工作欄位，除了目錄勾選、需求勾選與指令，都來自預覽列。** 代理、模型、交付與四鍵程式目標沒有控制項。相依需求在送出前就看得到，而且不能勾。
5. **Decision 11 的長句是狀態與無障礙名稱。** `start_unknown` 的恢復用 P6 的「Resume reconciliation」。下一輪的可見標題用回執 `labels`，不用另一張 §10 對照表。取消排隊指令的按鈕用伺服器的 `label`，因為更短的「取消」會和取消工作、中斷回合相混。
6. **下一輪只送 `after_current`。** 不提供 `now`。`now` 不是這顆送出的預設，也不是改向。
7. **排隊沒有原地編輯。** 失敗或取消的下一步把 `params.text` 填進輸入框，人再按送出才用新 key。不另讀 operation 來取全文。
8. **下一輪在 `durableForm` 上加 `releaseAfterAcknowledgement`。** 預設 false，所以既有表單仍鎖到成功。這個選項在 operation id 出現後才放開輸入框。沒有 id 之前不放開。
9. **人選了設定檔時，開始面板的預覽同時送 `profile_id`、`profile_revision` 與三鍵 `code_target`。** 有交付目標就把交付鎖成該值；沒有就維持可編輯。代理與模型鎖在表單上，隨 `work.start` 送出，不放進預覽 body。沒選時不自動套用預設。採用並開始不帶設定檔。換設定檔會重跑預覽；key 已寫入時改走新請求。
10. **父 operation 的書籤放在 `localStorage`，鍵含 operation id，不放進 hash。** E01 的返回允許清單沒有 operation id。
11. **錯誤碼只進 Details。** 主要句子用階段標題與 §1.5／§2.5／§3.5 的在地化說明。
