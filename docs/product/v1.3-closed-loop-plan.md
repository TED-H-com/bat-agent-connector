## 1. 本次要交付的三個成果

### C1：Dashboard 內的完整工作循環

在已就緒的 workspace，使用者不需要切去 BAT、終端機或外部 agent，便能完成：

**要求／討論 → 必要規劃 → 明確開始 → 即時輸出 → 檔案差異與驗證 → 追加修改 → PR／交付 → PM 回填。**

BAT／VS Code 仍可隨時開啟作深入 coding，但不再是完成基本 AI 工作的必經出口。無須先理解 checkpoint ID、work package ID、operation ID 或手寫 MCP 指令。

### C2：跨工具的可追溯 session 結果

BAT、原生 Claude Code、原生 Codex、VS Code Agent Host，以及後续通過驗證的 adapters，共用工作／執行／結果的呈現方式。

「能讀歷史」「能看即時輸出」「能建立新工作」「能追加自有工作」分開宣告。不能只因安裝了 CLI 或讀到一份 log 就標示完整支援。

### C3：人與外部 agents 使用同一條操作路徑

Dashboard、Web、Hermes、Grokbot 和其他 agent clients，使用同一個 Workspace Service 的操作、授權、狀態與成果紀錄。

外部 agents **不需要用瀏覽器點 Dashboard**；它們經 MCP／API 進來，Dashboard 觀察與管理相同工作。外部 agent 是另一個入口，不是讓 Dashboard 基本功能運作的必備中介。

**C1、C2、C3 都通過，才能稱為本次改版完整交付。**只完成漂亮畫面、只完成 BAT demo、只完成 observer，均應標示該階段範圍。

## 4. 產品架構與責任

```text
Tauri / Web Dashboard ─────────────┐
Hermes / Grokbot / MCP agents ─────┼── Workspace API / MCP
其他授權 clients ─────────────────┘          │
                                      共同 Command Service
                                    /          |          \
                                PM Harness  Orchestrator  Read Projections
                                    \          |          /
                                       既有 Journal
                                             │
                                  Adapter Registry / Workers
                                   /          |          \
                                 BAT      Native CLI    AHP / ACP
                                   \          |          /
                              原始 events / Session Results
                                             │
                                 Evidence / Work / PM views
                                             │
                                Git / PR / CI / Release
```

- **Workspace Service：**工作身分、操作紀錄、權限、排程與結果的管理來源。可以每 server 一個服務管理多個 workspace，不要求每個 workspace 起一整套程序。
- **Adapter worker：**必要的 subprocess／協定连接與事件解碼；重用既有服務排程。它不是第二個 Task Service。
- **PM Harness：**對話、需求提煉、工程包建議、判讀與 follow-up；不私自取得執行授權。
- **Orchestrator：**按已授權 intent、policy 與依賴執行工作及交付；不以模型判斷取代 Git／CI 事實。
- **Tauri native：**視窗、憑證、檔案、Fleet、transport；不保存另一份業務真相。
- **MCP：**正式產品能力的 agent 入口。標準化的說明與返回值，不要求 agent 熟悉內部 SQL 或 UI routes。

同一 server 的 Tailscale／SSH／Cloudflare route 是連線選擇，不是新的 workspace 身分。Transport 成功也不等於可以執行。已運作的部署先保留，不為「完全去中心化」重寫本次工作循環。

## 5. 預設使用流程

### F1：第一次設定——先得到一條真正能工作的路

選擇既有 Workspace Service 或準備本機服務，登錄 repo/workspace，選擇一個可用的工作 profile。記住服務端 repository binding、預設來源分支、runtime、模型及允許的交付範圍。

對每個 profile 清楚分開：已發現、已登入／可用、可觀察、可建立自有工作、可持續回覆、最近一次執行驗證。能力探測不得偷偷跑推論；「測試執行」是明確且有成本說明的選項。

已有設定不反覆要求輸入 token、host、SHA 和 path。缺少必要項目時只提出能解鎖這條工作流的最少設定，完成後回原草稿。PM 不可用時可以使用已就緒的 coding 路線，但畫面不能宣稱 PM ready。

本機 Git 不支援的平台，應提供已支援的遠端路徑與精確原因；不要求使用者自行拼湊假的 local-to-SSH fallback。若要對外宣稱「單機即可使用」，該 OS 的本機 Git、runtime、第二輪輸入和結果回收都必須實測。

### F2：自由 Idea——送出就能獲得對話回應

選擇／建立討論、貼 repo 或想法、送出。服務保存訊息並啟動**討論 reply**；回覆、引用與有必要的問題直接回同一串。

不把每次 Ask PM 都強制解讀成 proposal；允許漫長探索、比較、研究和暫時沒有結論。按「只存筆記」才純保存、不呼叫模型。PM 未連接時明示「尚未送給 PM」，不可用已保存訊息假裝已取得回覆。

Idea 可保存資料與討論，也可按授權作唯讀研究，但不啟動 coding、建立執行工作或改寫已採用 scope。研究工具及 repository hooks 的副作用由執行設定限制，不只靠 prompt。

### F3：把想法寫成計畫——一次審阅真正的改變

使用者要求「寫成 plan」後，PM 讀取已有資料、列少量關鍵缺口，形成可閱讀草稿。保留假設、排除項目、未決事項與來源，不能把模型的新增功能當成使用者要求。

需要保存正式文件時，按 workspace 既有設定，自動準備／沿用 PM 自有 worktree；不讓使用者每次手動重做 context wizard。已有 PM writer 活躍時排在後面，不能中止它。

使用者可以選「採用，稍後做」或「採用並開始選定工作」。後者一次授權兩個語意不同的階段；後端分開記錄，不假裝跨 DB、Git 和 runtime 存在單一原子交易。

### F4：快速修復——輕量 Planning，不走完整 PM 行政流程

例如「修正登入按鈕重複送出，補測試，先開 PR」。顯示一張短摘要：目標、變更範圍、完成條件、執行 profile、成果目的地。

明確的執行請求且在已採用政策內，可以自動建立薄的工作依據並開始；含糊訊息只做討論／提案。新建 Idea 專案尚未選擇投入時，必須先得到開始的明確意圖。

不要求小修復先建立完整 Charter、Sprint、所有 milestone 或完整工程包表單。需要的內部字段由系統填入並供展開核對；若是付款、schema migration、公開發布等高影響變更，依 policy 提升審閱程度。

### F5：執行與第二句修改——留在同一工作

開始後立即顯示固定 Work 卡與狀態：已受理、準備工作區、啟動中、執行中、等待、待驗證或需處理。自動連上該 Attempt 的輸出與成果，不只留下 operation ID。

使用者說「再補一個失敗案例」時，對自己控制的工作：原 turn 未完成就保存到 Connector 的下一輪工作序列，完成後再送；不默認 steer 正在執行的 turn。若 native protocol 無可靠排隊機制，使用既有服務命令序列，不能假裝 upstream 支援。

每則輸入有自己 ID 與回執。使用者明確要求平行才另開自有 worktree。中斷是針對自己的工作、另有意圖的操作，不綁在普通 Send 上。

### F6：讀取既有的外部 session——讀得到，仍不接管

啟用 adapter 的授權 workspace 觀察後，將外部 CLI／BAT／IDE session 的可用歷史、摘要、工具結果與 changeset 整理到 Dashboard。

畫面提供「查看原文／成果」「連到現有工作」「以此成果另開工作」。關聯到 PM Work **只增加資料關係，不轉移 session ownership**。

需要接續時，從明確 commit／checkpoint 和上下文建立新的 managed 工作。原 checkout 的未提交變更不會憑空被帶走；顯示來源範圍，必要時請原負責人保存，或使用另行驗證的快照機制。不得替對方 `git add -A`、commit、stash、reset。

### F7：外部 agent 發起——Dashboard 自動看得見

Hermes/Grokbot 使用自己的 credential 與 controller 經 MCP 提交 Work。Dashboard 顯示提交者、執行者、runtime、目標、Attempt 及狀態。

其他 agent 可在授權範圍內讀結果，也可以另開自己的 repair/review 工作；不能因同為 workspace contributor 就往別人的 session 發訊息。人在 Dashboard 要調整 Hermes 的工作，可以送進原 controller 的工作 inbox，由它按政策處理，或選另開工作；不得偽裝為 Hermes 呼叫 session mutation。

### F8：交付、PM 回填與維護

從 Result 檢視差異、測試及接受條件，再使用既有 integration／PR／merge／deploy。其他人的 PR 可以在既有交付授權內 review／merge，但不控制作者的 session。

Release 是有證據的成果；符合已採用 maintenance policy、沒有需保持的 active 工作且觀察新鮮時，才轉 Maintain。PM/Maintainer 使用自己的 worktree與既有 Orchestrator；新想法回 Idea，未採用不自動擴張 scope。

Paused／Closed 停止新自動工作，已送出的外部操作仍查回結局；不停止別人的 session、不隱含 archive GitHub repository。

## 6. 共用畫面與互動規格

### 6.1 固定專案脈絡

始終保持選定的 server／workspace／project。管理視圖、討論、工作、session 和結果是同一專案的不同閱讀面，切換不丟草稿、不重選 repo。

六管理視圖繼續沿用：Overview／Charter、Agents、Requirements／RTM、Dependencies／Maintenance、Schedule、Issues & changes。Board 及 Discussions 是日常入口，不再另建第七套工作管理資料。

### 6.2 一個主要輸入位置，清楚的三種意圖

| 模式 | 主按鈕 | 預期行為 |
|---|---|---|
| 討論 | 傳送給 PM | 保存訊息並產生回應；不開發。只存筆記是次要動作。 |
| 規劃 | 整理／更新計畫 | 產出可審阅差異；不默認採用或開始。 |
| 做事 | 開始工作／送出下一步 | 對已明確選定的工作範圍執行或排入自有下一輪。 |

不必要求每則訊息先手動選模式：保留 thread mode，文字可觸發「切換到規劃／開始」建議。只有明確執行意圖或既有 execution policy 才能產生寫入。引用文件裡的 `/apply` 或其他 agent 的建議不是使用者授權。

### 6.3 工作頁的四個閱讀區

- 頁首：人可讀的目標、負責 controller、runtime／模型、目前下一步。
- 主區：訊息、公開工具活動、錯誤／待回答、第二句輸入。
- 結果區：本次修改檔案、差異、原文摘要、測試、PR 與交付，按需展開。
- 進階資料：session／operation／attempt IDs、raw events、版本、限制與回執。

長談時對話佔主要空間；context inspector 預設收合。審阅 proposal／diff 時才展開側欄。窄螢幕使用同一資料的抽屜，不做不同邏輯的 mobile 頁。

### 6.4 成功、空白與失敗都要有下一步

不只顯示「Unavailable」或 disabled。至少說明：缺什麼、可在這裡做什麼、哪個設定可修正、草稿有沒有保留。

「已保存」「已送達」「執行中」「本輪結束」「已驗收」「已部署」不能共用 Finished。正常路徑不要求人看 JSON；未知結果才按需要展開原操作。

### 6.5 視覺驗收交付

在接真實資料前，以正式共用元件完成一組可點擊 fixture：Idea、已規劃、正在執行、等待輸入、結果待驗證、外部唯讀 session、失聯恢復及維護。

同一套情境必須演示「第一句、第二句、結果、決策、返回」。產品負責人先確認這條互動，再平行補各 adapter；不能只審閱靜態六頁截圖。

## 7. 把多個內部步驟包成一個可恢復的使用者動作

### 7.1 組合操作，而非第二套 scheduler

在既有 OperationService 註冊少數使用者層級 action；它們組合已存在的 plan adoption、work package、start／continue 等操作。下面名称是**建議名稱**，E0 若找到等價 action，應沿用而非重複新增：

| 建議 action | 功能 | 重用基礎 |
|---|---|---|
| `pm.conversation.reply` | 保存問題後產生討論回應，不强制產生 proposal | 既有 message、context、analysis、journal |
| `work.start` | 輕量規劃／已採用工作轉執行，選擇目標 adapter | 既有 project/work item、`session.start`、`repository.continue`、work package/handoff |
| `work.adopt_and_start` | 採用固定 proposal 並開始選定工作 | 原 adoption 與 `work.start`，保存每一步結果 |
| `work.follow_up` | 追加到自有工作，預設 after-current | 原 `session.send` 與既有 command sequence |
| `work.derive` | 由既有成果產生新的獨立工作 | 原 checkpoint／published source／handoff |

人與 MCP 同樣使用這些 actions。既有較低階 API 保留相容性，但不能成為繞過 controller 或 phase 規則的入口。

### 7.2 Admission snapshot

服務在受理時凍結必要資料：workspace、work、使用者意圖、controller、plan/spec revision、code basis、adapter instance/profile、模型、附件修訂、交付範圍、預算及相關版本檢查。

可讀名稱與目前 preview 顯示給使用者；不可要求使用者手填上述內部欄位。唯一 binding 可按已選專案帶入；多個合理目標才詢問。

第一次建立 private worktree、下模型工作、push 或發布的承諾，依工作政策適度呈現；重複的例行操作不再逐步彈窗。

### 7.3 分步保存，部分成功不重做

建議組合流程：

`保存 intent → 核對版本/授權 → 必要 plan 採用 → work/package 準備 → 自有工作區 → runtime 啟動 → 首句送出 → 結果關聯。`

每一外部 effect 前保存子操作身分及預期結果。啟動成功但 UI link 失敗，工作卡仍保留原 operation／session；修復關聯不再啟動。

採用成功、dispatch 失敗時顯示「計畫已採用，工作尚未開始」，僅恢復未完成階段。不回滾已採用計畫掩飾失敗，也不假裝整個 compound action 是原子交易。

### 7.4 版本改變的處理

短暫 preview 過期時，重新讀取並比較語意影響。在已核准的策略內可以刷新無影響的來源；scope、目標 branch、發布環境或權限改變則要求重新審閱受影響部分。

後續指令預設沿同一 Work 的 accepted basis。改變 scope 時產生 revision，不默默把進行中的舊 Attempt 改寫成新規格。

## 8. IDE adapter 能力契約

### 8.1 依能力登錄，不做「已安裝＝全部支持」

每個 adapter manifest 至少包含：工具及版本、protocol/decoder profile、server 安裝實例、可用 OS／transport、登入方式摘要、支援能力、限制、上次驗證與证據。

| Capability | 最少可驗證的承諾 |
|---|---|
| `discover` | 只在選定路徑／endpoint 找工具與可見 sessions，不改登入與設定。 |
| `read_history` | 讀既有 transcript／session，能表達 partial、缺頁與解析限制。 |
| `observe_live` | 被動收 event、subscribe 或增量讀取，不透過 resume 開啟外部 session。 |
| `read_results` | 取得原始成果、固定 changeset／檔案／Git／測試來源。 |
| `start_owned` | 在明確自有工作區建立新 session 並記錄 creation receipt。 |
| `send_owned` | 對有原始控制權的 session 送下一輪；busy 不默認 steer。 |
| `answer_owned` | 回覆指定 request/tool call，正確處理 stale request。 |
| `interrupt_owned` | 只中斷自有 turn/process，實際停止結果可核對。 |
| `reconcile` | 不確定結果可依原 key/session/turn 查回，不能猜測後重開。 |

部分 adapter 可以只具前四項，仍有觀測價值，但不能標記「可工作」。UI 的可見按鈕由實際 capability、caller 權限、ownership 和當前狀態共同決定。

### 8.2 首批支持路線

| 路線 | 本版交付目標 | 實作重點 |
|---|---|---|
| BAT | 完整直接工作循環＋外部 session 唯讀觀察 | 優先重用現有可靠執行入口；覆蓋已支持的 Claude／Codex 工作。 |
| Native Claude Code | 歷史／stream／結果；自有新工作與後續回合 | 使用正式 CLI／SDK 的事件外殼；不以 generic「最近 session」續接。 [P2][P3] |
| Native Codex | 歷史／結果及自有工作 | 選定並驗證 App Server 或 CLI route；`thread/read` 與 resume 分開。 [P4] |
| VS Code AHP | 維持現有只讀 profile，新增經驗證的自有 create／turn／結果 | AHP spec 與 VS Code 實際 wire version 分別 pin；不從協定共享能力推導任何 session 都可寫。 [R6][P1] |
| ACP | 選一個具名、固定版本 runtime 後依同一 adapter 契約驗收 | Generic ACP 支持不等於每個 backend 都有相同恢復／歷史能力。 |
| AGY／Grok CLI／OMP 等 | 登錄 exact upstream、版本及能力後按優先級擴充 | 不猜工具身分、不以名称承諾支持，不阻擋首批閉環。 |

AHP 是多 client 的 session 協調層，ACP 是 host/client 與 agent 的通信層；MCP 是本產品對 agents 暴露業務操作的入口，三者不可互換。以 adapter 使用既有 host，不要求 Connector 變成完整 AHP server。 [P1]

### 8.3 平台支持矩陣

第一條可交付路徑可採已就緒的 Windows/Mac Tauri client → Linux Workspace Service/BAT runtime。這是早期里程碑，不得以此宣稱 native Windows/Mac execution 完成。

每個 adapter 必須有 `OS × transport × observe/start/follow-up/results/recovery` 的已測矩陣與排除項目。未知版本降級為已驗證的能力或明確不可用，不偷偷換 engine、account 或模型。

使用 CLI 現有登入，不讀出 token 轉成另一種登入方式、不自動接受付費訂阅、不關掉企業管理政策。GUI shell 和 daemon 帳號的工具／憑證環境要在 readiness 中分開驗證。

## 9. Ownership 與「不接管」的實施

### 9.1 三種身分分開

- **Requester principal：**誰要求這個工作；憑證與 scope 由服務解析。
- **Controller：**哪個持久的控制身分負責執行生命週期；不等同模型名稱或本次 process PID。
- **Runtime agent：**實際使用的 BAT／CLI／provider；可以有多個 sessions/turns。

建立新工作時由服務固定 controller，保留原始 creation operation。參數不接受客戶端偽造「這是我的 session」。相同人的 Web/Tauri 可以使用該人原有 controller；換另一個 agent credential 不會自動取得同等控制權。

### 9.2 檢查點

所有 send、answer、permission、resume、interrupt、retry-start、cleanup，以及 background batch／maintenance 路線都重用同一檢查。檢查至少覆蓋 current principal/scopes、workspace membership、creation lineage、controller、bound host/runtime、session incarnation、phase/task 狀態。

PM/Maintainer 自有 session 也受相同規則；不能以「PM 是管理者」繞過 foreign session。

### 9.3 跨 controller 的合作

其他 actor 可以提交下一步建議到 Work inbox、回覆明確指派給他的業務問題、讀取獲准的成果，或另開一個獨立工作。owner/controller 處理 inbox 時保留 requester 與 policy 記錄；不把這個機制當成任意轉送 session command 的代理。

更換 PM runtime／模型時，在可確認舊 writer 結束後建立新的自有 run，保留 PM 文件與上下文。正在執行的 coding 工作不隨 UI 模型選單改變。

### 9.4 檔案安全與控制權是兩層

Connector 不接管 session 的保證由服務與 adapter 執行；Agent process 的 OS 檔案隔離取決於 sandbox／帳號權限。兩者分開標示。

自有 worktree 同時間只允許一個被管理的 writer；若偵測其他寫入或來源變動，暫停新的自動寫入並說明。普通使用者／外部程序在系統外直接修改時，不承諾 Connector 能阻止一切；提供隔離配置與變動偵測，不用虛假的 ownership badge 代替實際保護。

## 10. Session Result：從不同工具收回相同種類的成果

### 10.1 原始資料與整理資料分開

不要求 coding agent 在答案末尾輸出特製 JSON。adapter 可以使用工具提供的 JSON／stream-json／協定事件，這只是 transport，不改使用者的提示與回答格式。 [P2][P4]

保留可用原始資料及其引用；標準化的 index／projection 可以重建。格式不認識時保留可讀原文、parser version 和限制，不生成假的成功事件。不要收集或推定工具未提供的私密思考內容。

### 10.2 Result 最少資料

| 區塊 | 內容 |
|---|---|
| 身分 | server/workspace、adapter instance、原生 session/turn ID、incarnation；可用時 link Work/Attempt。 |
| 原始來源 | source URI／file identity、cursor/offset 或 native event ID、decoder version、digest、觀測時間與收集時間。 |
| 對話 | 公開的 user／assistant 內容、工具摘要、附件引用；完整原文按需讀取。 |
| 執行 | 已受理／starting／active／waiting／turn-ended／process-ended／failed／unknown，各有來源。 |
| 檔案／Git | base commit、result commit 或固定 patch artifact；changeset、檔案修訂及歸因範圍。 |
| 驗證 | command/check 身分、對應 commit、結果、時間與 log/artifact 引用。 |
| 交付 | PR、merge SHA、release／deploy 版本與結果。 |
| 用量 | 原來源提供的 token／時間／配額；缺少就 unknown，不把訂阅額度當美元花費。 |
| 完整度 | complete/partial/unavailable、原因、coverage、last successful observation。 |

原文寫「全部完成」先記為 self-reported。退出碼 0、停止 streaming、PR merged 與需求 acceptance 都不是同一狀態。

### 10.3 Session 身分與重複觀察

同一 session 可能被 BAT、native scanner 和 AHP 同時看到。以已證明的 native runtime identity／instance／session／incarnation 建立 alias 關係；不因 repo URL、資料夾、title 或內容相似就合併。

无法證明時先保留「可能重複」，不將兩份來源算成兩件交付。重試與模型接續是 Work 的多次 Attempt，不能讓進度被重複加總。

### 10.4 Stream、歷史與重播

- 有 native event ID 時以穩定來源 key 去重；沒有時使用原檔身分、generation、byte offset 與事件內容雜湊，不以時間相同作唯一依據。
- 檔案 rotation／truncate、socket gap、parser failure 都記 coverage。只能取得最後 N 則時，不宣稱完整歷史。
- Workspace journal 提供單調 local sequence；UI 重連從 cursor 續讀，游標過期則重新讀 snapshot 並保留草稿。
- raw token/high-volume blobs 可有保留期限；final result、操作與成果引用另有較長保留政策。刪原文後標明已到期，不保留看似可開的假連結。
- UI 對 token 更新合併 render，開啟的工作優先；PM 分析在 meaningful events／工作結束／CI 結果／授權時間點觸發，不逐 token 呼叫模型。

### 10.5 外部工作歸因

由服務派出的工作可使用確切 Work/Attempt lineage。外部 CLI 則依原生 session 與明確工作連結整理；僅靠 cwd、相近時間或整個 repo 的 diff，不能證明改動全由某個 session 產生。

對推論關聯顯示「建議對應」，允許一次確認或修正。安全且確定的關聯自動建立，不要求使用者逐筆填表。未歸類工作仍可閱讀、搜尋和提供 PM 研究素材。

## 11. 共用資料模型與 API/MCP 契約

### 11.1 模型關係

```text
Workspace / Project
  ├─ Discussion + phase + messages + proposals
  ├─ Adopted Plan / Spec revisions + Requirements
  ├─ WorkItem
  │    ├─ Attempts → Adapter Session / Turns
  │    ├─ Session Results → Artifacts / Git / Verification
  │    └─ Assessments → PR / Release / Deploy
  └─ Decisions / Sprint / Maintenance / Follow-ups
```

既有 tasks、executions、operations、work_items 和 links 先映射到此模型。同一 Work 不能因为换 UI tab、換模型或多個 attempts 而複製。

工作結果與 requirement／DoD assessment 綁定 exact spec revision 和成果版本。scope 或成果變了，重新評估受影響的結論，保留原結果歷史。

### 11.2 類型示意（不是現有 API payload）

```typescript
interface WorkIntentV1 {
  version: 1;
  workspaceId: string;
  kind: 'discussion' | 'plan' | 'execute' | 'follow_up' | 'derive';
  text: string;
  workId?: string;
  profileId?: string;        // 服務端已登錄的工作 profile，不是 executable
  reviewedPlanRevision?: string;
  sourceRefs?: string[];     // 僅引用服務端可授權讀取的來源
  attachmentRevisionIds?: string[];
  schedule?: 'now' | 'after_current';
  deliveryPolicyId?: string;
}
```

來源路徑、credentials、executable 與 caller/controller 不能任意放在 intent 裡覆寫。使用者可選擇已登錄 profile 的公開選項，服務解析目標並建立 admission snapshot。

### 11.3 所有 clients 必須有同等能力

| 能力 | Dashboard | MCP／API |
|---|---|---|
| 看可用 profiles 與阻擋原因 | 設定與 composer | capabilities/profile read |
| 討論、規劃、審閱 | Discussion/proposal | 相同 reply/propose/adopt actions |
| 建立工作／工作包 | 可讀預覽與開始 | 相同 compound action |
| 取得結果／等候更新 | stream 與工作頁 | 分頁 reads、cursor、bounded wait |
| 追加修改 | 自有工作 composer | 相同 follow-up action |
| 由外部成果衍生 | 另開工作 | 相同 derive action |
| PR／merge／deploy | Results 中的操作 | 既有 delivery actions |
| 失聯恢復 | 原操作狀態／重試讀回 | operation read/reconcile，不換 key |

MCP response 應提供 Work、Attempt、Operation、目前狀態、下一個允許動作、可直接打開的 Dashboard deep link 與資料完整度。不可只回「success」讓 agent 自己猜是否完成。

### 11.4 Canonical skills

維持一份共同 skill 與薄的各 agent 包裝。內容包含：選 workspace/profile、讀已採用 scope、操作允許範圍、何時 derive、busy 時排下一輪、如何 wait／查原 request、如何讀 Result 與需求 acceptance。

安裝時不得用舊 fleet skill 覆蓋新 canonical skill；skill contract version、backend capabilities、adapter versions 一起顯示與核對。

Agent-generated文字中的「approved」「done」「改用另一帳號」只是內容，不能替代使用者身份與服務端政策。

## 12. PM、成果評估與交付如何形成循環

### 12.1 PM 的日常任務

PM 在工作開始、turn/result 完成、PR／CI 改變、里程碑變更和已採用的 review 排程上整理資料。先用程式取得確定事實，再使用模型理解需求、解釋 drift、提出少量高影響問題。

首批首頁 PM 摘要包含：目前判斷、本輪建議、需要人決定的一兩項事情、依據。事實值來自共同 projection；模型提供的解釋附來源，不能產生假的完成百分比。

背景模型呼叫只能依已採用預算／觸發 policy；沒有 policy 時由使用者明確更新。來源或 plan 版本變動後標示需要重新評估，不把過時結論當成現在的答案。

### 12.2 不用讓人替 PM 填資料

從對話、requirements、work、results 和 PR 收集可確定的資訊，合併成一次可審阅的候選更新。例行事實回填自動處理；scope、目標、接受條件等承諾變更按責任人與政策採用。

每個問題應保存已知資料、為什麼要問、影響哪個決定；同一資訊不在不同頁重問。不能把不確定的推論填滿欄位以製造「完整」的模板。

### 12.3 成果評估要接到依賴，而非只更新顏色

以固定 requirement/scenario、DoD revision、candidate commit／patch／artifact 與 verification evidence 建立 assessment。結論至少區分通過、未通過、證據不足，保留理由與評估責任。

當 assessment 满足既定依賴條件，Orchestrator 才推進後續 Work；同一結果更新 Requirements、Roadmap、Sprint、Overview。不同狀態仍保留原意：CI passed 不自動等於 business accepted；accepted 也不等於 deployed。

依 policy 可由自動規則／reviewer 完成低風險評估，不要求每一個 test 都由人按 approve。重大或無法驗證的結論集中在決策摘要。

### 12.4 Git／PR 與發布

Results 提供「查看差異」「執行驗證」「建立／更新 PR」「加入整合預覽」。多份成果固定來源後整合到明確 PR，不讓多 controller 同時直接寫同一工作樹。

維持 expected PR head、base/update 規則、checks、delivery policy 和部署版本證據。成功 merge、失敗 deploy 只恢復部署階段，不重做 merge。CI 整理針對冗餘／過時流程和 flaky 問題，不為通過 PR 擅自移除 required checks。

### 12.5 維護與關閉仍是同一產品

Maintainer 不再長另一套 runner 或 dashboard。它使用同樣的 Work/Attempt/Result 和自有 profile，將 Issue／依賴發現變成有界修復工作，結果回 Maintenance Review。

發布後可繼續開發、依 policy 維護或明確暫停。實體留著 worktree 不等於仍在開發；也不能由無輸出推論所有工作已結束。關閉後持續保留歷史與原操作恢復，不自動執行舊排程。

## 13. 可靠性、安全及效能邊界

| 情境 | 必要處理 |
|---|---|
| Model／provider 不可用 | 草稿保留；說明是認證、模型、額度、host 或 adapter 問題；不靜默換帳號／付費路線。 |
| 指令 ACK 遺失 | 查原 key、native session/turn、transcript 或 receipt；無證據則標 unknown，不複製工作。 |
| 本輪 busy | 普通後續輸入留在已記錄的 Connector 序列；不透過「start-or-steer」偷改目前 turn。 |
| Process 啟動後 Connector 重啟 | 用既有 job/worker 身分、receipt 與 spool 恢復；不可確定則暫停派新 writer。 |
| UI 關閉／斷線 | server 上既有工作继续；重連重建 snapshot/events，不以 UI mounted 觸發重新派工。 |
| Adapter 只有歷史讀取 | 顯示 historical/partial；不偽造 live、busy、完成或可恢復。 |
| 來源／權限撤回 | 後端 read 和 subscription 重核；撤回已不允許的展示與派生分析，草稿依原私有範圍保留。 |
| 多重觀測／重複 hook | 本地事件去重與 native identity alias；不重复文字、不重复結果或計費。 |
| 惡意 repo／log／PR 文字 | 原文視為不可信資料；不能由其指令改 execution intent、權限、spec acceptance 或部署目標。 |
| 高頻輸出／大檔 | bounded buffers、分頁／引用、backpressure、parser 限制與磁碟保留；不堵住 cancel/status。 |
| Shell／hooks 副作用 | 枚舉不啟動 CLI hooks；用 verified SDK/CLI profile限制行為，不從任何 repo config 自動取得額外權限。 |

不把 durable schema 變成 UI 的表單清單。身分與資料來源檢查必須有效，但讀取路徑使用索引／有界 projection，避免為了畫一張工作卡每次遞迴掃完整專案歷史。

模型文字、HTML、ANSI／終端控制序列按不可信資料呈現。檔案開啟／artifact 讀取必須限制在已授權的來源，防止 path traversal、symlink 越界；tokens、auth 檔和其他 workspace 私有內容不進公開診斷或 PM 模型上下文。

傳輸可重試、events 可重播，不代表能對任何外部工具保證 exactly-once。宣告能力應是：保存原意圖、對已知副作用查回、遇到不確定不自動重做。

## 14. 用什麼衡量這次改版

以下是建議的產品驗收門檻，不是目前已測得數字。E0 可依目標機器調整效能門檻，但不能刪掉結果循環、ownership 或跨入口一致性要求。

| 指標 | 目標／量測方式 |
|---|---|
| 基本工作循環的外部工具切換 | 在已就緒 profile，要求→輸出→差異→第二句→結果：0 次必須離開 Dashboard。 |
| 前置背景重填 | 同一工作追加修改：0 次重貼 repo、spec、session ID；scope 真正改變時只看變更摘要。 |
| 一般使用者內部 ID 輸入 | 0；既有進階工具可以保留但不在正常路徑。 |
| 首次有效工作 | 至少 3 位未參與開發的測試者，在就緒 workspace 執行標準小任務，中位數 5 分鐘內看到自己的工作啟動；模型產出時間另記。 |

## 18. 遷移、測試、版本與範圍控制

### 遷移

保留原workspace/project/work/session/operation IDs、controller lineage、計畫版本與歷史URL。新Result和adapter資料優先附加映射；原始來源不被覆寫。舊 in-flight 工作使用原執行位置與adapter，不能隨設定更新被改道。

已有外部session預設observed/foreign；不得批量「認領」。新版compound action採 feature capability gate，舊client不會看到不支持的控制；fallback只提供原有功能，不靜默放寬。

### 測試

1. 每個adapter有固定版本的record/replay資料及contract suite。
2. 每個effect有權限、busy、重送與中斷恢復測試。
3. 共用UI測Web及Tauri transport；另外測實際WebView／打包 runtime。
4. 完整Golden flow不依賴手工塞入工作包或預設成功結果。
5. UI要在自己建立的真實Work上讀到真實結果，至少完成原生Claude、Codex、BAT、AHP目標路徑。

CI依改動範圍執行，核心與adapter修改需要對應合約及整體回歸。不得以刪除斷言、延長timeout或把核心流程skip掉宣告完成。大量跨平台build與真實模型測試分層安排，不讓每次文案修改都付同樣成本。

### 候選交付物

每個候選提供：exact commit、Desktop/Connector/skills versions、adapter compatibility matrix、變更與未完成項目、安裝入口、診斷檔、測試／操作錄影及實機證據。

不可把「已合併」「CI通過」「已打包」「owner已安裝」「真實模型／BAT驗收」混為同一狀態。這份計畫的完成度按實際情境通過數與限制說明報告，不填無證據的整體百分比。

## 19. 可直接交給開發 agents 的校正指令
